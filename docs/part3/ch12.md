# 第 12 章　WHERE・インデックス・UPDATE/DELETE — クエリオプティマイザの入り口

<span class="note-title">この章のゴール</span>

- WHERE を「反転比較でスキップする」バイトコードにコンパイルできる
- 主キー等値検索を SeekRowid プランへ最適化し、効果を実測できる
- UPDATE / DELETE を 2 相方式で実装し、その理由(カーソルの契約と Halloween problem)を説明できる

## 12.1　WHERE を実行計画に翻訳する

この章を経て、`codegen.go` は 226 行から 449 行に、`engine.go` は 138 行から 232 行に増えます。この章の実装は「第 3 部の総仕上げ」というだけあって、これまでの各章より掲載する分量が多くなります。なお解説の都合上、掲載順は実際の `codegen.go` 内の並び(`Compile` → `resolveColumns` 系 → `checkWhereType`/`isPKEquality`/`invertOp` → `compileSelect`/`compileSeekRowid`/`compileFullScan` → `compileInsert`/`checkValueType` → UPDATE/DELETE 系)とほぼ一致させていますが、無変更の `compileInsert` は再掲を省いています。完成形は `code/ch12/exec/codegen.go` を参照してください。

第 11 章の `Compile` には、こう書かれていました。

```go
case *sql.SelectStmt:
	if s.Where != nil {
		return nil, fmt.Errorf("WHERE 付きの SELECT は第 12 章で実装します")
	}
	return compileSelect(s, cat)
case *sql.InsertStmt:
	return compileInsert(s, cat)
case *sql.UpdateStmt:
	return nil, fmt.Errorf("UPDATE は第 12 章で実装します")
case *sql.DeleteStmt:
	return nil, fmt.Errorf("DELETE は第 12 章で実装します")
```

この章で、その 3 つのエラーをすべて本物に変えます。`SELECT name FROM users WHERE age = 55` のようなクエリを、実際に実行できるバイトコードへコンパイルできるようにし、`UPDATE`/`DELETE` も(12.3 節で)実装します。`Compile` 自身の変更はごく小さく、3 つの `case` から「未実装です」のエラーが消え、代わりに新しい関数を呼ぶだけになります。

**exec/codegen.go(1) — Compile**

```go
// Compile は構文木からバイトコードを生成する。
func Compile(stmt sql.Statement, cat *Catalog) ([]Instr, error) {
	switch s := stmt.(type) {
	case *sql.SelectStmt:
		return compileSelect(s, cat)
	case *sql.InsertStmt:
		return compileInsert(s, cat)
	case *sql.UpdateStmt:
		return compileUpdate(s, cat)
	case *sql.DeleteStmt:
		return compileDelete(s, cat)
	case *sql.CreateTableStmt:
		return nil, fmt.Errorf("CREATE TABLE はバイトコードを経由せず Engine が直接実行します")
	default:
		return nil, fmt.Errorf("未対応の文です: %T", stmt)
	}
}
```

`SelectStmt` の分岐から `s.Where != nil` の早期リターンが消えている点に注目してください。WHERE の有無・形の判定は、この後 `compileSelect` の内部(12.2 節)へ移動します。`Compile` はもう「対応している文かどうか」だけを見る、第 11 章から変わらない薄い入り口のままです。

方針は単純です。第 11 章の `compileSelect` が組み立てていたのは `OpenRead → Rewind → (列の読み出し) → ResultRow → Next` という全件スキャンのループでした。WHERE 付きの SELECT も、まずはこの同じループの中に条件判定を差し込むだけで実現できます——「行ごとに、WHERE の列とリテラルをレジスタに置き、条件を満たさなければこの行を読み飛ばす」という 1 手を、ループ本体の先頭に足すだけです。

ここで注意すべき点が 1 つあります。VM の比較命令(第 10 章 10.4 節)は「成立したらジャンプする」という向きでできています。`Eq` はレジスタが等しければジャンプし、`Lt` は小さければジャンプする——これは「条件が成立する行だけを処理する」という自然な発想とは逆向きです。フルスキャンのループでやりたいのは「条件が**不成立**の行を、この行の処理をスキップして次へ飛ばす」ことです。つまり `WHERE age = 55` をコンパイルするには、`Eq`(等しければジャンプ)ではなく **`Ne`(等しくなければジャンプ)** を使い、ジャンプ先を「次の行を読みに行く `Next` のアドレス」にする必要があります。「if 文の否定」というプログラミングの基本操作が、ここではバイトコードのオペコードの選び直しとして現れます。

この変換を担う小さな関数が `invertOp` です。

```go
// invertOp は WHERE の比較演算子 op を否定した演算子の VM 命令を返す
// (Eq↔Ne, Lt↔Ge, Gt↔Le)。フルスキャンのループで「条件が成立する行だけ
// 残す」ことを、「条件が不成立の行は否定条件が真になった時点で
// 次の行へ読み飛ばす」という形で実現するために使う。
func invertOp(op sql.CompareOp) Op {
	switch op {
	case sql.OpEq:
		return OpNe
	case sql.OpNe:
		return OpEq
	case sql.OpLt:
		return OpGe
	case sql.OpGe:
		return OpLt
	case sql.OpGt:
		return OpLe
	default: // sql.OpLe
		return OpGt
	}
}
```

`Eq` と `Ne`、`Lt` と `Ge`、`Gt` と `Le` がそれぞれ対をなす——ちょうど 6 個ある `sql.CompareOp` の値(`OpEq` / `OpNe` / `OpLt` / `OpGt` / `OpLe` / `OpGe`、9.5 節で確定させたサブセット)を、否定した側の VM オペコードへ機械的に対応づけるだけの関数です。この 12 行に「フルスキャン + フィルタ」という実行計画の骨格が凝縮されています。

### resolveColumns の整理 — resolveColumn への単体化

WHERE の列(`age`)は、SELECT で投影する列(`name`)とは別に、もう 1 度「実行時にどう読み出すか」へ解決する必要があります。第 11 章の `resolveColumns` は、複数の列名をまとめて解決する関数の中に「1 つの列名を解決する」ロジック(クロージャ `resolveOne`)を埋め込んでいました。この章では WHERE 句のためにその「1 つの列名を解決する」処理を単体で呼び出したくなるため、独立した関数 `resolveColumn` に切り出します。

**exec/codegen.go(2) — resolveColumns・resolveColumn・findColumn**

```go
// resolveColumns は SELECT の列指定(* または列名リスト)を、
// テーブルの列定義をもとに resolvedColumn の列へ解決する。
//
// PK 列(INTEGER PRIMARY KEY)は rowid そのものであり、レコードには
// 保存されていない。そのため、レコード内の列番号は「PK 列を除いた
// 位置」に詰めて対応づける必要がある。例えば列が (id PK, name, age) なら
// レコードには (name, age) の 2 列しか入っておらず、name は
// recordIndex=0、age は recordIndex=1 になる。
func resolveColumns(info *TableInfo, star bool, names []string) ([]resolvedColumn, error) {
	if star {
		names = make([]string, len(info.Columns))
		for i, col := range info.Columns {
			names[i] = col.Name
		}
	}

	cols := make([]resolvedColumn, len(names))
	for i, name := range names {
		rc, err := resolveColumn(info, name)
		if err != nil {
			return nil, err
		}
		cols[i] = rc
	}
	return cols, nil
}

// resolveColumn は列名 1 つを resolvedColumn へ解決する。
func resolveColumn(info *TableInfo, name string) (resolvedColumn, error) {
	// PK を除いた列がレコード内で何番目になるかを、対象の列に着くまで数える。
	idx := 0
	for i, col := range info.Columns {
		if col.Name != name {
			if i != info.PKIndex {
				idx++
			}
			continue
		}
		if i == info.PKIndex {
			return resolvedColumn{name: name, isRowid: true}, nil
		}
		return resolvedColumn{name: name, recordIndex: idx}, nil
	}
	return resolvedColumn{}, fmt.Errorf("列 %s は見つかりません", name)
}

// findColumn は列名から ColumnDef(型情報を含む)を引く。
func findColumn(info *TableInfo, name string) (sql.ColumnDef, error) {
	for _, col := range info.Columns {
		if col.Name == name {
			return col, nil
		}
	}
	return sql.ColumnDef{}, fmt.Errorf("列 %s は見つかりません", name)
}
```

`resolveColumns` は複数列をまとめて解決する薄いループへ縮み、`* `の展開(全列名を並べる)も「列名のリストへ展開してから同じ 1 列解決を繰り返す」という単純な形に整理されました。`resolveColumn` は第 11 章の `resolveOne` とほぼ同じ仕事をしますが、対応表(`recordIndex` スライス)を事前に作らず、**対象の列に着くまで数える**という 1 パスのループに書き換わっています。この整理は「事前計算した対応表を引く」から「その場で数える」への変更であり、計算量としては 1 列を解決するたびに O(列数) を要する点は変わりません(対応表方式は前計算に O(列数)、引くのは O(1) でしたが、複数列を解決すればどのみち合計の計算量は同じです)。整理の主目的は、WHERE 句のためにこの「1 列を解決する」処理を単体で呼べるようにすることにあります。

`findColumn` は新顔です。`resolveColumn` が返す `resolvedColumn` は「実行時にどう読むか」(rowid かレコード内の位置か)しか持たず、**列の型情報を持ちません**。WHERE 句やあとで見る UPDATE の SET 句は、リテラルの型が列の型と一致するかをコンパイル時に検査する必要があるため、`sql.ColumnDef`(型を含む)を引く別ルートとして `findColumn` を用意しました。

### checkWhereType — コンパイル時の型検査

第 11 章の `compileInsert` は、値の型が列の型と一致するかをコンパイル時に検査していました(`checkValueType`)。WHERE 句のリテラルにも同じ検査が要ります。`WHERE age = 'x'`(`age` は INTEGER 列)のような取り違えを、実行時まで持ち越す理由はありません。

```go
// checkWhereType は WHERE 句の列とリテラルの型が一致するかをコンパイル時に検査する。
func checkWhereType(info *TableInfo, where *sql.WhereClause) error {
	col, err := findColumn(info, where.Column)
	if err != nil {
		return err
	}
	return checkValueType(col, where.Value)
}
```

`checkValueType` そのものは第 11 章から変わっていませんが、doc コメントは書き換えました。

```go
// checkValueType は値がその列の型と一致するかをコンパイル時に検査する。
// INSERT の値検査と WHERE / UPDATE SET のリテラル検査を兼ねる。
func checkValueType(col sql.ColumnDef, v sql.Value) error {
	switch col.Type {
	case sql.TypeInteger:
		if v.IsText {
			return fmt.Errorf("列 %s は INTEGER ですが TEXT の値が指定されました", col.Name)
		}
	case sql.TypeText:
		if !v.IsText {
			return fmt.Errorf("列 %s は TEXT ですが INTEGER の値が指定されました", col.Name)
		}
	default:
		return fmt.Errorf("列 %s の型が不明です", col.Name)
	}
	return nil
}
```

「INSERT の値がその列の型と一致するか」だけを検査していた関数が、この章から WHERE 句と(12.3 節で見る)UPDATE の SET 句のリテラル検査も兼ねる共通部品に格上げされました。関数のコードは 1 行も変わっていません——**呼び出し側が増えただけ**です。これも、9.5 節以来この本で繰り返してきた「型で判定できる制約は早い段階(パーサ、あるいはコンパイラ)で弾く」という設計方針の延長です。

## 12.2　最初のクエリオプティマイザ — 主キー等値は Seek で

WHERE を素直にフルスキャン + フィルタへコンパイルするだけでも、SELECT は動くようになります。しかし、それだけでは物足りません。第 10 章 10.6 節で、`vmdemo` を使って `id = 2` の 1 行だけを `OpSeekRowid` で一発検索するプログラムを**手で組んで**動かしました。あのとき使った命令は、この章まで一度も自動生成されたことがありません。ここでようやく、その命令が Code Generator の出力として復活します。

### isPKEquality — たった 1 つの判定関数

WHERE が「PK 列 = 整数リテラル」という特定の形をしているとき**だけ**、minidb はまったく違うプログラムを生成します。全件スキャンではなく、木を根から一発で降りる `SeekRowid` です。この形かどうかを判定するのが `isPKEquality` です。

```go
// isPKEquality は where が「PK 列 = 整数リテラル」の形かどうかを判定する。
// この形のときだけ、全件スキャンではなく SeekRowid によるポイント
// ルックアップへコンパイルできる(第 10 章の point lookup と同じ形)。
func isPKEquality(info *TableInfo, where *sql.WhereClause) bool {
	if where == nil || info.PKIndex < 0 {
		return false
	}
	if where.Op != sql.OpEq {
		return false
	}
	if where.Column != info.Columns[info.PKIndex].Name {
		return false
	}
	return !where.Value.IsText
}
```

4 つの条件——WHERE があること、テーブルに PK があること、演算子が `=` であること、列名が PK 列であること、値が整数(TEXT でない)であること——を順に確認するだけの、飾り気のない関数です。**この 1 つの判定関数こそが、minidb のクエリオプティマイザのすべてです。** 「同じ `SELECT` でも、`WHERE` の形が違えば生成されるプログラムがまるごと違う」——**実行計画**という概念の核心を、この 12 行がそのまま体現しています。

<div class="sqlite-note">

<span class="note-title">SQLite ではこうなっている: where.c という巨大な領域</span> 本物のクエリオプティマイザは、統計情報(テーブルの行数やヒストグラム)、複数インデックスからの選択、JOIN の結合順序の決定まで扱う、RDBMS 実装の中でも屈指の難所です。SQLite では WHERE 句の解析と実行計画の生成を担う `where.c` が単独で約 7900 行あります(第 1 章 1.3 節の sqlite-note で触れた btree.c・約 1.2 万行に次ぐ大物です)。minidb の `isPKEquality` は、その巨大な領域が担う仕事のうち「使えるインデックス(この場合は主キー)が WHERE の形とぴったり一致するときだけ使う」という、最も単純な 1 パターンの種にすぎません。しかし種は種です——本物のオプティマイザも、根底では「この WHERE にはこのアクセス経路が使えるか」を判定する、同じ形の問いを大量に積み重ねています。

</div>

### compileSeekRowid — 第 10 章の point lookup が自動生成される

`isPKEquality` が true のとき、`compileSelect` は `compileSeekRowid` を呼びます。

```go
// compileSeekRowid は「PK 列 = 整数リテラル」の WHERE を、
// Init / OpenRead / Integer(キーを r[1] へ) / SeekRowid(不一致なら Halt へ)
// / 列読み出し / ResultRow / Halt という、全件スキャンを伴わないポイント
// ルックアップへコンパイルする。cols は投影(出力)する列。
func compileSeekRowid(info *TableInfo, where *sql.WhereClause, cols []resolvedColumn) []Instr {
	const keyReg = 1
	const baseReg = 2

	program := []Instr{
		{Op: OpInit, P2: 1, Comment: "アドレス 1 へジャンプ"},
		{Op: OpOpenRead, P1: cursorNum, P2: int(info.Root), Comment: fmt.Sprintf("%s を開く", info.Name)},
		{Op: OpInteger, P1: int(where.Value.Int), P2: keyReg, Comment: fmt.Sprintf("PK の探索値 %d を r[%d] へ", where.Value.Int, keyReg)},
	}

	seekAddr := len(program)
	program = append(program, Instr{Op: OpSeekRowid, P1: cursorNum, P3: keyReg, Comment: "r[1] で Seek。一致しなければ終了"})

	for i, col := range cols {
		reg := baseReg + i
		if col.isRowid {
			program = append(program, Instr{Op: OpRowid, P1: cursorNum, P2: reg,
				Comment: fmt.Sprintf("%s(rowid)を r[%d] へ", col.name, reg)})
			continue
		}
		program = append(program, Instr{Op: OpColumn, P1: cursorNum, P2: col.recordIndex, P3: reg,
			Comment: fmt.Sprintf("%s を r[%d] へ", col.name, reg)})
	}
	program = append(program, Instr{Op: OpResultRow, P1: baseReg, P2: len(cols), Comment: "1 行を出力"})

	haltAddr := len(program)
	program = append(program, Instr{Op: OpHalt, Comment: "終了"})
	program[seekAddr].P2 = haltAddr

	return program
}
```

`Rewind` も `Next` もありません。`OpInteger` でリテラルをレジスタへ置き、`OpSeekRowid` で一発で木を降り、一致しなければ(`P2` のバックパッチ先である)`Halt` へ直行します。一致すれば列を読み出して `ResultRow` を 1 回出すだけで終わりです。**ループが存在しない**という点が、12.1 節のフルスキャンとの決定的な違いです。10.6 節で手で組んだプログラムと見比べてみてください——`cursorNum` や `info.Root` がカタログから自動的に埋まる以外、命令の並びはほとんど同じ形をしています。あのとき「バイトコードとはこういうものだ」と手を動かして体感した形が、いま `Compile` の出力として自動的に生成されています。

### compileSelect — プラン選択の分岐

`compileSelect` 本体は、この 2 つのプラン(`compileSeekRowid` と、次に見る `compileFullScan`)をどちらか選ぶだけの薄い入り口に変わりました。

```go
// compileSelect は SELECT を、WHERE の有無・形に応じて次のどちらかへ
// コンパイルする。
//
//   - WHERE が「PK 列 = 整数リテラル」: compileSeekRowid(最適化)
//   - それ以外(WHERE なし、または一般の WHERE): compileFullScan
func compileSelect(stmt *sql.SelectStmt, cat *Catalog) ([]Instr, error) {
	info, err := cat.Get(stmt.Table)
	if err != nil {
		return nil, err
	}
	cols, err := resolveColumns(info, stmt.Star, stmt.Columns)
	if err != nil {
		return nil, err
	}
	if stmt.Where != nil {
		if err := checkWhereType(info, stmt.Where); err != nil {
			return nil, err
		}
	}

	if isPKEquality(info, stmt.Where) {
		return compileSeekRowid(info, stmt.Where, cols), nil
	}
	return compileFullScan(info, stmt.Where, cols)
}
```

`WHERE id = 2` と `WHERE age = 55` は、SQL の構文としては「WHERE 句を 1 つ持つ SELECT」という同じ形をしています。しかし `isPKEquality` の判定 1 つで、生成されるバイトコードはまったく別物になります——12.5 節で、この違いが実行時間の桁の違いとして現れるのを実測します。

`WHERE` の**構文上の形**は同じでも、`isPKEquality` という 1 つの分岐点を境に、生成されるプログラムはループを持つか持たないかという根本から分かれます。この分岐こそが「実行計画(query plan)」という言葉の指す実体です——同じ問い合わせでも、答えにたどり着く経路は 1 つではなく、コンパイラ(この場合はたった 1 つの `if` 文)がどちらを選ぶかによって、実行時間の桁が変わります。

### compileFullScan — SELECT/UPDATE/DELETE が共有する全件スキャン

`isPKEquality` が false のときに使われるのが `compileFullScan` です。この関数は、12.1 節で説明した「フルスキャン + WHERE によるフィルタ」の実装そのものであると同時に、この章の後半で見る UPDATE と DELETE からも**そのまま呼び出される**共通部品です。そのため引数はすでに「投影する列」を渡す汎用的な形(`cols []resolvedColumn`)になっています。

```go
// compileFullScan は SELECT/UPDATE/DELETE に共通する「全件スキャン +
// (あれば)行ごとのフィルタ」プログラムを生成する。cols は投影する列。
//
// WHERE があるループ本体は、行ごとに次を行う:
//
//  1. 比較対象の列値をレジスタへ(PK 列なら OpRowid、他は OpColumn)
//  2. リテラルをレジスタへ(OpInteger / OpString)
//  3. invertOp(where.Op) の比較命令で、条件が不成立ならこの行を
//     スキップする(Next のアドレスへジャンプ)
//  4. 通過したら cols を読み出して ResultRow
func compileFullScan(info *TableInfo, where *sql.WhereClause, cols []resolvedColumn) ([]Instr, error) {
	var program []Instr
	program = append(program,
		Instr{Op: OpInit, P2: 1, Comment: "アドレス 1 へジャンプ"},
		Instr{Op: OpOpenRead, P1: cursorNum, P2: int(info.Root), Comment: fmt.Sprintf("%s を開く", info.Name)},
	)

	rewindAddr := len(program)
	program = append(program, Instr{Op: OpRewind, P1: cursorNum, Comment: "先頭へ"})
	loopStart := len(program)

	baseReg := 1
	filterJumpAddr := -1
	if where != nil {
		whereCol, err := resolveColumn(info, where.Column)
		if err != nil {
			return nil, err
		}
		const whereReg = 1
		const litReg = 2
		if whereCol.isRowid {
			program = append(program, Instr{Op: OpRowid, P1: cursorNum, P2: whereReg,
				Comment: fmt.Sprintf("WHERE 列 %s(rowid)を r[%d] へ", whereCol.name, whereReg)})
		} else {
			program = append(program, Instr{Op: OpColumn, P1: cursorNum, P2: whereCol.recordIndex, P3: whereReg,
				Comment: fmt.Sprintf("WHERE 列 %s を r[%d] へ", whereCol.name, whereReg)})
		}
		if where.Value.IsText {
			program = append(program, Instr{Op: OpString, P1: litReg, P4: where.Value.Text,
				Comment: fmt.Sprintf("リテラル %q を r[%d] へ", where.Value.Text, litReg)})
		} else {
			program = append(program, Instr{Op: OpInteger, P1: int(where.Value.Int), P2: litReg,
				Comment: fmt.Sprintf("リテラル %d を r[%d] へ", where.Value.Int, litReg)})
		}
		filterJumpAddr = len(program)
		program = append(program, Instr{Op: invertOp(where.Op), P1: whereReg, P3: litReg,
			Comment: fmt.Sprintf("WHERE %s %s ... が不成立なら次の行へ", where.Column, where.Op)})
		baseReg = 3
	}

	for i, col := range cols {
		reg := baseReg + i
		if col.isRowid {
			program = append(program, Instr{Op: OpRowid, P1: cursorNum, P2: reg,
				Comment: fmt.Sprintf("%s(rowid)を r[%d] へ", col.name, reg)})
			continue
		}
		program = append(program, Instr{Op: OpColumn, P1: cursorNum, P2: col.recordIndex, P3: reg,
			Comment: fmt.Sprintf("%s を r[%d] へ", col.name, reg)})
	}
	program = append(program, Instr{Op: OpResultRow, P1: baseReg, P2: len(cols), Comment: "1 行を出力"})

	nextAddr := len(program)
	program = append(program, Instr{Op: OpNext, P1: cursorNum, P2: loopStart, Comment: "次の行があれば戻る"})

	haltAddr := len(program)
	program = append(program, Instr{Op: OpHalt, Comment: "終了"})
	program[rewindAddr].P2 = haltAddr
	if filterJumpAddr >= 0 {
		program[filterJumpAddr].P2 = nextAddr
	}

	return program, nil
}
```

第 11 章の `compileSelect` に対する変更点は 2 つです。1 つは `where != nil` のブロックがループ本体の先頭に挿入されたこと(WHERE 列をレジスタへ、リテラルをレジスタへ、`invertOp` で比較して不成立なら読み飛ばす)。もう 1 つは、WHERE があるときレジスタの割り当てを 1・2 番(WHERE 列・リテラル)が使うため、投影する列の開始レジスタ `baseReg` を 3 番からにずらしていることです(WHERE がなければ第 11 章と同じく 1 番から)。

バックパッチが 1 つ増えている点にも触れておきます。第 11 章では `Rewind` の飛び先(`rewindAddr`)だけをあとから埋めていましたが、この章では WHERE のジャンプ命令(`filterJumpAddr`)の飛び先も、`Next` の番地(`nextAddr`)が確定してから埋めます。**「不成立なら次の行へ」というジャンプ先は、`Next` 命令自身がプログラムのどこに配置されるかが決まるまで分からない**——これも 11.3 節で見たバックパッチと同じ理由による、後回しの解決です。

`cols`(投影する列)を汎用の引数として受け取っている理由は、この関数が UPDATE と DELETE からも呼ばれるからです。SELECT が投影するのは「ユーザーが指定した列」、UPDATE と DELETE が投影するのは「書き換え対象の行を特定するための列」——中身は違いますが、**「行ごとに WHERE を判定し、通過した行だけ何らかの列を出力する」という骨格は完全に同じ**です。この共有が、12.3 節で見る UPDATE / DELETE の実装をぐっと軽くします。

### 二次インデックスの理論 — 実装しない割り切り

`WHERE age = 55` は今のところ、フルスキャン + フィルタでしか実行できません。10 万行のテーブルなら 10 万行すべてを律儀に読みます。これを速くするには何が要るでしょうか。

答えは**二次インデックス**です。「`name` の値から、その行の rowid を素早く引ける変換表」があれば、`WHERE name = 'x'` はテーブル本体を全件読まずに、まずこの変換表を検索し(見つかった rowid で)テーブルを `SeekRowid` すればよくなります。この変換表の実体は、第 5 章 5.4 節で触れた**インデックス用の B-Tree**です。

> `WHERE name = 'Bob'` のような検索は、この 2 つの木のリレーで実行されます。
>
> 1. `name` 列に張られたインデックス用 B-Tree を検索し、`'Bob'` に対応する rowid を得る
> 2. その rowid を使ってテーブル用 B-Tree を検索し、実際の行データを取り出す

第 5 章のこの一節で説明したとおり、インデックス用 B-Tree はテーブル用 B-Tree(キー=rowid、値=レコード本体)とは似て非なる木で、**キーが列の値そのもの(この場合 `name`)、値を持たない(あるいは rowid だけを添える)**という構造をしています。この 2 段構えのリレーがあれば、`WHERE name = 'Bob'` は手順 1(インデックスの検索、O(log n))と手順 2(rowid での `SeekRowid`、これも O(log n))を合わせても、テーブルを全件読むより桁違いに速くなります。

minidb がこれを実装しない理由は、技術的な壁にあります。`btree.BTree` のキーは第 2 章以来一貫して `uint64` 固定です(第 6 章でセルのキーをそう定義しました)。`name`(TEXT)をキーにするインデックスを作るには、キーの比較を「数値の大小」から「バイト列の辞書順比較」へ拡張する必要があります——`interior.findChild` や `leaf.findSlot` の二分探索(第 6・7 章)が使っている `<` 比較を、`bytes.Compare` のようなバイト列比較に差し替える改修です。これは決して不可能な壁ではありませんが、影響範囲はキーの型を横断的に扱うすべての箇所(挿入時の位置決め、分割時のセパレータの選び方、削除時の再探索、カーソルの `Seek`)に及び、`btree` パッケージの主要な関数のほとんどを書き直すことになります。ページ形式(セルのキー幅)から見直しが必要になる可能性すらあり、この章 1 つに収める分量ではないと判断しました。

もう 1 つ、実装しない判断を後押しした理由があります。二次インデックスを追加すると、この章で実装した `UPDATE`/`DELETE` の 2 相方式にも影響が及びます。テーブル本体の行を書き換えたら、その行を指すすべてのインデックスも整合させて書き換えなければなりません——`UPDATE users SET name = 'X' WHERE id = 1` は、テーブル用 B-Tree の 1 箇所だけでなく、`name` のインデックス用 B-Tree からも古いエントリを消し、新しいエントリを足す必要があります。この「複数の木を同期させて書き換える」問題は、二次インデックスそのものの実装よりもさらに一段難しく、この章の範囲を明確に超えます。

ここでは理論の説明にとどめ、実装は読者への発展課題とします。第 16 章の「この先の学習へ」で、この宿題を改めて取り上げます。

## 12.3　UPDATE と DELETE — 2 相方式

WHERE の仕組みが整ったので、いよいよ第 3 部最後の機能——`UPDATE` と `DELETE`——に着手します。

### 役割分担: 探索はバイトコード、書き換えは Engine

一見、`UPDATE` は「WHERE に一致する行を見つけて、その場で書き換える」という 1 手で済みそうに見えます。しかし minidb はそうしません。**探索(どの行が対象か)はバイトコード VM に任せ、実際の木の書き換え(`Insert`/`Delete`)は `exec.Engine` が担う**という、2 つのフェーズに分けます。この役割分担には、はっきりした理由が 2 つあります。

**理由 1: カーソルの契約。** 第 10 章 10.3 節で `Cursor` を実装したとき、こう書きました。

> このカーソルは読み取り専用の走査だけを目的とする。カーソルが生きている間に対象の BTree へ Insert / Delete を行うことは想定していない(木の構造が変わると stack が指す位置の意味が崩れるため)。

`Cursor` の `stack` はページ番号とインデックスの組でしかなく、走査中に木が分割・収縮すればその意味は崩れます。VM のループが `Next` でカーソルを進めながら、同じループの中で `Insert`/`Delete` を呼ぶことは、この契約に真っ向から反します。

**理由 2: Halloween problem。** 走査しながら書き換えると、もう 1 つ別の問題が起きます。**書き換えた行を、走査自身が再訪してしまう**のです。これは 1976 年のハロウィンの日に、IBM の研究者たちがある UPDATE 文を検討していて発見した逸話にちなんで名付けられた、リレーショナルデータベース理論の古典的な問題です。定番の例で説明します。「給与が 25000 ドル未満の全従業員の給与を 10% 上げる」という `UPDATE employees SET salary = salary * 1.1 WHERE salary < 25000` を、給与でソートされたインデックスを走査しながら実行するとどうなるでしょうか。ある従業員の給与を 24000 ドルから 26400 ドルに上げると、その行はインデックス上で**まだ走査していない先の位置**(給与が高い側)へ移動します。走査がそこへ到達すると、たった今 10% 上げたばかりのその行を**もう一度**条件に合う行として見つけてしまい、さらに 10% 上げてしまいます——本来 1 回だけのはずの更新が、何度も繰り返されてしまうのです。「探索対象の集合そのものを、探索しながら書き換えてはいけない」——これが Halloween problem の教訓です。

minidb の `UPDATE`/`DELETE` は rowid をキーにした木の上で動くため、給与の例ほど劇的な移動は起きにくいものの、原理は同じです。**探索を完全に終わらせてから書き換える**——2 相方式は、この 2 つの理由(カーソルの契約と Halloween problem)への、最も単純な回答です。

### compileUpdate / compileDelete — 「対象行を列挙する SELECT」への脱糖

第 1 相(探索フェーズ)をコンパイルするのが `compileUpdate` と `compileDelete` です。どちらも、実は**中身は SELECT と同じ機構**——`compileSeekRowid` と `compileFullScan`——を、投影する列だけを変えて呼び出しているにすぎません。

```go
// updateProjectionColumns は UPDATE の探索プログラムが出力する列を返す。
// 「rowid + PK を除く全列の現在値」を、書き換えフェーズ(Engine)が
// 使える形で列挙する(compileUpdate のコメントを参照)。
func updateProjectionColumns(info *TableInfo) []resolvedColumn {
	cols := []resolvedColumn{{name: "rowid", isRowid: true}}
	idx := 0
	for i, col := range info.Columns {
		if i == info.PKIndex {
			continue
		}
		cols = append(cols, resolvedColumn{name: col.Name, recordIndex: idx})
		idx++
	}
	return cols
}

// deleteProjectionColumns は DELETE の探索プログラムが出力する列(rowid のみ)を返す。
func deleteProjectionColumns() []resolvedColumn {
	return []resolvedColumn{{name: "rowid", isRowid: true}}
}

// checkAssignments は UPDATE の SET 句をコンパイル時に検査する。
//   - 代入先の列が存在するか
//   - 型が一致するか
//   - PK 列への代入でないか(rowid の変更は木のキー変更を伴い、
//     この章の 2 相方式では扱えないため未対応)
func checkAssignments(info *TableInfo, assigns []sql.Assignment) error {
	for _, a := range assigns {
		if info.PKIndex >= 0 && info.Columns[info.PKIndex].Name == a.Column {
			return fmt.Errorf("PRIMARY KEY 列の UPDATE は未対応です(rowid の変更を伴うため)")
		}
		col, err := findColumn(info, a.Column)
		if err != nil {
			return err
		}
		if err := checkValueType(col, a.Value); err != nil {
			return err
		}
	}
	return nil
}

// compileUpdate は UPDATE を「対象行を列挙する SELECT」へ脱糖する。
//
// UPDATE は探索(どの行が対象か)と書き換え(木への Insert/Delete)の
// 2 相に分けて実行する(方針は engine.go の executeUpdate のコメントを
// 参照)。ここでコンパイルするのは探索フェーズのみで、WHERE の扱いは
// SELECT と全く同じ機構(compileSeekRowid / compileFullScan)を使い、
// ResultRow で「rowid + PK を除く全列の現在値」を出力する。
func compileUpdate(stmt *sql.UpdateStmt, cat *Catalog) ([]Instr, error) {
	info, err := cat.Get(stmt.Table)
	if err != nil {
		return nil, err
	}
	if err := checkAssignments(info, stmt.Set); err != nil {
		return nil, err
	}
	if stmt.Where != nil {
		if err := checkWhereType(info, stmt.Where); err != nil {
			return nil, err
		}
	}

	cols := updateProjectionColumns(info)
	if isPKEquality(info, stmt.Where) {
		return compileSeekRowid(info, stmt.Where, cols), nil
	}
	return compileFullScan(info, stmt.Where, cols)
}

// compileDelete は DELETE を「対象行の rowid を列挙する SELECT」へ脱糖する。
// UPDATE と同じく、探索フェーズだけをここでコンパイルし、実際の
// btree.Delete は engine.go の executeDelete(2 相の第 2 相)が行う。
func compileDelete(stmt *sql.DeleteStmt, cat *Catalog) ([]Instr, error) {
	info, err := cat.Get(stmt.Table)
	if err != nil {
		return nil, err
	}
	if stmt.Where != nil {
		if err := checkWhereType(info, stmt.Where); err != nil {
			return nil, err
		}
	}

	cols := deleteProjectionColumns()
	if isPKEquality(info, stmt.Where) {
		return compileSeekRowid(info, stmt.Where, cols), nil
	}
	return compileFullScan(info, stmt.Where, cols)
}
```

`compileUpdate` が生成するプログラムは、`UPDATE users SET age = 26 WHERE name = 'Bob'` であれば、実質的に `SELECT rowid, id, age FROM users WHERE name = 'Bob'` を実行するのと同じバイトコードです(PK 列 `id` があればそれを除いた残りの全列 + rowid)。`compileDelete` はさらに単純で、`SELECT rowid FROM users WHERE ...` に相当するプログラムを生成するだけです。**`UPDATE` と `DELETE` は、この章では独立した機能ではなく、「SELECT が返す行の集合に対して行う後処理」として脱糖されています。** `isPKEquality` による `SeekRowid` の最適化も、追加の実装なしにそのまま両方へ効きます——`UPDATE users SET age = 77 WHERE id = 2` も、探索部分は 12.2 節で見た `compileSeekRowid` を一発通るだけです。

`checkAssignments` にある **PK 列への代入エラー**は、この節の設計判断の中でも特に重要です。もし `UPDATE users SET id = 100 WHERE id = 1` を許してしまったらどうなるでしょうか。`id` は rowid そのもの(11.3 節)であり、木の中でのキーです。キーを書き換えるということは、木の中のその行の**位置そのもの**を変えることを意味します——それはもはや「1 行の値を更新する」という UPDATE の意味論ではなく、「古いキーの行を削除し、新しいキーで挿入し直す」という**移動**です。この章の 2 相方式(探索で集めた rowid をそのまま使って `Delete`→`Insert` する、次項参照)は、rowid が実行中に変わらないことを前提にしています。PK への代入を許せば、この前提が崩れます。実装を複雑にしてまで対応する価値は薄いと判断し、`checkAssignments` はコンパイル時にこの操作をきっぱり拒否します。

### engine.go — 第 2 相(書き換え)の実装

探索フェーズの結果(`rows`)を受け取り、実際に木を書き換えるのが `executeUpdate` と `executeDelete` です。

**exec/engine.go(1) — Execute の分岐追加**

```go
	switch s := stmt.(type) {
	case *sql.InsertStmt:
		return &Result{Message: "1 行を挿入しました"}, nil
	case *sql.SelectStmt:
		info, err := e.cat.Get(s.Table)
		if err != nil {
			return nil, err
		}
		columns := s.Columns
		if s.Star {
			columns = make([]string, len(info.Columns))
			for i, col := range info.Columns {
				columns[i] = col.Name
			}
		}
		return &Result{Columns: columns, Rows: rows}, nil
	case *sql.UpdateStmt:
		return e.executeUpdate(s, rows)
	case *sql.DeleteStmt:
		return e.executeDelete(s, rows)
	default:
		return nil, fmt.Errorf("未対応の文です: %T", stmt)
	}
```

`Execute` の骨格(`sql.Parse` → `Compile` → `VM.Run` → `applyRootMoves`)は第 11 章から変わりません。`vm.Run` が集めた `rows`(探索フェーズの結果)を、文の種類に応じて後処理する末尾の型スイッチに、`UpdateStmt` と `DeleteStmt` の分岐が加わっただけです。

**exec/engine.go(2) — executeUpdate・executeDelete・applyAssignments**

```go
// executeUpdate は UPDATE の書き換えフェーズ(2 相方式の第 2 相)。
// rows は探索フェーズ(compileUpdate が生成したバイトコード)が
// ResultRow で列挙した「rowid + PK を除く全列の現在値」の一覧。
//
// カーソルで走査しながら同じ木を書き換えない理由は 2 つある:
//  1. カーソルの契約上、カーソル使用中の木への Insert/Delete は未定義
//     (第 10 章 cursor.go の前提)。
//  2. 走査しながら書き換えると、書き換えた行を走査が再訪してしまう
//     おそれがある(Halloween problem として知られる古典的な問題)。
//
// そのため探索を先に完了させ(バイトコード)、対象行を確定させてから
// 改めて Engine が直接 btree を操作する。
func (e *Engine) executeUpdate(stmt *sql.UpdateStmt, rows [][]sql.Value) (*Result, error) {
	info, err := e.cat.Get(stmt.Table)
	if err != nil {
		return nil, err
	}
	tree := btree.OpenAt(e.pg, info.Root)
	beforeRoot := tree.Root()

	for _, row := range rows {
		rowid := uint64(row[0].Int)
		newValues := applyAssignments(info, row[1:], stmt.Set)
		data, err := EncodeRecord(newValues)
		if err != nil {
			return nil, err
		}
		if err := tree.Delete(rowid); err != nil {
			return nil, err
		}
		if err := tree.Insert(rowid, data); err != nil {
			return nil, err
		}
	}

	if afterRoot := tree.Root(); afterRoot != beforeRoot {
		if err := e.cat.UpdateRoot(info, afterRoot); err != nil {
			return nil, err
		}
	}
	return &Result{Message: fmt.Sprintf("%d 行を更新しました", len(rows))}, nil
}

// executeDelete は DELETE の書き換えフェーズ(2 相方式の第 2 相)。
// rows は探索フェーズが列挙した対象行の rowid の一覧(1 列のみ)。
// 方針は executeUpdate と同じ(コメント参照)。
func (e *Engine) executeDelete(stmt *sql.DeleteStmt, rows [][]sql.Value) (*Result, error) {
	info, err := e.cat.Get(stmt.Table)
	if err != nil {
		return nil, err
	}
	tree := btree.OpenAt(e.pg, info.Root)
	beforeRoot := tree.Root()

	for _, row := range rows {
		rowid := uint64(row[0].Int)
		if err := tree.Delete(rowid); err != nil {
			return nil, err
		}
	}

	if afterRoot := tree.Root(); afterRoot != beforeRoot {
		if err := e.cat.UpdateRoot(info, afterRoot); err != nil {
			return nil, err
		}
	}
	return &Result{Message: fmt.Sprintf("%d 行を削除しました", len(rows))}, nil
}

// applyAssignments は UPDATE の SET 句を、探索フェーズが読み出した
// 「PK を除く全列の現在値」(current、info.Columns の PK を除いた順)に
// 適用し、書き換え後の値の並びを返す。current 自体は書き換えない。
func applyAssignments(info *TableInfo, current []sql.Value, assigns []sql.Assignment) []sql.Value {
	newValues := append([]sql.Value(nil), current...)
	idx := 0
	for i, col := range info.Columns {
		if i == info.PKIndex {
			continue
		}
		for _, a := range assigns {
			if a.Column == col.Name {
				newValues[idx] = a.Value
			}
		}
		idx++
	}
	return newValues
}
```

`executeUpdate` の中心は、探索フェーズが返した `rows` を 1 行ずつ処理するループです。木に「値を上書きする」API がないのは、11.2 節でカタログの `UpdateRoot` を実装したときと事情がまったく同じです(第 6〜8 章の `BTree.Insert` は重複キーをエラーにする仕様でした)。そこで `executeUpdate` も同じ回り道——**`Delete` してから同じキーで `Insert` し直す**——で「更新」を表現します。`applyAssignments` が SET 句を現在値に適用して新しい値の並びを作り、`EncodeRecord` でレコード化してから書き戻す、という流れです。

`applyAssignments` の中身を、具体例で追ってみます。`users(id PK, name, age)` の `id=2` の行(`name="Bob"`, `age=25`)に対して `UPDATE users SET age = 26 WHERE id = 2` を実行するとします。探索フェーズの `ResultRow` は `updateProjectionColumns`(12.3 節冒頭)が決めた並び——rowid、続いて PK を除く列の現在値——で 1 行を出力するので、`row` は `[2, "Bob", 25]` になります。`executeUpdate` はこれを `rowid = 2` と `row[1:] = ["Bob", 25]`(`current`)に分け、`applyAssignments(info, current, stmt.Set)` を呼びます。`applyAssignments` は `current` のコピーを作り、`info.Columns` を PK を飛ばしながら先頭から辿り(`name` → `idx=0`, `age` → `idx=1`)、各列について `stmt.Set`(この例では `{Column: "age", Value: 26}` の 1 件)に一致する代入があれば `newValues[idx]` を上書きします。結果は `["Bob", 26]`——`name` は代入がなかったので `current` のままの `"Bob"`、`age` だけが `26` に置き換わります。これを `EncodeRecord` でレコード化し、`rowid=2` で `Delete` → `Insert` すれば、更新が完了します。SET 句にない列の値が**壊れずにそのまま残る**のは、この「現在値のコピーに対して、代入のある列だけ上書きする」という素直な実装のおかげです。

そして、`executeUpdate` の末尾にある**ルート追跡の後始末**を見てください。

```go
if afterRoot := tree.Root(); afterRoot != beforeRoot {
	if err := e.cat.UpdateRoot(info, afterRoot); err != nil {
		return nil, err
	}
}
```

これは第 11 章 11.4 節の `applyRootMoves` と、まったく同じ形をしています。`Delete`→`Insert` を繰り返せば、テーブルの木は分割や収縮を起こしてルートが動くことがあります。`OpInsert` 命令(11.3 節)はこの追跡を VM の内部で行い `rootMoves` に記録していましたが、`executeUpdate`/`executeDelete` はバイトコードの外(Engine が直接 `btree` を叩く第 2 相)で `Insert`/`Delete` を呼んでいるため、**VM の `rootMoves` の仕組みは使えません**。そこで `executeUpdate`/`executeDelete` はそれぞれ自分の手で `beforeRoot`/`afterRoot` を比較し、動いていればカタログを更新する——という、`applyRootMoves` と同じ責務を、同じ形のコードでもう一度自前で果たしています。「ルートが動くたびに、誰かが追いかけて記録し直さなければならない」という 11.2 節の設計原則が、この章でも寸分違わず再確認されます。

`executeDelete` は `executeUpdate` からレコード生成の手間を省いただけの、さらに単純な形です。対象の rowid を 1 つずつ `Delete` し、同じくルート追跡の後始末を行います。

### PK 列への代入は未対応 — もう一度確認しておく

12.3 節冒頭の `checkAssignments` で既に述べたとおり、`UPDATE t SET id = ... ` はコンパイル時にエラーになります。これは実装の手抜きではなく、**意味論上の判断**です。PK(rowid)は木のキーであり、キーを変えるということは行を別の場所へ**移動**させることに等しく、それは UPDATE(値の更新)ではなく「削除して別のキーで挿入し直す」という別の操作です。この章の 2 相方式が前提にしている「探索フェーズで確定した rowid は、書き換えフェーズでもそのまま有効である」という不変条件を守るために、この操作だけは対応範囲の外に置きました。

```go
// 2 相方式の統合テスト: 500 行に対する UPDATE(約半数が対象)が
// エラーなく完了し、件数・結果が正しいことを確認する。
func TestEngineUpdateManyRows(t *testing.T) {
	e, _ := openTestEngine(t)
	mustExec(t, e, "CREATE TABLE users (id INTEGER PRIMARY KEY, name TEXT, age INTEGER)")
	const n = 500
	wantUpdated := 0
	for i := 1; i <= n; i++ {
		age := i % 100
		if age < 50 {
			wantUpdated++
		}
		mustExec(t, e, fmt.Sprintf("INSERT INTO users VALUES (%d, 'user%d', %d)", i, i, age))
	}

	res := mustExec(t, e, "UPDATE users SET age = 200 WHERE age < 50")
	wantMsg := fmt.Sprintf("%d 行を更新しました", wantUpdated)
	if res.Message != wantMsg {
		t.Fatalf("Message = %q, want %q", res.Message, wantMsg)
	}

	all := mustExec(t, e, "SELECT id, age FROM users")
	if len(all.Rows) != n {
		t.Fatalf("Rows 件数 = %d, want %d", len(all.Rows), n)
	}
	got200 := 0
	for _, row := range all.Rows {
		id := int(row[0].Int)
		wantOld := id % 100
		if wantOld < 50 {
			got200++
			if row[1].Int != 200 {
				t.Fatalf("id=%d の age = %d, want 200", id, row[1].Int)
			}
		} else if row[1].Int != int64(wantOld) {
			t.Fatalf("id=%d の age = %d, want %d(更新対象外)", id, row[1].Int, wantOld)
		}
	}
	if got200 != wantUpdated {
		t.Fatalf("age=200 の件数 = %d, want %d", got200, wantUpdated)
	}
}
```

このテストが確かめているのは、単に「UPDATE が動く」ことだけではありません。**500 行のうち約半数が更新対象**という設定は、対象行の書き換え(木の `Delete`→`Insert`)によって木が何度も分割・収縮を起こす規模です。もし探索と書き換えを 1 相で(走査しながら)行っていたら、Halloween problem によって「一度更新した行を再訪して二重に更新してしまう」おそれがありました。このテストは、更新後の全件を読み直し、**対象だった行はちょうど 1 回だけ `age = 200` になり、対象外の行は元の値のまま**であることを検証することで、2 相方式が実際にその問題を避けられていることを裏付けています。`TestEngineDeleteManyRows`(削除版)と `TestEngineUpdateDeleteAcrossReopen`(UPDATE/DELETE 後にファイルを閉じて再オープンしても結果が保たれることの確認)も同じ精神の統合テストで、`code/ch12/exec/engine_test.go` に収録されています。

## 12.4　.timer — 速さを測る道具

WHERE の実行計画が最適化されていることは `.explain` で**見る**ことができます。しかしそれが実際に**速い**のかどうかは、時間を測らなければ分かりません。`cmd/minidb` に `.timer on`/`.timer off` という 1 対のメタコマンドを追加します。

```go
import (
	"bufio"
	"fmt"
	"io"
	"os"
	"strings"
	"time"

	"minidb/exec"
	"minidb/pager"
	"minidb/sql"
)
```

`"time"` パッケージが 1 つ増えただけです。`runREPL` にタイマーの on/off 状態を保持する変数を足し、メタコマンドと文の実行にそれぞれ引き渡します。

```go
func runREPL(engine *exec.Engine, in io.Reader, out io.Writer, interactive bool) {
	scanner := bufio.NewScanner(in)
	// timerOn は ".timer on/off" で切り替える、SQL 文の実行時間表示の
	// on/off 状態。メタコマンド自体は計測の対象にしない。
	timerOn := false
	for {
		if interactive {
			fmt.Fprint(out, prompt)
		}
		if !scanner.Scan() {
			return
		}

		line := strings.TrimSpace(scanner.Text())
		if !interactive {
			fmt.Fprintln(out, prompt+line)
		}
		switch {
		case line == "":
			continue
		case line == ".exit":
			return
		case strings.HasPrefix(line, "."):
			runMeta(engine, line, out, &timerOn)
		default:
			runStatement(engine, line, out, timerOn)
		}
	}
}
```

`timerOn` はループの外側(`runREPL` の中)で 1 つだけ持たれ、`runMeta` へは書き換えられるようにポインタ(`&timerOn`)で渡します。

```go
// runMeta は "." で始まるメタコマンドを実行する。
func runMeta(engine *exec.Engine, line string, out io.Writer, timerOn *bool) {
	switch {
	case line == ".tables":
		names, err := engine.Tables()
		if err != nil {
			fmt.Fprintf(out, "エラー: %v\n", err)
			return
		}
		for _, name := range names {
			fmt.Fprintln(out, name)
		}

	case line == ".timer on":
		*timerOn = true

	case line == ".timer off":
		*timerOn = false

	case strings.HasPrefix(line, ".explain "):
		sqlText := strings.TrimSpace(strings.TrimPrefix(line, ".explain "))
		table, err := engine.ExplainSQL(sqlText)
		if err != nil {
			fmt.Fprintf(out, "エラー: %v\n", err)
			return
		}
		fmt.Fprint(out, table)

	default:
		fmt.Fprintf(out, "エラー: 不明なメタコマンドです: %s\n", line)
	}
}

// runStatement は SQL 文を 1 つ実行し、結果を表示する。
// エラーは "エラー: ..." として表示するだけで、REPL は続行する。
// timerOn が true なら、Execute の実行時間(SQL 文のみが対象、
// メタコマンドは対象外)を結果表示の後に "実行時間: 12.345ms" の形式で表示する。
func runStatement(engine *exec.Engine, line string, out io.Writer, timerOn bool) {
	start := time.Now()
	res, err := engine.Execute(line)
	elapsed := time.Since(start)

	if err != nil {
		fmt.Fprintf(out, "エラー: %v\n", err)
		return
	}
	if res.Message != "" {
		fmt.Fprintln(out, res.Message)
	} else {
		printRows(res, out)
	}
	if timerOn {
		fmt.Fprintf(out, "実行時間: %.3fms\n", float64(elapsed)/float64(time.Millisecond))
	}
}
```

`runStatement` は `engine.Execute` の直前に `time.Now()` を取り、直後に `time.Since` で経過時間を測るだけです。計測の対象は**あくまで SQL 文の `Execute` のみ**——`runMeta` が扱うメタコマンド(`.tables` や `.explain` そのもの)は計測しません。この単純な仕掛けが、次の節で「同じ 1 行を返すクエリでも、プランが違えば速度が桁で変わる」ことを、自分の目で確かめる道具になります。

<div class="sqlite-note">

<span class="note-title">SQLite ではこうなっている: .timer へのオマージュ</span> 本物の `sqlite3` コマンドラインシェルにも `.timer on`/`.timer off` というドットコマンドがあり、CPU 時間と実時間の両方を、文を実行するたびに表示してくれます。minidb の `.timer` は名前と用法をそのまま借りた、機能を実時間の計測 1 つに絞ったオマージュです。11.5 節の `.tables`/`.explain` に続き、この章でもう 1 つ、本物の `sqlite3` の道具立てを自分の REPL に迎え入れます。

</div>

**cmd/seeddemo/main.go(全文)**

```go
// cmd/seeddemo/main.go
// users テーブルへダミー行を大量投入するベンチマーク用のツール。
//
// btree を直接操作するのではなく exec.Engine.Execute のループで
// INSERT を発行する。これは「アプリケーションから見た minidb」の
// 素直な使用例を兼ねる(内部実装ではなく SQL だけでデータを増やせる)。
//
// 使い方:
//
//	go run ./cmd/seeddemo <db ファイル> <件数 N>
//
// users テーブル(id INTEGER PRIMARY KEY, name TEXT, age INTEGER)が
// 無ければ作成し、既存の最大 id の続きから N 件を
// INSERT INTO users VALUES (i, 'user<i>', i % 100) の形で挿入する。
package main

import (
	"fmt"
	"os"
	"strconv"

	"minidb/exec"
	"minidb/pager"
)

func main() {
	if len(os.Args) != 3 {
		fmt.Fprintln(os.Stderr, "使い方: seeddemo <db ファイル> <件数 N>")
		os.Exit(1)
	}
	n, err := strconv.Atoi(os.Args[2])
	if err != nil || n < 0 {
		fmt.Fprintln(os.Stderr, "件数 N は 0 以上の整数で指定してください")
		os.Exit(1)
	}

	pg, err := pager.Open(os.Args[1])
	if err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}
	defer pg.Close()

	engine, err := exec.NewEngine(pg)
	if err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}

	startID, err := ensureUsersTable(engine)
	if err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}

	for i := 0; i < n; i++ {
		id := startID + i
		stmt := fmt.Sprintf("INSERT INTO users VALUES (%d, 'user%d', %d)", id, id, id%100)
		if _, err := engine.Execute(stmt); err != nil {
			fmt.Fprintln(os.Stderr, err)
			os.Exit(1)
		}
	}

	fmt.Printf("users に %d 件を挿入しました(合計 %d 件)\n", n, startID-1+n)
}

// ensureUsersTable は users テーブルが無ければ作成する。
// 戻り値は次に使う id(既存の最大 id + 1、テーブルが空/未作成なら 1)。
func ensureUsersTable(engine *exec.Engine) (int, error) {
	tables, err := engine.Tables()
	if err != nil {
		return 0, err
	}
	exists := false
	for _, t := range tables {
		if t == "users" {
			exists = true
			break
		}
	}
	if !exists {
		if _, err := engine.Execute("CREATE TABLE users (id INTEGER PRIMARY KEY, name TEXT, age INTEGER)"); err != nil {
			return 0, err
		}
		return 1, nil
	}

	res, err := engine.Execute("SELECT id FROM users")
	if err != nil {
		return 0, err
	}
	maxID := 0
	for _, row := range res.Rows {
		if id := int(row[0].Int); id > maxID {
			maxID = id
		}
	}
	return maxID + 1, nil
}
```

`ensureUsersTable` が「既存の最大 id の続きから」採番する理由は、このツールを同じ `bench.db` に対して複数回実行しても、主キーの重複エラーを起こさずデータを積み増せるようにするためです。中身は `.tables` で存在確認し、`SELECT id FROM users` で最大 id を調べるだけ——**minidb の外から見れば、これも SQL を発行するだけの 1 つのクライアントです**。btree や exec の内部 API には一切触れていません。

10 万行を投入したデータベースに対して、`.timer` を使って 2 つのクエリを比べます。

```console
minidb> SELECT name FROM users WHERE name = 'user77777';

minidb> .explain SELECT name FROM users WHERE id = 77777
```

**0.103ms と 24.601ms。約 240 倍の差です。** 同じ「1 行を返す」という結果を返す 2 つのクエリが、`WHERE` の形が違うというだけで、実行時間が 2 桁近く変わりました。第 5 章 5.5 節で「高さ 3 の木ならページ読み 3 回で済むが、全ページを読めば 10 万行なら数百〜数千ページを読む」という理論上の見積もりを立てました。ここでその見積もりが、**自分のデータベースの応答時間**として体感できたことになります。`id = 77777` は `SeekRowid` で木を根から高々 3 段(第 5 章 5.5 節の見積もりどおり、10 万行なら B-Tree の高さは 3 前後です)降りるだけで済みますが、`name = 'user77777'` は 10 万行すべてを `Column`→`Ne` で判定しながら読み進める必要があります。

`.explain` の出力にも、読み解くべき数字が並んでいます。

**`OpenRead` の P2 = 297。** 10 万行を挿入した結果、`users` テーブルの木のルートは**ページ 297** まで動いています。第 7 章で学んだとおり、木は分割のたびに新しいページを消費してルートを動かし、第 11 章の `applyRootMoves`(そしてこの章の `executeUpdate`/`executeDelete` に再登場したルート追跡)が、そのたびにカタログの記録を更新してきました。10 万行という規模で、この仕組みが延べ数百回動いた結果が、この `297` という数字に刻まれています。

**フルスキャン側の `Ne 1 8 2`。** `WHERE age = 55` という**等値**の条件が、命令としては `Eq` ではなく **`Ne`**(不成立なら addr 8 = `Next` へ)になっています。これが 12.1 節で実装した `invertOp` の実物です——「成立する行だけを処理する」という自然な発想が、「不成立の行を次へ読み飛ばす」という逆向きの命令として、ここに具体的な数字とオペコードの形で現れています。

## 12.6　まとめ

- `invertOp` が WHERE を「不成立なら次の行へ」というフルスキャン + フィルタのバイトコードに変換する。`checkWhereType` がリテラルと列の型不一致をコンパイル時に検査する
- `isPKEquality` というたった 1 つの判定関数が、minidb のクエリオプティマイザのすべてである。「PK 列 = 整数リテラル」のときだけ `compileSeekRowid` が全件スキャンを伴わないポイントルックアップを生成し、同じ `SELECT` でも WHERE の形によって生成されるプログラムが丸ごと変わることを体現している。二次インデックス(TEXT キーの B-Tree)は理論にとどめ、実装は読者への発展課題とした
- `UPDATE`/`DELETE` は「対象行を列挙する SELECT」への脱糖として `compileUpdate`/`compileDelete` にコンパイルされ、探索(バイトコード)と書き換え(`executeUpdate`/`executeDelete` による `Engine` 直接操作)を分ける 2 相方式で実装した。理由はカーソルの契約と Halloween problem の 2 つ。PK 列への代入は rowid の移動を意味するため未対応とした
- `.timer` によって、`WHERE id = 77777` と `WHERE name = 'user77777'` の実行時間差(約 240 倍)を自分の目で確かめた。同じ結果を返すクエリでも、実行計画が違えば速度の桁が変わる——第 5 章の理論上の見積もりが、自分のデータベースの応答時間として体感できた
- 第 1 章 1.1 節の「壁 2」で予告した UPDATE の難しさに、第 3 部の全 4 章を費やして正面から答えを出した

これで第 3 部——第 9 章から第 12 章まで、SQL 文字列を受け取ってから結果行を返すまでの、実行エンジンの全貌——が完成しました。`.timer` によって、自分のデータベースは「速さ」を手に入れました。しかし、まだ大きな欠落が残っています。第 11 章 11.4 節と 11.6 節の warn で繰り返し述べたとおり、**今の minidb は `.exit`(`pg.Close()` による `Flush`)まで、書き込んだ内容が一切ディスクに反映されません。** REPL を `Ctrl-C` で強制終了すれば、それまでの `INSERT`/`UPDATE`/`DELETE` はすべて消えます。速さの次に必要なのは、**壊れないこと**——第 1 章 1.1 節で立てた壁 3(クラッシュでデータが壊れる)と壁 4(同時アクセスで壊れる)です。第 4 部では、ジャーナリングと WAL によってこの壁を乗り越えます。
