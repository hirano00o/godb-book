# 第 11 章　CREATE TABLE・INSERT・SELECT の実装 — SQL が動き出す

<div class="chap-goal">

<span class="note-title">この章のゴール</span>

- カタログ(`sqlite_schema` の minidb 版)を実装し、複数テーブルを扱えるようにする
- 構文木からバイトコードを生成する Code Generator を実装できる
- REPL で `CREATE TABLE` / `INSERT` / `SELECT` を実行し、自分の SQL の実行計画を `.explain` で観察できる

</div>

## 11.1　最後の 1 枚をつなぐ

第 9 章で、SQL 文字列は `sql.Parse` を通じて構文木になりました。第 10 章で、命令列(`exec.Instr` の並び)を手で組めば `exec.VM` がそれを実行し、結果行を返せることを確かめました。2 つの部品はもうそろっています。残るのは、構文木を命令列へ変換する**たった 1 つの関数**——第 9 章 図 9-1 で "Code Generator" と名付けておいた箱——だけです。この章でそれを実装すれば、SQL 文字列を渡すだけでテーブルが作られ、行が挿入され、結果が返ってくるようになります。第 3 部(第 9〜12 章)の前半 2 章がかけ算のように積み上がって、ようやく掛け算の答えが出る章です。

ただし、Code Generator を書き始める前に片付けておかなければならない問題が 1 つあります。**テーブルはどこに覚えられているのか。**

第 10 章までの `exec.VM` は、`btree.BTree` を 1 本だけ受け取って動いていました(`NewVM(tree *btree.BTree, program []Instr) *VM`、10.4 節)。木は常に 1 本で、ヘッダページのルート(第 2 章で確定させたオフセット 16〜19)がその木を直接指していました。しかし `CREATE TABLE users (...)` を実行するというのは、「新しい木を 1 本作り、その木に `users` という名前を結びつける」という操作です。2 つ目のテーブル `orders` を作れば、木は 2 本になります。木が複数になった瞬間、ヘッダのルートというたった 1 つのポインタでは足りません。**「どの名前がどの木を指すか」を覚えておく仕組み**が要ります。

この問題には、見覚えがあるはずです。第 3 章 3.5 節で、本物の SQLite のファイルを `inspect` ツールで覗いたとき、こう書きました。

> 答えは `sqlite_schema`(旧称 `sqlite_master`)です。SQLite は「どんなテーブルがあり、その実体がどのページから始まるか」というカタログ情報自体を、1 つのテーブルとしてページ 1 に格納します。今回の 1 セルの中身は、私たちが実行した `CREATE TABLE users ...` の定義そのもの(と、users の実体がページ 2 にあるという情報)です。`SELECT * FROM users` が実行されるとき、SQLite はまずページ 1 のカタログを引いて users の在り処(ページ 2)を知り、それからページ 2 を読む——_メタデータもまたテーブルであり、テーブルはページに載る_。この再帰的な美しさは、minidb でも第 3 部でカタログを作るときに拝借します。

あの予告を、ここで回収します。「どの名前がどの木を指すか」を覚える仕組み自体を、**もう 1 本の B-Tree**として作ります。この章は次の順番で進みます。

- **カタログ**(11.2 節) — テーブル名とルートページの対応表を、B-Tree の上に実装する
- **Code Generator**(11.3 節) — 構文木からバイトコードを生成する `Compile` を実装する。あわせて、複数の木・複数のカーソルを扱えるように `exec.VM` を一般化する
- **Engine**(11.4 節) — パース・カタログ照会・コンパイル・実行・後始末を 1 つにまとめる `exec.Engine` を実装する
- **REPL**(11.5 節) — `Engine` を対話的に操作する `cmd/minidb` を実装する(第 10 章の `cmd/vmdemo` はここで役目を終え、削除します)
- **動作確認**(11.6 節) — 第 1 章で本物の SQLite に打った `CREATE TABLE` / `INSERT` / `SELECT` を、自分のデータベースで実行する

## 11.2　カタログ — スキーマもまたテーブルである

### 設計: ヘッダはカタログの木を指す

第 2 章で固めたヘッダページのレイアウトを思い出してください。オフセット 16〜19 に**ルートページ番号**が 1 つだけ記録されていました。第 10 章まではこれがそのままデータの木のルートでした。この章から、この 1 つの数字の意味を変えます。**ヘッダのルートは、これからは「カタログの木」のルートを指す**ことにします。

カタログの木は、ほかの B-Tree と何も変わらない普通の B-Tree です。ただし、そこに格納する値の中身が特別です。カタログの 1 行(1 セル)は、次の 3 つの値をレコード形式(第 10 章 10.2 節の `EncodeRecord`)でエンコードしたものです。

1. **テーブル名**(TEXT)
2. **ルートページ番号**(INTEGER) — そのテーブルの木がどのページから始まるか
3. **CREATE TABLE 文**(TEXT) — そのテーブルを作った `CREATE TABLE` 文そのもの

3 番目の列に注目してください。**スキーマ(列名・型・PRIMARY KEY の情報)を、構造化されたデータとしてではなく、CREATE TABLE 文のテキストそのものとして保存します。** テーブルの列定義が必要になるたびに、このテキストを第 9 章の `sql.Parse` で読み直し、`*sql.CreateTableStmt` へ再パースします。これはまさに、3.5 節で見た本物の `sqlite_schema` の `sql` 列がやっている手口です。「今回の 1 セルの中身は、私たちが実行した `CREATE TABLE users ...` の定義そのもの」——あの観察を、今度は自分の設計として採用します。この選択には実利があります。スキーマの表現方法(列名・型・PRIMARY KEY をどう並べるか)を**パーサ 1 か所に集約**でき、カタログのために別の表現形式を新しく設計・実装・テストする必要がなくなります。第 9 章のパーサは、ユーザーが打つ SQL 文だけでなく、**自分自身が過去に生成したメタデータを読み直す装置**としても働くことになります。

### btree の一般化 — 「ヘッダ直結の木」と「カタログ管理の木」

木が複数になると、第 10 章までの `btree.BTree` にはもう 1 つ困ったことが起きます。第 7 章で見たとおり、**木のルートは分割・収縮によって動きます**。リーフが満杯になって割れれば、新しい内部ページがルートになります(7.2 節)。今までは木が 1 本しかなかったので、「ルートが動いたらヘッダページに書き戻す」という単純な規則(`BTree.Insert` / `BTree.Delete` の中の `t.pg.SetRootPage` 呼び出し)で常に正しく動いていました。しかし木が複数本になったらどうでしょうか。`users` の木のルートが動くたびにヘッダのルートを書き換えてしまったら、ヘッダは(カタログではなく)`users` を指してしまい、カタログそのものを見失います。

**ルートが動くたびに、それを「誰が」追いかけて記録し直すか。** この役割分担が、この章の設計の核心です。答えはこうです。

- **カタログの木**は特別で、ルートが動いたら今までどおりヘッダページに書き戻す
- **テーブルの木**(`users` など)は、ルートが動いても自分では何も書き戻さない。木のルートが今どこにあるかは `BTree.Root()` で確認できるようにし、**カタログの対応する行を書き換える責任は呼び出し側(この後の Engine)に持たせる**

この切り分けを表す 1 つのフラグが `updateHeader` です。

**btree/btree.go(1) — BTree 構造体・updateHeader・Open**

```go
type BTree struct {
	pg   *pager.Pager
	root pager.PageID

	// updateHeader はルートが変わったとき(Insert のルート分割、Delete の
	// ルート差し替え)にヘッダページの RootPage も更新するかどうか。
	//
	// ヘッダのルートは、この pager が管理する「唯一の特別な木」——
	// カタログの木——専用の場所であり、複数のテーブルの木を同時に
	// 開ける第 11 章では、テーブルの木ごとにヘッダを上書きするわけには
	// いかない。そこで Open(ヘッダ由来、カタログ専用)だけ true にし、
	// OpenAt/Create(カタログが個別にルートページ番号を記録するテーブルの
	// 木)では false にして、新しいルートは呼び出し側が Root() で確認して
	// 自分の記録(カタログの行)を更新する形に切り分ける。
	updateHeader bool
}

// Open は pg 上の B-Tree を開く。ヘッダページにルートページ番号が
// 記録されていなければ、空のリーフページを 1 枚確保してルートにする。
// カタログの木を開くための専用の入り口であり、ルートが変わるたびに
// ヘッダページへ書き戻す。
func Open(pg *pager.Pager) (*BTree, error) {
	root, err := pg.RootPage()
	if err != nil {
		return nil, err
	}
	if root == 0 {
		page, err := pg.Allocate()
		if err != nil {
			return nil, err
		}
		initLeaf(page)
		pg.MarkDirty(page.ID)
		if err := pg.SetRootPage(page.ID); err != nil {
			return nil, err
		}
		root = page.ID
	}
	return &BTree{pg: pg, root: root, updateHeader: true}, nil
}
```

**btree/btree.go(2) — OpenAt・Create・Root・MaxKey**

```go
// OpenAt は root をルートとする既存の B-Tree を開く。
// カタログに記録されたテーブルの木を開くときに使う。ルートが変わっても
// ヘッダページは書き換えない(呼び出し側が Root() で新しいルートを
// 確認し、カタログの記録を更新する責任を持つ)。
func OpenAt(pg *pager.Pager, root pager.PageID) *BTree {
	return &BTree{pg: pg, root: root}
}

// Create は空のリーフ 1 枚をルートとする新しい B-Tree を作る。
// CREATE TABLE でテーブルの木を新規に作るときに使う。OpenAt と同じく
// ヘッダページは更新しない。
func Create(pg *pager.Pager) (*BTree, error) {
	page, err := pg.Allocate()
	if err != nil {
		return nil, err
	}
	initLeaf(page)
	pg.MarkDirty(page.ID)
	return &BTree{pg: pg, root: page.ID}, nil
}

// Root は現在のルートページ番号を返す。Insert / Delete によってルートは
// 変わりうるので、呼び出し側(カタログ)は操作後にこれを確認して
// 記録を更新する必要がある。
func (t *BTree) Root() pager.PageID {
	return t.root
}

// MaxKey は木の最大キーを返す。木が空なら ok が false。
// rowid の自動採番(最大値 + 1)に使う。
func (t *BTree) MaxKey() (key uint64, ok bool, err error) {
	pageID := t.root
	for {
		page, err := t.pg.Get(pageID)
		if err != nil {
			return 0, false, err
		}
		if !isInterior(page) {
			l := leaf{page: page}
			n := l.cellCount()
			if n == 0 {
				return 0, false, nil
			}
			return l.keyAt(n - 1), true, nil
		}
		// 内部ノードでは、どのセルのキーよりも右端の子の部分木のキーが
		// 大きいので、常に右端の子を辿ればよい。
		pageID = interior{page: page}.rightmost()
	}
}
```

`Open`(カタログ専用)・`OpenAt`(既存のテーブルの木を開く)・`Create`(新しいテーブルの木を作る)の 3 つの入り口が並びます。違いは戻り値の `updateHeader` フィールドだけです。`Open` だけが `updateHeader: true` を設定し、`OpenAt` と `Create` はゼロ値(`false`)のまま——構造体リテラルの `updateHeader` フィールドを明示的に書かない、という素直な形で「更新しない」がデフォルトになっています。`Root()` は現在のルートページ番号を返すだけの薄いアクセサですが、doc コメントにあるとおり「呼び出し側(カタログ)は操作後にこれを確認して記録を更新する必要がある」という**約束**を運ぶ、この章でいちばん重要な 1 行です。`MaxKey` は木の最大キーを返す新顔で、内部ノードでは常に右端の子をたどればよいという単純な性質(セルのキーはどれも右端の子の部分木のキーより小さい、7.3 節)を利用しています。カタログの ID 採番と、11.3 節で見る rowid の自動採番の両方で使います。

`updateHeader` フラグが実際に効いてくるのは、ルートが動く瞬間——`Insert` の分割と `Delete` の収縮です。第 10 章までは無条件に `t.pg.SetRootPage(...)` を呼んでいたところが、この章ではフラグで条件分岐します。

```go
// 変更前(第 10 章): ルートが変わったら無条件にヘッダへ書き戻す
if err := t.pg.SetRootPage(newRoot.ID); err != nil {
	return err
}

// 変更後(第 11 章): updateHeader が true のときだけ書き戻す
if t.updateHeader {
	if err := t.pg.SetRootPage(newRoot.ID); err != nil {
		return err
	}
}
```

まったく同じ形の条件分岐が `Delete`(内部ノードが縮んでルートが差し替わる箇所)にも入ります。`t.root = newRoot.ID` という行自体は条件と無関係にどちらのケースでも実行される——`updateHeader` が制御するのは「**ヘッダページへの書き戻し**」だけで、「**自分自身が保持するルート**」の更新はどちらの木でも欠かさず行われる、という点を見落とさないでください。テーブルの木も `t.root` は正しく最新のルートを指しています。ただ、それをヘッダへ伝える手段を持たない、という設計です。

### exec/catalog.go — カタログの実装

**exec/catalog.go(全文)**

```go
// catalog.go は minidb のテーブル定義一覧を管理するカタログを担当する。
// SQLite の sqlite_schema テーブルの minidb 版に相当する。
package exec

import (
	"errors"
	"fmt"

	"minidb/btree"
	"minidb/pager"
	"minidb/sql"
)

var (
	ErrTableNotFound = errors.New("テーブルが見つかりません")
	ErrTableExists   = errors.New("テーブルは既に存在します")
)

// TableInfo はカタログに登録されたテーブル 1 つの情報。
type TableInfo struct {
	ID   uint64 // カタログ内のキー
	Name string
	Root pager.PageID // テーブルの木のルートページ(分割・収縮で動く)

	Columns []sql.ColumnDef // CREATE TABLE 文を再パースして得る
	PKIndex int             // INTEGER PRIMARY KEY 列の位置。なければ -1
}

// Catalog はテーブル定義の一覧を管理する。
//
// 実体は特別なテーブルではなく、カタログ自身が 1 つの B-Tree で、
// キーはテーブル ID(挿入順の連番)、値は (テーブル名, ルートページ,
// CREATE TABLE 文)をエンコードしたレコードである。この木のルートは
// ヘッダページが指す、pager にとって唯一特別な木になる
// (テーブルの木は btree.OpenAt でカタログ経由でしか開けない)。
type Catalog struct {
	pg   *pager.Pager
	tree *btree.BTree

	nextID uint64
}

// OpenCatalog はヘッダページのルートが指すカタログの木を開く。
// まだ木が存在しなければ btree.Open が空の木を新規に作る。
func OpenCatalog(pg *pager.Pager) (*Catalog, error) {
	tree, err := btree.Open(pg)
	if err != nil {
		return nil, err
	}
	c := &Catalog{pg: pg, tree: tree}

	// 次に割り当てるテーブル ID は「現在の最大キー + 1」。カタログの木は
	// 行の削除(DROP TABLE 相当)を今のところ持たないので、MaxKey で
	// 十分足りる。
	maxKey, ok, err := tree.MaxKey()
	if err != nil {
		return nil, err
	}
	if ok {
		c.nextID = maxKey + 1
	}
	return c, nil
}

// CreateTable は CREATE TABLE 文からテーブルを作る。名前の重複はエラー。
func (c *Catalog) CreateTable(stmt *sql.CreateTableStmt, sqlText string) error {
	if _, err := c.Get(stmt.Table); err == nil {
		return fmt.Errorf("%w: %s", ErrTableExists, stmt.Table)
	} else if !errors.Is(err, ErrTableNotFound) {
		return err
	}

	table, err := btree.Create(c.pg)
	if err != nil {
		return err
	}

	id := c.nextID
	c.nextID++

	value, err := encodeCatalogRow(stmt.Table, table.Root(), sqlText)
	if err != nil {
		return err
	}
	return c.tree.Insert(id, value)
}

// Get は名前でテーブルを引く。見つからなければ ErrTableNotFound。
func (c *Catalog) Get(name string) (*TableInfo, error) {
	var found *TableInfo
	err := c.tree.Scan(func(key uint64, value []byte) error {
		info, err := decodeCatalogRow(key, value)
		if err != nil {
			return err
		}
		if info.Name == name {
			found = info
		}
		return nil
	})
	if err != nil {
		return nil, err
	}
	if found == nil {
		return nil, fmt.Errorf("%w: %s", ErrTableNotFound, name)
	}
	return found, nil
}

// List は全テーブルを ID 順に返す(.tables 用)。
// カタログの木は ID(挿入順の連番)をキーにしているので、Scan が
// そのまま昇順(= ID 順)で返す。
func (c *Catalog) List() ([]*TableInfo, error) {
	var infos []*TableInfo
	err := c.tree.Scan(func(key uint64, value []byte) error {
		info, err := decodeCatalogRow(key, value)
		if err != nil {
			return err
		}
		infos = append(infos, info)
		return nil
	})
	if err != nil {
		return nil, err
	}
	return infos, nil
}

// UpdateRoot はテーブルの木のルートページ番号を書き換える
// (テーブルへの書き込みでルートが動いたときに呼ぶ)。
//
// カタログの木は他の B-Tree と同じく「値の上書き」API を持たない
// (Insert は重複キーをエラーにする)。そのため、該当するカタログ行を
// 一度 Delete してから同じキーで Insert し直すことで更新を表現する。
func (c *Catalog) UpdateRoot(info *TableInfo, newRoot pager.PageID) error {
	if err := c.tree.Delete(info.ID); err != nil {
		return err
	}
	value, err := encodeCatalogRow(info.Name, newRoot, createTableText(info))
	if err != nil {
		return err
	}
	if err := c.tree.Insert(info.ID, value); err != nil {
		return err
	}
	info.Root = newRoot
	return nil
}

// encodeCatalogRow はカタログ 1 行分(テーブル名, ルートページ, CREATE
// TABLE 文)を EncodeRecord でバイト列にする。カタログ自身もテーブルの
// 木と同じレコード形式を流用する。
func encodeCatalogRow(name string, root pager.PageID, sqlText string) ([]byte, error) {
	return EncodeRecord([]sql.Value{
		{IsText: true, Text: name},
		{Int: int64(root)},
		{IsText: true, Text: sqlText},
	})
}

// decodeCatalogRow はカタログの 1 行を TableInfo に復元する。
//
// スキーマ(列定義)そのものはカタログに構造化して持たず、CREATE TABLE
// 文のテキストとして保存してあり、読み出すたびに sql.Parse で再解析する。
// これは SQLite の sqlite_schema がまさに採っている手口で、スキーマの
// 表現を 1 か所(パーサ)に集約できる利点がある。
func decodeCatalogRow(key uint64, value []byte) (*TableInfo, error) {
	values, err := DecodeRecord(value)
	if err != nil {
		return nil, err
	}
	if len(values) != 3 {
		return nil, fmt.Errorf("カタログの行の列数が不正です: %d", len(values))
	}
	name := values[0].Text
	root := pager.PageID(values[1].Int)
	sqlText := values[2].Text

	stmt, err := sql.Parse(sqlText)
	if err != nil {
		return nil, fmt.Errorf("カタログの CREATE TABLE 文の再解析に失敗しました: %w", err)
	}
	createStmt, ok := stmt.(*sql.CreateTableStmt)
	if !ok {
		return nil, fmt.Errorf("カタログの行が CREATE TABLE 文ではありません: %s", sqlText)
	}

	pkIndex := -1
	for i, col := range createStmt.Columns {
		if col.PrimaryKey {
			pkIndex = i
			break
		}
	}

	return &TableInfo{
		ID:      key,
		Name:    name,
		Root:    root,
		Columns: createStmt.Columns,
		PKIndex: pkIndex,
	}, nil
}

// createTableText は TableInfo から CREATE TABLE 文のテキストを組み立て
// 直す。UpdateRoot はルートページ番号だけを書き換えたいが、カタログの
// 行は (名前, ルート, SQL テキスト) の組でしか保存できないため、更新の
// たびに保存済みの列定義から SQL テキストを再構成する。
func createTableText(info *TableInfo) string {
	var b []byte
	b = append(b, "CREATE TABLE "...)
	b = append(b, info.Name...)
	b = append(b, " ("...)
	for i, col := range info.Columns {
		if i > 0 {
			b = append(b, ", "...)
		}
		b = append(b, col.Name...)
		b = append(b, ' ')
		b = append(b, col.Type.String()...)
		if col.PrimaryKey {
			b = append(b, " PRIMARY KEY"...)
		}
	}
	b = append(b, ')')
	return string(b)
}
```

`TableInfo` はカタログの 1 行を Go の構造体として復元した結果です。`Columns` と `PKIndex` は保存されているわけではなく、`decodeCatalogRow` が CREATE TABLE 文を再パースするたびに**毎回計算し直されます**——`PKIndex` は `createStmt.Columns` を先頭から見て `PrimaryKey` が立っている列を探すだけの単純なループで求まります(1 テーブルにつき PRIMARY KEY は高々 1 つ、という第 9 章 9.5 節の制約のおかげで、最初に見つかった 1 つを採用すれば十分です)。

`OpenCatalog` は `btree.Open` を呼ぶだけで、カタログの木そのものの生成・オープンは第 10 章までの B-Tree と何も変わりません。`nextID` の初期化に `MaxKey` を使っている点だけが新しく、「現在の最大キー + 1」というルールは、11.3 節で見る rowid の自動採番(`OpNewRowid`)とまったく同じ発想です。カタログの木は今のところ行の削除(`DROP TABLE` 相当)を持たないので、`MaxKey` を見るだけで ID の重複を避けられます。

`CreateTable` の骨格は 3 ステップです。同名テーブルがないか `Get` で確認し(`ErrTableNotFound` 以外のエラーはそのまま伝播させ、見つかった場合は `ErrTableExists` にラップして返す、という `errors.Is` を使った丁寧なエラー分岐に注目してください)、`btree.Create` でテーブル用の新しい木を 1 本作り、その (名前, ルート, SQL テキスト) をカタログの木へ `Insert` します。渡された `sqlText` は呼び出し側(11.4 節の `Engine.Execute`)がユーザーの入力そのままを渡してくるので、保存される CREATE TABLE 文は**ユーザーが実際にタイプした文字列そのまま**です。

`UpdateRoot` にはこの節でいちばん注意すべき割り切りがあります。**カタログの木には「値を上書きする」API がありません。** 第 6〜8 章で実装した `BTree.Insert` は重複キーを `ErrDuplicateKey` としてはじく仕様でした(6.4 節)。同じキーの値を書き換えたいだけなのに、そのための専用命令は用意していません。そこで `UpdateRoot` は「一度 `Delete` してから、同じキーで新しい値を `Insert` し直す」という回り道で更新を表現します。**削除して作り直す**という発想は、8.4 節で削除を実装したときの単純さの哲学(再配分やマージをしない)と地続きです——専用の「更新」オペレーションを B-Tree 層に足すより、既存の 2 つのオペレーション(`Delete` と `Insert`)を組み合わせる方が、実装もテストも増やさずに済みます。

ここでもう 1 つ見落としやすい点があります。`UpdateRoot` が書き直す行の SQL テキストは、`info.SQLText`(保存されていた元の文字列)ではなく、`createTableText(info)` で**列定義から再構成**したものです。なぜでしょうか。`TableInfo` はそもそも元の SQL テキストを保持していません(`decodeCatalogRow` が `stmt` から `Columns` と `PKIndex` だけを取り出し、`sqlText` 自体は使い捨てています)。カタログの行は (名前, ルート, SQL テキスト) の 3 つ組でしか保存できない以上、ルートだけを書き換えたくても行全体を書き直す必要があり、そのためには SQL テキストがどこかから調達できなければなりません。`createTableText` は `info.Columns` を `CREATE TABLE t (col TYPE, ...)` という正規化された形に組み立て直すことで、この問題を解決しています。この結果、**最初の `CREATE TABLE` 実行時にユーザーがタイプした表記(空白の入れ方など)は、テーブルへの書き込みで木が一度でも分割・収縮すると失われます**——保存されるのは、常に同じ規則で組み立て直された正規形になります。実害はありませんが、「保存されているテキストは不変ではない」という事実は、この設計の素直な帰結として押さえておいてください。

<div class="sqlite-note">

<span class="note-title">SQLite ではこうなっている: sqlite_schema の 5 列</span> 本物の `sqlite_schema` は `type` / `name` / `tbl_name` / `rootpage` / `sql` の 5 列を持ちます。`type` はそのオブジェクトが `table` か `index` か `view` かを区別する列で、テーブルだけでなく**インデックスやビューも同じ 1 つの表で管理**されます。`tbl_name` はインデックスがどのテーブルに属するかを示す列で、テーブル自身の行では `name` と同じ値になります。minidb のカタログはテーブルしか扱わないので `type` と `tbl_name` を持ちませんが、`name` / `rootpage` / `sql` に対応する 3 列は本物とそっくり同じ役割です。そして本物の SQLite でも、`rootpage` 列は autovacuum(空きページの整理でページが移動する機能)などによって書き換わることがあります——ルートページ番号は固定の定数ではなく、**書き戻しが必要になりうる値**だという性質は、規模の違いこそあれ minidb と同じです。

</div>

## 11.3　構文木を命令列へ — Code Generator

カタログが揃いました。次は、構文木(`sql.Statement`)を命令列(`[]exec.Instr`)へ変換する **Code Generator** です。この変換を担うのが `exec/codegen.go` の `Compile` 関数です。

**exec/codegen.go(全文)**

```go
// codegen.go は構文木(sql.Statement)からバイトコード(Instr の列)を
// 生成するコンパイラを担当する。
package exec

import (
	"fmt"

	"minidb/sql"
)

// カーソル番号は 0 固定とする。この章のコンパイラが生成するプログラムは
// テーブルを 1 つしか開かないので、複数カーソルを使い分ける必要がない。
const cursorNum = 0

// Compile は構文木からバイトコードを生成する。SELECT(WHERE なし)と
// INSERT だけに対応する。WHERE 付き SELECT や UPDATE、DELETE は
// 第 12 章でカーソルの Seek や条件分岐を組み合わせて対応するため、
// ここでは「未対応です」というエラーを返す。
func Compile(stmt sql.Statement, cat *Catalog) ([]Instr, error) {
	switch s := stmt.(type) {
	case *sql.SelectStmt:
		if s.Where != nil {
			return nil, fmt.Errorf("WHERE 付きの SELECT は第 12 章で実装します")
		}
		return compileSelect(s, cat)
	case *sql.InsertStmt:
		return compileInsert(s, cat)
	case *sql.UpdateStmt:
		return nil, fmt.Errorf("UPDATE は第 12 章で実装します")
	case *sql.DeleteStmt:
		return nil, fmt.Errorf("DELETE は第 12 章で実装します")
	case *sql.CreateTableStmt:
		return nil, fmt.Errorf("CREATE TABLE はバイトコードを経由せず Engine が直接実行します")
	default:
		return nil, fmt.Errorf("未対応の文です: %T", stmt)
	}
}

// resolvedColumn は SELECT の列 1 つを、実行時にどう読み出すかへ解決した結果。
// isRowid が true なら OpRowid、そうでなければ OpColumn で recordIndex 番目
// (PK を除いた、レコード内での位置)を読む。
type resolvedColumn struct {
	name        string
	isRowid     bool
	recordIndex int
}

// resolveColumns は SELECT の列指定(* または列名リスト)を、
// テーブルの列定義をもとに resolvedColumn の列へ解決する。
//
// PK 列(INTEGER PRIMARY KEY)は rowid そのものであり、レコードには
// 保存されていない。そのため、レコード内の列番号は「PK 列を除いた
// 位置」に詰めて対応づける必要がある。例えば列が (id PK, name, age) なら
// レコードには (name, age) の 2 列しか入っておらず、name は
// recordIndex=0、age は recordIndex=1 になる。
func resolveColumns(info *TableInfo, star bool, names []string) ([]resolvedColumn, error) {
	// PK を除いた列がレコード内で何番目になるかの対応表を先に作る。
	recordIndex := make([]int, len(info.Columns))
	idx := 0
	for i := range info.Columns {
		if i == info.PKIndex {
			recordIndex[i] = -1
			continue
		}
		recordIndex[i] = idx
		idx++
	}

	resolveOne := func(name string) (resolvedColumn, error) {
		for i, col := range info.Columns {
			if col.Name != name {
				continue
			}
			if i == info.PKIndex {
				return resolvedColumn{name: name, isRowid: true}, nil
			}
			return resolvedColumn{name: name, recordIndex: recordIndex[i]}, nil
		}
		return resolvedColumn{}, fmt.Errorf("列 %s は見つかりません", name)
	}

	if star {
		cols := make([]resolvedColumn, len(info.Columns))
		for i, col := range info.Columns {
			rc, err := resolveOne(col.Name)
			if err != nil {
				return nil, err
			}
			cols[i] = rc
		}
		return cols, nil
	}

	cols := make([]resolvedColumn, len(names))
	for i, name := range names {
		rc, err := resolveOne(name)
		if err != nil {
			return nil, err
		}
		cols[i] = rc
	}
	return cols, nil
}

// compileSelect は WHERE のない SELECT を、
// OpenRead → Rewind → (列の読み出し) → ResultRow → Next のループへ
// コンパイルする。
func compileSelect(stmt *sql.SelectStmt, cat *Catalog) ([]Instr, error) {
	info, err := cat.Get(stmt.Table)
	if err != nil {
		return nil, err
	}
	cols, err := resolveColumns(info, stmt.Star, stmt.Columns)
	if err != nil {
		return nil, err
	}

	// レジスタ 1..len(cols) に各列を読み出す。
	baseReg := 1
	var program []Instr
	program = append(program,
		Instr{Op: OpInit, P2: 1, Comment: "アドレス 1 へジャンプ"},
		Instr{Op: OpOpenRead, P1: cursorNum, P2: int(info.Root), Comment: fmt.Sprintf("%s を開く", info.Name)},
	)

	rewindAddr := len(program)
	program = append(program, Instr{Op: OpRewind, P1: cursorNum, Comment: "先頭へ"})
	loopStart := len(program)

	for i, col := range cols {
		reg := baseReg + i
		if col.isRowid {
			program = append(program, Instr{Op: OpRowid, P1: cursorNum, P2: reg,
				Comment: fmt.Sprintf("%s(rowid)を r[%d] へ", col.name, reg)})
			continue
		}
		program = append(program, Instr{Op: OpColumn, P1: cursorNum, P2: col.recordIndex, P3: reg,
			Comment: fmt.Sprintf("%s を r[%d] へ", col.name, reg)})
	}
	program = append(program, Instr{Op: OpResultRow, P1: baseReg, P2: len(cols), Comment: "1 行を出力"})
	program = append(program, Instr{Op: OpNext, P1: cursorNum, P2: loopStart, Comment: "次の行があれば戻る"})

	haltAddr := len(program)
	program = append(program, Instr{Op: OpHalt, Comment: "終了"})
	program[rewindAddr].P2 = haltAddr

	return program, nil
}

// compileInsert は INSERT を、
//
//   - INTEGER PRIMARY KEY 列があれば、その値をそのまま rowid として使う
//   - なければ OpNewRowid で自動採番する
//
// のどちらかでキーを決め、PK 以外の列を MakeRecord でレコード化して
// OpInsert する形にコンパイルする。列数の一致・型の一致はここ
// (コンパイル時)で検査する。
func compileInsert(stmt *sql.InsertStmt, cat *Catalog) ([]Instr, error) {
	info, err := cat.Get(stmt.Table)
	if err != nil {
		return nil, err
	}
	if len(stmt.Values) != len(info.Columns) {
		return nil, fmt.Errorf("値の数が列数と一致しません: 値 %d 個, 列 %d 個", len(stmt.Values), len(info.Columns))
	}
	for i, col := range info.Columns {
		if err := checkValueType(col, stmt.Values[i]); err != nil {
			return nil, err
		}
	}

	const keyReg = 1
	const recordStartReg = 2

	program := []Instr{
		{Op: OpInit, P2: 1, Comment: "アドレス 1 へジャンプ"},
		{Op: OpOpenWrite, P1: cursorNum, P2: int(info.Root), P4: info.Name, Comment: fmt.Sprintf("%s を書き込み用に開く", info.Name)},
	}

	if info.PKIndex >= 0 {
		v := stmt.Values[info.PKIndex]
		program = append(program, Instr{Op: OpInteger, P1: int(v.Int), P2: keyReg, Comment: "PK の値を rowid として r[1] へ"})
	} else {
		program = append(program, Instr{Op: OpNewRowid, P1: cursorNum, P2: keyReg, Comment: "rowid を自動採番して r[1] へ"})
	}

	reg := recordStartReg
	count := 0
	for i, col := range info.Columns {
		if i == info.PKIndex {
			continue
		}
		v := stmt.Values[i]
		if col.Type == sql.TypeText {
			program = append(program, Instr{Op: OpString, P1: reg, P4: v.Text, Comment: fmt.Sprintf("%s を r[%d] へ", col.Name, reg)})
		} else {
			program = append(program, Instr{Op: OpInteger, P1: int(v.Int), P2: reg, Comment: fmt.Sprintf("%s を r[%d] へ", col.Name, reg)})
		}
		reg++
		count++
	}

	program = append(program,
		Instr{Op: OpMakeRecord, P1: recordStartReg, P2: count, Comment: "PK を除く列をレコード化"},
		Instr{Op: OpInsert, P1: cursorNum, P2: keyReg, Comment: "rowid=r[1] でレコードを挿入"},
		Instr{Op: OpHalt, Comment: "終了"},
	)
	return program, nil
}

// checkValueType は INSERT の値がその列の型と一致するかをコンパイル時に検査する。
func checkValueType(col sql.ColumnDef, v sql.Value) error {
	switch col.Type {
	case sql.TypeInteger:
		if v.IsText {
			return fmt.Errorf("列 %s は INTEGER ですが TEXT の値が指定されました", col.Name)
		}
	case sql.TypeText:
		if !v.IsText {
			return fmt.Errorf("列 %s は TEXT ですが INTEGER の値が指定されました", col.Name)
		}
	default:
		return fmt.Errorf("列 %s の型が不明です", col.Name)
	}
	return nil
}
```

### Compile の入り口 — 何に対応し、何に対応しないか

`Compile` は `sql.Statement` を型スイッチで振り分けるだけの薄い入り口です。9.4 節で見た `Statement` インターフェースの型スイッチが、ここでも同じ形で登場します。`SelectStmt` は(`WHERE` がなければ)`compileSelect` へ、`InsertStmt` は `compileInsert` へ。`WHERE` 付き `SELECT`、`UpdateStmt`、`DeleteStmt` はどれも `"第 12 章で実装します"` という**正直なエラー**を返すだけです。これは手抜きではなく、意図した足場です——カーソルの `Seek` を条件分岐と組み合わせて `WHERE` を実行計画へ落とし込む仕事は、次章でクエリオプティマイザの入り口として丁寧に扱う予定であり、この章で中途半端に対応するより「まだです」と明言する方が誠実です。`CreateTableStmt` も `Compile` には来ません(11.4 節で見るとおり `Engine` がカタログを直接呼び出すため)が、念のためここでもエラーにしています。

### compileSelect — カタログから引いたルートページを OpenRead へ

`compileSelect` の骨格は、`OpenRead → Rewind → (列を読む) → ResultRow → Next` という、第 10 章 10.6 節で手組みした `fullScanProgram` とそっくりの形をしています。決定的に違うのは 1 か所だけです。

```go
Instr{Op: OpOpenRead, P1: cursorNum, P2: int(info.Root), Comment: fmt.Sprintf("%s を開く", info.Name)},
```

`P2` に**カタログから引いたルートページ番号**(`info.Root`)がそのまま入ります。第 1 章 1.2 節で本物の SQLite の `EXPLAIN` を見たとき、`OpenRead 0 2 0 2 0 root=2 iDb=0; users` という行がありました。あの `p2` 列の `2` こそ「カーソル 0 をルートページ 2 の木に開け」という意味で、当時は「いま個々の命令を覚える必要はまったくありません」とやり過ごした値です。あの数字の意味が、いま `cat.Get(stmt.Table)` から得た `info.Root` として、自分のコードの中に実体を持ちました。

### バックパッチ — 先の番地を、後から埋める

```go
rewindAddr := len(program)
program = append(program, Instr{Op: OpRewind, P1: cursorNum, Comment: "先頭へ"})
loopStart := len(program)
// ...(ループ本体を積み上げる)...
haltAddr := len(program)
program = append(program, Instr{Op: OpHalt, Comment: "終了"})
program[rewindAddr].P2 = haltAddr
```

`Rewind` 命令は「木が空なら `Halt` の番地へジャンプする」という `P2` を持ちます(第 10 章 10.4 節)。しかし `Halt` が実際に何番地に来るかは、ループ本体(列の数だけ並ぶ `Column`/`Rowid` 命令)を全部積み終えるまで分かりません。そこでこの関数は、`Rewind` 命令を**とりあえず `P2` を空(ゼロ値)のまま**プログラムに追加しておき(`rewindAddr` にその位置だけ覚えておきます)、プログラム全体を組み終えて `Halt` の番地が確定した瞬間に `program[rewindAddr].P2 = haltAddr` で**後から埋め直します**。これが**バックパッチ(backpatching)**と呼ばれる、コンパイラの古典的な技法です。「前方参照(まだ存在しない位置へのジャンプ)は、その位置が確定してから書き戻す」——アセンブラやリンカが再配置エントリを処理する仕組みと同じ発想が、この 7 行に凝縮されています。

### 列解決と PK — 「id が二重」の解消

`resolveColumns` が担うのは、`SELECT` の列指定(`*` または列名のリスト)を、実行時にどう読み出すかへ変換する作業です。ここで解決しなければならない問題が、第 10 章 10.6 節の最後で予告されていたものです。

> 第 11 章で `INTEGER PRIMARY KEY` を rowid の別名として扱うようになると……`id` 列を実体として二重に保存する必要がなくなり、この重複は解消されます。

第 10 章の `vmdemo` では `id` 列をレコードにもそのまま格納していたため、`rowid`(レジスタ 1)と `id` 列(レジスタ 2)が常に同じ値になる、という無駄がありました。この章ではその無駄をなくします。`INTEGER PRIMARY KEY` が指定された列は、**レコードには保存しません**。値は rowid そのものとして木のキーに格納されており、`SELECT` でその列が要求されたら `OpColumn` ではなく `OpRowid` で読み出せば済むからです。

これを実現するのが `resolveColumns` 冒頭の `recordIndex` テーブルです。列が `(id PK, name, age)` なら、レコードには `name` と `age` の 2 列しか実際には入っていません。`recordIndex` は「PK 列を除いて詰めた位置」を列ごとに事前計算しておく対応表で、`id` は `-1`(使われない)、`name` は `0`、`age` は `1` になります。`resolveOne` は名前で列を探し、それが PK 列なら `isRowid: true` を、そうでなければ `recordIndex[i]` を積んだ `resolvedColumn` を返します。`compileSelect` の本体は、この `isRowid` を見て `OpRowid` と `OpColumn` を出し分けるだけです。

### compileInsert — rowid の 2 つの決め方と、コンパイル時の検査

`compileInsert` はキーの決め方が 2 通りに分かれます。`info.PKIndex >= 0`(PRIMARY KEY 列がある)なら、`INSERT` の値に含まれるその列の値をそのまま `OpInteger` でレジスタ 1(rowid 用)に置きます。PRIMARY KEY がなければ、`OpNewRowid` で「木の現在の最大キー + 1」(空の木なら 1)を自動採番します——11.2 節で見た `BTree.MaxKey` を使う命令です。キーが決まったら、PK を除く列を順にレジスタへ積み(`TEXT` なら `OpString`、`INTEGER` なら `OpInteger`)、`OpMakeRecord` でレコード化し、`OpInsert` で挿入する——という流れです。

`compileInsert` の冒頭にある 2 つの検査、**列数の一致**(`len(stmt.Values) != len(info.Columns)`)と**型の一致**(`checkValueType`)に注目してください。これらはどちらも `VM.Run` が呼ばれる**前**、コンパイルの時点で行われます。もし検査を実行時まで先送りしていたら、`INSERT INTO users VALUES (1, 2, 3)`(`name` に `TEXT` ではなく数値を渡すミス)のような誤りは、`OpString` 命令が実際に実行されるその瞬間まで発覚しません。プログラムが長ければ、その手前で何行分もの副作用(別のテーブルへの書き込みなど、この章にはまだありませんが将来のトランザクション処理を想像してください)がすでに走っているかもしれない。**コンパイラを挟む方式**の利点の 1 つは、まさにこうした静的に分かる誤りを実行開始前に洗い出せることにあります。9.5 節で見た「構文だけで判定できる制約はパーサで」という切り分けの続きとして、「テーブルのスキーマが分かれば判定できる制約はコンパイラで、実データを見なければ分からない制約(重複キーなど)は VM の実行時で」という、もう 1 段の切り分けがここに加わります。

### vm.go の一般化 — 複数の木・複数のカーソル

Code Generator が `OpOpenWrite` や `OpNewRowid` のような新しい命令を出すためには、`exec.VM` 自身も第 10 章から進化する必要があります。第 10 章の `VM` は `tree *btree.BTree` を 1 本だけ抱え、カーソルも `cursor *btree.Cursor` を 1 つだけ持っていました(10.4 節)。この章からは、`CREATE TABLE` で複数のテーブルが作られ、`INSERT` は書き込み用のカーソルを開く必要があります。**VM は木を外から渡されなくなり、複数のカーソルをその場で開けるように**なります。

```go
// cursorState はカーソル 1 つぶんの状態。開いている木、走査位置
// (btree.Cursor)、そして書き込み用カーソルであれば「どのテーブルの
// カーソルか」を保持する。テーブル名は RootMoves がルート移動を報告する
// ときの キーに使う(カタログはテーブル名で行を引き直すため)。
type cursorState struct {
	tree      *btree.BTree
	cursor    *btree.Cursor
	writable  bool
	tableName string
}

// VM はバイトコードのプログラムを実行する仮想マシン。
//
// 第 10 章までは木が 1 本に固定されていたが、この章からカタログと
// 複数のテーブルの木を同時に扱えるよう、カーソルを P1 をキーにした
// map で管理する。木はもう VM の外から渡されず、OpOpenRead/OpOpenWrite
// が P2(ルートページ番号)を使ってその場で btree.OpenAt する。
type VM struct {
	pg      *pager.Pager
	program []Instr
	pc      int
	regs    []sql.Value
	cursors map[int]*cursorState

	// record は OpMakeRecord が作ったレコードのバイト列を保持する
	// 一時領域。本来なら「P3 で指定したレジスタに置く」ところだが、
	// レジスタ(sql.Value)はバイト列を持てる型ではないため、この章では
	// レジスタとは別にこの 1 本のフィールドに置き、直後の OpInsert が
	// そこから読む方式に簡略化する(OpMakeRecord の P3 は未使用)。
	// 複数のレコードを同時に組み立てて使い回すような高度なプログラムは
	// この章のコンパイラは生成しないので、この割り切りで十分足りる。
	record []byte

	// rootMoves は OpInsert によって木のルートが変わったテーブルの
	// 名前から新しいルートページ番号への対応。OpOpenWrite の P4 で
	// 覚えたテーブル名をキーにする。Engine は Run の後にこれを読んで
	// カタログの記録を更新する。
	rootMoves map[string]pager.PageID
}
```

`VM` は木そのものではなく `pg *pager.Pager` を持つように変わりました。`cursors map[int]*cursorState` が第 10 章の `cursor *btree.Cursor` 1 本を置き換えます——キーはカーソル番号(命令の `P1`)なので、`OpOpenRead`/`OpOpenWrite` が複数回呼ばれれば複数のカーソルが同時に開けます(この章のコンパイラは 1 本しか開きませんが、VM 自体の能力としては複数カーソルに対応しました)。`record` と `rootMoves` は新顔のフィールドで、それぞれ `record` フィールドの doc コメントと次の段落で説明します。

```go
// NewVM は pg の上で program を実行する VM を作る。
func NewVM(pg *pager.Pager, program []Instr) *VM {
	return &VM{
		pg:        pg,
		program:   program,
		regs:      make([]sql.Value, numRegisters),
		cursors:   make(map[int]*cursorState),
		rootMoves: make(map[string]pager.PageID),
	}
}

// RootMoves は Run の実行中に OpInsert でルートが変わったテーブルの
// 一覧を、テーブル名から新しいルートページ番号への対応として返す。
func (v *VM) RootMoves() map[string]pager.PageID {
	return v.rootMoves
}
```

`NewVM(pg *pager.Pager, program []Instr) *VM` というシグネチャの変化(第 10 章は `NewVM(tree *btree.BTree, program []Instr) *VM` でした)が、この章の VM が「1 本の木の上で動く実行器」から「pager の上で任意の木を開いて動く実行器」へ格上げされたことを最も端的に表しています。

`OpOpenRead` と `OpOpenWrite` は、この格上げの入り口です。

```go
		case OpOpenRead:
			cs, err := v.openCursor(instr.P2, false, "")
			if err != nil {
				return fmt.Errorf("OpenRead: %w", err)
			}
			v.cursors[instr.P1] = cs

		case OpOpenWrite:
			cs, err := v.openCursor(instr.P2, true, instr.P4)
			if err != nil {
				return fmt.Errorf("OpenWrite: %w", err)
			}
			v.cursors[instr.P1] = cs
```

```go
// openCursor はルートページ root の木を開き、その上にカーソルを立てる。
func (v *VM) openCursor(root int, writable bool, tableName string) (*cursorState, error) {
	tree := btree.OpenAt(v.pg, pager.PageID(root))
	c, err := tree.NewCursor()
	if err != nil {
		return nil, err
	}
	return &cursorState{tree: tree, cursor: c, writable: writable, tableName: tableName}, nil
}
```

第 10 章の `OpOpenRead` は「あらかじめ VM に渡されていた唯一の木」に対してカーソルを作るだけの命令でした。この章では `P2`(ルートページ番号)を使って `btree.OpenAt` でその場で木を開きます——11.3 節冒頭で述べた「`P2` にカタログから引いたルートページ番号が入る」という設計が、まさにこの 1 行(`btree.OpenAt(v.pg, pager.PageID(root))`)で受け止められています。`OpOpenWrite` は `OpOpenRead` と対になる書き込み用の版で、`writable: true` を立てるほかに、`P4`(テーブル名)を `cursorState.tableName` として覚えておきます。この名前が何のためにあるかは、`OpInsert` を見れば分かります。

```go
		case OpNewRowid:
			cs, err := v.requireCursor(instr.P1)
			if err != nil {
				return err
			}
			maxKey, ok, err := cs.tree.MaxKey()
			if err != nil {
				return fmt.Errorf("NewRowid: %w", err)
			}
			rowid := uint64(1)
			if ok {
				rowid = maxKey + 1
			}
			if err := v.setReg(instr.P2, sql.Value{Int: int64(rowid)}); err != nil {
				return fmt.Errorf("NewRowid: %w", err)
			}

		case OpMakeRecord:
			values, err := v.readRegs(instr.P1, instr.P2)
			if err != nil {
				return fmt.Errorf("MakeRecord: %w", err)
			}
			data, err := EncodeRecord(values)
			if err != nil {
				return fmt.Errorf("MakeRecord: %w", err)
			}
			v.record = data

		case OpInsert:
			cs, err := v.requireCursor(instr.P1)
			if err != nil {
				return err
			}
			if !cs.writable {
				return fmt.Errorf("Insert: カーソル %d は書き込み用に開かれていません(OpenWrite が必要です)", instr.P1)
			}
			key, err := v.regInt(instr.P2)
			if err != nil {
				return fmt.Errorf("Insert: %w", err)
			}
			beforeRoot := cs.tree.Root()
			if err := cs.tree.Insert(uint64(key), v.record); err != nil {
				return fmt.Errorf("Insert: %w", err)
			}
			if afterRoot := cs.tree.Root(); afterRoot != beforeRoot && cs.tableName != "" {
				v.rootMoves[cs.tableName] = afterRoot
			}
```

`OpNewRowid` は 11.2 節で追加した `BTree.MaxKey` をそのまま使い、「最大キー + 1(木が空なら 1)」をレジスタへ置くだけです。`OpMakeRecord` は `P1` からレジスタを `P2` 個読み出して `EncodeRecord`(第 10 章 10.2 節)へ渡し、結果を `v.record` に置きます。`v.record` は `VM` 構造体の doc コメントで断っているとおり、本来なら「レジスタに置く」べきところを、`sql.Value` がバイト列を保持できる型ではないという事情から**専用の 1 本のフィールドに簡略化**した割り切りです。

`OpInsert` がこの節でいちばん重要な命令です。挿入の前後で `cs.tree.Root()` を比較し(`beforeRoot` と `afterRoot`)、もしルートが変わっていたら(= 挿入によって木が分割された)、`v.rootMoves` に **テーブル名をキーとして**新しいルートを記録します。ここで `cs.tableName` が使われます——`OpOpenWrite` の `P4` にテーブル名を持たせておいたのは、まさにこの瞬間、「どのテーブルのルートが動いたか」をカタログが理解できる形(テーブル名)で報告するためでした。`RootMoves()` はこの `rootMoves` マップをそのまま返す薄いアクセサで、11.4 節の `Engine` が `Run` の直後にこれを読み、カタログへ反映します。

新しい命令の P1〜P4 の意味を、第 10 章 10.4 節の表に追加する形でまとめておきます。

| 命令         | P1           | P2                   | P3       | P4             | 意味                                                                                        |
| ------------ | ------------ | -------------------- | -------- | -------------- | ------------------------------------------------------------------------------------------- |
| `OpenRead`   | カーソル番号 | **ルートページ番号** | —        | —              | カーソル P1 を、ルートページ P2 の木に開く(第 10 章までは木が 1 本だけで P2 は未使用だった) |
| `OpenWrite`  | カーソル番号 | ルートページ番号     | —        | **テーブル名** | `OpenRead` と同じだが書き込み用に開く。P4 はルート移動の報告に使う                          |
| `NewRowid`   | カーソル番号 | 書き込み先レジスタ   | —        | —              | カーソル P1 の木の最大キー + 1(空なら 1)をレジスタ P2 へ                                    |
| `MakeRecord` | 開始レジスタ | 個数                 | (未使用) | —              | レジスタ P1 から P2 個をレコード化し `VM.record` へ置く                                     |
| `Insert`     | カーソル番号 | キーの入ったレジスタ | —        | —              | カーソル P1 の木に、キー=レジスタ P2、値=`VM.record` を挿入する                             |

		t.Fatal(err)
	}

// レジスタ 1=rowid, 2=id, 3=name, 4=age として ResultRow(1,4) で 4 列を出力する。
func fullScanProgram(root pager.PageID) []Instr {
	return []Instr{
		{Op: OpInit, P2: 1, Comment: "アドレス 1 へジャンプ"},
		{Op: OpOpenRead, P1: 0, P2: int(root), Comment: "カーソルをルート root の木に開く"},
		{Op: OpRewind, P1: 0, P2: 9, Comment: "先頭へ。空ならアドレス 9 へ"},

		{Op: OpColumn, P1: 0, P2: 1, P3: 3, Comment: "name 列を r[3] へ"},
		{Op: OpColumn, P1: 0, P2: 2, P3: 4, Comment: "age 列を r[4] へ"},
		{Op: OpResultRow, P1: 1, P2: 4, Comment: "4 列を出力"},
		{Op: OpNext, P1: 0, P2: 3, Comment: "次の行があればアドレス 3 へ"},
		{Op: OpHalt, Comment: "終了"},
	}

## 11.4　全部を束ねる — Engine

パース・カタログ照会・コンパイル・実行・後始末——ここまでバラバラに実装してきた部品を 1 本の流れにまとめるのが `exec.Engine` です。REPL(11.5 節)は、この `Engine` を通してだけデータベースを操作します。

**exec/engine.go(全文)**

```go
// engine.go は SQL 文字列を受け取り、解析・コンパイル・実行までを
// 束ねる Engine を提供する。REPL(cmd/minidb)はこの Engine を通してのみ
// データベースを操作する。
package exec

import (
	"fmt"

	"minidb/pager"
	"minidb/sql"
)

// Result は Execute の実行結果。結果行を持つ文(SELECT)では Columns と
// Rows が埋まり、それ以外(CREATE TABLE / INSERT)では Message が埋まる。
type Result struct {
	Columns []string
	Rows    [][]sql.Value
	Message string
}

// Engine は pg 上のデータベースに対して SQL を実行する。
type Engine struct {
	pg  *pager.Pager
	cat *Catalog
}

// NewEngine は pg 上のカタログを開いて Engine を作る。
func NewEngine(pg *pager.Pager) (*Engine, error) {
	cat, err := OpenCatalog(pg)
	if err != nil {
		return nil, err
	}
	return &Engine{pg: pg, cat: cat}, nil
}

// Execute は SQL 文字列 1 文を解析・実行する。
//
// CREATE TABLE だけは特別扱いで、バイトコードを経由せず Catalog を
// 直接呼び出す。本物の SQLite は CREATE TABLE も内部的にはバイトコード
// (sqlite_schema への INSERT など)で実行するが、minidb では
// スキーマ操作は VM を通さないと割り切り、実装を単純にしている。
func (e *Engine) Execute(input string) (*Result, error) {
	stmt, err := sql.Parse(input)
	if err != nil {
		return nil, err
	}

	if create, ok := stmt.(*sql.CreateTableStmt); ok {
		if err := e.cat.CreateTable(create, input); err != nil {
			return nil, err
		}
		return &Result{Message: fmt.Sprintf("テーブル %s を作成しました", create.Table)}, nil
	}

	program, err := Compile(stmt, e.cat)
	if err != nil {
		return nil, err
	}

	vm := NewVM(e.pg, program)
	var rows [][]sql.Value
	if err := vm.Run(func(row []sql.Value) error {
		rows = append(rows, append([]sql.Value(nil), row...))
		return nil
	}); err != nil {
		return nil, err
	}

	if err := e.applyRootMoves(vm.RootMoves()); err != nil {
		return nil, err
	}

	switch s := stmt.(type) {
	case *sql.InsertStmt:
		return &Result{Message: "1 行を挿入しました"}, nil
	case *sql.SelectStmt:
		info, err := e.cat.Get(s.Table)
		if err != nil {
			return nil, err
		}
		columns := s.Columns
		if s.Star {
			columns = make([]string, len(info.Columns))
			for i, col := range info.Columns {
				columns[i] = col.Name
			}
		}
		return &Result{Columns: columns, Rows: rows}, nil
	default:
		return nil, fmt.Errorf("未対応の文です: %T", stmt)
	}
}

// applyRootMoves は VM の実行中にルートが動いたテーブルをカタログへ反映する。
// テーブルへの書き込みで木が分割・収縮しルートページが変わっても、
// カタログの記録を更新しない限り、次回そのテーブルを開いたときに
// 古いルートを参照してしまう(木の残りの大部分を見失う)ため必須の後始末。
func (e *Engine) applyRootMoves(moves map[string]pager.PageID) error {
	for name, newRoot := range moves {
		info, err := e.cat.Get(name)
		if err != nil {
			return err
		}
		if err := e.cat.UpdateRoot(info, newRoot); err != nil {
			return err
		}
	}
	return nil
}

// ExplainSQL は SQL をコンパイルした命令列の EXPLAIN 表を返す(REPL の .explain 用)。
func (e *Engine) ExplainSQL(input string) (string, error) {
	stmt, err := sql.Parse(input)
	if err != nil {
		return "", err
	}
	if _, ok := stmt.(*sql.CreateTableStmt); ok {
		return "", fmt.Errorf("CREATE TABLE はバイトコードを経由しないため EXPLAIN できません")
	}
	program, err := Compile(stmt, e.cat)
	if err != nil {
		return "", err
	}
	return Explain(program), nil
}

// Tables はカタログに登録された全テーブル名を ID 順に返す(.tables 用)。
func (e *Engine) Tables() ([]string, error) {
	infos, err := e.cat.List()
	if err != nil {
		return nil, err
	}
	names := make([]string, len(infos))
	for i, info := range infos {
		names[i] = info.Name
	}
	return names, nil
}
```

`Execute` の流れを追います。まず `sql.Parse` で構文木を得ます。**`CREATE TABLE` だけはここで特別扱いです。** バイトコードを一切経由せず、`e.cat.CreateTable(create, input)` を直接呼びます。`input`(ユーザーがタイプした文字列そのまま)をそのまま渡している点が、11.2 節で見た「保存される SQL テキストはユーザーの入力そのまま」という設計を支えています。

<div class="sqlite-note">

<span class="note-title">SQLite ではこうなっている: CREATE TABLE もバイトコードで実行される</span> 本物の SQLite は、`CREATE TABLE` も内部的にはバイトコードにコンパイルされ、VDBE 上で `sqlite_schema` への `INSERT` として実行されます(第 1 章 1.2 節の図で見た層構造に、スキーマ操作も例外なく従います)。minidb がここで近道をしているのは、単純さを優先した割り切りです——`CREATE TABLE` を VM 経由にすると、`Catalog.CreateTable` が内部で行っている「新しい木を作る」という操作もバイトコードの命令として表現しなければならず、この章の命令セットがもう 1 段複雑になります。スキーマ操作は VM を通さない、という minidb の設計は、本物の SQLite の一貫性を犠牲にした分かりやすさです。

</div>

`CREATE TABLE` 以外の文は `Compile(stmt, e.cat)` でバイトコードへ変換され、`NewVM(e.pg, program)` で VM を作って実行されます。`vm.Run` のコールバックは結果行を `rows` に集めるだけの単純なものです。**実行が終わった直後、`e.applyRootMoves(vm.RootMoves())` を呼んでいる点を見逃さないでください。** これがこの章の設計全体を締めくくる後始末です。`INSERT` によってテーブルの木が分割されてルートが動いても、`exec.VM` はそのテーブルの木のルートを追跡しているだけで、**カタログの記録そのものを書き換える権限も責任も持っていません**(11.2 節で見たとおり、`updateHeader` は `false` のままです)。`applyRootMoves` が `vm.RootMoves()` の中身(テーブル名 → 新ルート)を 1 つずつ `e.cat.UpdateRoot` へ渡すことで、初めてカタログが最新のルートを覚えます。**この後始末を忘れると、次にそのテーブルを開いたとき、カタログは古いルートを指したままになり、木の大部分(分割によって新しく作られたページ群)を永遠に見失います。** 「ルートが動くたびに、誰かが追いかけて記録し直さなければならない」——11.2 節の設計の核心が、ここで実際に発火する瞬間です。

`Execute` の末尾は文の種類による結果の組み立てです。`InsertStmt` は固定のメッセージを返すだけ、`SelectStmt` は `Columns`(`*` の場合はカタログの列定義から名前を復元)と `Rows` を詰めて返します。`ExplainSQL` は `Compile` までを行い、`Explain`(第 10 章 10.5 節)にそのまま渡すだけの薄いラッパです。`CREATE TABLE` はバイトコードを経由しないため EXPLAIN できない、という制約もここで明示的にエラーにしています。

</div>

## 11.5　REPL — 対話するデータベース

`Engine` を対話的に操作するための REPL(Read-Eval-Print Loop)、`cmd/minidb` を実装します。第 10 章の `cmd/vmdemo`(手組みのバイトコードを 1 回実行するだけのデモ)は、この章でその役目を終え、削除しました。SQL 文字列を実際に受け取って実行する `cmd/minidb` が後を継ぎます。

**cmd/minidb/main.go(全文)**

```go
// cmd/minidb/main.go
// minidb の対話的な REPL(Read-Eval-Print Loop)。
//
// 使い方:
//
//	go run ./cmd/minidb <db ファイル>
//
// 1 行に SQL 文を 1 つ入力するとその場で実行し、結果を表示する。
// ドットで始まる行はメタコマンドとして扱う(.exit / .tables / .explain)。
package main

import (
	"bufio"
	"fmt"
	"io"
	"os"
	"strings"

	"minidb/exec"
	"minidb/pager"
	"minidb/sql"
)

const prompt = "minidb> "

func main() {
	if len(os.Args) != 2 {
		fmt.Fprintln(os.Stderr, "使い方: minidb <db ファイル>")
		os.Exit(1)
	}

	pg, err := pager.Open(os.Args[1])
	if err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}
	defer pg.Close()

	engine, err := exec.NewEngine(pg)
	if err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}

	// 標準入力が端末(対話)かどうかを調べる。パイプやリダイレクトで
	// 実行例を採取するとき、表示を対話セッションと同じ見た目にするため。
	info, statErr := os.Stdin.Stat()
	interactive := statErr == nil && info.Mode()&os.ModeCharDevice != 0

	runREPL(engine, os.Stdin, os.Stdout, interactive)
}

// runREPL は 1 行 1 文の SQL(またはメタコマンド)を読み取って実行する
// メインループ。".exit" を読むか入力が尽きたら戻る。
// interactive が true なら読み取り前にプロンプトを表示し、false
// (パイプ経由)ならプロンプトに続けて読み取った行をエコーする。
func runREPL(engine *exec.Engine, in io.Reader, out io.Writer, interactive bool) {
	scanner := bufio.NewScanner(in)
	for {
		if interactive {
			fmt.Fprint(out, prompt)
		}
		if !scanner.Scan() {
			return
		}

		line := strings.TrimSpace(scanner.Text())
		if !interactive {
			fmt.Fprintln(out, prompt+line)
		}
		switch {
		case line == "":
			continue
		case line == ".exit":
			return
		case strings.HasPrefix(line, "."):
			runMeta(engine, line, out)
		default:
			runStatement(engine, line, out)
		}
	}
}

// runMeta は "." で始まるメタコマンドを実行する。
func runMeta(engine *exec.Engine, line string, out io.Writer) {
	switch {
	case line == ".tables":
		names, err := engine.Tables()
		if err != nil {
			fmt.Fprintf(out, "エラー: %v\n", err)
			return
		}
		for _, name := range names {
			fmt.Fprintln(out, name)
		}

	case strings.HasPrefix(line, ".explain "):
		sqlText := strings.TrimSpace(strings.TrimPrefix(line, ".explain "))
		table, err := engine.ExplainSQL(sqlText)
		if err != nil {
			fmt.Fprintf(out, "エラー: %v\n", err)
			return
		}
		fmt.Fprint(out, table)

	default:
		fmt.Fprintf(out, "エラー: 不明なメタコマンドです: %s\n", line)
	}
}

// runStatement は SQL 文を 1 つ実行し、結果を表示する。
// エラーは "エラー: ..." として表示するだけで、REPL は続行する。
func runStatement(engine *exec.Engine, line string, out io.Writer) {
	res, err := engine.Execute(line)
	if err != nil {
		fmt.Fprintf(out, "エラー: %v\n", err)
		return
	}
	if res.Message != "" {
		fmt.Fprintln(out, res.Message)
		return
	}
	printRows(res, out)
}

// printRows は SELECT の結果を「列名ヘッダ + 区切り線 + 行」の単純な表で
// 表示する。列幅を揃える必要はなく、" | " 区切りで並べるだけでよい。
func printRows(res *exec.Result, out io.Writer) {
	header := strings.Join(res.Columns, " | ")
	fmt.Fprintln(out, header)
	fmt.Fprintln(out, strings.Repeat("-", len([]rune(header))))
	for _, row := range res.Rows {
		fmt.Fprintln(out, strings.Join(formatValues(row), " | "))
	}
}

// formatValues は 1 行分の値を表示用の文字列に変換する。
func formatValues(row []sql.Value) []string {
	cells := make([]string, len(row))
	for i, v := range row {
		if v.IsText {
			cells[i] = v.Text
		} else {
			cells[i] = fmt.Sprintf("%d", v.Int)
		}
	}
	return cells
}
```

`main` は `pager.Open` → `exec.NewEngine` → `runREPL` という 3 手だけです。第 4 章で確立した `defer pg.Close()` の作法(4.3 節)がここでも守られています——ただし、この `Close` がいつ・どのように呼ばれるかが 11.4 節末尾の warn の焦点でした。

`runREPL` の骨格は「プロンプトを出し、1 行読み、メタコマンドか SQL 文かで振り分ける」という単純なループです。目を引くのは `interactive` フラグの使い道です。

```go
info, statErr := os.Stdin.Stat()
interactive := statErr == nil && info.Mode()&os.ModeCharDevice != 0
```

標準入力が**端末(TTY)かどうか**を `os.Stdin.Stat()` の `os.ModeCharDevice` ビットで判定しています。端末に向かって対話的に使っているときは、期待どおり「プロンプトを出してから入力を待つ」動きをします。しかし本や本章の 11.6 節のように、ヒアドキュメントやパイプで一括投入して実行例を採取するときは、標準入力は端末ではありません。この場合 `runREPL` は、プロンプトを先に出す代わりに、**読み取った行をプロンプトに続けてそのままエコーします**(`fmt.Fprintln(out, prompt+line)`)。この一工夫のおかげで、パイプ経由で実行してキャプチャした出力(この章の 11.6 節がまさにそうです)が、**手で打った対話セッションとまったく同じ見た目**になります。実行例の再現性(この章の冒頭で立てた「掲載コードと `code/ch11/` の実ファイルから一字一句コピーする」という約束と同じ精神です)を支える、地味だが効いている仕掛けです。

`runMeta` は `.tables` と `.explain <SQL>` の 2 つのメタコマンドを実装しています。`.tables` は `engine.Tables()` をそのまま列挙するだけ、`.explain` は接頭辞 `".explain "` を取り除いた残りを `engine.ExplainSQL` に渡し、返ってきた表(第 10 章 10.5 節の `Explain` そのもの)をそのまま出力します。`printRows` は列名をヘッダに、`strings.Repeat("-", ...)` で区切り線を引くだけの簡素な表示で、第 10 章 10.5 節の `Explain` のような列幅を揃えるロジックはあえて持たせていません——REPL の出力は「読めれば十分」という割り切りです。

<div class="sqlite-note">

<span class="note-title">SQLite ではこうなっている: ドットコマンドへのオマージュ</span> `.tables` と `.explain` という名前は偶然ではありません。本物の `sqlite3` コマンドラインシェルには、`.tables`(テーブル一覧)、`.schema`(スキーマ表示)、`.explain`(EXPLAIN 出力の列幅整形モードを切り替える)といった「ドットコマンド」が数十種類あります(第 1 章 1.2 節で実際に `sqlite3 sample.db` を起動したときのプロンプトを思い出してください)。minidb の `.tables` と `.explain` は、その中でも本書がこれまで扱ってきた機能に対応するごく一部を、同じ名前・同じ用法で再現したオマージュです。

</div>

**この本の第 1 章で、本物の SQLite に打った文を思い出してください。**

```console
sqlite> CREATE TABLE users(id INTEGER PRIMARY KEY, name TEXT, age INTEGER);
sqlite> INSERT INTO users VALUES (1,'Alice',30),(2,'Bob',25),(3,'Carol',41);
sqlite> EXPLAIN SELECT name FROM users WHERE id = 2;
```

`CREATE TABLE` / `INSERT` / `SELECT` という 3 種類の文——第 1 章の `EXPLAIN` 実験で本物の SQLite に食わせた、まさにその 3 文が、**とうとう自分で書いたデータベースの上で動きました**。minidb はまだ複数行 `VALUES` や `WHERE` を `SELECT` に持ちませんが(次章の宿題です)、`CREATE TABLE` でテーブルを作り、`INSERT` で行を積み、`SELECT` で読み出すという核心の 3 手は、もう自分のコードだけで完結しています。第 9 章の冒頭で「木はまだ SQL を知りません」と書いたところから、ここまで積み上げてきました。感慨を惜しまず味わってよい瞬間です。

`.explain SELECT name FROM users` の出力にも、目を留めるべき一致があります。`1  OpenRead  0  2  0` の `p2` 列——**カーソル 0 を、ルートページ `2` の木に開く**という意味です。第 1 章 1.3 節で見た本物の `EXPLAIN` の出力はこうでした。

```console
1     OpenRead       0     2     0     2              0   root=2 iDb=0; users
```

**`root=2`。番号までぴったり一致しています。** これは偶然ではありません。どちらのデータベースも「スキーマ用の木をまず 1 本作り、その直後に最初のユーザーテーブルの木を作る」という同じ順序でページを割り当てているからです。minidb は**ヘッダ(ページ 0)+ カタログ(ページ 1)+ users(ページ 2)**、本物の SQLite は**`sqlite_schema`(ページ 1)+ users(ページ 2)**——minidb はページ 0 をヘッダ専用に使う分だけ全体が 1 つずれていますが(第 2 章の設計です)、「スキーマの木の次に最初のテーブルの木」という**相対的な位置関係**は完全に同じです。この一致は、11.1 節で回収した「メタデータもまたテーブルであり、テーブルはページに載る」という設計原理が、ページ番号という具体的な数字の上に正確に写し取られていることの証拠です。

もう 1 点。`SELECT * FROM users` の結果には `id` 列がちゃんと出ています(`1 | Alice | 30` の先頭の `1`)。しかし 11.3 節で見たとおり、`id` は `INTEGER PRIMARY KEY` 列なので**レコードには一切保存されていません**。この `1` は `OpRowid` によって、木のキー(rowid)から復元された値です。値がどこにも二重に存在しないまま、正しい列として出力されている——これが `resolveColumns` の `isRowid` フラグの成果です。

続けて、いったん終了して開き直します。

```console
$ go run ./cmd/minidb mini.db
minidb> SELECT * FROM users;

---------------
1 | Alice | 30
2 | Bob | 25
3 | Carol | 41
minidb> .exit
```

`.exit`(内部的には `pg.Close()`、第 4 章の `Flush`)を経て一度プロセスを終えても、`mini.db` を開き直せば同じ 3 行が読めます。カタログの木がヘッダのルートから、`users` の木がカタログの行から、それぞれ正しくたどり直せている——これも `applyRootMoves` の仕事の裏付けです(今回は 3 行だけなので分割は起きていませんが、11.4 節の `TestEngineManyInsertsTracksRootAcrossReopen` が、分割が起きるケースまで含めてこの仕組みを検証済みです)。

最後に、ヘッダを直接覗きます。

```console
$ xxd -l 32 mini.db
00000000: 6d69 6e69 6462 3031 0000 1000 0000 0003  minidb01........
00000010: 0000 0001 0000 0000 0000 0000 0000 0000  ................
```

第 2 章で設計したヘッダのレイアウトどおりに読み解きます。マジック文字列 `minidb01`(オフセット 0〜7)、ページサイズ `0x1000` = 4096 バイト(オフセット 8〜9)、そして**総ページ数がオフセット 12〜15 に `3`**(`0000 0003`)。ヘッダページ自身(ページ 0)、カタログの木(ページ 1)、`users` の木(ページ 2)——ちょうど 3 ページです。そして**オフセット 16〜19 の `0000 0001`**、これがルートページ番号です。ここが指しているのはもう `users` ではなく、**カタログの木(ページ 1)**です。第 2 章で「ファイルフォーマットとは未来の自分との契約書」だと述べたあのヘッダは、いまや単独のテーブルを指す 1 段構えの契約書ではなく、**ヘッダ → カタログ → テーブル**という 2 段構えのメタデータ構造の起点になりました。図 11-1 で描いた設計が、そのままバイト列として刻まれているのが確認できます。

<div class="warn">

<span class="note-title">再確認: この REPL を強制終了すると挿入は消える</span> 11.4 節の warn で述べたとおり、今の minidb は `.exit`(`pg.Close()` による `Flush`)まで、`INSERT` した内容はディスクに書かれていません。もし上の実行例の途中、`INSERT INTO users VALUES (3, 'Carol', 41);` の直後に `Ctrl-C` でこの REPL プロセスを強制終了していたら、`mini.db` にはヘッダとカタログしか残らず、`users` の 3 行はすべて失われていたはずです。**「安全にする」——1 文ごとにクラッシュ耐性を持たせる仕組みは、第 4 部の主題そのものです。**

</div>

## 11.7　まとめ

- カタログ(`exec/catalog.go`)は、`sqlite_schema` と同じ手口——スキーマを CREATE TABLE 文のテキストとして保存し、読むたびに第 9 章のパーサで再解析する——で実装した。ヘッダのルートはもうテーブルを直接指さず、カタログの木を指す
- `btree.BTree` は `updateHeader` フラグで一般化され、「ヘッダに書き戻すカタログの木」と「カタログが個別にルートを追跡するテーブルの木」を切り分けた。`OpenAt` / `Create` / `Root` / `MaxKey` が新しい入り口とアクセサになった
- Code Generator(`exec/codegen.go` の `Compile`)が、第 9 章の構文木を第 10 章のバイトコードへ変換する最後の 1 枚をつないだ。バックパッチ、PK 列の rowid 別名化(`resolveColumns`)、コンパイル時の型・列数検査が、この節の骨格
- `exec.VM` は複数の木・複数のカーソルを同時に扱えるよう一般化され(`cursorState`)、`OpOpenWrite` / `OpNewRowid` / `OpMakeRecord` / `OpInsert` という書き込み系の命令一式と、ルート移動をテーブル名で報告する `RootMoves` を獲得した
- `exec.Engine` が全体を束ね、実行後の `applyRootMoves` によってカタログを最新のルートへ書き戻す——この後始末を怠ると木の大部分を見失うという、この章でいちばん壊れやすい繋ぎ目
- 今の minidb は `Close` までデータが永続化されない。「1 文ごとに安全に書く」仕組みは第 4 部の主題として持ち越される

`SELECT` は今のところ全件スキャンしかできません。`WHERE id = 2` のような条件は `Compile` に投げると「第 12 章で実装します」というエラーが返ってきます。次章では、この `WHERE` を実行計画へ翻訳し、`SeekRowid`(第 10 章で用意しておいた命令です)を使って主キー検索を全件スキャンではなく一発の `Seek` に最適化します——クエリオプティマイザの入り口です。あわせて `UPDATE` と `DELETE` も実装し、第 3 部の実装範囲(9.2 節)を完成させます。
