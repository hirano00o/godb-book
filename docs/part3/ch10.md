## 10.1　構文木から実行へ — 2 つの方式

第 9 章で、SQL 文字列は `Parse` を通じて `SelectStmt` という構文木になりました。`&SelectStmt{Table: "users", Columns: []string{"name"}, Where: &WhereClause{Column: "id", Op: OpEq, Value: Value{Int: 2}}}` — これは正しい構造体ですが、これだけではまだ 1 行のデータも取り出せません。「木を実行する」とは具体的にどういうことか、ここから考えていきます。

実行エンジンの実装方式には、大きく分けて 2 つの流儀があります。

**方式 1: tree-walking。** 構文木を根から再帰的にたどり、ノードを訪れたその場で処理を行う方式です。`SelectStmt` を受け取ったら `WHERE` を評価し、条件に合う行を B-Tree から取り出し、`Columns` に従って列を選び、その場で出力する——関数呼び出しの入れ子がそのまま実行の骨格になります。実装が短く、多くの言語のインタプリタがまず最初に採用する方式でもあります。

**方式 2: バイトコード VM。** 構文木をいったん**命令列(バイトコード)**へコンパイルし、単純なループでその命令列を実行する方式です。「構文木を解釈する」処理と「命令列を実行する」処理が分離され、コンパイルは 1 回、実行はループで何度でも、という 2 段構えになります。

第 1 章 1.2 節で、この分岐に触れていました。

> 実装方式には、構文木を再帰的にたどる tree-walking 方式と、いったんバイトコードに落として仮想マシンで実行する VM 方式があります。SQLite は後者で、この選択は第 3 部で minidb の設計を決めるときに改めて検討します。

第 3 部(第 9〜12 章)もこの章で折り返しです。ここでその検討を実際に行います。SQLite(と minidb)が VM を選ぶ理由は、大きく 3 つあります。

**(a) コンパイル 1 回、実行は何度でも。** 第 9 章 図 9-1(第 1 章 図 1-2 の再掲)を思い出してください。Code Generator から VDBE へ向かう矢印には「バイトコード(プリペアドステートメント)」という注記がついていました。SQL 文字列の構文解析は、スペースの数や大文字小文字の表記ゆれまで含めて毎回やり直すコストのかかる処理です。しかしいったんバイトコードにコンパイルしてしまえば、`WHERE id = ?` のように条件の値だけを差し替えて同じ構造のクエリを何度も実行するとき、コンパイル結果そのものを使い回せます。**プリペアドステートメント**という言葉の正体は、この「コンパイル済みの命令列」です。

**(b) 実行計画が命令列という目に見える形になる。** tree-walking の実行過程は、関数呼び出しの入れ子の中に埋もれています。「今どこを実行しているか」を覗くには、デバッガでコールスタックを追うしかありません。バイトコードは違います。命令列は最初から最後まで 1 本の配列であり、`EXPLAIN` で丸ごと表示できます。第 1 章で SQLite の `EXPLAIN` を見たときの、あの `addr / opcode / p1 p2 p3 p4 / comment` という表がまさにこれです。

**(c) 実行ループが単純になる。** VM の本体は「命令を 1 つ読み、その命令に応じて分岐し、次の命令へ進む」という単純なループだけです。どの命令で何が起きるかが 1 箇所(この後実装する `Run` メソッド)に集約され、実行時の挙動を追跡・デバッグしやすくなります。

minidb もこの 3 つの理由から VM を選びます。ただし本章では、**パーサとはまだ接続しません**。構文木からバイトコードを生成する Code Generator は第 11 章の仕事です。この章でやるのは、命令列を**手で組んで**バイトコード VM そのものの設計を固めることです。料理に例えるなら、レシピ(構文木)から材料の手順書(命令列)を自動で書き起こす前に、まず手順書という書式そのものと、それを読んで実際に手を動かす人(VM)を用意する、という順番です。

この章で作る部品は 4 つです。

- **レコード形式**(10.2 節) — Alice の手作りバイト列を、列の型を持つ本物のレコードに置き換える
- **カーソル**(10.3 節) — VM のループが必要とする「一時停止できる走査」を B-Tree の上に実装する
- **VM**(10.4 節) — 命令セットを設計し、命令列を実行するループを実装する
- **EXPLAIN**(10.5 節) — 命令列を人間が読める表として表示する

## 10.2　レコード形式 — Alice を本物のレコードにする

第 9 章の冒頭で、こう書きました。

> 今の Alice のレコードは、まだ `[]byte("Alice,30")` という手作りのバイト列にすぎません。列の型も、カラム名も、`WHERE` も知りません。

第 2 部を通じて、B-Tree に格納してきた値は常にこの手作りの文字列でした。カンマで区切っただけのバイト列は、それ自体としては「どこまでが 1 列目か」も「この列が整数か文字列か」も一切知りません。呼び出し側が `strings.Split` するときの申し合わせに頼っているだけです。第 2 章でヘッダページのレイアウトを固めたとき、こう述べました。

> *ファイルフォーマットとは未来の自分との契約書*であり、読み方を決めるパラメータはファイル自身に刻んでおく

この言葉の SQL 版が必要です。列の数、列ごとの型、値の境界——これらをバイト列自身に刻み込む**レコード形式**を設計します。担当するのは新しいパッケージ `exec` です。実行エンジンの部品(レコード・カーソル・VM・EXPLAIN)は、この章からすべて `exec` パッケージに集約していきます。

**exec/record.go(全文)**

```go
// Package exec は minidb の実行エンジン(レコード形式・バイトコード VM)を担当する。
package exec

import (
	"encoding/binary"
	"fmt"

	"minidb/sql"
)

// レコードの型タグ。0 は NULL 用に予約してあるが、この章ではまだ使わない。
const (
	tagInteger = 1
	tagText    = 2
)

// EncodeRecord は値の並びを B-Tree のセルに格納するバイト列へ変換する。
//
// レイアウト:
//
//	オフセット 0-1 : 列数(ビッグエンディアン uint16)
//	続く 1 バイトずつ: 列ごとの型タグ(1=INTEGER, 2=TEXT)
//	続くバイト列    : 値本体。INTEGER は int64 を uint64 として 8 バイト
//	                  ビッグエンディアン、TEXT は長さ(uint16 BE)+ バイト列。
//
// TEXT の長さが uint16 に収まらない(65535 バイト超)場合はエラーを返す。
func EncodeRecord(values []sql.Value) ([]byte, error) {
	buf := make([]byte, 2, 2+len(values))
	binary.BigEndian.PutUint16(buf, uint16(len(values)))

	for _, v := range values {
		if v.IsText {
			buf = append(buf, tagText)
		} else {
			buf = append(buf, tagInteger)
		}
	}

	for _, v := range values {
		if v.IsText {
			if len(v.Text) > 0xffff {
				return nil, fmt.Errorf("TEXT が長すぎます: %d バイト(上限 65535)", len(v.Text))
			}
			lenBuf := make([]byte, 2)
			binary.BigEndian.PutUint16(lenBuf, uint16(len(v.Text)))
			buf = append(buf, lenBuf...)
			buf = append(buf, v.Text...)
		} else {
			intBuf := make([]byte, 8)
			binary.BigEndian.PutUint64(intBuf, uint64(v.Int))
			buf = append(buf, intBuf...)
		}
	}
	return buf, nil
}

// DecodeRecord は EncodeRecord が生成したバイト列を値の並びに戻す。
// 途中で切れているなど不正な形式の場合はエラーを返す。
func DecodeRecord(data []byte) ([]sql.Value, error) {
	if len(data) < 2 {
		return nil, fmt.Errorf("レコードが短すぎます: %d バイト(列数ヘッダに 2 バイト必要)", len(data))
	}
	n := int(binary.BigEndian.Uint16(data[0:2]))

	tagsEnd := 2 + n
	if len(data) < tagsEnd {
		return nil, fmt.Errorf("型タグが途中で切れています: 列数=%d, 残り %d バイト", n, len(data)-2)
	}
	tags := data[2:tagsEnd]

	values := make([]sql.Value, n)
	pos := tagsEnd
	for i, tag := range tags {
		switch tag {
		case tagInteger:
			if len(data)-pos < 8 {
				return nil, fmt.Errorf("列 %d(INTEGER)の値本体が不足しています: 残り %d バイト", i, len(data)-pos)
			}
			values[i] = sql.Value{Int: int64(binary.BigEndian.Uint64(data[pos : pos+8]))}
			pos += 8
		case tagText:
			if len(data)-pos < 2 {
				return nil, fmt.Errorf("列 %d(TEXT)の長さフィールドが不足しています: 残り %d バイト", i, len(data)-pos)
			}
			textLen := int(binary.BigEndian.Uint16(data[pos : pos+2]))
			pos += 2
			if len(data)-pos < textLen {
				return nil, fmt.Errorf("列 %d(TEXT)の値本体が不足しています: 必要 %d バイト, 残り %d バイト", i, textLen, len(data)-pos)
			}
			values[i] = sql.Value{IsText: true, Text: string(data[pos : pos+textLen])}
			pos += textLen
		default:
			return nil, fmt.Errorf("列 %d: 未知の型タグ 0x%02x", i, tag)
		}
	}
	return values, nil
}
```

package doc コメント「minidb の実行エンジン(レコード形式・バイトコード VM)を担当する」が、`exec` パッケージそのものの初登場です。このパッケージは `minidb/sql` に依存します(`sql.Value` を読み書きするため)が、`minidb/pager` には依存しません——レコードのエンコード・デコードは、ページの存在を意識しない純粋なバイト列変換だからです。

レイアウトは `EncodeRecord` の doc コメントに書いたとおり、3 つのパートに分かれます。

1. **列数**(オフセット 0-1、`uint16` ビッグエンディアン)
2. **型タグ列**(列数ぶんの 1 バイトずつ) — 各列が `INTEGER`(`tagInteger = 1`)か `TEXT`(`tagText = 2`)かを示す
3. **値本体** — `INTEGER` は `int64` を `uint64` として 8 バイト固定長、`TEXT` は長さ(`uint16` BE)+ バイト列という可変長

`EncodeRecord` は 3 つのパートをこの順で `buf` に積み上げるだけの素直な実装です。型タグをすべて書き終えてから値本体をまとめて書く、という 2 パス構成になっている点に注目してください。型タグと値本体を交互に書く(列ごとに「タグ 1 バイト + 値」を繰り返す)実装も考えられますが、`EncodeRecord` と `DecodeRecord` を対称な 2 パスの手順(まず型タグ列をひとまとめに、続けて値本体を順に)に揃えておいた方が、双方の実装をシンプルに保てます。先回りして言っておくと、10.4 節で見る `Column` 命令はこの構成を利用して部分デコードするような凝ったことはせず、行全体をそのつど律儀にフルデコードします——2 パス構成は `Column` を高速化するための工夫ではなく、あくまで `EncodeRecord` / `DecodeRecord` 自身の実装を読みやすく保つための選択です。

コメントの 1 行、「型タグ 0 は NULL 用に予約してあるが、この章ではまだ使わない」を見過ごさないでください。9.2 節で確定させた minidb の SQL サブセットに `NULL` リテラルはありません。だから `tagInteger = 1` から始まっていて構わないはずですが、あえて 0 を空けています。第 2 章でヘッダページのレイアウトを解説したとき、残り領域を「予約(ゼロ)」と表記していたのと同じ流儀です。**使われていない値をわざと予約しておく**ことで、将来 `NULL` を導入するときにレコード形式そのもの(列数・型タグ・値本体という骨格)を変えずに済みます。今は空席を 1 つ用意しておくだけの、安いコストの先行投資です。

`DecodeRecord` は `EncodeRecord` の逆変換ですが、単なる逆再生ではありません。**バイト列の長さを一度も信用しない**という一貫した姿勢で書かれています。列数を読んだ直後に「型タグ列を格納するだけの長さがあるか」を確認し、各値を読む直前にも「この型に必要なバイト数が残っているか」を確認してからでないと `data` を読みに行きません。ディスクから読んだページの中身は、プログラムのバグやディスク破損によって不正な形式になっている可能性が常にあります。範囲チェックを怠って `data[pos:pos+8]` のようなスライス操作をいきなり行えば、不正な入力は例外(panic)としてプログラムを落とします。1 つ 1 つの `if len(data)-pos < n` は地味ですが、「壊れた入力はエラー値として返す、決して panic させない」という約束を守るための、必要不可欠な防御線です。

<div class="sqlite-note">

<span class="note-title">SQLite ではこうなっている: varint とシリアル型</span> 本物の SQLite のレコード形式は、minidb よりずっと省スペースです。ヘッダの長さも、列ごとの型と長さの情報(**シリアル型**と呼ばれます)も、すべて **varint**(可変長整数、1〜9 バイト)で表現されます。整数値の列は、値の大きさに応じてシリアル型ごと 1〜8 バイトへ縮みます(`0` は 0 バイト、`1` は 1 バイト整数、……というように)。テキスト列は「シリアル型の値そのもの」から長さを逆算できるようエンコードされており、minidb のように「型タグ 1 バイト+長さ 2 バイト」を毎回律儀に書くようなことはしません。第 3 章でページヘッダの構造まで解剖しましたが、セル本体の中身まではあえて踏み込みませんでした。ここがその中身です。minidb の「固定長タグ+固定長整数」という設計は、この省スペースな仕組みを可変長のまま実装せず、固定長の 2 段階(型タグ列 → 値本体)にほどいた、いわば素直な展開版です。バイト数の節約より、`EncodeRecord` / `DecodeRecord` の実装と読解のしやすさを優先しています。

</div>

**exec/record_test.go(全文)**

```go
package exec

import (
	"reflect"
	"strings"
	"testing"

	"minidb/sql"
)

// EncodeRecord で作ったバイト列を DecodeRecord に戻すと元の値の並びに一致することを確認する。
func TestEncodeDecodeRecordRoundTrip(t *testing.T) {
	tests := []struct {
		name   string
		values []sql.Value
	}{
		{
			name:   "INTEGER のみ",
			values: []sql.Value{{Int: 1}, {Int: 2}, {Int: 3}},
		},
		{
			name:   "TEXT のみ",
			values: []sql.Value{{IsText: true, Text: "Alice"}, {IsText: true, Text: "Bob"}},
		},
		{
			name:   "INTEGER と TEXT の混在",
			values: []sql.Value{{Int: 1}, {IsText: true, Text: "Alice"}, {Int: 30}},
		},
		{
			name:   "負の整数",
			values: []sql.Value{{Int: -1}, {Int: -9223372036854775808}},
		},
		{
			name:   "空文字列",
			values: []sql.Value{{IsText: true, Text: ""}},
		},
		{
			name:   "列数 0",
			values: []sql.Value{},
		},
	}

	for _, tc := range tests {
		t.Run(tc.name, func(t *testing.T) {
			data, err := EncodeRecord(tc.values)
			if err != nil {
				t.Fatalf("EncodeRecord failed: %v", err)
			}
			got, err := DecodeRecord(data)
			if err != nil {
				t.Fatalf("DecodeRecord failed: %v", err)
			}
			if len(got) == 0 && len(tc.values) == 0 {
				return
			}
			if !reflect.DeepEqual(got, tc.values) {
				t.Fatalf("DecodeRecord(EncodeRecord(%v)) = %v, want %v", tc.values, got, tc.values)
			}
		})
	}
}

// TEXT が 65535 バイトを超える場合、EncodeRecord はエラーを返す。
func TestEncodeRecordTextTooLarge(t *testing.T) {
	values := []sql.Value{{IsText: true, Text: strings.Repeat("x", 0x10000)}}
	if _, err := EncodeRecord(values); err == nil {
		t.Fatal("EncodeRecord error = nil, want エラー")
	}
}

// 不正な形式のバイト列を渡したとき、DecodeRecord がエラーを返すことを確認する。
func TestDecodeRecordErrors(t *testing.T) {
	tests := []struct {
		name string
		data []byte
	}{
		{
			name: "空入力",
			data: []byte{},
		},
		{
			name: "型タグ途中で切れている",
			// 列数 2 だが型タグは 1 バイトしかない。
			data: []byte{0x00, 0x02, tagInteger},
		},
		{
			name: "INTEGER の値本体が足りない",
			// 列数 1, 型タグ INTEGER だが値本体が 8 バイトに満たない。
			data: []byte{0x00, 0x01, tagInteger, 0x00, 0x00, 0x00},
		},
		{
			name: "TEXT の長さフィールドが足りない",
			data: []byte{0x00, 0x01, tagText, 0x00},
		},
		{
			name: "TEXT の値本体が足りない",
			// 長さ 5 バイトを宣言しているが実際には 2 バイトしかない。
			data: []byte{0x00, 0x01, tagText, 0x00, 0x05, 'a', 'b'},
		},
		{
			name: "未知の型タグ",
			data: []byte{0x00, 0x01, 0x03, 0x00, 0x00, 0x00, 0x00, 0x00, 0x00, 0x00, 0x00},
		},
	}

	for _, tc := range tests {
		t.Run(tc.name, func(t *testing.T) {
			if _, err := DecodeRecord(tc.data); err == nil {
				t.Fatal("DecodeRecord error = nil, want エラー")
			}
		})
	}
}
```

9.6 節で確立したテーブル駆動テストの流儀そのままです。`EncodeRecord` と `DecodeRecord` は「値の並びを渡すと、決まったバイト列(またはその逆)が返る」という純粋関数なので、この形が最も相性がいいことに変わりありません。

`TestEncodeDecodeRecordRoundTrip` はラウンドトリップ(`Decode(Encode(v)) == v`)を確認するテストです。`INTEGER` のみ・`TEXT` のみ・混在・負の整数(`int64` の最小値 `-9223372036854775808` まで)・空文字列・列数 0 という 6 ケースが並びます。負の整数の最小値をわざわざケースに含めているのは、`uint64(v.Int)` というビット列としての変換(`EncodeRecord` の最後のブロック)と `int64(binary.BigEndian.Uint64(...))` という逆変換(`DecodeRecord`)が、符号ビットの境界でも正しく効くことを確かめるためです。`reflect.DeepEqual` で比較しているのは、`sql.Value` が `IsText` / `Int` / `Text` の 3 フィールドを持つ構造体で、フィールドごとの比較を手で書くより素直だからです。

`TestEncodeRecordTextTooLarge` は `EncodeRecord` の唯一のエラー経路 — `TEXT` の長さが `uint16` の上限(65535 バイト)を超える場合 — を確認します。`TestDecodeRecordErrors` は `DecodeRecord` の防御線を 1 つずつ潰していくテストです。空入力、型タグ列が途中で切れている、`INTEGER` の値本体が足りない、`TEXT` の長さフィールドが足りない、`TEXT` の値本体が足りない、そして未知の型タグ(`0x03`)——コード中の 5 つの `if len(data)-pos < n` チェックと未知タグの `default` 節、その 1 つ 1 つに対応するケースが用意されています。

## 10.3　木を一歩ずつ歩く — カーソル

VM のループがどう動くかを、先に少しだけ覗いておきます。10.4 節で実装する `Run` メソッドは、「`Rewind` で先頭へ位置づけ、行があれば `Column` などで処理し、`Next` で次へ進み、行がなくなったら抜ける」という**ジャンプ**によって制御されるループになります。これは while ループというより、アセンブリの `jmp` に近い動きです。

この動きに、第 7 章で実装した `BTree.Scan` はそのままでは使えません。

```go
func (t *BTree) Scan(fn func(key uint64, value []byte) error) error
```

`Scan` はコールバック `fn` を渡すと、木の全件を昇順にひととおり呼び終えるまで戻ってきません。「全部を一気に」しかできない設計です。VM のループは 1 命令ずつ実行され、`Next` が実行されるたびに「次の 1 件」だけを取り出して pc を戻す必要があります。`Scan` の内部に VM の実行ループを埋め込むことはできません——コールバックの外側にいる VM の `Run` ループとは、そもそも制御の主導権が逆だからです。

必要なのは、**一時停止できる走査**です。呼び出し側が「次へ進めて」と言ったときにだけ 1 つ進み、その場で制御を返す。これが**カーソル**です。

**btree/cursor.go(1) — cursorFrame・Cursor・NewCursor・アクセサ群・Next**

```go
package btree

import (
	"sort"

	"minidb/pager"
)

// cursorFrame はカーソルがルートからリーフへ降りる経路上の 1 段を表す。
//
// pageID はページ番号だけを持ち、ページオブジェクト自体は保持しない。
// pager の LRU キャッシュはいつでもページを追い出しうるため、btree.go の
// insertIntoInterior / deleteFromInterior と同じ規約に従い、セルへ
// アクセスするたびに BTree.pg.Get(pageID) で取得し直す。
//
// index はこのページで「どの子へ降りたか」を表す(0..cellCount)。
// 0..cellCount-1 はセル index の子、cellCount は右端の子を表す。
type cursorFrame struct {
	pageID pager.PageID
	index  int
}

// Cursor は B-Tree のリーフセルを昇順に 1 つずつたどる読み取り専用カーソル。
// 内部ノードからリーフへ降りる経路を stack として保持する。
//
// このカーソルは読み取り専用の走査だけを目的とする。カーソルが生きている
// 間に対象の BTree へ Insert / Delete を行うことは想定していない
// (木の構造が変わると stack が指す位置の意味が崩れるため)。
type Cursor struct {
	t     *BTree
	stack []cursorFrame

	valid      bool
	leafPageID pager.PageID
	leafIndex  int
}

// NewCursor は t の先頭(最小キー)に位置づけたカーソルを返す。
// 木が空であれば、返されたカーソルは Valid() が false になる。
func (t *BTree) NewCursor() (*Cursor, error) {
	c := &Cursor{t: t}
	if err := c.descendLeftmost(t.root); err != nil {
		return nil, err
	}
	return c, nil
}

// Valid はカーソルが有効なセルを指しているかを返す(木が空、または末尾を超えたら false)。
func (c *Cursor) Valid() bool {
	return c.valid
}

// Key は現在のセルのキーを返す。Valid() が false のときの戻り値は未定義。
func (c *Cursor) Key() uint64 {
	page, err := c.t.pg.Get(c.leafPageID)
	if err != nil {
		return 0
	}
	return leaf{page: page}.keyAt(c.leafIndex)
}

// Value は現在のセルの値を返す(ページ内部のバイト列のコピー)。
// Valid() が false のときの戻り値は未定義。
func (c *Cursor) Value() []byte {
	page, err := c.t.pg.Get(c.leafPageID)
	if err != nil {
		return nil
	}
	src := leaf{page: page}.valueAt(c.leafIndex)
	value := make([]byte, len(src))
	copy(value, src)
	return value
}

// Next は次のセルへ進む。末尾を超えたら Valid() が false になる。
// 既に Valid() が false のカーソルに対しては何もしない(no-op)。
func (c *Cursor) Next() error {
	if !c.valid {
		return nil
	}

	page, err := c.t.pg.Get(c.leafPageID)
	if err != nil {
		return err
	}
	l := leaf{page: page}
	if c.leafIndex+1 < l.cellCount() {
		c.leafIndex++
		return nil
	}

	// リーフを読み切った: stack を 1 段ずつ遡り、まだ降りていない
	// 次の子を探す。
	return c.advanceFromStack()
}
```

`cursorFrame` のコメントにある設計判断が、このカーソル全体の性格を決めています。**stack にはページ番号(`pageID`)だけを積み、ページオブジェクト自体は持ちません**。第 8 章 8.5 節で導入した LRU キャッシュの規約を思い出してください。「ページはいつでも追い出されうる」——`insertIntoInterior` や `deleteFromInterior` が子への再帰から戻るたびに `t.pg.Get(pageID)` でページを取り直していたのと、まったく同じ理由です。カーソルは(木への書き込みが起きなくても)LRU の追い出し対象そのものであり、`Key()` や `Value()` や `Next()` が呼ばれるたびに `c.t.pg.Get(c.leafPageID)` で改めてページを取得しています。一度取得したポインタを握りしめておく実装は、ここでは選ばれていません。

`Cursor` 構造体は、経路(`stack`)と現在位置(`leafPageID` / `leafIndex`)を分けて持ちます。`stack` はルートからリーフの**手前**までの内部ノードの経路だけを記録し、リーフそのものの位置は `leafPageID` / `leafIndex` という専用の 2 フィールドで直接持ちます。`NewCursor` は `descendLeftmost(t.root)` を呼ぶだけで、常に最左のリーフ(最小キー)に位置づけられたカーソルを返します。

`Next` の骨格は単純です。今のリーフの中でまだ読んでいないセルがあれば(`c.leafIndex+1 < l.cellCount()`)、`leafIndex` を 1 つ進めるだけで終わります。リーフを読み切っていたら、`advanceFromStack`(10.3 節後半で見ます)に処理を委ねます。この「リーフ内で進める」と「リーフ間をまたいで進める」の 2 段構えが、次に見る図 10-1 の内容そのものです。

**btree/cursor.go(2) — Seek・descendLeftmost・advanceFromStack・ヘルパ**

```go
// Seek はキー key 以上の最小のセルへ位置づける。完全一致検索を行いたい
// 場合は、呼び出し側が Valid() と Key() == key を確認すること。
// key 以上のキーが存在しなければ Valid() が false になる。
func (c *Cursor) Seek(key uint64) error {
	c.stack = c.stack[:0]

	pageID := c.t.root
	for {
		page, err := c.t.pg.Get(pageID)
		if err != nil {
			return err
		}
		if !isInterior(page) {
			l := leaf{page: page}
			idx, _ := l.findSlot(key)
			c.leafPageID = pageID
			c.leafIndex = idx
			if idx < l.cellCount() {
				c.valid = true
				return nil
			}
			// このリーフに key 以上のセルがない。削除によってリーフの
			// 実際の最大キーが親のセパレータより小さくなっている場合に
			// 起こる。key 以上のキーは次のリーフ以降にあるかもしれない
			// ので、stack を使って次のリーフの先頭へ進む
			// (advanceFromStack が valid を適切に設定し直す)。
			return c.advanceFromStack()
		}

		it := interior{page: page}
		idx := seekChildIndex(it, key)
		c.stack = append(c.stack, cursorFrame{pageID: pageID, index: idx})
		pageID = childAtIndex(it, idx)
	}
}

// descendLeftmost はページ pageID を根とする部分木の最左のリーフまで
// 常に子 0 を選んで降り、通過した内部ノードを stack に積む。
// 到達したリーフにセルが 1 つもなければ(空の木)カーソルを無効にする。
func (c *Cursor) descendLeftmost(pageID pager.PageID) error {
	for {
		page, err := c.t.pg.Get(pageID)
		if err != nil {
			return err
		}
		if !isInterior(page) {
			l := leaf{page: page}
			c.leafPageID = pageID
			c.leafIndex = 0
			c.valid = l.cellCount() > 0
			return nil
		}

		c.stack = append(c.stack, cursorFrame{pageID: pageID, index: 0})
		pageID = childAtIndex(interior{page: page}, 0)
	}
}

// advanceFromStack はリーフを読み終えたときに呼ばれる。stack を末尾から
// 遡り、まだ降りていない次の子が見つかったページからその子の最左の
// リーフへ再び降りる。どの段でも次の子が見つからなければ(木全体を
// 読み終えた)stack が空になり、カーソルを無効にする。
func (c *Cursor) advanceFromStack() error {
	for len(c.stack) > 0 {
		top := &c.stack[len(c.stack)-1]
		page, err := c.t.pg.Get(top.pageID)
		if err != nil {
			return err
		}
		it := interior{page: page}

		top.index++
		if top.index > it.cellCount() {
			// このページの子はすべて辿り終えた: 1 段上へ。
			c.stack = c.stack[:len(c.stack)-1]
			continue
		}
		return c.descendLeftmost(childAtIndex(it, top.index))
	}

	c.valid = false
	return nil
}

// seekChildIndex は key 以上の最小のセルの位置を二分探索で返す。
// 該当するセルがなければ cellCount(右端の子を表す)を返す。
// interior.findChild と同じ探索だが、子ページ番号ではなく
// カーソルの stack フレームに積むための位置(インデックス)を返す。
func seekChildIndex(it interior, key uint64) int {
	n := it.cellCount()
	return sort.Search(n, func(i int) bool {
		return it.keyAt(i) >= key
	})
}

// childAtIndex はカーソルのフレームが持つインデックス(0..cellCount)に
// 対応する子ページ番号を返す。index == cellCount は右端の子を表す。
func childAtIndex(it interior, index int) pager.PageID {
	if index == it.cellCount() {
		return it.rightmost()
	}
	return it.childAt(index)
}
```

`descendLeftmost` は「常に子 0 を選んで降りる」だけの単純な関数で、通過した内部ノードを `stack` に積みながらリーフへ達したら `valid` を `l.cellCount() > 0` にセットします。空の木では最初のページ自体がセル数 0 のリーフなので、これだけで「空の木では `Valid()` が最初から false」という挙動が実現できます。

`advanceFromStack` は図 10-1 で見た「1 段上へ戻って次の子へ降り直す」を、木の高さぶん**繰り返す**一般形です。`stack` を末尾(最も深い階層)から遡り、そのページでまだ降りていない子(`top.index++` した結果が `cellCount()` 以下)が見つかればそこへ `descendLeftmost` で降り直します。見つからなければ(そのページの子をすべて読み終えていれば)そのフレームを `stack` から取り除き、さらに 1 段上で同じことを試します。`stack` が空になるまでこれを続けても次の子が見つからなければ、木全体を読み終えたということなので `valid = false` にして終わります。

`Seek` は「キー `key` 以上の最小のセルへ位置づける」操作です。ルートから内部ノードを二分探索(`seekChildIndex`、`interior.findChild` と同じ探索)でたどり、リーフに着いたら `findSlot` で位置を特定する——ここまでは `BTree.Search` と同じ発想です。しかし、ここに**この節でいちばん重要な設計上の落とし穴**があります。

リーフに降りたとき、`idx, _ := l.findSlot(key)` の結果が `idx == l.cellCount()`(「`key` 以上のセルがこのリーフには 1 つもない」)だったら、そこで `Valid()` を false にして終わってよいでしょうか。**だめです。**

理由は第 8 章の削除の仕様にあります。`deleteFromLeaf`(第 8 章 8.4 節)はリーフからキーを取り除きますが、その結果リーフが空にならない限り、**親のセパレータは更新しません**。セパレータは「分割した瞬間の左ページの最大キー」として記録されたきりで、その後リーフから同じキーを削除しても書き換えられないのです。だから「リーフの実際の最大キーが、親に記録されたセパレータより小さい」という状態が起こり得ます——**削除済みキーの亡霊**です。

具体的に言うと、あるリーフの最大キーがちょうどセパレータの値そのものだったとします(分割直後はこれが必ず成り立ちます)。そのキーを `Delete` すると、リーフの実際の最大キーはセパレータより真に小さくなりますが、親のセパレータ自体はそのまま残ります。この状態で `Seek(sep)` を呼ぶと、`findChild` はセパレータの値どおりに「そのリーフ」を選んで降ろします。しかし降りた先のリーフには、もう `sep` 以上のキーは 1 つもありません——`idx == cellCount()` です。ここで即座に無効とみなしてしまうと、`sep` より大きいキー(たとえば `sep+1`)が**次のリーフに実在するのに**、見つからなかったことにしてしまいます。

`Seek` のコードのコメントが、この状況への対処を説明しています。

```go
// このリーフに key 以上のセルがない。削除によってリーフの
// 実際の最大キーが親のセパレータより小さくなっている場合に
// 起こる。key 以上のキーは次のリーフ以降にあるかもしれない
// ので、stack を使って次のリーフの先頭へ進む
// (advanceFromStack が valid を適切に設定し直す)。
return c.advanceFromStack()
```

`idx == l.cellCount()` になったら、そこで諦めず `advanceFromStack` を呼んで**次のリーフの先頭まで進んでから**改めて判定します。次のリーフに `sep` 以上のキーがあれば、そこで `Valid()` が true になって正しく着地します。木全体を読み終えてもなお見つからなければ、そこで初めて `Valid()` が false になります。

このバグはレビューで実際に見つかったものを教材化しています。`btree/cursor_test.go` の `TestCursorSeekAfterDelete` は、まさにこのシナリオ(セパレータと同じキーを削除してから `Seek` する)を再現し、正しく次のリーフへ進めることを確認するテストです。ここから得られる教訓は 1 つです — **不変条件が緩いほど、それを使う側が背負う。** 第 8 章の削除は「セパレータは更新しない」という緩い不変条件をあえて選びました(再配分・マージをしないという単純さとのトレードオフです)。その緩さのツケは、削除そのものではなく、削除された木を**あとから読む側**(この `Seek`)が払うことになります。

最後に、カーソルの前提を確認しておきます。`Cursor` の doc コメントにあるとおり、**カーソルが生きている間に対象の `BTree` へ `Insert` / `Delete` を行うことは想定していません**。`stack` はページ番号とインデックスの組でしかなく、木の構造(セルの位置)が変わればその意味は崩れます。本物の SQLite はここがもっと頑丈で、カーソルの save/restore 機構を持ち、書き込みで木が変化してもカーソルの位置を追跡し直せるようになっています。minidb では、この章で作るカーソルは読み取り専用の走査に用途を絞ります。

```go
func TestCursorHeightThree(t *testing.T) {

// 削除によって「リーフの実際の最大キーが親のセパレータより小さい」状態を
// 作ったとき、Seek がそのリーフで止まらず次のリーフへ進めることを確認する
// (セパレータは削除済みキーの亡霊として残るため)。
func TestCursorSeekAfterDelete(t *testing.T) {
	pg, tree := openTestTree(t)

	const n = 1000
	value := bytes.Repeat([]byte("v"), 8)
	for key := uint64(1); key <= n; key++ {
		if err := tree.Insert(key, value); err != nil {
			t.Fatalf("Insert(%d) failed: %v", key, err)
		}
	}

	// 白箱: ルート(内部ノード)の最初のセルのキー = 最初のリーフの最大キー。
	root, err := pg.RootPage()
	if err != nil {
		t.Fatal(err)
	}
	page, err := pg.Get(root)
	if err != nil {
		t.Fatal(err)
	}
	if !isInterior(page) {
		t.Fatal("前提が崩れています: ルートが内部ノードではありません")
	}
	sep := interior{page: page}.keyAt(0)

	// セパレータと同じキーを削除する。親のセパレータは残ったままになる。
	if err := tree.Delete(sep); err != nil {
		t.Fatalf("Delete(%d) failed: %v", sep, err)
	}

	// sep 以上の最小キーは sep+1 のはず(連番なので)。
	c, err := tree.NewCursor()
	if err != nil {
		t.Fatal(err)
	}
	if err := c.Seek(sep); err != nil {
		t.Fatalf("Seek(%d) failed: %v", sep, err)
	}
	if !c.Valid() {
		t.Fatalf("Seek(%d) 後の Valid() = false, want true(次のリーフへ進むべき)", sep)
	}
	if got := c.Key(); got != sep+1 {
		t.Fatalf("Seek(%d) 後の Key() = %d, want %d", sep, got, sep+1)
	}
}
```

`TestCursorSeek` は `Seek` の 3 パターン(完全一致・存在しないキーが次のキーに着地・全キーより大きいキーで無効になる)を確認し、`TestCursorHeightThree` は高さ 3 に育つ規模(60000 件)でも `Next` で全件を正しくたどれることを白箱検査(`treeHeight` は第 7 章のヘルパをそのまま再利用)で確かめます。そして `TestCursorSeekAfterDelete` が、直前で解説した削除済みキーの亡霊のケースです。

`Op` は 17 種類の命令を持つ列挙型です。コメントの冒頭にあるとおり、これは「SQLite の VDBE のオペコードを、この章で必要な最小限まで削ったもの」です。`String()` メソッドがオペコード名を `"Op"` という接頭辞なし(`"Init"`, `"OpenRead"`, …)で返しているのは、第 1 章で見た本物の `EXPLAIN` の `opcode` 列の見た目(`Init`, `OpenRead`, `SeekRowid`, …)にそのまま合わせるためです。10.6 節で自分の `EXPLAIN` の出力を本物と並べて見比べるとき、この一致が効いてきます。

`Instr` 構造体を見てください。`P1`, `P2`, `P3` という無骨な整数オペランドと、文字列オペランド `P4`。この命名は SQLite の流儀をそのまま踏襲しています。「使わないフィールドはゼロ値のままにする」という約束——たとえば `OpHalt` はどのフィールドも使いませんから `Instr{Op: OpHalt}` で済みますし、`OpInteger` は `P3` を使いません。第 1 章で見た本物の `EXPLAIN` の出力でも、使われない `p1`〜`p4` の列には `0` や空欄がそのまま出ていました。あれと同じ割り切りです。

命令ごとの P1〜P4 の意味を、コード中のコメントから一覧にまとめておきます。

**exec/vm.go(2) — Instr・VM・Run**

```go
// Instr は命令 1 つ。P1〜P3 は整数オペランド、P4 は文字列オペランド。
// 各フィールドの意味は命令ごとに違う(SQLite の P1〜P4 と同じ流儀で、
// 使わないフィールドはゼロ値のままにする)。
type Instr struct {
	Op         Op
	P1, P2, P3 int
	P4         string

	// Comment は EXPLAIN 表示用の注釈。実行には一切影響しない。
	Comment string
}

const (
	// numRegisters は VM が持つレジスタの本数。
	numRegisters = 32
	// maxSteps は無限ループ対策としての実行ステップ数の上限。
	maxSteps = 1_000_000
)

// VM はバイトコードのプログラムを実行する仮想マシン。
// この章では読み取り専用で、対象は 1 本の B-Tree に固定する
// (複数テーブル・複数カーソルへの対応は後の章で扱う)。
type VM struct {
	tree       *btree.BTree
	program    []Instr
	pc         int
	regs       []sql.Value
	cursor     *btree.Cursor
	haveCursor bool
}

// NewVM は tree の上で program を実行する VM を作る。
func NewVM(tree *btree.BTree, program []Instr) *VM {
	return &VM{
		tree:    tree,
		program: program,
		regs:    make([]sql.Value, numRegisters),
	}
}

// Run はプログラムを実行し、OpResultRow のたびに fn を呼ぶ。
// fn がエラーを返したら実行を打ち切りそのエラーを返す。
func (v *VM) Run(fn func(row []sql.Value) error) error {
	v.pc = 0
	steps := 0

	for {
		if v.pc < 0 || v.pc >= len(v.program) {
			return fmt.Errorf("pc がプログラム範囲外です: pc=%d, プログラム長=%d", v.pc, len(v.program))
		}
		steps++
		if steps > maxSteps {
			return fmt.Errorf("実行ステップ数が上限 %d を超えました(無限ループの疑い)", maxSteps)
		}

		instr := v.program[v.pc]
		next := v.pc + 1

		switch instr.Op {
		case OpInit:
			next = instr.P2

		case OpOpenRead:
			c, err := v.tree.NewCursor()
			if err != nil {
				return fmt.Errorf("OpenRead: %w", err)
			}
			v.cursor = c
			v.haveCursor = true

		case OpRewind:
			if err := v.requireCursor(); err != nil {
				return err
			}
			// カーソルを作り直して先頭へ巻き戻す。OpenRead 直後は既に
			// 先頭にいるが、同じプログラム内で 2 周目を回す場合にも
			// 「先頭へ位置づける」という意味論を守るため。
			c, err := v.tree.NewCursor()
			if err != nil {
				return fmt.Errorf("Rewind: %w", err)
			}
			v.cursor = c
			if !v.cursor.Valid() {
				next = instr.P2
			}

		case OpNext:
			if err := v.requireCursor(); err != nil {
				return err
			}
			if err := v.cursor.Next(); err != nil {
				return fmt.Errorf("Next: %w", err)
			}
			if v.cursor.Valid() {
				next = instr.P2
			}

		case OpSeekRowid:
			if err := v.requireCursor(); err != nil {
				return err
			}
			key, err := v.regInt(instr.P3)
			if err != nil {
				return fmt.Errorf("SeekRowid: %w", err)
			}
			if err := v.cursor.Seek(uint64(key)); err != nil {
				return fmt.Errorf("SeekRowid: %w", err)
			}
			if !v.cursor.Valid() || v.cursor.Key() != uint64(key) {
				next = instr.P2
			}

		case OpColumn:
			if err := v.requireValidCursor(); err != nil {
				return err
			}
			values, err := DecodeRecord(v.cursor.Value())
			if err != nil {
				return fmt.Errorf("Column: レコードのデコードに失敗しました: %w", err)
			}
			if instr.P2 < 0 || instr.P2 >= len(values) {
				return fmt.Errorf("Column: 列番号 %d が範囲外です(列数 %d)", instr.P2, len(values))
			}
			if err := v.setReg(instr.P3, values[instr.P2]); err != nil {
				return fmt.Errorf("Column: %w", err)
			}

		case OpRowid:
			if err := v.requireValidCursor(); err != nil {
				return err
			}
			if err := v.setReg(instr.P2, sql.Value{Int: int64(v.cursor.Key())}); err != nil {
				return fmt.Errorf("Rowid: %w", err)
			}

		case OpInteger:
			if err := v.setReg(instr.P2, sql.Value{Int: int64(instr.P1)}); err != nil {
				return fmt.Errorf("Integer: %w", err)
			}

		case OpString:
			if err := v.setReg(instr.P1, sql.Value{IsText: true, Text: instr.P4}); err != nil {
				return fmt.Errorf("String: %w", err)
			}

		case OpResultRow:
			row, err := v.readRegs(instr.P1, instr.P2)
			if err != nil {
				return fmt.Errorf("ResultRow: %w", err)
			}
			if err := fn(row); err != nil {
				return err
			}

		case OpEq, OpNe, OpLt, OpGt, OpLe, OpGe:
			ok, err := v.compare(instr)
			if err != nil {
				return err
			}
			if ok {
				next = instr.P2
			}

		case OpGoto:
			next = instr.P2

		case OpHalt:
			return nil

		default:
			return fmt.Errorf("不正な命令です: pc=%d, op=%v", v.pc, instr.Op)
		}

		v.pc = next
	}
}
```

`VM` 構造体は「対象の木は 1 本」「カーソルは高々 1 つ」という、この章の割り切りをそのまま体現しています。`regs` は 32 本の `sql.Value` のスライスで、VM 全体で共有される作業用のレジスタです。第 9 章で `Value` が `Int` / `Text` / `IsText` の 3 フィールドで整数と文字列を 1 つの型にまとめていたのと同じ発想が、レジスタの型としてもそのまま使われています。

`Run` の骨格は、次のスケルトンに集約されます(`// ...` の部分に各命令の `case` が並びます)。

```go
instr := v.program[v.pc]
next := v.pc + 1
switch instr.Op {
    // ...
}
v.pc = next
```

**デフォルトでは次の命令(`pc+1`)へ進み、ジャンプ系の命令だけが `next` を上書きする。** `OpInit` と `OpGoto` は無条件に `next = instr.P2`。`OpRewind` と `OpNext` と比較命令群、`OpSeekRowid` は「ある条件が成立したときだけ」`next` を書き換えます。条件が成立しなければ `next` はデフォルトの `pc+1` のまま——if 文で「ジャンプするケース」だけを書けば、「ジャンプしないケース」は何も書かなくても自然に処理される、という単純な形にまとまっています。

ループの先頭には `steps` というカウンタと `maxSteps = 1_000_000` という上限があります。これは安全網です。`OpGoto` だけを使えば `{Op: OpGoto, P2: 0}` という 1 行で無限ループが書けてしまいます——バイトコードという表現力の代償として、プログラム自体のバグ(誤ったジャンプ先、終了条件の書き漏らし)がそのまま無限ループになり得ます。`maxSteps` を超えたら実行を打ち切ってエラーを返す、という安全網がなければ、バグの混じった命令列は VM を(そしてそれを呼び出したプロセスを)永遠に止めてしまいます。

`OpRewind` の実装で 1 つ目を引く点があります。カーソルを**作り直している**のです。

```go
c, err := v.tree.NewCursor()
// ...
v.cursor = c
```

`OpOpenRead` の直後、カーソルはすでに `NewCursor` によって先頭に位置づけられています。だから `OpRewind` は一見不要に思えます。しかし「先頭へ位置づける」という `Rewind` の意味論は、**同じプログラムの中で 2 周目のループが回るとき**にも守られなければなりません(この章のプログラムでは 2 周目は出てきませんが、第 11 章以降で `JOIN` に類する処理を書けば、内側のループを外側のループの反復ごとに `Rewind` し直す、という使われ方が出てきます)。既存のカーソルの内部状態を巻き戻す代わりに `NewCursor` で作り直しているのは、「Rewind は必ず先頭に戻す」という約束を、内部状態がどうであれ常に成り立たせるための、いちばん単純な実装です。

`OpColumn` の実装も割り切りが分かりやすい箇所です。

```go
values, err := DecodeRecord(v.cursor.Value())
```

列が 1 つ欲しいだけなのに、**行全体を毎回デコードしています**。本物の SQLite はここでもっと賢く、必要な列までしか部分デコードしなかったり、同じ行に対する複数回の `Column` 呼び出しの結果をキャッシュしたりします。minidb はそこまでの最適化をせず、`DecodeRecord` を毎回律儀に呼ぶ素朴な実装で割り切っています。10.2 節で先回りして触れたとおり、`DecodeRecord` が「型タグ列をまとめて読んでから値本体を走査する」という単純な 2 パス構成のままなのも、この素朴な呼び出し方と釣り合いが取れているからです。

比較命令(`OpEq` 〜 `OpGe`)は「成立したらジャンプする」という形に統一されています。高水準言語の `if 条件 { goto ラベル }` を思い浮かべてください。バイトコードのレベルでは「条件」と「飛び先」がちょうどこの形——**条件式そのものと、それが真だったときの分岐先**——に分解されます。これは何か特別な設計ではなく、CPU の機械語がまさにこの形(`CMP` に続けて `JE` / `JNE` のような条件ジャンプ)をしていることと同じです。バイトコード VM は、ソフトウェアで実装された小さな CPU なのだと考えると、この設計の必然性が見えてきます。

```go
// requireCursor はカーソルが開かれていることを確認する(Valid である必要はない)。
func (v *VM) requireCursor() error {
	if !v.haveCursor {
		return fmt.Errorf("カーソルが開かれていません(OpenRead が必要です)")
	}
	return nil
}

// requireValidCursor はカーソルが開かれ、かつ有効な行を指していることを確認する。
func (v *VM) requireValidCursor() error {
	if err := v.requireCursor(); err != nil {
		return err
	}
	if !v.cursor.Valid() {
		return fmt.Errorf("カーソルが有効な行を指していません")
	}
	return nil
}

// reg はレジスタ番号の範囲を検査してから値を返す。
func (v *VM) reg(n int) (sql.Value, error) {
	if n < 0 || n >= len(v.regs) {
		return sql.Value{}, fmt.Errorf("レジスタ番号 %d が範囲外です(0..%d)", n, len(v.regs)-1)
	}
	return v.regs[n], nil
}

// setReg はレジスタ番号の範囲を検査してから値を書き込む。
func (v *VM) setReg(n int, value sql.Value) error {
	if n < 0 || n >= len(v.regs) {
		return fmt.Errorf("レジスタ番号 %d が範囲外です(0..%d)", n, len(v.regs)-1)
	}
	v.regs[n] = value
	return nil
}

// regInt はレジスタから整数値を取り出す。TEXT が入っていればエラーになる。
func (v *VM) regInt(n int) (int64, error) {
	value, err := v.reg(n)
	if err != nil {
		return 0, err
	}
	if value.IsText {
		return 0, fmt.Errorf("レジスタ %d は TEXT です(INTEGER が必要)", n)
	}
	return value.Int, nil
}

// readRegs はレジスタ start から count 個ぶんの値をコピーして返す。
func (v *VM) readRegs(start, count int) ([]sql.Value, error) {
	row := make([]sql.Value, count)
	for i := 0; i < count; i++ {
		value, err := v.reg(start + i)
		if err != nil {
			return nil, err
		}
		row[i] = value
	}
	return row, nil
}

// compare は比較命令を実行し、「r[P1] op r[P3] が成立したら true」を返す。
// 整数同士・文字列同士の比較だけを許し、型が食い違ったらエラーにする
// (この VM の型検査は素朴なもので割り切る)。
func (v *VM) compare(instr Instr) (bool, error) {
	left, err := v.reg(instr.P1)
	if err != nil {
		return false, fmt.Errorf("%v: %w", instr.Op, err)
	}
	right, err := v.reg(instr.P3)
	if err != nil {
		return false, fmt.Errorf("%v: %w", instr.Op, err)
	}
	if left.IsText != right.IsText {
		return false, fmt.Errorf("%v: 型が一致しません(r[%d]=%s, r[%d]=%s)",
			instr.Op, instr.P1, typeName(left), instr.P3, typeName(right))
	}

	var cmp int
	if left.IsText {
		cmp = compareString(left.Text, right.Text)
	} else {
		cmp = compareInt(left.Int, right.Int)
	}

	switch instr.Op {
	case OpEq:
		return cmp == 0, nil
	case OpNe:
		return cmp != 0, nil
	case OpLt:
		return cmp < 0, nil
	case OpGt:
		return cmp > 0, nil
	case OpLe:
		return cmp <= 0, nil
	case OpGe:
		return cmp >= 0, nil
	default:
		return false, fmt.Errorf("compare: 比較命令ではありません: %v", instr.Op)
	}
}

func typeName(v sql.Value) string {
	if v.IsText {
		return "TEXT"
	}
	return "INTEGER"
}

func compareInt(a, b int64) int {
	switch {
	case a < b:
		return -1
	case a > b:
		return 1
	default:
		return 0
	}
}

func compareString(a, b string) int {
	switch {
	case a < b:
		return -1
	case a > b:
		return 1
	default:
		return 0
	}
}
```

`requireCursor` と `requireValidCursor` は、`Run` 内の各 case で繰り返し現れる前提条件(「カーソルが開かれているか」「カーソルが有効な行を指しているか」)を、意味の異なる 2 つの検査として切り出したものです。`OpColumn` や `OpRowid` は行の中身を読むので `requireValidCursor`(有効な行が必要)を、`OpNext` や `OpSeekRowid` は無効なカーソルに対しても意味のある操作(次へ進む・探し直す)なので `requireCursor`(開かれてさえいればよい)を、それぞれ使い分けています。

`reg` / `setReg` はレジスタ番号の範囲チェックを一本化した薄いラッパです。`v.regs[n]` への直接アクセスをこの 2 関数の外で行わないようにすることで、範囲外アクセスの panic を「エラー値を返す」という一貫した形に変換しています。`regInt` は `SeekRowid` のようにレジスタから整数だけを取り出したい場面のための補助です——`TEXT` が入っていれば、それもエラーとして扱います。

`compare` が比較命令 6 種すべての実処理を担います。まず左右のレジスタを読み、**型が食い違っていたらエラー**にします(`INTEGER` と `TEXT` を `<` で比べる、といった操作は許しません)。型が揃っていれば `compareInt` か `compareString` で 3 値比較(`-1` / `0` / `1`)を行い、その結果を `switch instr.Op` で「等しいか」「小さいか」……という具体的な判定に変換します。3 値比較を 1 か所にまとめておくことで、6 つの比較命令それぞれに大小判定のロジックを重複して書かずに済んでいます。

第 1 章で、本物の SQLite の `EXPLAIN` をこの目で見ました。`addr` / `opcode` / `p1 p2 p3 p4` / `comment` という列が並んだ、あの表です。今や自分の VM にも `Instr` という命令列があります。同じ形で表示してみましょう。

**exec/explain.go(全文)**

```go
package exec

import (
	"fmt"
	"strconv"
	"strings"
)

// Explain はプログラムを人間が読める一覧表として書式化する。
// 第 1 章で見た SQLite の EXPLAIN と同じ、addr / opcode / p1 p2 p3 / p4 / comment の
// 列幅を揃えた等幅の表(ヘッダ行 + 罫線)で返す。
func Explain(program []Instr) string {
	headers := []string{"addr", "opcode", "p1", "p2", "p3", "p4", "comment"}
	rows := make([][]string, len(program))
	for i, instr := range program {
		rows[i] = []string{
			strconv.Itoa(i),
			instr.Op.String(),
			strconv.Itoa(instr.P1),
			strconv.Itoa(instr.P2),
			strconv.Itoa(instr.P3),
			instr.P4,
			instr.Comment,
		}
	}

	widths := make([]int, len(headers))
	for i, h := range headers {
		widths[i] = len([]rune(h))
	}
	for _, row := range rows {
		for i, cell := range row {
			if n := len([]rune(cell)); n > widths[i] {
				widths[i] = n
			}
		}
	}

	var b strings.Builder
	writeRow(&b, headers, widths)
	writeSeparator(&b, widths)
	for _, row := range rows {
		writeRow(&b, row, widths)
	}
	return b.String()
}

// writeRow は 1 行ぶんのセルを、列幅に合わせて左詰めで空白パディングしながら書く。
// 最終列(comment)は末尾の空白パディングを省く。
func writeRow(b *strings.Builder, cells []string, widths []int) {
	for i, cell := range cells {
		if i > 0 {
			b.WriteString("  ")
		}
		if i == len(cells)-1 {
			b.WriteString(cell)
			continue
		}
		fmt.Fprintf(b, "%-*s", widths[i], cell)
	}
	b.WriteByte('\n')
}

// writeSeparator はヘッダ行の下に引く罫線を書く。
func writeSeparator(b *strings.Builder, widths []int) {
	cells := make([]string, len(widths))
	for i, w := range widths {
		cells[i] = strings.Repeat("-", w)
	}
	writeRow(b, cells, widths)
}
```

`Explain` がやっていることは、突き詰めれば「命令列を `[][]string` の表に変換し、列ごとに最大幅を測って、その幅で埋めながら出力する」というだけです。`headers` に `addr`, `opcode`, `p1`, `p2`, `p3`, `p4`, `comment` の 7 列を定義し、各命令を 1 行に変換します。`P1`〜`P3` はゼロ値のときも `"0"` という文字列としてそのまま表示され、`P4` と `Comment` は空文字列なら空欄になります——ここでも「使わないフィールドはゼロ値のまま出す」という 10.4 節の約束が、表示にそのまま表れています。

列幅計算は 2 段階です。まずヘッダの文字数(`len([]rune(h))`、マルチバイト文字を考慮してルーン単位で数えます)を初期値にし、続けて全行を走査してそれより長いセルがあれば幅を広げます。`writeRow` はこの幅に合わせて `%-*s` で左詰めパディングしますが、**最終列(`comment`)だけは末尾のパディングを省きます**。理由は単純で、コメントのあとに意味のない空白を大量に並べても読みにくいだけだからです。

`Comment` フィールドについて、最後に 1 点だけ強調しておきます。**この文字列は実行に一切影響しません。** `VM.Run` のどこにも `instr.Comment` を読む処理はなく、`Explain` の表示にしか使われません。10.4 節で組み立てるプログラムの `Comment` は、コード自身のための注釈であると同時に、`EXPLAIN` の読者(つまり私たち)のための注釈でもあります。この二重の役割は、本物の SQLite の `EXPLAIN` の `comment` 列とまったく同じ性質です。

## 10.6　動かして確かめる — 手組みのバイトコードで SELECT

レコード形式・カーソル・VM・EXPLAIN の 4 部品が揃いました。これらを使って、`SELECT` 相当の処理を手組みのバイトコードで実際に動かします。

**cmd/vmdemo/main.go(全文)**

```go
// cmd/vmdemo/main.go
// exec パッケージのバイトコード VM の動作確認デモ。
//
// mini.db を開いて(木が空なら)users 相当のレコードを 3 件挿入したうえで、
// 手で組んだ 2 種類のプログラム
//
//   - SELECT name FROM users WHERE id = 2
//   - SELECT * FROM users(全件スキャン)
//
// をそれぞれ EXPLAIN で表示してから実行し、結果行を表示する。
package main

import (
	"fmt"
	"os"

	"minidb/btree"
	"minidb/exec"
	"minidb/pager"
	"minidb/sql"
)

func main() {
	pg, err := pager.Open("mini.db")
	if err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}
	defer pg.Close()

	tree, err := btree.Open(pg)
	if err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}

	if err := seedUsers(tree); err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}

	fmt.Println("=== SELECT name FROM users WHERE id = 2 ===")
	pointLookup := pointLookupProgram()
	fmt.Println(exec.Explain(pointLookup))
	if err := runAndPrint(tree, pointLookup); err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}

	fmt.Println()
	fmt.Println("=== SELECT * FROM users ===")
	fullScan := fullScanProgram()
	fmt.Println(exec.Explain(fullScan))
	if err := runAndPrint(tree, fullScan); err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}
}

// seedUsers は木が空であれば、キー 1,2,3 に users 相当のレコード
// (id, name, age)を挿入する。id 列には rowid と同じ値を格納する。
func seedUsers(tree *btree.BTree) error {
	c, err := tree.NewCursor()
	if err != nil {
		return err
	}
	if c.Valid() {
		// 既にデータがある(2 回目以降の実行): 何もしない。
		return nil
	}

	rows := []struct {
		id   int64
		name string
		age  int64
	}{
		{1, "Alice", 30},
		{2, "Bob", 25},
		{3, "Carol", 41},
	}
	for _, r := range rows {
		data, err := exec.EncodeRecord([]sql.Value{{Int: r.id}, {IsText: true, Text: r.name}, {Int: r.age}})
		if err != nil {
			return err
		}
		if err := tree.Insert(uint64(r.id), data); err != nil {
			return err
		}
	}
	return nil
}

// pointLookupProgram は「SELECT name FROM users WHERE id = 2」相当の
// プログラムを組み立てる。カーソル P1=0、レジスタ r[1]=検索キー、r[2]=結果の name。
func pointLookupProgram() []exec.Instr {
	return []exec.Instr{
		{Op: exec.OpInit, P2: 1, Comment: "アドレス 1 へジャンプ"},
		{Op: exec.OpOpenRead, P1: 0, Comment: "カーソルを開く"},
		{Op: exec.OpInteger, P1: 2, P2: 1, Comment: "r[1]=2"},
		{Op: exec.OpSeekRowid, P1: 0, P2: 6, P3: 1, Comment: "r[1] で Seek。一致しなければアドレス 6 へ"},
		{Op: exec.OpColumn, P1: 0, P2: 1, P3: 2, Comment: "name 列を r[2] へ"},
		{Op: exec.OpResultRow, P1: 2, P2: 1, Comment: "r[2] を 1 列の結果として出力"},
		{Op: exec.OpHalt, Comment: "終了"},
	}
}

// fullScanProgram は「SELECT * FROM users」相当の全件スキャンプログラムを組み立てる。
// カーソル P1=0、レジスタ r[1]=rowid, r[2]=id, r[3]=name, r[4]=age。
func fullScanProgram() []exec.Instr {
	return []exec.Instr{
		{Op: exec.OpInit, P2: 1, Comment: "アドレス 1 へジャンプ"},
		{Op: exec.OpOpenRead, P1: 0, Comment: "カーソルを開く"},
		{Op: exec.OpRewind, P1: 0, P2: 9, Comment: "先頭へ。木が空ならアドレス 9 へ"},
		{Op: exec.OpRowid, P1: 0, P2: 1, Comment: "rowid を r[1] へ"},
		{Op: exec.OpColumn, P1: 0, P2: 0, P3: 2, Comment: "id 列を r[2] へ"},
		{Op: exec.OpColumn, P1: 0, P2: 1, P3: 3, Comment: "name 列を r[3] へ"},
		{Op: exec.OpColumn, P1: 0, P2: 2, P3: 4, Comment: "age 列を r[4] へ"},
		{Op: exec.OpResultRow, P1: 1, P2: 4, Comment: "r[1..4] を 1 行として出力"},
		{Op: exec.OpNext, P1: 0, P2: 3, Comment: "次の行があればアドレス 3 へ"},
		{Op: exec.OpHalt, Comment: "終了"},
	}
}

// runAndPrint はプログラムを実行し、結果行を "| 値 | 値 | ..." の簡素な形式で表示する。
func runAndPrint(tree *btree.BTree, program []exec.Instr) error {
	vm := exec.NewVM(tree, program)
	return vm.Run(func(row []sql.Value) error {
		fmt.Print("|")
		for _, v := range row {
			if v.IsText {
				fmt.Printf(" %s |", v.Text)
			} else {
				fmt.Printf(" %d |", v.Int)
			}
		}
		fmt.Println()
		return nil
	})
}
```

`main` の流れは単純です。`mini.db` を開き、木が空なら `seedUsers` で(id, name, age)のレコードを 3 件(Alice/Bob/Carol)仕込みます。そのうえで 2 種類のプログラム——`pointLookupProgram`(`SELECT name FROM users WHERE id = 2` 相当)と `fullScanProgram`(`SELECT * FROM users` 相当)——をそれぞれ `Explain` で表示してから `runAndPrint` で実行し、結果行を `| 値 | 値 | ...` という簡素な形式で表示します。

`seedUsers` が「木が空であれば」という条件をわざわざ確認しているのは、このデモを 2 回目以降に実行したとき(`mini.db` がすでに存在するとき)に重複挿入で `ErrDuplicateKey` にならないようにするためです。`id` 列には rowid と同じ値をそのまま格納しています——この点は後で回収します。

`pointLookupProgram` を読み解きます。`OpInit` が `P2=1` でアドレス 1(`OpOpenRead`)へジャンプして始まり、`OpInteger` でレジスタ 1 に検索キー `2` を置き、`OpSeekRowid` でカーソルをそのキーへ Seek します。一致すれば `OpColumn` で `name` 列(列番号 1)をレジスタ 2 へ読み、`OpResultRow` で 1 列の結果として出力し、`OpHalt` で終了。一致しなければ `OpSeekRowid` の `P2=6` がそのまま `OpHalt` を指しているので、`Column` を経由せず直接終了します。

`fullScanProgram` は `OpRewind` でカーソルを先頭へ位置づけたあと、アドレス 3〜7 のブロックを 1 行ぶんの処理として、`OpNext` でアドレス 3 へ戻る——という**ループ**になっています。`OpRowid` で rowid をレジスタ 1 へ、3 つの `OpColumn` で `id` / `name` / `age` の各列をレジスタ 2〜4 へ読み、`OpResultRow` で 4 列まとめて出力し、`OpNext` で次の行があればアドレス 3 へ戻ります。木が空なら `OpRewind` の `P2=9` が直接 `OpHalt` を指すので、ループ本体は一度も実行されません。

**1 本目のプログラムと、本物の SQLite を並べて見比べます。** 第 1 章で `SELECT name FROM users WHERE id = 2` を本物の SQLite の `EXPLAIN` に食わせたとき、こう出力されました。

```console
addr  opcode         p1    p2    p3    p4             p5  comment
----  -------------  ----  ----  ----  -------------  --  -------------
0     Init           0     7     0                    0   Start at 7
1     OpenRead       0     2     0     2              0   root=2 iDb=0; users
2     Integer        2     1     0                    0   r[1]=2
3     SeekRowid      0     6     1                    0   intkey=r[1]
4     Column         0     1     2                    0   r[2]= cursor 0 column 1
5     ResultRow      2     1     0                    0   output=r[2]
6     Halt           0     0     0                    0
7     Transaction    0     0     1     0              1   usesStmtJournal=0
8     Goto           0     1     0                    0
```

minidb 版は 7 命令、本物は 9 命令です。差分は `Transaction`(addr 7)と `Goto`(addr 8)の 2 つだけ——本物は読み取り 1 つであってもトランザクションの開始から実行が始まる(`Init` が addr 7 へ飛び、`Goto` で addr 1 に戻る)のに対し、minidb はまだトランザクションを持っていません(第 4 部の主題です)。それを除けば、**命令の並びも、各命令の役割も、ほぼそっくりそのまま**です。`Init` → `OpenRead` → `Integer` → `SeekRowid` → `Column` → `ResultRow` → `Halt` という骨格は 1 対 1 で対応しています。第 1 章で「いま個々の命令を覚える必要はまったくありません」と言ってやり過ごしたあの出力が、いまや 1 命令ずつ、自分の実装の言葉で説明できるようになりました。

**2 本目のプログラムはループの実例です。** `Rewind`(addr 2)で先頭へ位置づけたあと、`Rowid` → `Column` × 3 → `ResultRow`(addr 3〜7)という「1 行を処理する」ブロックが続き、`Next`(addr 8)がアドレス 3 へジャンプして戻る——**後端(back edge)**です。`Next` が「まだ行があればループ先頭へ戻る」という役割を持つことが、この 1 行(`8  Next  0  3  0`)にそのまま表れています。

出力の全件スキャンの結果、`| 1 | 1 | Alice | 30 |` のように **rowid(レジスタ 1)と id 列(レジスタ 2)が同じ値**になっていることに気づいたはずです。これは偶然ではありません。`seedUsers` が `id` 列に rowid と同じ値をそのまま格納しているからです。今のところこの重複は無害ですが、無駄でもあります。第 11 章で `INTEGER PRIMARY KEY` を rowid の別名として扱うようになると(第 9 章 9.4 節で `ColumnDef.PrimaryKey` に触れたとき予告したとおりです)、`id` 列を実体として二重に保存する必要がなくなり、この重複は解消されます。

ここまで、**SQL 文字列は 1 行も登場していません。** `pointLookupProgram` も `fullScanProgram` も、Go のコードとして手で組んだバイトコードです。第 9 章のパーサは `SELECT name FROM users WHERE id = 2` という文字列から `SelectStmt` を作れますし、今日の VM はここで見たような命令列を実行できます。両者の間に足りない最後の 1 枚——構文木から命令列を生み出す **Code Generator**——を作れば、SQL は初めて実際に動き出します。それが次章の主役です。

## 10.8　まとめ

- 実行方式には tree-walking とバイトコード VM の 2 つの流儀があり、SQLite(と minidb)は後者を選ぶ。理由はプリペアドステートメントとしての再利用性、`EXPLAIN` で観察できる可視性、そして単純な実行ループの 3 点
- レコード形式(`exec/record.go`)は、列数・型タグ列・値本体という 3 パート構成で、Alice の手作り文字列を型付きのバイト列に置き換えた。型タグ 0 を NULL 用に予約しておく判断は、第 2 章の「予約(ゼロ)」と同じ流儀
- カーソル(`btree/cursor.go`)は、VM のジャンプ制御されたループが必要とする「一時停止できる走査」を B-Tree の上に実装したもので、ページオブジェクトを持たずページ番号だけを stack に積む点で第 8 章の LRU 規約に従う。`Seek` が削除済みキーの亡霊(親のセパレータが更新されないまま残る状態)を正しく扱うための一手間は、この章でいちばん重要な設計の落とし穴だった
- VM(`exec/vm.go`)は P1〜P4 という無骨なオペランドを持つ命令列を、`pc` と `next` だけで駆動する単純なループで実行する。比較命令が「成立したらジャンプ」という形に統一されているのは、機械語の条件分岐と同じ発想
- `EXPLAIN`(`exec/explain.go`)によって、命令列は目に見える表になった。10.6 節で見たとおり、手組みのプログラムは本物の SQLite の `EXPLAIN` 出力とほぼ同じ骨格を持つ

この章では、SQL 文字列を 1 行も実行していません。命令列はすべて手で組みました。次章(第 11 章)では、第 9 章の構文木からこの章の命令列を自動生成する **Code Generator** を実装し、`CREATE TABLE` / `INSERT` / `SELECT` を接続します。あわせて `sqlite_schema` の minidb 版にあたる**カタログ**(テーブル定義をどう覚えておくか)を用意し、簡単な **REPL** を作ります。第 9 章のパーサと、この章の VM——2 つの部品がついにつながり、SQL が初めて実際に動き出します。
