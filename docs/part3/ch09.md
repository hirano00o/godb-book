第 3 部は 4 章に分かれます。本章(第 9 章)で Tokenizer と Parser、つまり SQL 文字列を構文木に変換する前半を作ります。第 10 章でレコード形式(Alice のバイト列を本物のレコードに置き換える)と VM の設計、第 11 章で `CREATE TABLE` / `INSERT` / `SELECT` が実際に動くところまで、第 12 章で `WHERE` の最適化と `UPDATE` / `DELETE` を仕上げます。

本章にはもう 1 つ、これまでの章にはなかった特徴があります。**pager にも btree にも一切依存しない、純粋なテキスト処理**だということです。これから作る `sql` パッケージの import を先取りして見ると、そのことがよく分かります。

```
lexer.go  → fmt, strings, unicode/utf8
ast.go    → fmt
parser.go → fmt, strconv
```

`minidb/pager` も `minidb/btree` もどこにも出てきません。SQL 文字列をトークン列に刻み、トークン列を構文木に組み立てる処理は、**データベースファイルが 1 バイトも存在しなくても動きます**。これは手抜きではなく、第 1 章で強調した層構造の実践そのものです。上の層は下の層が何をしているかを知らなくてよく、下の層も上の層の都合に引きずられない — Tokenizer と Parser は SQL という言語だけを相手にする、独立した言語処理系です。

新設するパッケージは `sql` で、ファイルは 3 つです。

- `lexer.go` — SQL 文字列をトークン列に分割する(9.3 節)
- `ast.go` — 構文木のノード型を定義する(9.4 節)
- `parser.go` — トークン列を再帰下降パーサで構文木に変換する(9.5 節)

## 9.2　対応する SQL を決める

minidb が対応する SQL サブセットを、先に確定させておきます。

| 文             | 構文(概略)                                                 |
| -------------- | ---------------------------------------------------------- |
| `CREATE TABLE` | `CREATE TABLE t (col INTEGER \| TEXT [PRIMARY KEY], ...)`  |
| `INSERT`       | `INSERT INTO t VALUES (リテラル, ...)`                     |
| `SELECT`       | `SELECT col, ... \| * FROM t [WHERE col op リテラル]`      |
| `UPDATE`       | `UPDATE t SET col = リテラル, ... [WHERE col op リテラル]` |
| `DELETE`       | `DELETE FROM t [WHERE col op リテラル]`                    |

補足のルールが 3 つあります。

- 列の型は `INTEGER` と `TEXT` の 2 種類のみ
- `PRIMARY KEY` は `INTEGER` 列に、1 テーブルにつき最大 1 つまで指定できる
- `WHERE` は「列名 演算子 リテラル」という**単一の比較**だけを表す。演算子は `= != < > <= >=` の 6 種類

割り切りを明示しておきます。

<div class="warn">

<span class="note-title">minidb の割り切り(第 3 部の実装範囲)</span>

- **`AND` / `OR` による複合条件は扱わない** — `WHERE` は列名・演算子・リテラルの単一比較のみ
- **`JOIN` は扱わない** — 1 つの文が扱うテーブルは常に 1 つ
- **`GROUP BY` / `ORDER BY` / 集約関数は扱わない**
- **型は `INTEGER` と `TEXT` のみ** — `FLOAT` / `BLOB` / `NULL` などは扱わない
- **サブクエリ・関数呼び出し・算術式は扱わない** — 値は常にリテラル 1 つ

</div>

本物の SQL 標準の広さと比べれば、これはほんの一角です。しかしこの小さなサブセットの中にも、字句解析・構文解析・木構造・エラー処理という、コンパイラ技術の骨格はひととおり詰まっています。

文字列リテラルは SQLite 流に `'...'` で囲み、引用符自体を含めたいときは `''` と 2 つ連続させてエスケープします(`'it''s'` → `it's`)。キーワード(`SELECT` や `FROM` など)は大文字小文字を区別しません — `select` と書いても `SELECT` と書いても同じトークンになります。

## 9.3　文字列をトークンに刻む — lexer

字句解析(lexer)は、SQL 文字列を**トークン**という単位に分割する処理です。なぜこの中間表現が必要なのか — パーサが 1 文字ずつ相手にする代わりに、「キーワード」「識別子」「数値」「記号」といった**語**を相手にできるようにするためです。文字を語にまとめる仕事と、語を文法規則に従って組み立てる仕事を分離することで、パーサ側のコードは驚くほどシンプルになります(9.5 節で実感できます)。

**sql/lexer.go(1) — 型定義と Tokenize**

```go
// lexer.go は SQL 文字列を字句解析してトークン列に分割する。
// pager や btree には依存しない、純粋なテキスト処理。
package sql

import (
	"fmt"
	"strings"
	"unicode/utf8"
)

// TokenKind はトークンの種別を表す。
type TokenKind int

const (
	TokenKeyword TokenKind = iota // SELECT, FROM, WHERE, CREATE, TABLE, INSERT, INTO, VALUES, UPDATE, SET, DELETE, INTEGER, TEXT, PRIMARY, KEY
	TokenIdent                    // テーブル名・列名
	TokenNumber                   // 整数リテラル(符号なし。負数はパーサが単項マイナスとして処理する)
	TokenString                   // '...' 文字列リテラル(Text にはエスケープ解決済みの中身が入る)
	TokenSymbol                   // ( ) , * ; = != < > <= >= -
	TokenEOF
)

// Token は字句解析結果の 1 単位。
type Token struct {
	Kind TokenKind
	Text string // キーワードは大文字に正規化される。文字列リテラルは引用符を除いた中身
	Pos  int    // 入力文字列中のバイト位置(エラーメッセージ用)
}

// keywords は識別子のうちキーワードとして扱う語の集合(大文字で保持)。
var keywords = map[string]bool{
	"SELECT": true, "FROM": true, "WHERE": true, "CREATE": true, "TABLE": true,
	"INSERT": true, "INTO": true, "VALUES": true, "UPDATE": true, "SET": true,
	"DELETE": true, "INTEGER": true, "TEXT": true, "PRIMARY": true, "KEY": true,
}

// Tokenize は input を字句解析してトークン列を返す。
// 末尾には必ず TokenEOF のトークンが 1 つ付く。
func Tokenize(input string) ([]Token, error) {
	var tokens []Token
	i := 0
	for i < len(input) {
		c := input[i]
		switch {
		case c == ' ' || c == '\t' || c == '\n' || c == '\r':
			i++
		case c == '\'':
			tok, next, err := scanString(input, i)
			if err != nil {
				return nil, err
			}
			tokens = append(tokens, tok)
			i = next
		case isDigit(c):
			tok, next := scanNumber(input, i)
			tokens = append(tokens, tok)
			i = next
		case isIdentStart(c):
			tok, next := scanIdent(input, i)
			tokens = append(tokens, tok)
			i = next
		default:
			tok, next, err := scanSymbol(input, i)
			if err != nil {
				return nil, err
			}
			tokens = append(tokens, tok)
			i = next
		}
	}
	tokens = append(tokens, Token{Kind: TokenEOF, Pos: len(input)})
	return tokens, nil
}
```

`Token` は種別(`Kind`)・テキスト(`Text`)・位置(`Pos`)の 3 フィールドだけの単純な構造体です。`Pos` は入力文字列中のバイト位置で、**すべてのトークンに例外なく刻まれます**。地味な 1 フィールドですが、9.5 節で見るとおり、エラーメッセージの品質はこの位置情報の有無で決定的に変わります。

`Tokenize` のメインループは、先頭の 1 文字を見て次にどの `scan` 関数へ委譲するかを振り分けるだけの単純な状態機械です。空白はスキップし、`'` なら文字列、数字なら数値、識別子の先頭になりうる文字(英字とアンダースコア)なら識別子かキーワード、それ以外は記号として `scanSymbol` に渡します。ループを抜けたら末尾に必ず `TokenEOF` を 1 つ追加します — パーサ側が「まだ読める」か「もう終わり」かを、範囲外アクセスを気にせず一貫した判定で扱えるようにするためです。

**sql/lexer.go(2) — 各 scan 関数**

```go
func isDigit(c byte) bool { return c >= '0' && c <= '9' }

func isIdentStart(c byte) bool {
	return c == '_' || (c >= 'A' && c <= 'Z') || (c >= 'a' && c <= 'z')
}

func isIdentPart(c byte) bool { return isIdentStart(c) || isDigit(c) }

func scanNumber(input string, start int) (Token, int) {
	i := start
	for i < len(input) && isDigit(input[i]) {
		i++
	}
	return Token{Kind: TokenNumber, Text: input[start:i], Pos: start}, i
}

func scanIdent(input string, start int) (Token, int) {
	i := start
	for i < len(input) && isIdentPart(input[i]) {
		i++
	}
	text := input[start:i]
	upper := strings.ToUpper(text)
	if keywords[upper] {
		return Token{Kind: TokenKeyword, Text: upper, Pos: start}, i
	}
	return Token{Kind: TokenIdent, Text: text, Pos: start}, i
}

// scanString は先頭のクオート文字の位置 start から文字列リテラルを読み取る。
// クオート文字を 2 個連続させると、引用符自体を表すエスケープとして
// 1 個のクオート文字に解決する(SQLite 流)。
func scanString(input string, start int) (Token, int, error) {
	quote := input[start]
	var b strings.Builder
	i := start + 1
	for {
		if i >= len(input) {
			return Token{}, 0, fmt.Errorf("位置 %d: 閉じられていない文字列リテラルです", start)
		}
		if input[i] == quote {
			if i+1 < len(input) && input[i+1] == quote {
				b.WriteByte(quote)
				i += 2
				continue
			}
			i++
			break
		}
		b.WriteByte(input[i])
		i++
	}
	return Token{Kind: TokenString, Text: b.String(), Pos: start}, i, nil
}

// scanSymbol は記号 1 つを読み取る。<=, >=, != の 2 文字演算子は
// 1 文字目だけで判定しないよう先読みする。
func scanSymbol(input string, start int) (Token, int, error) {
	if start+1 < len(input) {
		switch input[start : start+2] {
		case "<=", ">=", "!=":
			return Token{Kind: TokenSymbol, Text: input[start : start+2], Pos: start}, start + 2, nil
		}
	}
	switch input[start] {
	case '(', ')', ',', '*', ';', '=', '<', '>', '-':
		return Token{Kind: TokenSymbol, Text: string(input[start]), Pos: start}, start + 1, nil
	}
	r, _ := utf8.DecodeRuneInString(input[start:])
	return Token{}, 0, fmt.Errorf("位置 %d: 予期しない文字 %q", start, r)
}
```

キーワード判定のコツは `scanIdent` に表れています。**先に識別子として読み切ってから**、その文字列を大文字化して `keywords` マップと照合する、という順序です。「`SELECT` というキーワードを探す」のではなく「識別子を 1 つ読み、それがたまたまキーワード集合に含まれていたら種別を差し替える」という発想であり、識別子とキーワードの文字集合(英数字とアンダースコア)が同じだからこそ成立する単純な実装です。キーワードの `Text` は大文字に正規化して格納しますが(`select` と書いても `Text` は `"SELECT"`)、`TokenIdent` の `Text` は入力のままの大文字小文字を保持します — テーブル名や列名の表記まで書き換えてしまっては困るからです。

`scanString` は `'` に遭遇したところから始まり、次の `'` が来るまで 1 文字ずつ読み進めます。ここでの工夫は、クオート文字そのものを 2 個連続させたときのエスケープです。ループの中で「今見ている文字がクオートで、かつ**その次**の文字もクオートなら」1 個のクオート文字として `b.WriteByte` し、2 文字分まとめて読み飛ばします。1 文字先読みではなく **2 文字先読み**が必要になる、地味だが典型的なパターンです。

`scanSymbol` にも同じ「先読み」の考え方が現れます。`<=` `>=` `!=` という 2 文字演算子を扱うには、**1 文字目だけを見て確定してはいけません**。`<` を読んだ瞬間に「これは `<` トークンだ」と決めてしまうと、続く `=` を見落として `<=` を `<` と `=` の 2 トークンに誤って分割してしまいます。だから `scanSymbol` はまず `input[start:start+2]` を切り出して 2 文字演算子の集合と照合し、一致しなければ改めて 1 文字の記号として判定する、という順序を取ります。未知の文字に遭遇したときは `utf8.DecodeRuneInString` でルーン単位にデコードしてからエラーメッセージに含めます — バイト列の途中で切ってしまうと、マルチバイト文字を含む不正な入力のエラーメッセージが文字化けするためです。

<div class="sqlite-note">

<span class="note-title">SQLite ではこうなっている: 手書きトークナイザと Lemon パーサジェネレータ</span> 本物の SQLite のトークナイザは手書きの C コードです(`src/tokenize.c`、約 900 行)。一方パーサは違います。文法定義ファイル `src/parse.y`(約 2200 行)から、**Lemon** という SQLite 専用のパーサジェネレータが C コードを自動生成しています(3.53.3 実測)。Lemon は yacc / bison といった一般的な LALR パーサジェネレータとよく似た発想の道具ですが、SQLite プロジェクトのために独自に書かれたものです。minidb の文法はこのサブセットに収まるほど小さいので、生成系を使わず手書きの再帰下降パーサで書きます。生成系を挟まない分、**文法とコードの対応が目で追える**という教材的な利点があります。次節でその対応を実際に確認します。

## 9.4　構文木 — SQL 文を Go の構造体にする

トークン列ができたら、次はそれを**構文木**に組み立てます。構文木のノード型を定義するのが `ast.go` です。AST は Abstract Syntax Tree(抽象構文木)の略ですが、ここで言う「木」は、第 2 部でディスク上に作った B-Tree とはまったく別物です。B-Tree はキーで検索するためのディスク上のデータ構造でしたが、こちらの木は**構文の入れ子構造をメモリ上で表現する**ためのものです。同じ「木」という言葉が、章によってまったく違う意味で使われている——このことは頭の片隅に置いておいてください。

**sql/ast.go(全文)**

```go
// ast.go は sql パッケージが扱う構文木のノード型を定義する。
package sql

import "fmt"

// Statement は SQL 文を表す構文木のルート型。
type Statement interface{ stmtNode() }

// ColumnType は CREATE TABLE における列の型。
type ColumnType int

const (
	TypeInteger ColumnType = iota + 1
	TypeText
)

// String は列型を SQL のキーワード表記で返す。
func (t ColumnType) String() string {
	switch t {
	case TypeInteger:
		return "INTEGER"
	case TypeText:
		return "TEXT"
	default:
		return fmt.Sprintf("ColumnType(%d)", int(t))
	}
}

// ColumnDef は CREATE TABLE の列定義 1 つ。
type ColumnDef struct {
	Name       string
	Type       ColumnType
	PrimaryKey bool
}

// Value はリテラル値(整数または文字列)を表す。
type Value struct {
	IsText bool
	Int    int64
	Text   string
}

// CompareOp は WHERE 句の比較演算子。
type CompareOp int

const (
	OpEq CompareOp = iota
	OpNe
	OpLt
	OpGt
	OpLe
	OpGe
)

// String は比較演算子を SQL の記号表記で返す。
func (op CompareOp) String() string {
	switch op {
	case OpEq:
		return "="
	case OpNe:
		return "!="
	case OpLt:
		return "<"
	case OpGt:
		return ">"
	case OpLe:
		return "<="
	case OpGe:
		return ">="
	default:
		return fmt.Sprintf("CompareOp(%d)", int(op))
	}
}

// WhereClause は「列名 演算子 リテラル」の単一比較を表す。
// このサブセットでは AND/OR による複合条件は扱わない。
type WhereClause struct {
	Column string
	Op     CompareOp
	Value  Value
}

// CreateTableStmt は CREATE TABLE 文。
type CreateTableStmt struct {
	Table   string
	Columns []ColumnDef
}

func (*CreateTableStmt) stmtNode() {}

// InsertStmt は INSERT INTO 文。値はリテラルのみを受け付ける。
type InsertStmt struct {
	Table  string
	Values []Value
}

func (*InsertStmt) stmtNode() {}

// SelectStmt は SELECT 文。Star が true のときは Columns を無視する。
type SelectStmt struct {
	Star    bool
	Columns []string
	Table   string
	Where   *WhereClause
}

func (*SelectStmt) stmtNode() {}

// Assignment は UPDATE の SET 句 1 つ分(列名と代入する値)。
type Assignment struct {
	Column string
	Value  Value
}

// UpdateStmt は UPDATE 文。
type UpdateStmt struct {
	Table string
	Set   []Assignment
	Where *WhereClause
}

func (*UpdateStmt) stmtNode() {}

// DeleteStmt は DELETE FROM 文。
type DeleteStmt struct {
	Table string
	Where *WhereClause
}

func (*DeleteStmt) stmtNode() {}
```

軸は `Statement` インターフェースです。中身は `stmtNode()` という空のメソッドが 1 つあるだけの、**マーカーインターフェース**です。5 つの文の型(`CreateTableStmt` / `InsertStmt` / `SelectStmt` / `UpdateStmt` / `DeleteStmt`)がそれぞれこのメソッドを実装することで、「どの文か」を Go の型システムで表現します。パーサや(第 11 章以降の)実行エンジンは、`Statement` を受け取ったら `switch s := stmt.(type)` という**型スイッチ**で分岐すればよく、9.7 節の `parsedemo` の `printStatement` がまさにこの形をしています。

`Value` は整数(`Int`)と文字列(`Text`)を 1 つの型にまとめ、`IsText` で判別する設計です。Go には共用体(union)がないので、フィールドを両方持たせて使わない方を空にしておく、という素朴な形を取っています。`WhereClause` は 9.2 節で決めた「列名・演算子・リテラル」の単一比較をそのまま構造体にしたもので、`CompareOp` は 6 種類の比較演算子を整数の列挙型として表します。`ColumnDef` の `PrimaryKey` フィールドは、いまはただの `bool` ですが、第 11 章で `INTEGER PRIMARY KEY` が SQLite と同じく **rowid の別名**になるときの土台になります。

## 9.5　再帰下降パーサ — 文法をそのままコードに

いよいよパーサです。`parser.go` はトークン列の先頭から順に読み進め、文法規則に従って `Statement` を組み立てます。この節で採用する**再帰下降(recursive descent)**という手法の勘所は 1 つだけです — **文法規則 1 つにつき、関数を 1 つ書く**。文法とコードが 1:1 に対応するので、読むときも書くときも「今どの規則を処理しているか」を見失いません。5 つに分けて見ていきます。

**sql/parser.go(1) — Parse とヘルパ群**

```go
// parser.go は Tokenize が生成したトークン列を再帰下降パーサで構文木に変換する。
package sql

import (
	"fmt"
	"strconv"
)

// parser はトークン列を先頭から読み進める。
type parser struct {
	tokens []Token
	pos    int
}

// Parse は SQL 文字列 1 文を解析して構文木を返す。
func Parse(input string) (Statement, error) {
	tokens, err := Tokenize(input)
	if err != nil {
		return nil, err
	}
	p := &parser{tokens: tokens}

	tok := p.peek()
	if tok.Kind == TokenEOF {
		return nil, fmt.Errorf("位置 %d: SQL 文が空です", tok.Pos)
	}

	var stmt Statement
	switch {
	case p.isKeyword("CREATE"):
		stmt, err = p.parseCreateTable()
	case p.isKeyword("INSERT"):
		stmt, err = p.parseInsert()
	case p.isKeyword("SELECT"):
		stmt, err = p.parseSelect()
	case p.isKeyword("UPDATE"):
		stmt, err = p.parseUpdate()
	case p.isKeyword("DELETE"):
		stmt, err = p.parseDelete()
	default:
		return nil, fmt.Errorf("位置 %d: 文の先頭となるキーワードが必要ですが %q があります", tok.Pos, tok.Text)
	}
	if err != nil {
		return nil, err
	}

	if tok := p.peek(); tok.Kind == TokenSymbol && tok.Text == ";" {
		p.next()
	}
	if tok := p.peek(); tok.Kind != TokenEOF {
		return nil, fmt.Errorf("位置 %d: 余分なトークン %q があります", tok.Pos, tok.Text)
	}
	return stmt, nil
}

func (p *parser) peek() Token { return p.tokens[p.pos] }

func (p *parser) next() Token {
	tok := p.tokens[p.pos]
	if p.pos < len(p.tokens)-1 {
		p.pos++
	}
	return tok
}

func (p *parser) isKeyword(kw string) bool {
	tok := p.peek()
	return tok.Kind == TokenKeyword && tok.Text == kw
}

func (p *parser) expectKeyword(kw string) (Token, error) {
	tok := p.peek()
	if tok.Kind != TokenKeyword || tok.Text != kw {
		return Token{}, fmt.Errorf("位置 %d: %s が必要ですが %q があります", tok.Pos, kw, tok.Text)
	}
	return p.next(), nil
}

func (p *parser) expectSymbol(sym string) (Token, error) {
	tok := p.peek()
	if tok.Kind != TokenSymbol || tok.Text != sym {
		return Token{}, fmt.Errorf("位置 %d: %q が必要ですが %q があります", tok.Pos, sym, tok.Text)
	}
	return p.next(), nil
}

func (p *parser) expectIdent() (Token, error) {
	tok := p.peek()
	if tok.Kind != TokenIdent {
		return Token{}, fmt.Errorf("位置 %d: 識別子が必要ですが %q があります", tok.Pos, tok.Text)
	}
	return p.next(), nil
}

func (p *parser) expectNumber() (Token, error) {
	tok := p.peek()
	if tok.Kind != TokenNumber {
		return Token{}, fmt.Errorf("位置 %d: 数値が必要ですが %q があります", tok.Pos, tok.Text)
	}
	return p.next(), nil
}
```

`parser` 構造体はトークン列 `tokens` と現在位置 `pos` だけを持ちます。読み進めるための道具は 3 種類だけです。`peek` は今の位置のトークンを**消費せずに**覗き見る、`next` はそれを 1 つ**消費して**返す、そして `expectKeyword` / `expectSymbol` / `expectIdent` / `expectNumber` は「次のトークンがこの種別・このテキストであるはず」という期待を検査し、外れていればエラーを、合っていれば `next()` で消費して返します。これから見る `parseXxx` 関数群は、すべてこの 3 種の道具の組み合わせだけで書かれています。

`Parse` の本体はまず `Tokenize` を呼び、先頭のキーワードを見て 5 つの `parseXxx` へ振り分けます。パースが終わったら、末尾のセミコロンは**あってもなくても許容**し(`;` があれば読み捨てるだけ)、そのうえで**まだトークンが残っていないか**を確認します。ここが 9.6 節のテストケース「`SELECT * FROM t WHERE a = 1 AND b = 2`」が失敗する理由です。`AND` 以降は `parseSelect` が知らない余りものなので、`Parse` はこの最終チェックで「余分なトークンがあります」というエラーにします。9.2 節で決めた「`AND` は扱わない」という割り切りが、コードのこの 1 行に具体的な形で現れているわけです。

`next()` の実装にも注意点があります。`p.pos < len(p.tokens)-1` という条件があるおかげで、`EOF` トークンより先には位置が進みません。これにより、`EOF` に達したあとに何度 `next()` を呼んでも同じ `EOF` トークンが返り続け、範囲外アクセスが起きません。

**sql/parser.go(2) — parseCreateTable + parseColumnDef**

```go
// parseCreateTable は CREATE TABLE t (col INTEGER [PRIMARY KEY], col TEXT, ...) を解析する。
func (p *parser) parseCreateTable() (Statement, error) {
	if _, err := p.expectKeyword("CREATE"); err != nil {
		return nil, err
	}
	if _, err := p.expectKeyword("TABLE"); err != nil {
		return nil, err
	}
	nameTok, err := p.expectIdent()
	if err != nil {
		return nil, err
	}
	if _, err := p.expectSymbol("("); err != nil {
		return nil, err
	}

	var columns []ColumnDef
	hasPrimaryKey := false
	for {
		col, primaryPos, err := p.parseColumnDef()
		if err != nil {
			return nil, err
		}
		if col.PrimaryKey {
			if hasPrimaryKey {
				return nil, fmt.Errorf("位置 %d: PRIMARY KEY は 1 つのテーブルに 1 つまでです", primaryPos)
			}
			hasPrimaryKey = true
		}
		columns = append(columns, col)

		if tok := p.peek(); tok.Kind == TokenSymbol && tok.Text == "," {
			p.next()
			continue
		}
		break
	}
	if _, err := p.expectSymbol(")"); err != nil {
		return nil, err
	}
	return &CreateTableStmt{Table: nameTok.Text, Columns: columns}, nil
}

// parseColumnDef は列定義 1 つを解析する。primaryPos は PRIMARY KEY が
// 指定されていた場合にその位置を返し(重複検出に使う)、なければ -1。
func (p *parser) parseColumnDef() (col ColumnDef, primaryPos int, err error) {
	primaryPos = -1

	nameTok, err := p.expectIdent()
	if err != nil {
		return ColumnDef{}, 0, err
	}

	var typ ColumnType
	switch {
	case p.isKeyword("INTEGER"):
		p.next()
		typ = TypeInteger
	case p.isKeyword("TEXT"):
		p.next()
		typ = TypeText
	default:
		tok := p.peek()
		return ColumnDef{}, 0, fmt.Errorf("位置 %d: 列の型(INTEGER または TEXT)が必要ですが %q があります", tok.Pos, tok.Text)
	}

	primaryKey := false
	if p.isKeyword("PRIMARY") {
		primaryTok := p.peek()
		p.next()
		if _, err := p.expectKeyword("KEY"); err != nil {
			return ColumnDef{}, 0, err
		}
		if typ != TypeInteger {
			return ColumnDef{}, 0, fmt.Errorf("位置 %d: PRIMARY KEY は INTEGER 列にのみ指定できます", primaryTok.Pos)
		}
		primaryKey = true
		primaryPos = primaryTok.Pos
	}

	return ColumnDef{Name: nameTok.Text, Type: typ, PrimaryKey: primaryKey}, primaryPos, nil
}
```

`parseCreateTable` を読めば、9.2 節の文法「`CREATE TABLE t (col TYPE [PRIMARY KEY], ...)`」がほぼそのままコードの行の並びになっているのが分かります。`CREATE` を確認し、`TABLE` を確認し、テーブル名を識別子として読み、`(` を確認し、カンマ区切りで `parseColumnDef` をループし、`)` を確認する。文法規則の語順と、`expectXxx` 呼び出しの並び順が一致しています。

`PRIMARY KEY` の制約検査が 2 か所に分かれている点に注目してください。「`INTEGER` 列にしか付けられない」という検査は `parseColumnDef` の中で、その列の型を見た直後に行います。一方「1 テーブルにつき 1 つまで」という検査は `parseCreateTable` の側で、`hasPrimaryKey` という状態を持ちながら列を読むたびに確認します。前者は 1 列だけを見れば分かる**局所的な**制約、後者は複数の列にまたがる**全体の**制約だからです。`primaryPos` を `parseColumnDef` の戻り値として持ち回っているのは、重複が見つかったときに「2 つ目の `PRIMARY KEY` があった位置」を指してエラーを出すための工夫です。

ここで整理しておきたいのは、**この検査がパーサ層で行われている**という設計判断そのものです。テーブルが実際に存在するかどうかや、列名が重複していないかといった検査は、この章では一切行いません。それらは第 11 章で実行エンジンがスキーマ情報を持つようになって初めて可能になる、**実行時**の検査です。「構文だけで判定できる制約はパーサで、実データを見なければ分からない制約は実行時で」という切り分けは、どの RDBMS でも共通する設計判断です。

**sql/parser.go(3) — parseInsert + parseValue**

```go
// parseInsert は INSERT INTO t VALUES (expr, ...) を解析する。
func (p *parser) parseInsert() (Statement, error) {
	if _, err := p.expectKeyword("INSERT"); err != nil {
		return nil, err
	}
	if _, err := p.expectKeyword("INTO"); err != nil {
		return nil, err
	}
	nameTok, err := p.expectIdent()
	if err != nil {
		return nil, err
	}
	if _, err := p.expectKeyword("VALUES"); err != nil {
		return nil, err
	}
	if _, err := p.expectSymbol("("); err != nil {
		return nil, err
	}

	var values []Value
	for {
		v, err := p.parseValue()
		if err != nil {
			return nil, err
		}
		values = append(values, v)

		if tok := p.peek(); tok.Kind == TokenSymbol && tok.Text == "," {
			p.next()
			continue
		}
		break
	}
	if _, err := p.expectSymbol(")"); err != nil {
		return nil, err
	}
	return &InsertStmt{Table: nameTok.Text, Values: values}, nil
}

// parseValue はリテラル(整数、単項マイナス付き整数、または文字列)を解析する。
func (p *parser) parseValue() (Value, error) {
	tok := p.peek()

	if tok.Kind == TokenSymbol && tok.Text == "-" {
		p.next()
		numTok, err := p.expectNumber()
		if err != nil {
			return Value{}, err
		}
		n, err := strconv.ParseInt(numTok.Text, 10, 64)
		if err != nil {
			return Value{}, fmt.Errorf("位置 %d: 数値リテラルが不正です: %v", numTok.Pos, err)
		}
		return Value{Int: -n}, nil
	}
	if tok.Kind == TokenNumber {
		p.next()
		n, err := strconv.ParseInt(tok.Text, 10, 64)
		if err != nil {
			return Value{}, fmt.Errorf("位置 %d: 数値リテラルが不正です: %v", tok.Pos, err)
		}
		return Value{Int: n}, nil
	}
	if tok.Kind == TokenString {
		p.next()
		return Value{IsText: true, Text: tok.Text}, nil
	}
	return Value{}, fmt.Errorf("位置 %d: リテラル(数値または文字列)が必要ですが %q があります", tok.Pos, tok.Text)
}
```

`parseValue` は本節でいちばん「字句解析と構文解析の役割分担」がよく見える関数です。単項マイナス(`-5` のような負の数)を思い出してください。9.3 節の `lexer_test.go` で確認したとおり、`lexer` は `-42` を `-` という**記号トークン 1 つ**と `42` という**数値トークン 1 つ**に分けるだけで、「これは負の数だ」とは一切判断しません。負の数として解釈するのは `parseValue` の仕事です。`peek()` で次のトークンが `-` 記号だったら、それを消費してから数値を読み、符号を反転する。記号 1 文字がどんな意味を持つかは**文脈**(ここでは「リテラルの先頭に来た」という文脈)によって決まり、その文脈を知っているのはパーサだけです。字句解析は文字を見て、構文解析は並びを見る——役割の違いがこの数行に凝縮されています。

**sql/parser.go(4) — parseSelect + parseColumnList + parseOptionalWhere + parseCompareOp**

```go
// parseSelect は SELECT col, ... FROM t [WHERE cond] と
// SELECT * FROM t [WHERE cond] を解析する。
func (p *parser) parseSelect() (Statement, error) {
	if _, err := p.expectKeyword("SELECT"); err != nil {
		return nil, err
	}

	stmt := &SelectStmt{}
	if tok := p.peek(); tok.Kind == TokenSymbol && tok.Text == "*" {
		p.next()
		stmt.Star = true
	} else {
		cols, err := p.parseColumnList()
		if err != nil {
			return nil, err
		}
		stmt.Columns = cols
	}

	if _, err := p.expectKeyword("FROM"); err != nil {
		return nil, err
	}
	nameTok, err := p.expectIdent()
	if err != nil {
		return nil, err
	}
	stmt.Table = nameTok.Text

	where, err := p.parseOptionalWhere()
	if err != nil {
		return nil, err
	}
	stmt.Where = where
	return stmt, nil
}

// parseColumnList は "col, col, ..." 形式の列名リストを解析する。
func (p *parser) parseColumnList() ([]string, error) {
	var cols []string
	for {
		tok, err := p.expectIdent()
		if err != nil {
			return nil, err
		}
		cols = append(cols, tok.Text)

		if next := p.peek(); next.Kind == TokenSymbol && next.Text == "," {
			p.next()
			continue
		}
		break
	}
	return cols, nil
}

// parseOptionalWhere は WHERE 句があれば解析し、なければ nil を返す。
func (p *parser) parseOptionalWhere() (*WhereClause, error) {
	if !p.isKeyword("WHERE") {
		return nil, nil
	}
	p.next()

	colTok, err := p.expectIdent()
	if err != nil {
		return nil, err
	}
	op, err := p.parseCompareOp()
	if err != nil {
		return nil, err
	}
	value, err := p.parseValue()
	if err != nil {
		return nil, err
	}
	return &WhereClause{Column: colTok.Text, Op: op, Value: value}, nil
}

// parseCompareOp は比較演算子(= != < > <= >=)を解析する。
func (p *parser) parseCompareOp() (CompareOp, error) {
	tok := p.peek()
	if tok.Kind != TokenSymbol {
		return 0, fmt.Errorf("位置 %d: 比較演算子が必要ですが %q があります", tok.Pos, tok.Text)
	}
	var op CompareOp
	switch tok.Text {
	case "=":
		op = OpEq
	case "!=":
		op = OpNe
	case "<":
		op = OpLt
	case ">":
		op = OpGt
	case "<=":
		op = OpLe
	case ">=":
		op = OpGe
	default:
		return 0, fmt.Errorf("位置 %d: 比較演算子が必要ですが %q があります", tok.Pos, tok.Text)
	}
	p.next()
	return op, nil
}
```

`parseSelect` こそ、この節の冒頭で述べた「文法規則とコードの 1:1 対応」がもっとも分かりやすい形で現れている関数です。9.2 節の文法 `SELECT 列リスト FROM テーブル [WHERE 条件]` の語順をそのまま上から読めば、`SELECT` を確認し、`*` か列名リストかを判定し、`FROM` を確認し、テーブル名を読み、最後に**あるかもしれない** `WHERE` を試す——コードの行の並びが、文法の語順とまったく同じです。

`[WHERE 条件]` という角括弧(「あってもなくてもよい」)は、`parseOptionalWhere` の中の `if !p.isKeyword("WHERE") { return nil, nil }` という 1 行にそのまま対応します。文法の「省略可能」は、コードでは「先頭を覗いて、なければ早期リターン」という if 文に翻訳される——これが再帰下降パーサの基本パターンです。`parseCompareOp` は 9.2 節で決めた 6 種類の比較演算子を `switch` で列挙するだけの単純な関数ですが、`scanSymbol`(9.3 節)が `<=` `>=` `!=` を正しく 1 トークンに刻んでくれているおかげで、ここでは文字列の比較だけで済んでいます。字句解析の仕事がきちんとしていれば、構文解析は驚くほど単純になる——この 2 つの関数の対比が、その好例です。

**sql/parser.go(5) — parseUpdate + parseDelete**

```go
// parseUpdate は UPDATE t SET col = expr, ... [WHERE cond] を解析する。
func (p *parser) parseUpdate() (Statement, error) {
	if _, err := p.expectKeyword("UPDATE"); err != nil {
		return nil, err
	}
	nameTok, err := p.expectIdent()
	if err != nil {
		return nil, err
	}
	if _, err := p.expectKeyword("SET"); err != nil {
		return nil, err
	}

	var assigns []Assignment
	for {
		colTok, err := p.expectIdent()
		if err != nil {
			return nil, err
		}
		if _, err := p.expectSymbol("="); err != nil {
			return nil, err
		}
		v, err := p.parseValue()
		if err != nil {
			return nil, err
		}
		assigns = append(assigns, Assignment{Column: colTok.Text, Value: v})

		if tok := p.peek(); tok.Kind == TokenSymbol && tok.Text == "," {
			p.next()
			continue
		}
		break
	}

	where, err := p.parseOptionalWhere()
	if err != nil {
		return nil, err
	}
	return &UpdateStmt{Table: nameTok.Text, Set: assigns, Where: where}, nil
}

// parseDelete は DELETE FROM t [WHERE cond] を解析する。
func (p *parser) parseDelete() (Statement, error) {
	if _, err := p.expectKeyword("DELETE"); err != nil {
		return nil, err
	}
	if _, err := p.expectKeyword("FROM"); err != nil {
		return nil, err
	}
	nameTok, err := p.expectIdent()
	if err != nil {
		return nil, err
	}
	where, err := p.parseOptionalWhere()
	if err != nil {
		return nil, err
	}
	return &DeleteStmt{Table: nameTok.Text, Where: where}, nil
}
```

`parseUpdate` と `parseDelete` は、ここまでに作った部品の組み合わせで書けます。`parseUpdate` は `SET` 句をカンマ区切りでループする点が `parseCreateTable` の列リストや `parseInsert` の値リストと同じ形をしていますし、`WHERE` 句の処理は `parseSelect` とまったく同じ `parseOptionalWhere` を**そのまま再利用**しています。`parseDelete` に至っては `DELETE` `FROM` テーブル名 `[WHERE]` の 4 ステップだけで、全パーサの中でもっとも短い関数です。1 つの文法規則が 1 つの関数になり、その関数が別の文法規則からも再利用される——再帰下降パーサが「文法の組み立てやすさ」をそのままコードの組み立てやすさに変換していることが、この最後の 2 関数によく表れています。

エラーメッセージについても、ここまでの 5 分割全体を通した約束を確認しておきます。`expectXxx` 系のエラーはすべて `"位置 %d: 〇〇が必要ですが %q があります"` という同じ形をしています。**位置・期待していたもの・実際にあったもの**の 3 点セットです。9.7 節の `parsedemo` で、この形式がどれだけデバッグの役に立つかを実際に見てもらいます。

## 9.6　テストで検証する — テーブル駆動テスト

この章のテストは、第 2 部までとは書き方を変えます。**テーブル駆動テスト(table-driven test)**で書きます。第 6〜8 章の `btree` のテストは、`pager` を開いて木を作り、挿入や削除を呼び、状態を確認する——という**手続き型**のテストでした。状態を持つものを検証するにはこの形が自然です。しかし `Tokenize` と `Parse` は違います。「文字列を渡すと、決まった構造体が返る」という**純粋関数**であり、入力と期待する出力の組を表として並べ、1 つのループでまとめて検証するテーブル駆動テストが、Go では標準的な流儀です。ケースを 1 つ足すたびにやることは、スライスの要素を 1 つ増やすだけで済みます。

## 9.7　動かして確かめる — parsedemo

テストは通っていますが、字句解析と構文解析の結果を**目で見る**ツールも用意しておきます。SQL 文字列を 1 つ受け取り、トークン列と構文木を両方表示する `parsedemo` です。

**cmd/parsedemo/main.go(全文)**

```go
// cmd/parsedemo/main.go
// SQL 文字列を 1 つ受け取り、字句解析したトークン列と、
// パースした構文木を表示するデモツール。
// sql パッケージのトークナイザ・パーサの動作を目視で確認するために使う。
package main

import (
	"fmt"
	"os"
	"strings"

	"minidb/sql"
)

func main() {
	if len(os.Args) != 2 {
		fmt.Fprintf(os.Stderr, "使い方: %s \"SQL 文\"\n", os.Args[0])
		os.Exit(1)
	}
	input := os.Args[1]

	tokens, err := sql.Tokenize(input)
	if err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}
	fmt.Println("トークン列:")
	for _, tok := range tokens {
		fmt.Printf("  %-7s %-15q pos=%d\n", tokenKindName(tok.Kind), tok.Text, tok.Pos)
	}

	stmt, err := sql.Parse(input)
	if err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}
	fmt.Println("\n構文木:")
	printStatement(stmt)
}

// tokenKindName は TokenKind を表示用の短い名前に変換する。
func tokenKindName(k sql.TokenKind) string {
	switch k {
	case sql.TokenKeyword:
		return "KEYWORD"
	case sql.TokenIdent:
		return "IDENT"
	case sql.TokenNumber:
		return "NUMBER"
	case sql.TokenString:
		return "STRING"
	case sql.TokenSymbol:
		return "SYMBOL"
	case sql.TokenEOF:
		return "EOF"
	default:
		return "?"
	}
}

// printStatement は構文木を文の種類ごとに整形して表示する。
// %#v による Go の内部表現ではなく、SQL の構造が読み取れる形にする。
func printStatement(stmt sql.Statement) {
	switch s := stmt.(type) {
	case *sql.CreateTableStmt:
		fmt.Printf("CreateTableStmt\n")
		fmt.Printf("  Table: %s\n", s.Table)
		fmt.Printf("  Columns:\n")
		for _, c := range s.Columns {
			pk := ""
			if c.PrimaryKey {
				pk = " PRIMARY KEY"
			}
			fmt.Printf("    - %s %s%s\n", c.Name, c.Type, pk)
		}

	case *sql.InsertStmt:
		fmt.Printf("InsertStmt\n")
		fmt.Printf("  Table: %s\n", s.Table)
		fmt.Printf("  Values:\n")
		for _, v := range s.Values {
			fmt.Printf("    - %s\n", formatValue(v))
		}

	case *sql.SelectStmt:
		fmt.Printf("SelectStmt\n")
		fmt.Printf("  Table: %s\n", s.Table)
		if s.Star {
			fmt.Printf("  Columns: *\n")
		} else {
			fmt.Printf("  Columns: %s\n", strings.Join(s.Columns, ", "))
		}
		printWhere(s.Where)

	case *sql.UpdateStmt:
		fmt.Printf("UpdateStmt\n")
		fmt.Printf("  Table: %s\n", s.Table)
		fmt.Printf("  Set:\n")
		for _, a := range s.Set {
			fmt.Printf("    - %s = %s\n", a.Column, formatValue(a.Value))
		}
		printWhere(s.Where)

	case *sql.DeleteStmt:
		fmt.Printf("DeleteStmt\n")
		fmt.Printf("  Table: %s\n", s.Table)
		printWhere(s.Where)

	default:
		fmt.Printf("%#v\n", stmt)
	}
}

// printWhere は WHERE 句を 1 段インデントして表示する。なければ "なし" と表示する。
func printWhere(w *sql.WhereClause) {
	if w == nil {
		fmt.Printf("  Where: なし\n")
		return
	}
	fmt.Printf("  Where: %s %s %s\n", w.Column, w.Op, formatValue(w.Value))
}

func formatValue(v sql.Value) string {
	if v.IsText {
		return fmt.Sprintf("%q", v.Text)
	}
	return fmt.Sprintf("%d", v.Int)
}
```

`printStatement` は 9.4 節で見た `Statement` の型スイッチをそのまま体現しています。5 つの文の型を `switch s := stmt.(type)` で分岐し、それぞれの構造体のフィールドを SQL らしい見た目に整形して出力します。`%#v` で Go の内部表現をそのまま出すのではなく、あえて `printWhere` や `formatValue` といった専用の整形関数を書いているのは、構文木が正しく組み立てられているかを**人間が一目で確認できる**形にするためです。

```console
  IDENT   "id"            pos=29
  SYMBOL  "="             pos=32
  NUMBER  "2"             pos=34
  EOF     ""              pos=35

構文木:
SelectStmt

  Columns: name
  Where: id = 2
```

第 1 章で `EXPLAIN` に食わせたのと同じ文です。あのときは SQLite が「トークン化 → 構文解析 → バイトコード生成」を一気に済ませ、9 個の VDBE 命令として結果を見せてくれました。いま自分の手で再現できているのは、その最初の 2 段階です。トークン列は `SELECT` `name` `FROM` `users` `WHERE` `id` `=` `2` ときれいに 8 個(+ `EOF`)に刻まれ、構文木は `SelectStmt{Table: users, Columns: [name], Where: id = 2}` という形にまとまっています。バイトコードの一歩手前まで来ました。Code Generator(構文木をバイトコードへ変換する処理)は次章の仕事です。

## 9.8　まとめ

- SQL 文字列は `Tokenize` でトークン列に、`Parse` でトークン列から構文木に変換される。この 2 段階は pager にも btree にも依存しない純粋なテキスト処理であり、データベースファイルが存在しなくても動く
- 再帰下降パーサは「文法規則 1 つ = 関数 1 つ」という単純な原則で書かれており、`peek` / `next` / `expectXxx` という 3 種の道具だけで、9.2 節の文法表とコードの行の並びが 1:1 に対応する
- minidb が対応する SQL は `CREATE TABLE` / `INSERT` / `SELECT` / `UPDATE` / `DELETE` と、単一比較の `WHERE` に絞られている。`AND` / `OR` や `JOIN` を持たないこの割り切りが、本章のパーサをシンプルに保っている
- テーブル駆動テストは、純粋関数の入出力を検証するのに Go では標準的な書き方であり、ケースを増やす保守コストが低い

構文木は、しょせん「言葉の形」にすぎません。`CreateTableStmt` や `SelectStmt` を手にしても、まだテーブルは 1 つも作られていませんし、1 行のデータも挿入されていません。次章では、今の Alice のレコード `[]byte("Alice,30")` という手作りのバイト列を、列の型を持つ本物のレコード形式に置き換え、この構文木を一連の命令へ変換して実行する VM を設計します。
