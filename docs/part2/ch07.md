リーフが割れると、親には「(セパレータ, 新ページ)」という 1 組の情報が届きます。親がそれをセル列に組み込んだ結果、親自身があふれれば親も割れ、さらに上へ同じ情報が伝わる — この電話連鎖がルートまで達すると、最後にルート自身が割れて**木の高さが 1 増えます**。「木は下に伸びるのではなく上に伸びる」という第 5 章 5.2 節の伏線を、ここで実装として回収します。

実装は 3 つの部品に分かれます。

- **リーフの分割**(`splitLeaf`) — あふれたリーフを 2 枚に分ける
- **分割の親への伝播**(`insertIntoInterior` と、内部ノード自身の分割 `splitInterior`) — 子の分割を親のセル列に組み込み、親自身もあふれれば分割する
- **ルート分割**(新しい `Insert`) — 伝播が根まで達したら、新しいルートを作って木を 1 段高くする

この章を経て、`btree.go` は 217 行から 582 行に増えます。ただし増えた部分のすべてが新規というわけではありません。`leaf` 型のアクセサ群・`findSlot`・`leaf.insert`・`initLeaf`、そして `Open` は**第 6 章のまま**変わっていません。第 6 章の 5 本のテスト(`TestInsertAndSearch` など)もそのまま生き残ります。本章で掲載するのは、これらの土台の上に積み増された「分割」まわりの部品だけです。なお解説の都合上、掲載順は実際の `btree.go` 内の並びとは異なる箇所があります。完成形は `code/ch07/btree/btree.go` を参照してください。

まず、新しく追加された定数と、意味が変わった 2 つのコメント/エラーメッセージから見ていきます。

**btree/btree.go(1) — パッケージ宣言・定数・エラー・BTree 構造体**

```go
// Package btree は minidb のテーブル用 B-Tree を担当する。
// リーフページが満杯になると分割し、内部ノードを介した複数ページの
// 木構造へと成長する。
package btree

import (
	"encoding/binary"
	"errors"
	"slices"
	"sort"

	"minidb/pager"
)

const (
	leafPageType    = 0x0d // SQLite のテーブルリーフと同じ値
	leafHeaderSize  = 8    // 種別(1) + セル数(2) + セル本体開始(2) + 予約(3)
	cellPointerSize = 2
	// leafCellOverhead はセル 1 つあたりのキーと値の長さのバイト数。
	leafCellOverhead = 10 // キー(8) + 値の長さ(2)

	// MaxValueSize は 1 セルがページに収まるための値サイズ上限。
	MaxValueSize = pager.PageSize - leafHeaderSize - cellPointerSize - leafCellOverhead

	interiorPageType   = 0x05 // SQLite のテーブル内部ノードと同じ値
	interiorHeaderSize = 12   // 種別(1) + セル数(2) + セル本体開始(2) + 右端の子(4) + 予約(3)
	interiorCellSize   = 12   // キー(8) + 子ページ番号(4)、内部ノードのセルは固定長

	// maxInteriorCells は 1 ページに収まる内部ノードのセル数の上限。
	maxInteriorCells = (pager.PageSize - interiorHeaderSize) / (interiorCellSize + cellPointerSize)
)

var (
	ErrKeyNotFound   = errors.New("キーが見つかりません")
	ErrDuplicateKey  = errors.New("キーが重複しています")
	ErrValueTooLarge = errors.New("値が大きすぎます")
	ErrPageFull      = errors.New("ページに空きがありません")
)

// BTree はキーと値の組を管理する索引構造。
// ルートページ番号は木が成長する(ルートが割れる)たびに変わる。
type BTree struct {
	pg   *pager.Pager
	root pager.PageID
}

```

package doc コメントが「リーフページ 1 枚だけからなる木を扱う」(第 6 章)から「内部ノードを介した複数ページの木構造へと成長する」(本章)に変わりました。import に `slices` が増えているのは、7.4 節で使う `slices.Insert` のためです。

`const` ブロックには内部ノード用の定数が 4 つ増えています。`interiorPageType = 0x05` は第 5 章の設計どおり SQLite のテーブル内部ノードと同じ値、`interiorHeaderSize = 12` はヘッダのバイト数(種別 1 + セル数 2 + セル本体開始 2 + 右端の子 4 + 予約 3)、`interiorCellSize = 12` は内部ノードのセル 1 つのバイト数(キー 8 + 子ページ番号 4)です。リーフのセルは値の長さぶん可変長でしたが、内部ノードのセルは**固定長**である点が、7.5 節で効いてきます。`maxInteriorCells` はその固定長セルとポインタから逆算した、1 ページに収まるセル数の上限です。

`ErrPageFull` のメッセージからは「(分割は第 7 章で実装)」という一文が消えました。分割を実装した今、このエラーは「今の実装の限界」ではなく「(7.3 節の warn で触れる極端な場合を除き)本来起きないはずの異常」に意味が変わっています。`BTree` のコメントも「ルートが常にリーフページ」から「ルートページ番号は木が成長するたびに変わる」に変わりました。ここが本章の実装のいちばんの外形的な変化です — 木が育つと、ルートの居場所そのものが動きます(詳しくは 7.6 節)。

## 7.2　内部ノードを Go の型にする

第 5 章の内部ページレイアウト表(5.6 節)を、`leaf` 型と対になる `interior` 型として実装します。

**btree/btree.go(2) — interior 型・アクセサ群・initInterior・appendCell・findChild**

```go
// interior は内部ページ 1 枚を薄くラップする。
//
// ページレイアウト:
//
//	オフセット 0    : 種別(0x05 固定)
//	オフセット 1-2  : セル数(ビッグエンディアン uint16)
//	オフセット 3-4  : セル本体開始オフセット(ビッグエンディアン uint16)
//	オフセット 5-8  : 右端の子ページ番号(ビッグエンディアン uint32)
//	オフセット 9-11 : 予約領域
//	オフセット 12-  : セルポインタ配列(各 2 バイト、セル数ぶん)
//	...
//	末尾から手前へ  : セル本体(キー 8 バイト + 子ページ番号 4 バイト、固定 12 バイト)
//
// セル i の子が指す部分木のキーはすべて「セル i のキー以下」である。
// 右端の子はどのセルのキーよりも大きいキーを持つ。セルはキー昇順に並ぶ。
type interior struct {
	page *pager.Page
}

// initInterior はページをセル数 0 の内部ノードとして初期化する。
// rightmost には初期状態での右端の子ページ番号を渡す。
func initInterior(page *pager.Page, rightmost pager.PageID) {
	page.Data[0] = interiorPageType
	it := interior{page: page}
	it.setCellCount(0)
	it.setContentStart(pager.PageSize)
	it.setRightmost(rightmost)
}

func (it interior) cellCount() int {
	return int(binary.BigEndian.Uint16(it.page.Data[1:3]))
}

func (it interior) setCellCount(n int) {
	binary.BigEndian.PutUint16(it.page.Data[1:3], uint16(n))
}

func (it interior) contentStart() int {
	return int(binary.BigEndian.Uint16(it.page.Data[3:5]))
}

func (it interior) setContentStart(offset int) {
	binary.BigEndian.PutUint16(it.page.Data[3:5], uint16(offset))
}

func (it interior) rightmost() pager.PageID {
	return pager.PageID(binary.BigEndian.Uint32(it.page.Data[5:9]))
}

func (it interior) setRightmost(id pager.PageID) {
	binary.BigEndian.PutUint32(it.page.Data[5:9], uint32(id))
}

func (it interior) pointerOffset(i int) int {
	return interiorHeaderSize + cellPointerSize*i
}

func (it interior) cellOffset(i int) int {
	p := it.pointerOffset(i)
	return int(binary.BigEndian.Uint16(it.page.Data[p : p+2]))
}

func (it interior) setCellOffset(i, offset int) {
	p := it.pointerOffset(i)
	binary.BigEndian.PutUint16(it.page.Data[p:p+2], uint16(offset))
}

func (it interior) keyAt(i int) uint64 {
	off := it.cellOffset(i)
	return binary.BigEndian.Uint64(it.page.Data[off : off+8])
}

func (it interior) childAt(i int) pager.PageID {
	off := it.cellOffset(i)
	return pager.PageID(binary.BigEndian.Uint32(it.page.Data[off+8 : off+12]))
}

// appendCell はセル本体開始位置の手前にセルを追記し、ポインタ配列の
// 末尾に登録する。writeCells がキー昇順のセル列を詰め直すときにだけ
// 使うので、途中への挿入は考慮しない。
func (it interior) appendCell(key uint64, child pager.PageID) {
	n := it.cellCount()
	newStart := it.contentStart() - interiorCellSize
	binary.BigEndian.PutUint64(it.page.Data[newStart:newStart+8], key)
	binary.BigEndian.PutUint32(it.page.Data[newStart+8:newStart+12], uint32(child))
	it.setContentStart(newStart)
	it.setCellOffset(n, newStart)
	it.setCellCount(n + 1)
}

// findChild は key を含みうる子のページ番号を二分探索で求める。
// 「セルのキー ≥ key」となる最初のセルの子を返す。
// どのセルのキーも key 未満なら、右端の子を返す。
func (it interior) findChild(key uint64) pager.PageID {
	n := it.cellCount()
	i := sort.Search(n, func(i int) bool {
		return it.keyAt(i) >= key
	})
	if i == n {
		return it.rightmost()
	}
	return it.childAt(i)
}
```

`interior` のコメントに書いたレイアウトは、5.6 節の表をそのまま Go のコメントへ落としたものです。オフセット 0 は種別バイト `0x05`、5〜8 は右端の子ページ番号、12 以降がセルポインタ配列 — `leaf` との違いは「右端の子」という専用フィールドを持つ点だけです。アクセサ群(`cellCount` / `setCellCount` / `contentStart` / `setContentStart` / `rightmost` / `setRightmost` / `pointerOffset` / `cellOffset` / `setCellOffset` / `keyAt` / `childAt`)は `leaf` のものと瓜二つで、同じ両端成長の作法(ポインタ配列は先頭から、セル本体は末尾から)を内部ノードにも適用しています。`appendCell` は末尾に 1 セル追記するだけの単純な操作で、あとで見る `writeCells` がセル列を詰め直すときにだけ使います。

`findChild` は `leaf.findSlot` と同じ二分探索の骨格を使っていますが、目的が違います。`findSlot` は「このキーがどこにあるか(または挿入されるべきか)」を*見つける*関数でした。`findChild` は「このキーを含みうる部分木はどの子か」を*選ぶ*関数です。`sort.Search` が返す `i` は「キー ≥ key となる最初のセル」の位置ですが、`i == n`(どのセルのキーも key 未満)のときだけは特別扱いし、**右端の子**を返します。

N 個のセル(=N 個の仕切り)は N+1 個の区間を作ります。区間の数はセルの数より必ず 1 つ多いので、最後の区間を担当する子だけは「どのセルのキーとも対応しない」独立した存在として持つ必要があります。これが**右端の子だけがセル配列の外、専用フィールドに置かれている理由**です。第 5 章の図 5-2 で見た「≤ 5」「6〜17」「18 以上」という 3 区間・2 キーの関係が、そのまま N 区間・N-1 個のセル+右端の子として一般化されています。

### 論理セル列に持ち上げる

ここで、この章を通して繰り返し使う設計方針を宣言しておきます。**内部ノードのセル列を直接ページ上でシャッフルするのではなく、いったん Go のスライスに読み出し(`readCells`)、スライス操作で組み立て直してからページへ書き戻す(`writeCells`)**、という方針です。

**btree/btree.go(3) — interiorCell・readCells・writeCells**

```go
// interiorCell は内部ノードのセル 1 つぶんの論理表現。
type interiorCell struct {
	key   uint64
	child pager.PageID
}

// readCells はページ上のセルをすべて Go のスライスへ読み出す。
func (it interior) readCells() []interiorCell {
	n := it.cellCount()
	cells := make([]interiorCell, n)
	for i := 0; i < n; i++ {
		cells[i] = interiorCell{key: it.keyAt(i), child: it.childAt(i)}
	}
	return cells
}

// writeCells はページをゼロクリアして initInterior からセル列を詰め直す。
// cells はキー昇順であること。
func (it interior) writeCells(cells []interiorCell, rightmost pager.PageID) {
	it.page.Data = [pager.PageSize]byte{}
	initInterior(it.page, rightmost)
	for _, c := range cells {
		it.appendCell(c.key, c.child)
	}
}
```

第 6 章の `leaf.insert` はページ上のポインタ配列を直接ずらして書き込む実装でした。内部ノードでも同じやり方はできますが、あえてそうしませんでした。理由は更新頻度の違いです。内部ノードが書き換わるのは*子が分割したとき*だけで、リーフのように「1 件ずつ頻繁に挿入される」対象ではありません。頻度が低いなら、ページ内オフセットを直接いじる効率よりも、`[]interiorCell` という読みやすいスライスの上で `slices.Insert` や `append` を使う明快さを優先できます。この判断が、次節以降の `insertIntoInterior` や `splitInterior` の実装をシンプルにしています。

## 7.3　リーフを割る — splitLeaf

分割の起点、リーフの分割です。

**btree/btree.go(4) — leafCell・splitLeaf**

```go
// leafCell はリーフノードのセル 1 つぶんの論理表現。分割のときだけ使う。
type leafCell struct {
	key   uint64
	value []byte
}

// splitLeaf はリーフページ l があふれて挿入できなかったときに呼ぶ。
// 挿入予定だったキーと値も含めた論理セル列をいったん組み立て、
// セル数で二等分してから元のページと新しいページに書き戻す
// (「分割してから改めて挿入」ではなく「挿入した状態で分割」する)。
//
// 戻り値は分割後の左ページの最大キー(セパレータ)と、新しいページの ID。
func splitLeaf(pg *pager.Pager, l leaf, idx int, key uint64, value []byte) (uint64, pager.PageID, error) {
	n := l.cellCount()
	cells := make([]leafCell, 0, n+1)
	for i := 0; i < idx; i++ {
		cells = append(cells, leafCell{key: l.keyAt(i), value: append([]byte(nil), l.valueAt(i)...)})
	}
	cells = append(cells, leafCell{key: key, value: value})
	for i := idx; i < n; i++ {
		cells = append(cells, leafCell{key: l.keyAt(i), value: append([]byte(nil), l.valueAt(i)...)})
	}

	// 左に入れる件数。奇数個は左を 1 件多くする。
	mid := (len(cells) + 1) / 2

	rightPage, err := pg.Allocate()
	if err != nil {
		return 0, 0, err
	}
	initLeaf(rightPage)
	right := leaf{page: rightPage}

	// 左は元のページをゼロクリアしてから詰め直す。
	// 値は上で cells にコピー済みなので、ここで元のバイト列を潰してよい。
	l.page.Data = [pager.PageSize]byte{}
	initLeaf(l.page)
	for i, c := range cells[:mid] {
		if err := l.insert(i, c.key, c.value); err != nil {
			return 0, 0, err
		}
	}
	for i, c := range cells[mid:] {
		if err := right.insert(i, c.key, c.value); err != nil {
			return 0, 0, err
		}
	}

	pg.MarkDirty(l.page.ID)
	pg.MarkDirty(rightPage.ID)

	sep := cells[mid-1].key
	return sep, rightPage.ID, nil
}
```

設計の勘所は 3 つです。

**(1) 挿入予定のセルも含めてから二等分する。** `splitLeaf` の呼び出し元は「挿入しようとしたが `ErrPageFull` で失敗した」直後です。素朴に考えると「まず既存のセルだけで分割し、そのあと改めて挿入する」という手順を思いつきますが、この方式には落とし穴があります。分割後にどちらの半分へ再挿入するかを判定し、そちらのページに*また*空きがなければ、再帰的にもう一段の処理が要ります。`splitLeaf` は挿入予定のキーと値を**含めた**論理セル列 `cells`(既存 n 件 + 新規 1 件 = n+1 件)をまず組み立て、それを二等分してから両方のページへ書き戻します。挿入込みで分けてしまえば、再挿入が失敗するケースが構造的に消えます。

**(2) セパレータ = 左の最大キー。リーフのキーはコピーも移動もしない。** `sep := cells[mid-1].key` は左に入った最後のセルのキーです。リーフのキーと値は実データそのものなので、分割してもどちらか一方のページに実体として残るだけで、セパレータとして親に渡すのはその**値のコピー**にすぎません。次節で見る内部ノードの分割はこれと対照的に、セパレータそのものを**移動**させます。

**(3) 元ページをゼロクリアする前に、値を Go のスライスへコピーしておく。** `l.valueAt(i)` が返すスライスはページの `Data` を指す生のメモリです。分割の後半で `l.page.Data = [pager.PageSize]byte{}` として元のページをまるごとゼロクリアしますが、このとき `cells` に `valueAt` の参照だけを保持していたら、値そのものが消えてしまいます。だから `append([]byte(nil), l.valueAt(i)...)` で明示的にコピーを取ってから `cells` に積んでいます。

## 7.4　子の分割を親に伝える — insertIntoInterior

リーフが分割されたら、その事実を親に伝えなければなりません。伝える情報の型と、再帰の骨格から見ていきます。

**btree/btree.go(5) — splitResult・insertInto・insertIntoLeaf・insertIntoInterior**

```go
// splitResult は子ページの分割が発生したときに親へ伝える情報。
// sep 以下のキーは分割された元のページが、sep より大きいキーは
// 新しいページ right が受け持つ。
type splitResult struct {
	sep   uint64
	right pager.PageID
}

// insertInto はページ pageID を根とする部分木にキーと値を再帰的に挿入する。
// そのページ自身が分割された場合は splitResult を返す(分割しなければ nil)。
func (t *BTree) insertInto(pageID pager.PageID, key uint64, value []byte) (*splitResult, error) {
	page, err := t.pg.Get(pageID)
	if err != nil {
		return nil, err
	}
	if isInterior(page) {
		return t.insertIntoInterior(page, key, value)
	}
	return t.insertIntoLeaf(page, key, value)
}

// insertIntoLeaf はリーフページへの挿入を試み、あふれた場合は splitLeaf で分割する。
func (t *BTree) insertIntoLeaf(page *pager.Page, key uint64, value []byte) (*splitResult, error) {
	l := leaf{page: page}
	idx, found := l.findSlot(key)
	if found {
		return nil, ErrDuplicateKey
	}

	err := l.insert(idx, key, value)
	if err == nil {
		t.pg.MarkDirty(page.ID)
		return nil, nil
	}
	if !errors.Is(err, ErrPageFull) {
		return nil, err
	}

	sep, right, err := splitLeaf(t.pg, l, idx, key, value)
	if err != nil {
		return nil, err
	}
	return &splitResult{sep: sep, right: right}, nil
}

// insertIntoInterior は key を含みうる子へ再帰的に挿入し、子が割れて
// 戻ってきた場合はこのページのセル列に (sep, 新ページ) を組み込む。
// 組み込んだ結果このページ自身があふれた場合は splitInterior で分割する。
func (t *BTree) insertIntoInterior(page *pager.Page, key uint64, value []byte) (*splitResult, error) {
	it := interior{page: page}
	childID := it.findChild(key)

	split, err := t.insertInto(childID, key, value)
	if err != nil || split == nil {
		return nil, err
	}

	cells := it.readCells()
	rightmost := it.rightmost()

	inserted := false
	for i, c := range cells {
		if c.child == childID {
			// 子 childID はセル i の子だった: セル i の子を新ページに差し替え、
			// その手前に (sep, 元の子) を挿入する。
			cells[i].child = split.right
			cells = slices.Insert(cells, i, interiorCell{key: split.sep, child: childID})
			inserted = true
			break
		}
	}
	if !inserted {
		// 子 childID は右端の子だった: 末尾に (sep, 元の子) を追加し、
		// 右端の子を新ページに差し替える。
		cells = append(cells, interiorCell{key: split.sep, child: childID})
		rightmost = split.right
	}

	if len(cells) <= maxInteriorCells {
		it.writeCells(cells, rightmost)
		t.pg.MarkDirty(page.ID)
		return nil, nil
	}

	sep, right, err := splitInterior(t.pg, it, cells, rightmost)
	if err != nil {
		return nil, err
	}
	return &splitResult{sep: sep, right: right}, nil
}
```

再帰の形はシンプルです。`insertInto` はページがリーフか内部かで `insertIntoLeaf` / `insertIntoInterior` に振り分けます。**「分割が起きたら `splitResult` が上に伝播し、起きなければ `nil` が返る」**という電話連鎖が、この再帰の骨格そのものです。`insertIntoLeaf` は第 6 章の `leaf.insert` をまず試し、`ErrPageFull` が返ってきたときだけ `splitLeaf` を呼びます。

`insertIntoInterior` は 2 段構えです。まず `findChild` で降りる先の子を選び、`insertInto` を再帰呼び出しします。子から `nil` が返れば(分割が起きなければ)何もせず終わります。`split` が返ってきたら、そのページ自身のセル列を書き換えます。

`insertIntoInterior` の中の `for i, c := range cells` ループは、この図をそのままコードにしたものです。子 `childID` を担当していたセル `i` を見つけたら、そのセルの子を新ページ `split.right` に差し替え、その**手前**に `(split.sep, childID)` を挿入します。これは「子 C はもう `sep` までのキーしか持っていない、`sep` より大きく `K` 以下のキーは新しい子 N が持っている」という**担当区間の再割り当て**です。C を指していたセルが N を指すように変わり、C の代わりにできた区間(≤ sep)を指す新しいセルが、その手前に生まれます。

`childID` がどのセルにも見つからなかった場合、それは C が**右端の子**だったケースです。この場合はセル列の末尾に `(sep, childID)` を追加し、右端の子そのものを N に差し替えます。区間の再割り当てという考え方は変わりません — 右端の子が担当していた「セル n-1 より大きい」区間が、「(sep, C) が担当する区間」と「N が担当する sep より大きい区間」に分かれるだけです。

ここで 1 つ、不変条件を確認しておきます。新しく挿入するセルのキーは常に `sep`(= 分割された子 C の中身の一部の最大値)であり、それが元々あったセルのキー `K` より必ず小さいという関係(`sep < K`)は、C が K 以下のキーだけを持っていた部分木だったことから自動的に成り立ちます。だからこの組み込みのあとも、内部ノードのセルはキーの昇順を保ち続けます。

組み込んだ結果、セル数が `maxInteriorCells` を超えたら、`splitInterior` でこのページ自身を分割します。

## 7.5　内部ノードも割れる — splitInterior

内部ノードの分割は、リーフの分割と 1 点だけ決定的に違います。

**btree/btree.go(6) — splitInterior**

```go
// splitInterior は readCells + 追加セルであふれた内部ページ it を 2 つに分割する。
// セルは固定長なので、この分割は容量不足で失敗することがない。
//
// mid 番目のセルのキーを昇格させる。リーフの分割と異なり、内部ノードの
// キーは道標に過ぎないのでコピーではなく移動でよい(左右どちらのページにも
// 残す必要がない)。
//
// 左(元のページ it)にはセル 0..mid-1 を、右端の子には mid 番目のセルの子を置く。
// 右(新しいページ)にはセル mid+1..末尾を、右端の子には元の右端の子(rightmost)を置く。
func splitInterior(pg *pager.Pager, it interior, cells []interiorCell, rightmost pager.PageID) (uint64, pager.PageID, error) {
	mid := len(cells) / 2
	sep := cells[mid].key
	promotedChild := cells[mid].child

	rightPage, err := pg.Allocate()
	if err != nil {
		return 0, 0, err
	}
	right := interior{page: rightPage}
	right.writeCells(cells[mid+1:], rightmost)

	it.writeCells(cells[:mid], promotedChild)

	pg.MarkDirty(it.page.ID)
	pg.MarkDirty(rightPage.ID)
	return sep, rightPage.ID, nil
}
```

リーフの分割ではセパレータは「左の最大キーのコピー」でした。内部ノードの分割では違います。`mid` 番目のセルの**キーはどちらのページにも残らず、そのまま親へ昇格(移動)します**。左ページは `cells[:mid]`、右ページは `cells[mid+1:]` — `mid` 番目そのものはどちらにも入っていません。

なぜコピーではなく移動でよいのか。内部ノードのキーは実データではなく、単なる道標(「この子より下はこのキー以下」)だからです。境界の情報そのものを親に引き継いでしまえば、自分の中に重複して持っておく理由がありません。子の扱いにも同じロジックが表れています。昇格したセルが持っていた子ページ番号 `promotedChild` は、左ページの新しい**右端の子**になります(左ページの最後の区間を、元々 `mid` 番目のセルが担当していた子が引き継ぐ、という意味です)。右ページの右端の子は、元のページの右端の子(`rightmost`)がそのまま横滑りします。

もう 1 点、リーフとの対比です。リーフの分割は値のサイズが可変なので `ErrPageFull` のまま失敗する可能性が理論上残りました(7.3 節の warn)。内部ノードのセルは `interiorCellSize = 12` バイト固定なので、`splitInterior` は**容量不足で失敗することがありません**。`mid := len(cells) / 2` で機械的に半分に割るだけで、必ずどちらのページにも収まります。

<div class="sqlite-note">

<span class="note-title">SQLite ではこうなっている: balance 関数群</span> 教科書的な整理では「B+Tree のリーフ分割はキーをコピー、内部ノードの分割はキーを昇格」とまとめられます。本節で実装したのはまさにこの教科書どおりの姿です。しかし本物の SQLite の実装はここまで単純ではありません。btree.c の balance 関数群は、1 対 2 の単純な分割だけでなく隣接ページへのセルの再配分(リバランス)まで含む、ソースコードの中でも最難関とされる領域です。セルを移すたびに親のポインタを更新し、フリーブロックの断片化まで気にする必要があるためです。minidb がここで止めている単純さは手抜きではなく、教科書の骨格を最短距離で実装として固めるための意図的な選択です。

## 7.6　ルートが割れて、木が伸びる — Insert

子の分割が再帰的に親へ伝わっていき、最後にルートまで到達したらどうなるか。公開 API の `Insert` を書き換えます。

**btree/btree.go(7) — Insert**

```go
// Insert はキーと値を挿入する。
// 値が MaxValueSize を超える場合は ErrValueTooLarge、
// キーが既に存在する場合は ErrDuplicateKey を返す。
func (t *BTree) Insert(key uint64, value []byte) error {
	if len(value) > MaxValueSize {
		return ErrValueTooLarge
	}

	split, err := t.insertInto(t.root, key, value)
	if err != nil {
		return err
	}
	if split == nil {
		return nil
	}

	// ルートが割れた: 新しい内部ページをルートにし、木を 1 段高くする。
	// SQLite はルートページ番号を固定して中身だけを移すが、
	// minidb では単純さを優先し、成長のたびにルートページ番号が変わる。
	newRoot, err := t.pg.Allocate()
	if err != nil {
		return err
	}
	initInterior(newRoot, split.right)
	interior{page: newRoot}.appendCell(split.sep, t.root)
	t.pg.MarkDirty(newRoot.ID)

	if err := t.pg.SetRootPage(newRoot.ID); err != nil {
		return err
	}
	t.root = newRoot.ID
	return nil
}
```

`t.insertInto(t.root, key, value)` が `nil` を返せば、分割はどこにも起きなかった(あるいは起きても途中の階層で吸収された)ということなので、そのまま終わります。`split` が返ってきたら、それは**ルートページ自身が分割した**ということです。新しい内部ページを 1 枚確保し、`split.right` を右端の子として `initInterior` で初期化し、`(split.sep, t.root)` — 「元のルート(左側)」をそのセルとして組み込みます。この新しいページを `SetRootPage` でヘッダに記録し、`t.root` を更新すれば、木は 1 段高くなります。

<div class="sqlite-note">

<span class="note-title">SQLite ではこうなっている: ルートページ番号を固定する</span> minidb はルートが割れるたびにルートページ番号そのものが変わります(この `Insert` の最後で `t.root = newRoot.ID`)。SQLite はここが違います。`sqlite_schema` テーブルの `rootpage` 列がテーブルごとのルートページ番号を記録しているため、ルート分割のたびに `rootpage` を書き換えるのは(スキーマの変更を伴う)高くつく操作です。そこで SQLite は分割時、**ルートページ番号は固定したまま、ルートだった中身を新しく確保したページへ移し**、元のルートページには新しい内部ノード(移動後のページと、通常の分割で生まれたもう 1 枚を子に持つ)だけを書き込みます。番号は動かさず、中身だけを移す — この一手間で `rootpage` を書き換えずに済ませています。

minidb がこの一手間を省けるのは、ルートの所在をヘッダページのオフセット 16〜19 という**専用の 4 バイト**に記録しているからです(第 6 章 6.2 節)。テーブルごとにルートページ番号を持つ SQLite の `sqlite_schema` と違い、minidb は木が 1 つしかないので、書き換えるコストも 4 バイトの上書きだけで済みます。「どこにルートの所在を記録しているか」という設計上の選択が、分割の実装そのものの形を決めています。

</div>

高さが 1 増える瞬間は、木全体を通じて**ルート分割のときだけ**です。リーフの分割や中間の内部ノードの分割は、木の高さを変えません(セル数が増えるだけです)。だからこそ第 5 章 5.2 節の不変条件 — _すべてのリーフが同じ深さにある_ — が常に保たれます。分割はどの階層で起きても必ずルートに向かって上に伝わり、木全体が一斉に 1 段伸びるときにしか高さは変わらないので、リーフだけが深くなったり浅くなったりすることが構造的に起こりえないのです。

## 7.7　検索と走査を木に対応させる — Search と Scan

木が複数ページ・複数階層になったので、`Search` も書き換えが必要です。

**btree/btree.go(8) — isInterior・Search・Scan・scanPage**

```go
// isInterior はページが内部ノードかどうかを、先頭バイトの種別で判定する。
func isInterior(page *pager.Page) bool {
	return page.Data[0] == interiorPageType
}

// Search はキーに対応する値を検索する。
// 見つかった場合はページの内容をコピーして返す(呼び出し側に
// ページ内部のメモリを直接握らせないため)。見つからなければ
// ErrKeyNotFound を返す。
func (t *BTree) Search(key uint64) ([]byte, error) {
	pageID := t.root
	for {
		page, err := t.pg.Get(pageID)
		if err != nil {
			return nil, err
		}
		if !isInterior(page) {
			l := leaf{page: page}
			idx, found := l.findSlot(key)
			if !found {
				return nil, ErrKeyNotFound
			}
			src := l.valueAt(idx)
			value := make([]byte, len(src))
			copy(value, src)
			return value, nil
		}
		pageID = interior{page: page}.findChild(key)
	}
}

// Scan は全キーを昇順にたどり、キーと値のペアごとに fn を呼ぶ。
// fn がエラーを返したら走査を打ち切りそのエラーを返す。
func (t *BTree) Scan(fn func(key uint64, value []byte) error) error {
	return t.scanPage(t.root, fn)
}

// scanPage はページ pageID を根とする部分木を中間順に走査する。
// 内部ノードでは、セル 0, セル 1, ..., 右端の子の順に子を辿る。
func (t *BTree) scanPage(pageID pager.PageID, fn func(key uint64, value []byte) error) error {
	page, err := t.pg.Get(pageID)
	if err != nil {
		return err
	}

	if !isInterior(page) {
		l := leaf{page: page}
		for i := 0; i < l.cellCount(); i++ {
			src := l.valueAt(i)
			value := make([]byte, len(src))
			copy(value, src)
			if err := fn(l.keyAt(i), value); err != nil {
				return err
			}
		}
		return nil
	}

	it := interior{page: page}
	for i := 0; i < it.cellCount(); i++ {
		if err := t.scanPage(it.childAt(i), fn); err != nil {
			return err
		}
	}
	return t.scanPage(it.rightmost(), fn)
}
```

新しい `Search` はループで木を降ります。各階層で `isInterior` を見て、**内部ノードなら `findChild` で次に降りる子を選び、リーフに着いたら第 6 章の `findSlot` でキーを探す**という単純な繰り返しです。第 5 章 5.5 節で 100 万行の実ファイルを解析し、「ルート → 内部 → リーフ」の**わずか 3 ページ**でどんな行にも到達できることを実測しました。あの実測結果が、このループのコードとしてそのまま姿を現しています。

`Scan` は中間順走査(in-order traversal)です。リーフなら全セルを先頭から順に、内部ノードなら**セル 0 の子 → セル 1 の子 → … → 右端の子**の順に再帰的に辿ります。セル `i` の子が担当するキー範囲は「セル `i-1` のキーより大きく、セル `i` のキー以下」でしたから、この順で子を辿れば、リーフから読み出されるキーは必ず昇順になります。今はまだ `Scan` を直接叩けるテストとツールしかありませんが、この「全件を昇順に読む」機能は第 3 部で実装する `SELECT`(全行スキャン)の土台にそのままなります。

## 7.8　テストで検証する

方針を 1 つ、明確にしておきます。第 6 章の `TestPageFull` はこの章で**引退**します。分割を実装した以上、正常な値サイズであれば `ErrPageFull` は(7.3 節の warn で触れた極端なケースを除き)もう起こりません。第 6 章では「満杯になったら止まる」ことが仕様でしたが、この章でその仕様自体が変わりました。仕様変更でテストが消える、その典型例です。

代わりに、分割まわりの振る舞いを確認する 4 本のテストと、白箱検査用のヘルパを追加します。

**btree/btree_test.go(追記) — treeHeight ヘルパ**

```go
// treeHeight は白箱検査用に、ページ id を根とする部分木の高さを
// 実際にページを辿って数える(リーフを 1 とする)。
func treeHeight(t *testing.T, pg *pager.Pager, id pager.PageID) int {
	t.Helper()
	page, err := pg.Get(id)
	if err != nil {
		t.Fatal(err)
	}
	if !isInterior(page) {
		return 1
	}

	it := interior{page: page}
	height := treeHeight(t, pg, it.rightmost())
	for i := 0; i < it.cellCount(); i++ {
		if h := treeHeight(t, pg, it.childAt(i)); h > height {
			height = h
		}
	}
	return height + 1
}
```

`treeHeight` はページを実際に辿って部分木の高さを数える、テスト専用のヘルパです。内部ノードならすべての子(通常のセルと右端の子)を再帰的に辿り、その最大値 + 1 を返します。リーフなら 1 です(`openTestTree` 自体は第 6 章から変わっていません)。

```go
// キー 1..1000 を決定的な擬似ランダム順((i*7)%1000+1、gcd(7,1000)=1 なので
// 全キーをちょうど一巡する)で挿入し、Scan で回収したキー列が

func TestManyInsertsAndScan(t *testing.T) {
	_, tree := openTestTree(t)

	const n = 1000
	for i := 0; i < n; i++ {
		key := uint64((i*7)%n) + 1
		value := fmt.Sprintf("value-%d", key)

			t.Fatalf("Insert(%d) failed: %v", key, err)
		}
	}

	var got []uint64
	err := tree.Scan(func(key uint64, value []byte) error {
		got = append(got, key)
		if want := fmt.Sprintf("value-%d", key); string(value) != want {
			t.Fatalf("Scan: key=%d value=%q, want %q", key, value, want)
		}
		return nil
	})
	if err != nil {
		t.Fatalf("Scan failed: %v", err)
	}

	if len(got) != n {
		t.Fatalf("Scan で得られた件数 = %d, want %d", len(got), n)
```

## 7.9　動かして確かめる — 木の成長を観察する

第 3 章では本物の SQLite ファイルを `inspect` で解析しました。ここでは自分の木を解析する minidb 版、`cmd/treedump` を用意します。

**cmd/treedump/main.go(全文)**

```go
// cmd/treedump/main.go
// mini.db を開き、ルートページから B-Tree をたどって各ページの種別・
// セル数・(内部ノードなら)セルの一覧と木の高さを表示するツール。
// SQLite ファイルを対象にした cmd/inspect の、minidb 版に相当する。
//
// ページの中身は btree パッケージが管理する非公開の型だが、
// バイト列としてのレイアウトは第 5・7 章で解説した固定フォーマットなので、
// inspect と同様にここでも自前でバイト列を解析する。
package main

import (
	"encoding/binary"
	"fmt"
	"os"

	"minidb/pager"
)

const (
	leafPageType       = 0x0d
	interiorPageType   = 0x05
	interiorHeaderSize = 12
	cellPointerSize    = 2

	// maxShownCells は内部ノードのセルを先頭から何個まで表示するかの上限。
	maxShownCells = 5
)

func main() {
	path := "mini.db"
	if len(os.Args) > 1 {
		path = os.Args[1]
	}

	pg, err := pager.Open(path)
	if err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}
	defer pg.Close()

	root, err := pg.RootPage()
	if err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}
	if root == 0 {
		fmt.Println("B-Tree はまだ作られていません")
		return
	}

	height, err := dumpPage(pg, root, 0)
	if err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}
	fmt.Printf("\n木の高さ: %d (ルート = ページ %d)\n", height, root)
}

// interiorCell は表示用の (キー, 子ページ番号) の組。
type interiorCell struct {
	key   uint64
	child pager.PageID
}

// dumpPage はページ id を根とする部分木を、インデントで階層を表しながら
// 表示する。戻り値はその部分木の高さ(リーフを 1 とする)。
func dumpPage(pg *pager.Pager, id pager.PageID, depth int) (int, error) {
	page, err := pg.Get(id)
	if err != nil {
		return 0, err
	}
	indent := ""
	for i := 0; i < depth; i++ {
		indent += "  "
	}

	cellCount := int(binary.BigEndian.Uint16(page.Data[1:3]))

	if page.Data[0] == leafPageType {
		fmt.Printf("%sページ %d: リーフ セル数=%d\n", indent, id, cellCount)
		return 1, nil
	}

	rightmost := pager.PageID(binary.BigEndian.Uint32(page.Data[5:9]))
	fmt.Printf("%sページ %d: 内部ノード セル数=%d 右端の子=%d\n", indent, id, cellCount, rightmost)

	cells := make([]interiorCell, cellCount)
	for i := 0; i < cellCount; i++ {
		p := interiorHeaderSize + cellPointerSize*i
		off := int(binary.BigEndian.Uint16(page.Data[p : p+2]))
		cells[i] = interiorCell{
			key:   binary.BigEndian.Uint64(page.Data[off : off+8]),
			child: pager.PageID(binary.BigEndian.Uint32(page.Data[off+8 : off+12])),
		}
	}

	shown := cells
	omitted := 0
	if len(shown) > maxShownCells {
		omitted = len(shown) - maxShownCells
		shown = shown[:maxShownCells]
	}
	for _, c := range shown {
		fmt.Printf("%s  セル: キー=%d 子=%d\n", indent, c.key, c.child)
	}
	if omitted > 0 {
		fmt.Printf("%s  ...(他 %d 件省略)\n", indent, omitted)
	}

	height := 0
	for _, c := range cells {
		h, err := dumpPage(pg, c.child, depth+1)
		if err != nil {
			return 0, err
		}
		if h > height {
			height = h
		}
	}
	h, err := dumpPage(pg, rightmost, depth+1)
	if err != nil {
		return 0, err
	}
	if h > height {
		height = h
	}
	return height + 1, nil
}
```

冒頭のコメントに書いたとおり、`treedump` が読んでいるページの中身は `btree` パッケージの非公開型(`leaf` / `interior`)であり、外部パッケージである `cmd/treedump` からは本来アクセスできません。しかしページのバイト列としてのレイアウトは、第 5 章と本章で解説したとおり**固定フォーマット**として仕様が決まっています。だから `inspect`(第 3 章)がそうしていたように、ここでも `binary.BigEndian` で自前にオフセットを読み解いています。型システムの届かないところにも意味のある構造がある、という第 3 章からの一貫した姿勢です。`dumpPage` は木を再帰的に辿りながらインデントで階層を表現し、内部ノードのセルは `maxShownCells`(5 件)を超えたら省略して残り件数だけ表示します。戻り値は部分木の高さで、リーフを 1 として再帰的に `+1` していく数え方は、7.8 節で見たテスト用の `treeHeight` とまったく同じ考え方です。

`btreedemo` も、挿入件数を引数で受け取れるように変えました。

<div class="sqlite-note">

<span class="note-title">SQLite ではこうなっている: 右端ページの分割を特別扱いする</span> minidb の `splitLeaf` は常に機械的に半分ずつへ分けます。順次(昇順)挿入だと、分割で生まれた右ページに新しいキーが際限なく追記され続け、次にそのページが満杯になったときにまた機械的に半分へ割る — その結果、平均するとおおむね半分強の充填率に落ち着きます。

SQLite はここに一手間加えています。挿入対象が**テーブル末尾(rightmost)のページ**であるとき、balance 処理はそのページを単純に二等分せず、新しいページをほぼ空の状態で作って、そこに以降の挿入を詰め続けます。テーブルへの追記が昇順(`INTEGER PRIMARY KEY` の自動採番など)であるケースは非常に多いため、この特別扱いだけでページ密度が大きく変わります。5.5 節で見た「1 ページに約 240 セル」というほぼ満杯の実測値は、この最適化があってこそのものです。minidb の素朴な二等分と実測データを見比べると、「同じ分割というアイデアでも、挿入パターンを想定した特別扱いの有無で密度が変わる」ことが数字として体感できます。

</div>

最後に、ルートページ(ページ 3、ファイルオフセット 12288 = 3 × 4096)を直接覗いてみます。

```console
$ rm -f mini.db && go run ./cmd/btreedemo 1000
mini.db に 1000 件を挿入しました
$ xxd -s 12288 -l 16 mini.db
00003000: 0500 080f a000 0000 0a00 0000 0ff4 0fe8  ................
```

先頭バイト `05` — 内部ノードです。第 3 章で本物の SQLite ファイルを解析したとき目にした、あの `table interior` の値そのものが、自分の作った B-Tree にも刻まれています。続く `00 08` はセル数 8(先ほどの treedump の「セル数=8」と一致)。`0f a0` = 4000 はセル本体開始オフセットで、`4096 − 8 × 12 = 4000`(固定 12 バイトのセルが 8 個ぶん、末尾から詰まっている)という 7.2 節の `interiorCellSize` の計算どおりです。続く `00 00 00 0a` は右端の子ページ番号 = **10**(treedump の「右端の子=10」と一致)。ここまでで 12 バイトのヘッダが終わり、続く `0f f4` `0f e8` … がセルポインタ配列の先頭 2 要素です。バイト列と、7.2 節で実装した `interiorHeaderSize = 12` という定数が、寸分違わず対応しています。

## 7.10　まとめ

- 分割は「リーフ分割 → 親への伝播(内部ノードへの組み込みと、あふれれば内部ノード自身の分割)→ ルート分割」という電話連鎖であり、木の高さが増えるのはルートが割れた瞬間だけである
- リーフの分割はセパレータを**コピー**する(キーは実データだから)。内部ノードの分割はセパレータを**昇格(移動)**する(キーは道標に過ぎないから)。この非対称性が第 7 章の核心
- ルート分割だけが高さを 1 増やすからこそ、「すべてのリーフが同じ深さ」という第 5 章の不変条件が常に保たれる
- `Scan` による中間順走査は、第 3 部で実装する `SELECT`(全行スキャン)の土台になる

挿入したものは、いつか消したくなります。第 6 章・第 7 章と積み上げてきた木に、次章では**削除**を実装します。削除はノードを空けますが、空いたページを放置すればファイルは肥大化し続けます。空いたページを再利用する仕組み(フリーリスト)と、ページキャッシュに上限を設ける LRU — 第 2 部最後の第 8 章で、この木の物語をひとまず完結させます。
