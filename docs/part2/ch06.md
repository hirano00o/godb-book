## 6.1　この章で作るもの — 高さ 1 の木

前章で設計図を描いた minidb の B-Tree を、いよいよ実装します。ただし本章で作るのは完全な B-Tree ではありません。リーフページ 1 枚だけからなる、**高さ 1 の木**です。

- `Insert` でキーと値をリーフページに書き込む
- `Search` でキーを渡してリーフページから値を取り出す
- リーフページが満杯になったら `ErrPageFull` を返して止まる

「満杯になったら止まる」は手抜きではなく、この章の意図的な区切りです。ページが埋まったときにノードを分割し、木を「上に」伸ばして高さ 2 以上にする処理は第 7 章の仕事です。第 5 章の最後で描いたロードマップ(リーフ単体 → 分割と内部ノード → 削除とフリーリスト)の第一段を、この章で確実に踏み固めます。

実装するパッケージは新設の `btree` です。この章は、第 4 章で作った `pager` の上に初めて乗る「上位層」でもあります。第 4 章で強調した*「ページャはページの中身を一切知らない」*という無関心さの対岸に立つのが `btree` パッケージであり、ページの中身(リーフの種別バイト、セルポインタ配列、セル本体)に意味を与える責任を負います。同じバイト列でも、どの層から見るかで意味がまったく変わる — それを実装しながら体感してください。

## 6.2　pager にルートの居場所を教える

木を開くには、どのページが根(ルート)なのかをどこかに永続化しておく必要があります。第 5 章で決めたとおり、ヘッダページのオフセット 16〜19 にルートページ番号を記録します。第 2 章で「予約(ゼロ)」としていたあの領域に、初めての住人が入ります。

`pager` パッケージに `RootPage` / `SetRootPage` を追加します。

**pager/pager.go(追記)**

```go
// ルートページ番号はヘッダページのオフセット 16-19 に記録する。
// 0 は「B-Tree がまだ作られていない」ことを表す。
const rootPageOffset = 16

// RootPage はヘッダページに記録された B-Tree のルートページ番号を返す。
func (p *Pager) RootPage() (PageID, error) {
	header, err := p.Get(headerPageID)
	if err != nil {
		return 0, err
	}
	return PageID(binary.BigEndian.Uint32(header.Data[rootPageOffset : rootPageOffset+4])), nil
}

// SetRootPage はルートページ番号をヘッダページに記録する。
func (p *Pager) SetRootPage(id PageID) error {
	header, err := p.Get(headerPageID)
	if err != nil {
		return err
	}
	binary.BigEndian.PutUint32(header.Data[rootPageOffset:rootPageOffset+4], uint32(id))
	header.dirty = true
	return nil
}
```

値 0 を「木がまだ作られていない」ことを示す番兵として使っています。これは第 3 章で見た SQLite のフリーリスト先頭ページ番号 0(「フリーリストは空」を意味する)とまったく同じ発想です。専用のフラグを別途持たず、絶対に現れない値(ページ 0 はヘッダページであり、B-Tree のルートには決してならない)を番兵に流用する — 省コストな設計判断が、ここでも繰り返されています。

テストも合わせて追加します。

**pager/pager_test.go(追記)**

```go
// ルートページ番号がヘッダページに正しく記録され、
// 再オープン後も読み戻せることを検証する。
func TestRootPageRoundTrip(t *testing.T) {
	path := filepath.Join(t.TempDir(), "test.db")

	p, err := Open(path)
	if err != nil {
		t.Fatal(err)
	}

	got, err := p.RootPage()
	if err != nil {
		t.Fatal(err)
	}
	if got != 0 {
		t.Fatalf("新規ファイルの RootPage = %d, want 0", got)
	}

	if err := p.SetRootPage(1); err != nil {
		t.Fatal(err)
	}
	if err := p.Close(); err != nil {
		t.Fatal(err)
	}

	p2, err := Open(path)
	if err != nil {
		t.Fatal(err)
	}
	defer p2.Close()

	got, err = p2.RootPage()
	if err != nil {
		t.Fatal(err)
	}
	if got != 1 {
		t.Fatalf("再オープン後の RootPage = %d, want 1", got)
	}
}
```

新規作成直後は `RootPage` が 0 を返し、`SetRootPage` で書き込んだ値が `Close` → `Open` をまたいで読み戻せることを確認しています。ラウンドトリップの型は第 4 章の `TestPagerRoundTrip` とまったく同じです。書いて、閉じて、開き直して、読める。この一連の流れを検証できて初めて「永続化した」と言えます。

## 6.3　リーフページを Go の型にする

ここからが本題です。`btree` パッケージを新設し、まずは全体の骨格から見ていきます。なお `btree.go` は解説の都合で「内部の部品 → 公開 API」の順に分割して掲載します。ファイル内の実際の並び(公開 API が先)とは一部順序が異なりますが、Go は宣言の順序に依存しないため、掲載順のまま写経しても問題なく動きます。完成形は `code/ch06/btree/btree.go` を参照してください。

**btree/btree.go(1) — パッケージ宣言・定数・エラー・BTree 構造体**

```go
// Package btree は minidb のテーブル用 B-Tree を担当する。
// この章ではリーフページ 1 枚だけからなる木を扱う。
// ページが満杯になったときの分割(ノード数の増加)は第 7 章で実装する。
package btree

import (
	"encoding/binary"
	"errors"
	"sort"

	"minidb/pager"
)

const (
	leafPageType    = 0x0d // SQLite のテーブルリーフと同じ値
	leafHeaderSize  = 8    // 種別(1) + セル数(2) + セル本体開始(2) + 予約(3)
	cellPointerSize = 2
	// leafCellOverhead はセル 1 つあたりのキーと値の長さのバイト数。
	leafCellOverhead = 10 // キー(8) + 値の長さ(2)

	// MaxValueSize は 1 セルがページに収まるための値サイズ上限。
	MaxValueSize = pager.PageSize - leafHeaderSize - cellPointerSize - leafCellOverhead
)

var (
	ErrKeyNotFound   = errors.New("キーが見つかりません")
	ErrDuplicateKey  = errors.New("キーが重複しています")
	ErrValueTooLarge = errors.New("値が大きすぎます")
	ErrPageFull      = errors.New("ページに空きがありません(分割は第 7 章で実装)")
)

// BTree はキーと値の組を管理する索引構造。
// 現時点ではルートが常にリーフページであり、木の高さは 1 に固定される。
type BTree struct {
	pg   *pager.Pager
	root pager.PageID
}
```

`MaxValueSize = 4096 - 8 - 2 - 10 = 4076` という式は、「1 セルだけでもページに入りきる値の上限」を表しています。ページサイズ 4096 から、リーフヘッダ 8 バイト、そのセル 1 個ぶんのポインタ 2 バイト、セル本体のキー+値長のオーバーヘッド 10 バイトを引いた残りが、値そのものに使える最大バイト数です。空のページに 1 セルだけ入れる極限を計算しているので、実際には他のセルが既にあればこれより小さい値しか入りません。

エラーは 4 種類、それぞれ役割が異なります。`ErrKeyNotFound` は検索で見つからなかったときの当然のエラー、`ErrDuplicateKey` と `ErrValueTooLarge` は呼び出し側の入力ミスを弾く事前条件違反、そして `ErrPageFull` だけが毛色が違います。これは「今のリーフ単体実装の限界」を表すエラーであり、第 7 章で分割を実装すればこの発生条件そのものが変わります。コメントに「分割は第 7 章で実装」と書き添えているのはそのためです。

続いて、リーフページをバイト列からキー・値の単位で読み書きするための型 `leaf` です。

**btree/btree.go(2) — leaf 型とアクセサ群**

```go
// leaf はリーフページ 1 枚を薄くラップし、ページ内のバイト列を
// キー・値の単位で読み書きするための型。
//
// ページレイアウト:
//
//	オフセット 0    : 種別(0x0d 固定)
//	オフセット 1-2  : セル数(ビッグエンディアン uint16)
//	オフセット 3-4  : セル本体開始オフセット(ビッグエンディアン uint16)
//	オフセット 5-7  : 予約領域
//	オフセット 8-   : セルポインタ配列(各 2 バイト、セル数ぶん)
//	...
//	末尾から手前へ  : セル本体(キー 8 バイト + 値長 2 バイト + 値)
//
// セルポインタ配列はキーの昇順を保つ。セル本体はページ末尾側から
// 詰めて書き込み、断片化を避けるためポインタ配列とは逆方向に伸びる。
type leaf struct {
	page *pager.Page
}

// initLeaf はページをセル数 0 の空のリーフとして初期化する。
func initLeaf(page *pager.Page) {
	page.Data[0] = leafPageType
	l := leaf{page: page}
	l.setCellCount(0)
	l.setContentStart(pager.PageSize)
}

func (l leaf) cellCount() int {
	return int(binary.BigEndian.Uint16(l.page.Data[1:3]))
}

func (l leaf) setCellCount(n int) {
	binary.BigEndian.PutUint16(l.page.Data[1:3], uint16(n))
}

func (l leaf) contentStart() int {
	return int(binary.BigEndian.Uint16(l.page.Data[3:5]))
}

func (l leaf) setContentStart(offset int) {
	binary.BigEndian.PutUint16(l.page.Data[3:5], uint16(offset))
}

// pointerOffset はセルポインタ配列の i 番目の要素の位置を返す。
func (l leaf) pointerOffset(i int) int {
	return leafHeaderSize + cellPointerSize*i
}

func (l leaf) cellOffset(i int) int {
	p := l.pointerOffset(i)
	return int(binary.BigEndian.Uint16(l.page.Data[p : p+2]))
}

func (l leaf) setCellOffset(i, offset int) {
	p := l.pointerOffset(i)
	binary.BigEndian.PutUint16(l.page.Data[p:p+2], uint16(offset))
}

func (l leaf) keyAt(i int) uint64 {
	off := l.cellOffset(i)
	return binary.BigEndian.Uint64(l.page.Data[off : off+8])
}

func (l leaf) valueAt(i int) []byte {
	off := l.cellOffset(i)
	vlen := int(binary.BigEndian.Uint16(l.page.Data[off+8 : off+10]))
	return l.page.Data[off+10 : off+10+vlen]
}
```

*ページはただのバイト列*です。`pager.Page` の `Data` フィールドは `[4096]byte` でしかなく、そこに何が書いてあるかを知っているのは `pager` ではなく `btree` です。`leaf` 型のコメントに書いたレイアウト図は、第 5 章の表(リーフページのレイアウト)をそのまま Go のコメントへ落とし込んだものです。型とメソッドがこの図に意味を与え、`keyAt` や `valueAt` を呼べば「n 番目のセルのキー(または値)」という*意味のある単位*でバイト列を扱えるようになります。オフセット計算の泥臭さはすべてこの層に閉じ込め、上位のコードは二度とバイトオフセットを直接触らずに済みます。

`leaf` の全メソッドはレシーバが値型 `leaf` です。中身は `*pager.Page` へのポインタ 1 つだけなので、コピーのコストは無視できるほど小さく、`leaf{page: page}` とその場で軽量にラップできます。

## 6.4　二分探索で挿入位置を探す — findSlot

セルポインタ配列がキー昇順に並んでいるなら、キーの位置探しは二分探索で済みます。

**btree/btree.go(3) — findSlot**

```go
// findSlot はキーが入るべきセルポインタ配列上の位置を二分探索で求める。
// 戻り値の bool は、そのキーが既に存在するかどうかを表す。
func (l leaf) findSlot(key uint64) (int, bool) {
	n := l.cellCount()
	i := sort.Search(n, func(i int) bool {
		return l.keyAt(i) >= key
	})
	if i < n && l.keyAt(i) == key {
		return i, true
	}
	return i, false
}
```

`sort.Search(n, f)` は「`f` を初めて満たす最小のインデックス」を二分探索で返す標準ライブラリの関数です。`f(i)` を `l.keyAt(i) >= key` にしているので、返ってくる `i` は「`key` 以上のキーが初めて現れる位置」、すなわち `key` を挿入すべき位置(既存キーがあればその位置)になります。あとは `i` が範囲内でかつそのキーが `key` と一致するかどうかを見れば、挿入位置と存在有無の 2 つの情報を 1 回の二分探索でまとめて手に入れられます。

この関数が二分探索として成立しているのは、*ポインタ配列が常に昇順である*という不変条件があるからです。`findSlot` 自身はこの不変条件を検証しません。順序を守る責任は、次に見る挿入側にあります。

## 6.5　両端成長を実装する — insert

挿入位置が決まったら、実際にセルをページへ書き込みます。

**btree/btree.go(4) — insert**

```go
// insert はセルポインタ配列の idx 番目にキーと値のセルを挿入する。
// 空き容量が足りない場合は ErrPageFull を返す。
func (l leaf) insert(idx int, key uint64, value []byte) error {
	cellSize := leafCellOverhead + len(value)
	n := l.cellCount()

	// 空き容量 = セル本体開始位置 - (ヘッダ + 既存ポインタ配列)
	free := l.contentStart() - (leafHeaderSize + cellPointerSize*n)
	if free < cellSize+cellPointerSize {
		return ErrPageFull
	}

	// セル本体はセル本体開始位置の手前に詰めて書き込む。
	newStart := l.contentStart() - cellSize
	binary.BigEndian.PutUint64(l.page.Data[newStart:newStart+8], key)
	binary.BigEndian.PutUint16(l.page.Data[newStart+8:newStart+10], uint16(len(value)))
	copy(l.page.Data[newStart+10:newStart+10+len(value)], value)
	l.setContentStart(newStart)

	// ポインタ配列の idx 以降を 1 つ後ろへずらし、挿入位置を空ける。
	for i := n; i > idx; i-- {
		l.setCellOffset(i, l.cellOffset(i-1))
	}
	l.setCellOffset(idx, newStart)
	l.setCellCount(n + 1)
	return nil
}
```

空き容量の計算式 `free := l.contentStart() - (leafHeaderSize + cellPointerSize*n)` は、「セル本体が始まる位置」から「ヘッダと既存ポインタ配列が占めている領域」を引いたものです。これが図 5-3 で見た「空き(ghost)」の幅そのものです。この空きが、これから書き込むセル本体 `cellSize` に加えて新しいポインタ 1 個ぶん `cellPointerSize` を足した分より小さければ、`ErrPageFull` を返して諦めます。ポインタ配列とセル本体は両方とも 1 個ずつ増えるので、両方の増分を空き容量と比較しなければなりません。

処理は 2 段構えです。まずセル本体を `contentStart` の手前に書き込み、`contentStart` 自体をその新しい位置に更新します。「手前に書くだけ」で済むのは、セル本体の領域が常にページ末尾から連続して詰まっているからです。削除がまだ存在しない今の実装では、途中に穴が開くことはなく、断片化は起こりません。この性質を第 8 章で削除を実装するときにどう壊れるか(あるいは壊れないよう工夫するか)が、次の伏線になります。

次にポインタ配列側です。`idx` の位置にポインタを差し込むには、`idx` から末尾までの既存ポインタを 1 つずつ後ろへずらしてから、空いた `idx` に新しいオフセットを書き込みます。これは配列への挿入そのもの、計算量は O(n) です。第 5 章で「配列は静的なデータにしか向かない、挿入は O(n)」と述べたその O(n) が、ここで実際に姿を現しています。ただし恐れるようなコストではありません。1 ページに収まるセル数は多くても数百程度で、しかもこのシフトはメモリ上の数百バイトのコピーに閉じており、ページをまたぐ I/O は一切発生しません。「木全体を辿るのが O(log n)、辿り着いた 1 ページの中だけが O(n)」という役割分担こそが B-Tree の設計そのものです。

## 6.6　木として束ねる — Open・Insert・Search

部品が揃ったので、`BTree` の公開 API を実装します。

**btree/btree.go(5) — Open・Insert・Search**

```go
// Open は pg 上の B-Tree を開く。ヘッダページにルートページ番号が
// 記録されていなければ、空のリーフページを 1 枚確保してルートにする。
func Open(pg *pager.Pager) (*BTree, error) {
	root, err := pg.RootPage()
	if err != nil {
		return nil, err
	}
	if root == 0 {
		page, err := pg.Allocate()
		if err != nil {
			return nil, err
		}
		initLeaf(page)
		pg.MarkDirty(page.ID)
		if err := pg.SetRootPage(page.ID); err != nil {
			return nil, err
		}
		root = page.ID
	}
	return &BTree{pg: pg, root: root}, nil
}

// Insert はキーと値を挿入する。
// 値が MaxValueSize を超える場合は ErrValueTooLarge、
// キーが既に存在する場合は ErrDuplicateKey、
// ページに空きがない場合は ErrPageFull を返す。
func (t *BTree) Insert(key uint64, value []byte) error {
	if len(value) > MaxValueSize {
		return ErrValueTooLarge
	}

	page, err := t.pg.Get(t.root)
	if err != nil {
		return err
	}
	l := leaf{page: page}

	idx, found := l.findSlot(key)
	if found {
		return ErrDuplicateKey
	}
	if err := l.insert(idx, key, value); err != nil {
		return err
	}
	t.pg.MarkDirty(page.ID)
	return nil
}

// Search はキーに対応する値を検索する。
// 見つかった場合はページの内容をコピーして返す(呼び出し側に
// ページ内部のメモリを直接握らせないため)。見つからなければ
// ErrKeyNotFound を返す。
func (t *BTree) Search(key uint64) ([]byte, error) {
	page, err := t.pg.Get(t.root)
	if err != nil {
		return nil, err
	}
	l := leaf{page: page}

	idx, found := l.findSlot(key)
	if !found {
		return nil, ErrKeyNotFound
	}

	src := l.valueAt(idx)
	value := make([]byte, len(src))
	copy(value, src)
	return value, nil
}
```

`Open` はルートページ番号が 0(=未作成)なら、新しいページを `Allocate` し、`initLeaf` で空のリーフとして初期化し、`SetRootPage` でヘッダに記録する、という一連の初期化を行います。2 回目以降の `Open` はこの分岐を素通りし、既存のルートをそのまま使います。「初回だけ初期化する」というこの形は、第 4 章の `Pager.Open` が新規ファイルと既存ファイルを見分けていた分岐とまったく同じ考え方です。

`Search` が値の**コピー**を返している点は、意図的な設計判断です。`l.valueAt(idx)` が返すのはページの `Data` 配列を指すスライス — つまりキャッシュ上のメモリそのものです。これをそのまま呼び出し側に渡してしまうと、あとで誰かが同じページを書き換えたとき(たとえば別のキーを `Insert` したとき)、呼び出し側が握っていたはずの値まで静かに変わってしまいます。キャッシュの中身と、外に渡す値の生存期間は別物である — この境界でコピーを取ることで、`btree` パッケージの外は安心してスライスを保持し続けられます。

`Insert` が重複キーを `ErrDuplicateKey` で弾く挙動は、SQLite で同じ rowid に対して `INSERT` したときに一意制約違反になるのと同じ役割です。既存の値を書き換えたいなら `UPDATE` を使うべきで、`INSERT` の仕事ではありません。minidb でも「上書き」は別の操作として第 12 章で導入します。今の `Insert` はあくまで新規追加専用です。

3 段に分けて読み解きます。

**1. ヘッダページ** — 1 個目の `xxd` はオフセット 0〜31。0〜7 はマジック `minidb01`、8〜11 はページサイズ `00 00 10 00` = 4096、12〜15 は総ページ数 `00 00 00 02`(ヘッダ+リーフの 2 枚)。そして本章の主役、オフセット 16〜19 が `00 00 00 01` — **ルートはページ 1** です。6.2 節で実装した `SetRootPage` が、たしかにこの位置に書き込んでいます。

**2. リーフヘッダ** — ページ 1 の先頭 16 バイトです。オフセット 4096(=ページ 1 の先頭)の 1 バイト目が `0d`。これはテーブルリーフを表すあの値で、第 3 章で本物の SQLite ファイルを解析したときに実際に目にした種別バイトそのものです。続くセル数は `00 03`(3 件)、セル本体開始オフセットは `0f cc` = 4044(ページ内オフセット。ファイル全体では 4096+4044 = 8140)。そのあとに続く 3 つの `uint16` `0f ee` `0f de` `0f cc` = **4078, 4062, 4044** が、セルポインタ配列です。この 3 つの値そのものはキーの大小と無関係な「ページ内の場所」ですが、並び順はキー 1, 2, 3 の**昇順**になっています。

**3. セル本体** — 3 個目の `xxd` は、先ほど計算した 8140(= 4096 + 4044、コンソールの `-s` に指定した位置)から 52 バイトです。真っ先に見えるのは **Carol**(キー 3)のセルです。物理的な並びはキー順ではなく**挿入順の逆**(末尾から手前へ 1 件ずつ積むため、最後に挿入した Carol が一番手前=先頭に来る)ですが、2 で見たポインタ配列はちゃんとキー 1, 2, 3 の昇順を指しています。これこそが**物理順序と論理順序を分離する**、セルポインタ配列という仕組みそのものの存在意義です。物理的にどこにあろうと、論理的な順序はポインタ配列の並びだけが担保します。

セル 1 個の中身も素読みしてみましょう。先頭の `0000 0000 0000 0003` は `uint64` のビッグエンディアンでキー **3**、続く `0008` は値の長さ **8**、そして `Carol,41` という 8 バイトの値がそのまま続きます。キー(8)+値長(2)+値(8) = 18 バイトが 1 セルの全体で、これは 6.5 節で見た `leafCellOverhead(10) + len(value)` の計算と一致します。

<span class="note-title">SQLite ではこうなっている: 本物のリーフセルはもっと複雑</span> 本物の SQLite のリーフセルは varint だらけです。ペイロード長も rowid も可変長エンコーディングで、小さい値ほど少ないバイト数で表現されます。さらにレコード本体そのものも、各列の型を表すシリアル型ヘッダを先頭に持つ独自の構造をしています(この構造は第 3 部でレコード形式を扱うときに作ります)。minidb がここで使っている「固定 8 バイトのキー + 固定 2 バイトの値長」は、その簡略版です。可変長にすればページの利用効率は上がりますが、オフセット計算のたびに先頭から読み進める必要が生まれ、実装の複雑さと引き換えになります。第 5 章の「minidb の割り切り」で明示したとおり、この単純さは本書が意図的に選んだトレードオフです。

## 6.9　まとめ

- `btree` パッケージは `pager` の上に初めて乗る上位層で、ページのバイト列に「リーフ」という意味を与える
- ルートページ番号はヘッダページのオフセット 16〜19 に永続化し、0 を「未作成」の番兵として使う
- セルポインタ配列が昇順を保つおかげで `findSlot` は二分探索でき、`insert` はセル本体を末尾側から、ポインタを先頭側から伸ばす両端成長で断片化なく書き込める
- `Search` は境界でコピーを返し、キャッシュ上のメモリを外部に握らせない設計にしている

今のリーフは 1 枚だけ、4096 バイトの器です。4 件どころか数百件を詰め込めば、いずれ `ErrPageFull` に突き当たります。次章では、満杯になったリーフを分割し、内部ノードを作って木を「上に」伸ばす処理を実装します。高さ 1 の木が高さ 2 になる、その瞬間を自分の手で作ります。
