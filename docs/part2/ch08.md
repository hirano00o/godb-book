# 第 8 章　削除と再編成 — フリーリストと LRU

<div class="chap-goal">

<span class="note-title">この章のゴール</span>

- 削除の理論(再配分・マージ)と minidb の割り切り(空ページの回収のみ)を説明できる
- フリーリストを実装し、削除で空いたページが再利用されることを確かめられる
- LRU キャッシュと「dirty は追い出さない」規約を実装し、キャッシュと参照の整合性問題を説明できる

</div>

## 8.1　消すことの難しさ

Insert の対称形のはず — そう思って手を付けると、Delete は挿入よりずっと難しいことにすぐ気づきます。教科書の B-Tree は、削除によってノードのセル数が下限を割り込むと、第 5 章 5.2 節で確認した不変条件「各ノードは一定以上埋まっている(目安として半分以上)」を守るために 2 つの手段のどちらかを取ります。隣接ノードから何セルか分けてもらう**再配分(redistribution)**か、隣接ノードと 1 つに合体する**マージ(merge)**です。マージが起きると親からセルが 1 つ消え、その結果親自身が下限を割ればさらに 1 段上でマージが起きる——分割の「電話連鎖」(第 7 章 7.1 節)と同じ形の連鎖が、削除でも上へ伝わります。ただし削除の連鎖は分割よりずっと込み入っています。左右どちらの兄弟と組むか、兄弟の側にも空きがなければどうするか、といった場合分けが増え、実装量は分割の比ではありません。

minidb はこの複雑さを、第 5 章 5.6 節の「割り切り」であらかじめ手放すと宣言していました。

> 削除時のマージ・リバランスは実装せず、理論の説明にとどめる — 本物は削除のたびにノードの結合や再配分を行い、半分埋まりの不変条件を保つ(第 8 章)

本章はこの宣言をそのまま実装に落とします。**再配分もマージもしない。ページはスカスカになるのを許す。** ただし 1 点だけは手を抜きません — **完全に空になったページは木から外し、回収します。** これだけで「全部消せばファイルの中身は全部空きに戻る」という、直感的で確かめやすい性質が成り立ちます。

<div class="sqlite-note">

<span class="note-title">SQLite ではこうなっている: フリーリストと VACUUM</span> 本物の SQLite も、削除のたびに即座にページを再編成するわけではありません。ページ内で空いた領域は**フリーブロック**(第 3 章 3.3 節でオフセット 1-2 に見た「ページ内フリーブロックの先頭オフセット」)としてページ内に留め置かれ、ページ単位で完全に空になったページは本章で実装するのと同じ**フリーリスト**で管理されます。ファイル全体を詰め直して縮める完全な再編成は、`VACUUM` コマンド(または `auto_vacuum` 設定)を明示的に実行したときだけ行われる、コストの高い操作です。「削除のたびに自動で再編成する」のではなく「空きを取っておき、必要になったら使い回す」という設計判断は、minidb も本物も同じ方向を向いています。

</div>

この章にはもう 1 つの主役がいます。第 4 章 4.2 節で交わした約束です。

> 第 1 版のキャッシュは「読んだものは全部保持」という最も単純な戦略を採ります。メモリ上限を設けた追い出し(LRU)は、B-Tree が動き出してアクセスパターンが生まれてから導入するほうが、効果を測りながら設計できます(第 2 部末で扱います)。

いよいよこれを回収します。削除とキャッシュ上限は一見無関係に見えますが、根っこでつながっています。空いたページを回収する処理も、木を書き換える処理も、すべてページャの `Get` と `Allocate` を経由します。上限のあるキャッシュの下でこれらの処理が安全に動くことを保証するのが、8.5 節の主題です。

## 8.2　道具を先に磨く — リーフも論理セル列へ

この章を経て、`btree.go` は 582 行から 788 行に、`pager.go` は 226 行から 392 行に増えます。ただし増えた部分のすべてが新規というわけではありません。`Get` / `Search` / `Scan` / `Flush` / `Close` など、木を読み出すための処理は**第 7 章のまま**変わっていません。本章で掲載するのは、この土台の上に積み増された「削除」「フリーリスト」「LRU キャッシュ」まわりの部品だけです。なお解説の都合上、掲載順は実際の `btree.go` / `pager.go` 内の並びとは異なる箇所があります。完成形は `code/ch08/btree/btree.go` と `code/ch08/pager/pager.go` を参照してください。

第 7 章 7.2 節で内部ノードに導入した設計方針 — セル列をページ上で直接シャッフルせず、いったん Go のスライスへ読み出し(`readCells`)、スライス操作で組み立て直してからページへ書き戻す(`writeCells`) — を、本章ではリーフにも適用します。理由は削除にあります。次節で見る `deleteFromLeaf` は「指定した位置のセルを 1 つ取り除いた残りを書き戻す」という操作を必要としますが、これは `slices.Delete` でスライスを操作してから `writeCells` で詰め直す、という形にするのが最も素直です。`splitLeaf` の書き直しも、この道具の恩恵を受けます。

**btree/btree.go(1) — leafCell・readCells・writeCells・leafCellsSize**

```go
// leafCell はリーフノードのセル 1 つぶんの論理表現。分割・削除のときに使う。
type leafCell struct {
	key   uint64
	value []byte
}

// readCells はページ上のセルをすべて Go のスライスへ読み出す。
func (l leaf) readCells() []leafCell {
	n := l.cellCount()
	cells := make([]leafCell, n)
	for i := 0; i < n; i++ {
		cells[i] = leafCell{key: l.keyAt(i), value: append([]byte(nil), l.valueAt(i)...)}
	}
	return cells
}

// writeCells はページをゼロクリアして initLeaf からセル列を詰め直す。
// cells はキー昇順で、合計サイズがページに収まることは呼び出し側が
// 保証する(削除は元の部分集合なので自明、分割は事前検査で確かめる)。
func (l leaf) writeCells(cells []leafCell) error {
	l.page.Data = [pager.PageSize]byte{}
	initLeaf(l.page)
	for i, c := range cells {
		if err := l.insert(i, c.key, c.value); err != nil {
			return err
		}
	}
	return nil
}

// leafCellsSize は cells をページに詰めたときに消費されるバイト数
// (セル本体とセルポインタ)の合計を返す。
func leafCellsSize(cells []leafCell) int {
	total := 0
	for _, c := range cells {
		total += leafCellOverhead + len(c.value) + cellPointerSize
	}
	return total
}
```

`leafCell` のコメントが「分割のときだけ使う」(第 7 章)から「分割・削除のときに使う」に変わった 1 語が、この節の主旨そのものです。`readCells` は、第 7 章の `splitLeaf` がその場限りのループで書いていた「セルを 1 件ずつ Go のスライスへ複製する」処理を、再利用できるメソッドに切り出したものです。`writeCells` も同様に、「ページをゼロクリア → `initLeaf` → 1 件ずつ `insert`」という第 7 章では `splitLeaf` に直接書かれていた手順を独立させています。`leafCellsSize` だけは完全に新規です。用途は次の `splitLeaf` の事前検査で使います。

続けて `splitLeaf` を書き直します。骨格 — 挿入予定のセルを含めてから二等分し、両方のページへ書き戻す — は第 7 章 7.3 節のままですが、2 点変わりました。

**btree/btree.go(2) — splitLeaf(書き換え版)**

```go
// splitLeaf はリーフページ l があふれて挿入できなかったときに呼ぶ。
// 挿入予定だったキーと値も含めた論理セル列をいったん組み立て、
// セル数で二等分してから元のページと新しいページに書き戻す
// (「分割してから改めて挿入」ではなく「挿入した状態で分割」する)。
//
// 戻り値は分割後の左ページの最大キー(セパレータ)と、新しいページの ID。
func splitLeaf(pg *pager.Pager, l leaf, idx int, key uint64, value []byte) (uint64, pager.PageID, error) {
	cells := slices.Insert(l.readCells(), idx, leafCell{key: key, value: value})

	// 左に入れる件数。奇数個は左を 1 件多くする。
	mid := (len(cells) + 1) / 2

	// 値サイズが極端に偏っていると、二等分してもどちらかのページに
	// 収まらないことがある。その場合は何も書き換えないうちに
	// ErrPageFull を返す。書き換えを始めてから失敗すると木が壊れて
	// しまうため、この検査は必ず最初に行う。
	avail := pager.PageSize - leafHeaderSize
	if leafCellsSize(cells[:mid]) > avail || leafCellsSize(cells[mid:]) > avail {
		return 0, 0, ErrPageFull
	}

	// Allocate はキャッシュの追い出しを引き起こしうるので、その前に
	// l のページを dirty にしておく(追い出し防止)。
	pg.MarkDirty(l.page.ID)
	rightPage, err := pg.Allocate()
	if err != nil {
		return 0, 0, err
	}
	initLeaf(rightPage)
	right := leaf{page: rightPage}

	// 左は元のページをゼロクリアしてから詰め直す。
	// 値は上で cells にコピー済みなので、ここで元のバイト列を潰してよい。
	if err := l.writeCells(cells[:mid]); err != nil {
		return 0, 0, err
	}
	if err := right.writeCells(cells[mid:]); err != nil {
		return 0, 0, err
	}

	pg.MarkDirty(l.page.ID)
	pg.MarkDirty(rightPage.ID)

	sep := cells[mid-1].key
	return sep, rightPage.ID, nil
}
```

**1 点目は事前検査です。** 第 7 章 7.3 節の warn で触れたとおり、値のサイズが極端に偏っていると、二等分してもどちらかのページに収まらないケースが理論上あります。第 7 章はこれを「そのまま `ErrPageFull` を返す」とだけ書いて済ませていましたが、素直に実装するとそこに落とし穴があります。`cells[:mid]` を先に元のページへ `writeCells` してしまってから `cells[mid:]` を新しいページへ書き込もうとして初めて容量不足に気づいたら、元のページはもうゼロクリアされたスケルトンに変わっており、後戻りできません。**複数ステップからなる操作を、失敗する可能性がなくなるまで検査してから初めて書き換えに着手する** — これは第 4 部でトランザクションの原子性を学ぶときに本格的に扱う考え方の、小さな先取りです。ここでは `leafCellsSize` で両半分のサイズをあらかじめ計算し、どちらか一方でも `avail`(ページの空き容量)を超えれば、ページを一切書き換えないうちに `ErrPageFull` を返します。

**2 点目は、`pg.Allocate()` を呼ぶ直前に `pg.MarkDirty(l.page.ID)` を呼ぶようになったことです。** 第 7 章の `splitLeaf` は、両方のページを書き終えたあとにまとめて `MarkDirty` を呼んでいました。本章ではその一方(`l`)だけを、`Allocate` を呼ぶ**前**に前倒ししています。なぜこの 1 行が必要になったのか — 理由は 8.5 節で LRU キャッシュの追い出し規則を実装したときに明らかになります。ここでは「分割の途中で `Allocate` を呼ぶ処理には、この前倒しが必要になる」という事実だけを覚えておいてください。

事前検査が実際に効いていることを確認するテストを追加します。

**btree/btree_test.go(追記) — TestSplitUnbalancedValues**

```go
// 値サイズが極端に偏り、二等分してもページに収まらない場合は、
// panic せず ErrPageFull が返ること、そして分割前の事前検査のおかげで
// 木が一切書き換えられていない(全キーが読める)ことを確認する。
func TestSplitUnbalancedValues(t *testing.T) {
	_, tree := openTestTree(t)

	small := bytes.Repeat([]byte("s"), 8)
	for key := uint64(1); key <= 100; key++ {
		if err := tree.Insert(key, small); err != nil {
			t.Fatalf("Insert(%d) failed: %v", key, err)
		}
	}

	huge := bytes.Repeat([]byte("h"), 4000)
	if err := tree.Insert(200, huge); !errors.Is(err, ErrPageFull) {
		t.Fatalf("巨大な値の Insert error = %v, want ErrPageFull", err)
	}

	// 失敗した挿入は木に何の変更も残していない。
	for key := uint64(1); key <= 100; key++ {
		if _, err := tree.Search(key); err != nil {
			t.Fatalf("ErrPageFull 後の Search(%d) failed: %v", key, err)
		}
	}
	if err := tree.Insert(101, small); err != nil {
		t.Fatalf("ErrPageFull 後の通常の Insert failed: %v", err)
	}
}
```

8 バイトの小さい値を 100 件挿入したあと、4000 バイトの巨大な値を挿入して分割を誘発します。二等分しても 4000 バイトの値 1 件だけで既にページの空き容量を超えるので、必ず `ErrPageFull` になります。ここで確認したいのは、失敗が起きても panic しないことだけではありません。**失敗した直後、既存の 100 件が 1 件も欠けずに検索できること**、そして**その後の通常の挿入が問題なく続けられること**まで確認しています。事前検査のおかげで、書き換えが始まる前に失敗が確定するので、木は「何も起きなかった」ときとまったく同じ状態を保ち続けます。

## 8.3　空きページを取っておく — フリーリスト

第 3 章で本物の SQLite のファイルヘッダを解析したとき、こう予告していました。

> **フリーリスト**は、レコード削除などで不要になったページを捨てずに「空きページの連結リスト」として取っておく仕組みです。ファイルは一度伸びたら基本的に縮まず、空きは再利用される — この設計は第 8 章(削除)で minidb にも導入します。

その伏線を、自分のフォーマットで回収します。まずヘッダページのレイアウトに、フリーリスト用の 2 フィールドを追加します。

**pager/pager.go(1) — initHeader・loadHeader(ヘッダレイアウト更新)**

```go
// initHeader はヘッダページを初期化してディスクに書き込む。
// レイアウト:
//
//	オフセット 0-7  : マジック文字列 "minidb01"
//	オフセット 8-11 : ページサイズ(ビッグエンディアン uint32)
//	オフセット 12-15: 総ページ数(ビッグエンディアン uint32)
//	オフセット 16-19: ルートページ番号(ビッグエンディアン uint32)
//	オフセット 20-23: フリーリスト先頭ページ番号(ビッグエンディアン uint32、0=空)
//	オフセット 24-27: フリーリストのページ数(ビッグエンディアン uint32)
func (p *Pager) initHeader() error {
	page := &Page{ID: headerPageID}
	copy(page.Data[0:8], Magic)
	binary.BigEndian.PutUint32(page.Data[8:12], PageSize)

	p.numPages = 1 // ヘッダページ自身
	binary.BigEndian.PutUint32(page.Data[12:16], p.numPages)

	p.cache[headerPageID] = page
	p.touch(headerPageID)
	page.dirty = true
	return p.Flush()
}

// loadHeader は既存ファイルのヘッダページを読み込んで検証する。
func (p *Pager) loadHeader() error {
	page, err := p.readPage(headerPageID)
	if err != nil {
		return err
	}
	if string(page.Data[0:8]) != Magic {
		return errors.New("minidb ファイルではありません")
	}
	if got := binary.BigEndian.Uint32(page.Data[8:12]); got != PageSize {
		return fmt.Errorf("ページサイズが不一致: file=%d, build=%d", got, PageSize)
	}
	p.numPages = binary.BigEndian.Uint32(page.Data[12:16])
	p.cache[headerPageID] = page
	p.touch(headerPageID)
	return nil
}
```

追加されたのはオフセット 20-23(フリーリスト先頭ページ番号)と 24-27(フリーリストのページ数)の 2 フィールドです。関数の中身自体はほぼ変わっていません(`p.touch(headerPageID)` という 1 行が両方の関数に増えていますが、これはヘッダページ自身も LRU の管理対象にするという 8.5 節の話です。ここではレイアウトのコメント更新にだけ注目してください)。

次に、実際にページを確保・解放する処理です。

**pager/pager.go(2) — Allocate・allocateNew・allocateFromFreelist**

```go
// Allocate はページを 1 枚確保して返す。フリーリストにページがあれば
// そこから再利用し(ファイルは伸びない)、空ならファイル末尾に新しい
// ページを追加する。ディスクへの書き込みは Flush まで遅延される。
func (p *Pager) Allocate() (*Page, error) {
	header, err := p.Get(headerPageID)
	if err != nil {
		return nil, err
	}
	head := PageID(binary.BigEndian.Uint32(header.Data[freelistHeadOffset : freelistHeadOffset+4]))
	if head != 0 {
		return p.allocateFromFreelist(head)
	}
	return p.allocateNew()
}

// allocateNew はファイル末尾に新しいページを追加する。
func (p *Pager) allocateNew() (*Page, error) {
	page := &Page{ID: PageID(p.numPages), dirty: true}
	p.numPages++
	p.cache[page.ID] = page
	p.touch(page.ID)

	// ヘッダページの総ページ数も更新する
	header, err := p.Get(headerPageID)
	if err != nil {
		return nil, err
	}
	binary.BigEndian.PutUint32(header.Data[12:16], p.numPages)
	header.dirty = true
	return page, nil
}

// allocateFromFreelist はフリーリスト先頭のページ head を取り出して再利用する。
func (p *Pager) allocateFromFreelist(head PageID) (*Page, error) {
	page, err := p.Get(head)
	if err != nil {
		return nil, err
	}
	next := binary.BigEndian.Uint32(page.Data[0:4])
	// この直後の Get(headerPageID) で追い出しが起こっても page 自身が
	// 消えないよう、内容を書き換える前に dirty にしておく。
	p.MarkDirty(head)

	header, err := p.Get(headerPageID)
	if err != nil {
		return nil, err
	}
	binary.BigEndian.PutUint32(header.Data[freelistHeadOffset:freelistHeadOffset+4], next)
	count := binary.BigEndian.Uint32(header.Data[freelistCountOffset : freelistCountOffset+4])
	binary.BigEndian.PutUint32(header.Data[freelistCountOffset:freelistCountOffset+4], count-1)
	header.dirty = true

	page.Data = [PageSize]byte{}
	return page, nil
}
```

`Allocate` の外形は変わりません(呼び出し側からは「ページを 1 枚もらう」だけ)が、中身は分岐します。まずヘッダページからフリーリスト先頭を読み、0 でなければ(空きページがあれば)`allocateFromFreelist` で再利用し、0 なら(空きがなければ)第 6・7 章までの `Allocate` がしていた処理そのものを `allocateNew` という名前で切り出しただけです。

`allocateFromFreelist` は、フリーリスト先頭のページ `head` を `Get` し、その先頭 4 バイトを読みます。これが「次の空きページ番号」です。**解放されたページ自身が連結リストの 1 ノードとして再利用されている** — 専用のフリーリスト管理領域を別に確保するのではなく、「どうせ中身が空である解放済みページの先頭数バイトを、リストの next ポインタとして間借りする」という発想です。次の空きページ番号をヘッダのフリーリスト先頭へ書き戻し、カウントを 1 減らし、最後に `page.Data` を丸ごとゼロクリアしてから返します。呼び出し側は「まっさらな新しいページ」を期待しているので、以前の中身(旧データやリストのポインタ)を残してはいけません。

コード中のコメント「この直後の `Get(headerPageID)` で追い出しが起こっても `page` 自身が消えないよう」は、8.5 節で説明する LRU 追い出し規約の先取りです。ここでは読み飛ばしてかまいません。

解放する側です。

**pager/pager.go(3) — Free**

```go
// Free はページをフリーリストへ返却する。ページの内容は破棄され、
// 先頭 4 バイトが「次の空きページ番号」として使われる。
func (p *Pager) Free(id PageID) error {
	page, err := p.Get(id)
	if err != nil {
		return err
	}
	// この直後の Get(headerPageID) で追い出しが起こっても page 自身が
	// 消えないよう、内容を書き換える前に dirty にしておく。
	p.MarkDirty(id)
	page.Data = [PageSize]byte{}

	header, err := p.Get(headerPageID)
	if err != nil {
		return err
	}
	oldHead := binary.BigEndian.Uint32(header.Data[freelistHeadOffset : freelistHeadOffset+4])
	binary.BigEndian.PutUint32(page.Data[0:4], oldHead)

	binary.BigEndian.PutUint32(header.Data[freelistHeadOffset:freelistHeadOffset+4], uint32(id))
	count := binary.BigEndian.Uint32(header.Data[freelistCountOffset : freelistCountOffset+4])
	binary.BigEndian.PutUint32(header.Data[freelistCountOffset:freelistCountOffset+4], count+1)
	header.dirty = true
	return nil
}
```

`Free` は `allocateFromFreelist` の鏡像です。ページの内容をゼロクリアしたあと、その先頭 4 バイトに「現在のフリーリスト先頭」を書き込み(自分が次の空きページを指すようにする)、ヘッダのフリーリスト先頭を自分自身の ID に書き換え、カウントを 1 増やします。これは**スタック(LIFO)**として動く連結リストです — 最後に解放されたページが、次に `Allocate` されるときいちばん先に取り出されます。

最後に、外部から状態を覗くための公開 API です。

**pager/pager.go(4) — freelistHeadOffset・freelistCountOffset・FreelistHead・FreelistCount**

```go
// フリーリスト先頭ページ番号とページ数は、ヘッダページの
// オフセット 20-23, 24-27 に記録する。先頭 = 0 は「フリーリストが空」を表す。
// 解放されたページはオフセット 0-3 に「次の空きページ番号」を持つ
// 連結リストになる(SQLite のフリーリストの最小版。トランクページは作らない)。
const (
	freelistHeadOffset  = 20
	freelistCountOffset = 24
)

// FreelistHead はフリーリスト先頭のページ番号を返す(空なら 0)。
func (p *Pager) FreelistHead() PageID {
	header, err := p.Get(headerPageID)
	if err != nil {
		return 0
	}
	return PageID(binary.BigEndian.Uint32(header.Data[freelistHeadOffset : freelistHeadOffset+4]))
}

// FreelistCount はフリーリストに繋がっているページ数を返す。
func (p *Pager) FreelistCount() uint32 {
	header, err := p.Get(headerPageID)
	if err != nil {
		return 0
	}
	return binary.BigEndian.Uint32(header.Data[freelistCountOffset : freelistCountOffset+4])
}
```

<span class="note-title">SQLite ではこうなっている: トランクページ方式のフリーリスト</span> SQLite のフリーリストは、実はもう 1 段複雑です。本物は**トランクページ**という管理専用ページを用意し、1 枚のトランクページが複数の空きページ番号(リーフページ)をまとめて配列として保持します。トランクページ自体もチェーン状に連結されます。この方式だと、空きページの数がどれだけ増えても、フリーリスト全体を辿るための読み込み回数を抑えられます。minidb の `Free` / `allocateFromFreelist` は、トランクページを作らず「解放されたページ自身が next ポインタを 1 つだけ持つ単純連結リスト」という最小版です。空きページ数が非常に多くなると辿るコストが線形に増えますが、実装のシンプルさを優先しました。

**pager/pager_test.go(追記) — TestFreeAndReuse**

```go
// Free したページが Allocate で再利用され、その間 NumPages が
// 増えないことを確認する。フリーリストが枯渇すれば再び増える。
func TestFreeAndReuse(t *testing.T) {
	path := filepath.Join(t.TempDir(), "test.db")
	p, err := Open(path)
	if err != nil {
		t.Fatal(err)
	}
	defer p.Close()

	ids := make([]PageID, 3)
	for i := range ids {
		page, err := p.Allocate()
		if err != nil {
			t.Fatal(err)
		}
		ids[i] = page.ID
	}
	numAfterAlloc := p.NumPages()

	if err := p.Free(ids[1]); err != nil {
		t.Fatal(err)
	}
	if err := p.Free(ids[2]); err != nil {
		t.Fatal(err)
	}
	if got := p.FreelistCount(); got != 2 {
		t.Fatalf("Free 後の FreelistCount() = %d, want 2", got)
	}

	reused := make(map[PageID]bool)
	for i := 0; i < 2; i++ {
		page, err := p.Allocate()
		if err != nil {
			t.Fatal(err)
		}
		reused[page.ID] = true
	}
	if got := p.NumPages(); got != numAfterAlloc {
		t.Fatalf("フリーリスト再利用後の NumPages = %d, want %d(増えないはず)", got, numAfterAlloc)
	}
	if !reused[ids[1]] || !reused[ids[2]] {
		t.Fatalf("解放したページが再利用されていません: reused=%v", reused)
	}
	if got := p.FreelistCount(); got != 0 {
		t.Fatalf("再利用後の FreelistCount() = %d, want 0", got)
	}

	// フリーリストが空になったので、次の Allocate はファイルを伸ばす。
	if _, err := p.Allocate(); err != nil {
		t.Fatal(err)
	}
	if got := p.NumPages(); got != numAfterAlloc+1 {
		t.Fatalf("フリーリスト枯渇後の NumPages = %d, want %d", got, numAfterAlloc+1)
	}
}
```

3 枚確保 → 2 枚解放 → 2 枚再確保、という手順で `NumPages` が増えないこと(再利用が起きたこと)と `FreelistCount` の増減を確かめます。最後にフリーリストが枯渇した状態でもう 1 枚 `Allocate` すると、今度はちゃんとファイルが伸びる(`allocateNew` にフォールバックする)ことまで確認しています。

## 8.4　削除を実装する — Delete と木の収縮

道具(`readCells` / `writeCells` / `leafCellsSize` / 事前検査)とフリーリストが揃ったので、いよいよ `Delete` を実装します。まずは公開 API と、リーフの削除です。

**btree/btree.go(3) — deleteResult・Delete・deleteFrom・deleteFromLeaf**

```go
// deleteResult は子ページの変化を親へ伝える(挿入の splitResult と対になる)。
// removed と replaceWith が同時に意味を持つことはない
// (リーフは removed だけを、内部ノードは replaceWith だけを報告する)。
type deleteResult struct {
	// removed は子(リーフ)が空になったことを表す。親は該当の子への
	// ポインタをセル列から取り除き、子ページを Free してよい。
	removed bool

	// replaceWith は、子(内部ノード)がセル数 0 になり右端の子 1 枚だけを
	// 持つ状態に縮んだことを表す。0 以外の値のときは、親は子ページへの
	// ポインタをこのページ番号に差し替え、縮んだ子ページを Free してよい。
	// 0 は「差し替え不要」を表す(ページ 0 はヘッダページ専用で
	// 子ページの ID にはなり得ないので、有効な子ページ番号と衝突しない)。
	replaceWith pager.PageID
}

// Delete はキーを削除する。キーが存在しなければ ErrKeyNotFound を返す。
//
// 部分的に空いたページの再配分やマージは行わない。空になったページを
// フリーリストへ返却するだけの単純な実装であり、木の高さが縮むのは
// ルートの内部ノードがセル 0・右端の子 1 枚だけになったときに限る。
func (t *BTree) Delete(key uint64) error {
	result, err := t.deleteFrom(t.root, key)
	if err != nil {
		return err
	}
	if result == nil || result.replaceWith == 0 {
		// リーフのルートが空になった場合を含め、これ以上やることはない
		// (空の木として維持する)。
		return nil
	}

	// ルートの内部ノードが縮んだ: ルートをその子に付け替える。
	// 木の高さが縮む唯一の瞬間。
	oldRoot := t.root
	if err := t.pg.SetRootPage(result.replaceWith); err != nil {
		return err
	}
	t.root = result.replaceWith
	return t.pg.Free(oldRoot)
}

// deleteFrom はページ pageID を根とする部分木からキーを再帰的に削除する。
func (t *BTree) deleteFrom(pageID pager.PageID, key uint64) (*deleteResult, error) {
	page, err := t.pg.Get(pageID)
	if err != nil {
		return nil, err
	}
	if isInterior(page) {
		return t.deleteFromInterior(pageID, key)
	}
	return t.deleteFromLeaf(page, key)
}

// deleteFromLeaf はリーフページからキーに対応するセルを取り除く。
// キーが見つからなければ ErrKeyNotFound を返す。
func (t *BTree) deleteFromLeaf(page *pager.Page, key uint64) (*deleteResult, error) {
	l := leaf{page: page}
	idx, found := l.findSlot(key)
	if !found {
		return nil, ErrKeyNotFound
	}

	t.pg.MarkDirty(page.ID)
	cells := slices.Delete(l.readCells(), idx, idx+1)
	// 削除後のセル列は元の部分集合なので、詰め直しは必ず収まる。
	if err := l.writeCells(cells); err != nil {
		return nil, err
	}

	if len(cells) == 0 {
		return &deleteResult{removed: true}, nil
	}
	return nil, nil
}
```

`deleteResult` は、第 7 章 7.4 節の `splitResult` と見比べると意図がよくわかります。`splitResult` は「子が割れて増えた」ことを、セパレータと新しいページ番号という形で親へ伝える電話連鎖でした。`deleteResult` はその鏡像です — 「子が空になった(`removed`)」か「子(内部ノード)が縮んで置き換えが必要になった(`replaceWith`)」かを親へ伝えます。挿入が上向きに「増えた」を伝播させるのに対し、削除は上向きに「空になった/縮んだ」を伝播させる、同じ形の電話連鎖です。`removed` と `replaceWith` が同時に意味を持たない、というコメントの理由も明確です。`deleteFromLeaf` はリーフだけを担当するので必ず `removed` だけを、次に見る `deleteFromInterior` は内部ノードだけを担当するので必ず `replaceWith` だけを使います。

`Delete` の本体は薄いラッパです。`deleteFrom` が `nil` を返すか、返ってきた結果の `replaceWith` が 0 なら(リーフのルートが空になった場合を含め)何もしません — 空の木は空の木のまま維持されます。`replaceWith` が 0 でなければ、それは**ルート自身の内部ノードが縮んだ**ということです。`SetRootPage` で新しいルート(縮んだ結果残った唯一の子)をヘッダへ記録し、古いルートページを `Free` でフリーリストへ返します。**ここが第 7 章 7.6 節「ルートが割れて木が伸びる、高さが増える唯一の瞬間」の対句です。木の高さが縮むのは、ルートの内部ノードがセル 0・右端の子 1 枚だけに縮んだこの瞬間だけです。**

`deleteFromLeaf` は `findSlot` でキーの位置を見つけ、見つからなければ `ErrKeyNotFound`。見つかれば `readCells` で読み出したスライスから `slices.Delete` でそのセルを取り除き、`writeCells` で詰め直します。コメントにあるとおり「削除後のセル列は元の部分集合」なので、詰め直しが容量不足で失敗することは構造上あり得ません — だから `splitLeaf` のような事前検査はここには要りません。セル数が 0 になれば `removed: true` で「このリーフは空になった」と親へ報告します。

木を縮める本体、`deleteFromInterior` です。

**btree/btree.go(4) — deleteFromInterior**

```go
// deleteFromInterior は key を含みうる子へ再帰的に削除し、子の状態変化
// (removed / replaceWith)をこのページのセル列へ反映する。
//
// ページ自体ではなく pageID を受け取るのは insertIntoInterior と同じ理由:
// 子への再帰の間に LRU の追い出しが起こりうるため、再帰から戻った後
// セル列を書き換える前に改めて Get してページを取り直す。
func (t *BTree) deleteFromInterior(pageID pager.PageID, key uint64) (*deleteResult, error) {
	page, err := t.pg.Get(pageID)
	if err != nil {
		return nil, err
	}
	it := interior{page: page}
	childID := it.findChild(key)

	childResult, err := t.deleteFrom(childID, key)
	if err != nil || childResult == nil {
		return nil, err
	}

	// 子への再帰中に追い出されていた場合に備え、ページを取り直す。
	page, err = t.pg.Get(pageID)
	if err != nil {
		return nil, err
	}
	it = interior{page: page}
	t.pg.MarkDirty(page.ID)

	cells := it.readCells()
	rightmost := it.rightmost()

	if childResult.replaceWith != 0 {
		// 子(内部ノード)が縮んだ: 対応するポインタを差し替えるだけで、
		// このページ自身のセル数は変わらない。
		replaced := false
		for i, c := range cells {
			if c.child == childID {
				cells[i].child = childResult.replaceWith
				replaced = true
				break
			}
		}
		if !replaced {
			// 縮んだ子は右端の子だった。
			rightmost = childResult.replaceWith
		}
		it.writeCells(cells, rightmost)
		return nil, t.pg.Free(childID)
	}

	// 子(リーフ)が空になった: そのポインタごとセルを取り除く。
	removedCell := false
	for i, c := range cells {
		if c.child == childID {
			cells = slices.Delete(cells, i, i+1)
			removedCell = true
			break
		}
	}
	if !removedCell {
		// 空になった子は右端の子だった: 最後のセルの子を新しい右端の子にし、
		// そのセルを削除する。
		last := len(cells) - 1
		rightmost = cells[last].child
		cells = cells[:last]
	}
	it.writeCells(cells, rightmost)

	if err := t.pg.Free(childID); err != nil {
		return nil, err
	}

	if len(cells) == 0 {
		// 右端の子だけが残った: このページ自身が縮んだことを親へ伝える。
		return &deleteResult{replaceWith: rightmost}, nil
	}
	return nil, nil
}
```

順を追って読み解きます。

**1. 子を選んで再帰する。** `findChild` で削除対象のキーを含みうる子を選び、`deleteFrom` を再帰呼び出しします。子から `nil` が返れば(削除は起きたが子のページ構成に変化はなかった)何もせず終わります。

**2. ページを取り直す。** 子への再帰の間に LRU の追い出しが起こりうるため(詳しくは 8.5 節)、再帰前に取得した `page` は信用できません。次に見る `insertIntoInterior` とまったく同じ理由で、再帰から戻った直後に `Get` でページを取り直しています。

**3. 子(内部ノード)が縮んだ場合(`childResult.replaceWith != 0`)。** このページの直接の子が内部ノードで、その子がさらに孫の変化を吸収した結果セル 0・右端の子 1 枚に縮んだ、というケースです。このページ自身のセル数は変わりません — 対応するポインタを `childResult.replaceWith` へ差し替えるだけです。差し替え先が見つからなければ(縮んだのが右端の子だったなら)`rightmost` を差し替えます。書き戻したら、縮んだ古い子ページを `Free` します。

**4. 子(リーフ)が空になった場合。** `childResult.replaceWith == 0` の残りのケース、つまりリーフが空になったケースでは、対応するセルそのものを取り除きます。ここに**空リーフ回収の意味論**があります。セル `(K, C)` を取り除くと、`C` が担当していたキー区間は暗黙に右隣の子へ吸収されます。`findChild` は「セルのキー ≥ key となる最初のセルの子」を選ぶルールでしたから、`K` のセルが消えれば、その区間の担当は自動的に次のセルか右端の子に移ります。`C` は `K` 以下のキーを 1 件も持たない空のリーフでした。だから、以後の検索がその区間へ降りても、降りた先は「`C` を消したあとの正しい子」であり、「空だった `C` を探しに行って見つからない」という誤りは起こりません。区間の再割り当てが、削除によって正しく行われているわけです。

**5. 右端の子が空になったケース。** 対応するセルが見つからなければ(`removedCell == false`)、それは空になった子が**右端の子**だったということです。この場合はセル列の末尾のセルを取り除き、そのセルが持っていた子を新しい右端の子に昇格させます。右端の子という「セル配列の外にある特別枠」は空のままにできないので、隣の最後のセルを 1 つ削って肩代わりさせる処理です。

**6. このページ自身が空になったケース。** すべての処理のあと `len(cells) == 0` になっていれば、このページは右端の子 1 枚だけが残った状態に縮んでいます。`&deleteResult{replaceWith: rightmost}` を返し、この縮みを親へ伝えます。親はこれを受け取ると 3 のロジックでこのページ自身へのポインタを `rightmost` へ差し替え、このページを `Free` します — 本節冒頭で見た `Delete` のルート特別扱いと同じ処理が、内部ノードのどの階層でも同じロジックで再帰的に起こる、ということです。違うのはルートだけが `SetRootPage` という特別な仕上げを必要とする点だけです。

## 8.5　キャッシュに上限を — LRU と、追い出してはいけないページ

第 4 章 4.2 節で採った「読んだものは全部保持」という最も単純な戦略を、ここで卒業します。B-Tree が実際に動き、ページを読んだり書いたりするアクセスパターンが揃った今こそ、上限付きキャッシュを効果を測りながら設計できるタイミングです。

**pager/pager.go(5) — 定数・Pager 構造体・Open・SetCacheLimit**

```go

	headerPageID PageID = 0

	// これを超えたら、dirty でないページを LRU 順(最も長く参照されて

	defaultMaxCached = 64
```

```go
// Pager はページの読み書きとキャッシュを担当する。
// 上位層(B-Tree)はファイルオフセットを一切意識せず、
// PageID だけでページを取得・更新する。
//
// キャッシュは無制限に膨らまないよう LRU(Least Recently Used)で
// 上限を管理する。lru はページ参照の新しい順を保つ双方向リストで、
// 先頭が最も新しく参照されたページ、末尾が最も長く参照されていない
// ページを表す。lruIndex は PageID からリスト要素への逆引き。
type Pager struct {
	file     *os.File
	numPages uint32           // ヘッダページ含む総ページ数
	cache    map[PageID]*Page // 読み込み済みページのキャッシュ

	lru       *list.List
	lruIndex  map[PageID]*list.Element
	maxCached int
}
```

```go
// Open は minidb ファイルを開く。存在しなければ新規作成し、
// ヘッダページ(ページ 0)を初期化する。
func Open(path string) (*Pager, error) {
	file, err := os.OpenFile(path, os.O_RDWR|os.O_CREATE, 0o644)
	if err != nil {
		return nil, err
	}

	p := &Pager{
		file:      file,
		cache:     make(map[PageID]*Page),
		lru:       list.New(),
		lruIndex:  make(map[PageID]*list.Element),
		maxCached: defaultMaxCached,
	}

	info, err := file.Stat()
	if err != nil {
		file.Close()
		return nil, err
	}

	if info.Size() == 0 {
		// 新規ファイル: ヘッダページを作って書き込む
		if err := p.initHeader(); err != nil {
			file.Close()
			return nil, err
		}
		return p, nil
	}

	// 既存ファイル: ヘッダページを検証して総ページ数を読み取る
	if err := p.loadHeader(); err != nil {
		file.Close()
		return nil, err
	}
	return p, nil
}
```

```go

func (p *Pager) SetCacheLimit(n int) {

}
```

この 4 つは `pager.go` 内で連続していません(定数ブロックと `Pager` 構造体の間には、変更のない `PageID` / `Page` 型定義が挟まっています)。ここでは変更箇所だけを抜き出して並べています。import に `container/list` が増えています — Go 標準ライブラリの双方向連結リストです。`Pager` 構造体に増えた 3 つのフィールドのうち、`lru` は「参照の新しい順」を保つリストそのもの、`lruIndex` は `PageID` からリスト要素への逆引きマップです。逆引きがあることで、あるページが再度参照されたときに、リスト全体を走査せず `O(1)` で先頭へ移動(`MoveToFront`)できます。`maxCached` はキャッシュに保持してよいページ数の上限で、`defaultMaxCached = 64` という値そのものは(1 ページ 4096 バイトなので約 256KB 相当)本書のデモや白箱テストで追い出しを起こしやすくするための小さめの値です。`Open` はこれら 3 つのフィールドを初期化するようになっただけです。`SetCacheLimit` はコメントのとおりテスト専用の裏口で、8.6 節以降のテストで積極的に使います。

キャッシュへの参照を記録し、必要なら追い出す役目を持つ 2 つの関数です。

**pager/pager.go(6) — touch・evictIfNeeded**

```go
// touch はページ id への参照を LRU の先頭(最も新しい位置)に記録し、
// キャッシュ収容数が上限を超えていれば 1 枚だけ追い出しを試みる。
func (p *Pager) touch(id PageID) {
	if elem, ok := p.lruIndex[id]; ok {
		p.lru.MoveToFront(elem)
	} else {
		p.lruIndex[id] = p.lru.PushFront(id)
	}
	p.evictIfNeeded(id)
}

// evictIfNeeded はキャッシュ収容数が上限を超えている場合、LRU の末尾から
// 辿って最初に見つかった dirty でないページを 1 枚追い出す。dirty な
// ページは書き換え中(または未書き戻し)なので絶対に追い出さない。
// また justUsed(たった今参照され、これから呼び出し側に渡るページ)も
// 追い出さない — 他の全ページが dirty のとき、追い出せる唯一の clean な
// ページが「今まさに返そうとしているページ自身」になってしまうため。
// すべて追い出せないなら何もしない(あくまでソフトな上限)。
func (p *Pager) evictIfNeeded(justUsed PageID) {
	if len(p.cache) <= p.maxCached {
		return
	}
	for e := p.lru.Back(); e != nil; e = e.Prev() {
		id := e.Value.(PageID)
		if id == justUsed {
			continue
		}
		page, ok := p.cache[id]
		if !ok || page.dirty {
			continue
		}
		delete(p.cache, id)
		delete(p.lruIndex, id)
		p.lru.Remove(e)
		return
	}
}
```

`touch` は `Get` が呼ばれるたびに(キャッシュヒットでもミスでも)実行されます。LRU リストの先頭 — 最も新しく参照された位置 — にそのページを移動し(すでにリストにあれば `MoveToFront`、なければ新規 `PushFront`)、続けて `evictIfNeeded` を呼びます。

`evictIfNeeded` が本章の核心です。**キャッシュ収容数が上限を超えていなければ何もしません** — あくまでソフトな上限で、超過してから初めて動きます。超えていれば、LRU リストの末尾(最も長く参照されていないページ)から手前へ辿り、**最初に見つかった dirty でないページを 1 枚だけ**追い出します。

ここに「何を追い出してはいけないか」という 3 つの規則が姿を現します。

1. **dirty なページは追い出さない。** `if !ok || page.dirty { continue }` がそれです。未書き戻しの変更を積んだページをキャッシュから消してしまえば、`Flush` するまでもなくデータが消えます。dirty なページは、次の `Flush` まで必ずキャッシュに居座り続けなければなりません。
2. **たった今 `Get` / `Allocate` で返そうとしているページ(`justUsed`)は追い出さない。** `if id == justUsed { continue }` がそれです。呼び出し側は `Get` や `Allocate` の戻り値をまだ受け取っておらず、`MarkDirty` を呼ぶ機会すらありません。もし `justUsed` 自身が追い出し候補になってしまったら — たとえば他のすべてのページが dirty で、clean(追い出せる)なページが `justUsed` しかない状況 — 呼び出し側に返そうとしているまさにそのページが、返す前にキャッシュから消え去るという事故が起こり得ます。`touch` の引数が `id` を受け取り、そのまま `evictIfNeeded` へ `justUsed` として渡されているのは、この事故を防ぐためです。
3. **上位層の規約: 書き換えの途中で `Get` / `Allocate` を呼ぶなら、対象のページを先に `MarkDirty` しておく。** これは規則 1 の帰結です。dirty なページは追い出されない — つまり **dirty はピン留めの代用として機能します**。書き換えの途中(複数ステップにまたがる操作)で `Get` や `Allocate` を呼ぶと、その内部で `touch` が走り `evictIfNeeded` が発動する可能性があります。もしそのとき自分が書き換えている最中のページがまだ clean だったら、追い出されてしまうかもしれません。だから、書き換えを始める前に対象ページを dirty にしておく — これが `MarkDirty` の意味が「書き換えたら呼ぶ」から「書き換える前に呼ぶ」へ変わった理由です。

この規約が実際に守られていることを、コードで確認しておきます。

**pager/pager.go(7) — MarkDirty(コメント更新)**

```go
// MarkDirty はページの内容を書き換えたことをページャに伝える。
// 上位層は Data を書き換える前に必ずこれを呼ぶこと。dirty なページは
// LRU 追い出しの対象から外れるので、特に「書き換えの途中で Get や
// Allocate を呼ぶ」場合(その間にキャッシュの追い出しが起こりうる)は、
// 書き換え対象のページを先に MarkDirty しておくことが必須になる。
// これを怠ると、書き換え途中のページがキャッシュから追い出され、
// 変更が失われる可能性がある。

		page.dirty = true
	}
```

`MarkDirty` の実装は 1 行も変わっていません。変わったのはコメント、つまり**意味**です。

具体例を 2 つ確認します。1 つ目は 8.2 節で伏線として残した `splitLeaf` の `MarkDirty` 前倒しです。`splitLeaf` は `Allocate` を呼ぶ直前、`pg.MarkDirty(l.page.ID)` で `l` を dirty にしています。`Allocate` はフリーリストが空なら `allocateNew` でファイルを伸ばし、その中でヘッダページを `Get` します — この `Get` が `touch` を経て `evictIfNeeded` を引き起こす可能性があります。もし `l` がまだ clean のまま `Allocate` を呼んでいたら、`l` 自身が追い出し候補になり得ました(`l` はこの時点でまだ書き換え途中 — 古い内容のまま、これから分割で書き換えられる予定のページです)。追い出されれば、そのあと `l.writeCells` で書き込む内容は、キャッシュ上の別オブジェクトへの書き込みになり、実際にはどこにも保存されないという事故になります。`splitInterior` にも同じ理由で同じ 1 行が加わっています。

**btree/btree.go(5) — splitInterior(MarkDirty 追加)**

```go
// splitInterior は readCells + 追加セルであふれた内部ページ it を 2 つに分割する。
// セルは固定長なので、この分割は容量不足で失敗することがない。
//
// mid 番目のセルのキーを昇格させる。リーフの分割と異なり、内部ノードの
// キーは道標に過ぎないのでコピーではなく移動でよい(左右どちらのページにも
// 残す必要がない)。
//
// 左(元のページ it)にはセル 0..mid-1 を、右端の子には mid 番目のセルの子を置く。
// 右(新しいページ)にはセル mid+1..末尾を、右端の子には元の右端の子(rightmost)を置く。
func splitInterior(pg *pager.Pager, it interior, cells []interiorCell, rightmost pager.PageID) (uint64, pager.PageID, error) {
	mid := len(cells) / 2
	sep := cells[mid].key
	promotedChild := cells[mid].child

	// Allocate はキャッシュの追い出しを引き起こしうるので、その前に
	// it のページを dirty にしておく(追い出し防止)。
	pg.MarkDirty(it.page.ID)
	rightPage, err := pg.Allocate()
	if err != nil {
		return 0, 0, err
	}
	right := interior{page: rightPage}
	right.writeCells(cells[mid+1:], rightmost)

	it.writeCells(cells[:mid], promotedChild)

	pg.MarkDirty(it.page.ID)
	pg.MarkDirty(rightPage.ID)
	return sep, rightPage.ID, nil
}
```

第 7 章の `splitInterior` との差分は `pg.MarkDirty(it.page.ID)` が `Allocate` の直前に 1 行増えただけです。理由は `splitLeaf` とまったく同じです。

2 つ目の例は、`insertIntoInterior` のシグネチャ変更です。第 7 章の `insertIntoInterior` は `*pager.Page` を直接受け取っていましたが、本章では `pageID` を受け取るように書き換えました。

**btree/btree.go(6) — insertIntoInterior(pageID 受け取り+再取得)**

```go
// insertIntoInterior は key を含みうる子へ再帰的に挿入し、子が割れて
// 戻ってきた場合はこのページのセル列に (sep, 新ページ) を組み込む。
// 組み込んだ結果このページ自身があふれた場合は splitInterior で分割する。
//
// ページ自体ではなく pageID を受け取るのは、子への再帰の間に LRU の
// 追い出しが起こりうるため。追い出されて再読み込みされた場合、再帰前に
// 取得した *pager.Page はキャッシュ上のオブジェクトと一致しなくなり、
// それを書き換えても変更が失われる。そのため再帰から戻った後、
// セル列を書き換える前に改めて Get してページを取り直す。
func (t *BTree) insertIntoInterior(pageID pager.PageID, key uint64, value []byte) (*splitResult, error) {
	page, err := t.pg.Get(pageID)
	if err != nil {
		return nil, err
	}
	it := interior{page: page}
	childID := it.findChild(key)

	split, err := t.insertInto(childID, key, value)
	if err != nil || split == nil {
		return nil, err
	}

	// 子への再帰中に追い出されていた場合に備え、ページを取り直す。
	page, err = t.pg.Get(pageID)
	if err != nil {
		return nil, err
	}
	it = interior{page: page}

	cells := it.readCells()
	rightmost := it.rightmost()

	inserted := false
	for i, c := range cells {
		if c.child == childID {
			// 子 childID はセル i の子だった: セル i の子を新ページに差し替え、
			// その手前に (sep, 元の子) を挿入する。
			cells[i].child = split.right
			cells = slices.Insert(cells, i, interiorCell{key: split.sep, child: childID})
			inserted = true
			break
		}
	}
	if !inserted {
		// 子 childID は右端の子だった: 末尾に (sep, 元の子) を追加し、
		// 右端の子を新ページに差し替える。
		cells = append(cells, interiorCell{key: split.sep, child: childID})
		rightmost = split.right
	}

	if len(cells) <= maxInteriorCells {
		it.writeCells(cells, rightmost)
		t.pg.MarkDirty(page.ID)
		return nil, nil
	}

	sep, right, err := splitInterior(t.pg, it, cells, rightmost)
	if err != nil {
		return nil, err
	}
	return &splitResult{sep: sep, right: right}, nil
}
```

理由はコメントのとおりです。子への再帰(`t.insertInto(childID, ...)`)の間には、子のページやそのまた先の孫のページを読み書きするための多数の `Get` / `Allocate` が呼ばれます。これが LRU の追い出しを引き起こしうる — もし自分自身のページ(`pageID`)が追い出されてしまうと、再帰の前に握っていた `*pager.Page` は、キャッシュ上の(追い出されたあと再読み込みされた)新しいオブジェクトとは別物になります。それを書き換えても、キャッシュ上の実体には反映されません。だから再帰から戻った直後、セル列を書き換える**前**に改めて `Get(pageID)` し、キャッシュの最新の実体を取り直します。8.4 節で見た `deleteFromInterior` もまったく同じ理由で同じ 2 行(再帰直後の再取得)を持っています — 「子への再帰の間に LRU の追い出しが起こりうるため」というコメントが、両者に共通しています。

<div class="sqlite-note">

<span class="note-title">SQLite ではこうなっている: ピン留め(参照カウント)</span> 本物のデータベースは、この問題を dirty フラグの流用ではなく**ピン留め(pinning)** — 参照カウントで解きます。ページを使用中の間はカウントをインクリメントし、使い終えたらデクリメントする。カウントが 0 より大きいページはキャッシュから絶対に追い出さない、というルールです。SQLite のページキャッシュ(pcache)も同様に、参照中のページを追い出し対象から外します。minidb は専用の参照カウントを持たず、「dirty = 追い出されない」という既存の性質を借用してピン留めの代用にしています。書き換え中のページはどうせ最終的に dirty にする必要があるので、これは的確な簡略化です — ただし読み取り専用の参照(たとえば `Scan` で長時間居座るページ)まではこの仕組みではピン留めできない、という限界も併せて意識しておいてください。

</div>

`MarkDirty` の意味はこうして成長してきました。第 4 章 4.3 節ではすでに小さな伏線が仕込まれていました — 「後述のジャーナルでは書き換え*前*の宣言が本質的に重要になります」「第 13 章でジャーナルを導入すると、この `MarkDirty` が『変更前のページ内容を退避するフック』へと成長します」。本章で `MarkDirty` が「書き換える前に呼ぶ」という新しい意味を獲得したのは、この伏線の**半分の回収**です — ここではまだ「追い出されないためのピン留め」という、LRU キャッシュの文脈に閉じた意味にとどまっています。第 13 章でジャーナル(WAL)を実装するとき、「書き換える前に呼ぶ」という同じ規約が「変更前の内容を退避してから初めて書き換える」という、クラッシュ耐性のための本質的な役割へ育ちます。

最後に、LRU 追い出しそのものと、dirty なページが決して追い出されないことを確認する 2 本のテストです。

**pager/pager_test.go(追記) — TestLRUEviction**

```go
// キャッシュ上限を超えるページ数を扱っても、追い出し → 再読み込みが
// 透過的に行われ、常に正しい内容が読めることを確認する。
func TestLRUEviction(t *testing.T) {
	path := filepath.Join(t.TempDir(), "test.db")
	p, err := Open(path)
	if err != nil {
		t.Fatal(err)
	}
	defer p.Close()

	p.SetCacheLimit(4)

	const n = 10
	ids := make([]PageID, n)
	for i := 0; i < n; i++ {
		page, err := p.Allocate()
		if err != nil {
			t.Fatal(err)
		}
		copy(page.Data[:], fmt.Sprintf("page-%d", i))
		p.MarkDirty(page.ID)
		ids[i] = page.ID
	}
	if err := p.Flush(); err != nil {
		t.Fatal(err)
	}

	// Flush 後は全ページが clean になり、追い出し対象になり得る。
	// 追い出しが起きても Get で正しい内容へ透過的に読み戻せることを確認する。
	for i := 0; i < n; i++ {
		page, err := p.Get(ids[i])
		if err != nil {
			t.Fatal(err)
		}
		want := fmt.Sprintf("page-%d", i)
		if !bytes.HasPrefix(page.Data[:], []byte(want)) {
			t.Fatalf("ページ %d の内容 = %q, want prefix %q", ids[i], page.Data[:len(want)], want)
		}
	}

	// 白箱検査: 同じページを繰り返し参照して他のページを追い出させ続けると、
	// キャッシュ収容数が上限付近まで縮むことを確認する。
	for i := 0; i < 3*n; i++ {
		if _, err := p.Get(ids[0]); err != nil {
			t.Fatal(err)
		}
	}
	if len(p.cache) > p.maxCached+1 {
		t.Fatalf("キャッシュサイズ = %d, 上限 %d 付近に収まっていません", len(p.cache), p.maxCached)
	}
}
```

`SetCacheLimit(4)` で上限をわざと小さくし、10 ページを確保・書き込み・`Flush` します。`Flush` 後は全ページが clean になるので、以降の `Get` で追い出しが実際に起こり得ます。それでも `Get` で読み出した内容が(追い出されて再読み込みされていても)正しいことを確認したあと、同じページを繰り返し参照してキャッシュサイズが上限付近まで縮むことまで白箱で確かめます。

**pager/pager_test.go(追記) — TestDirtyPageNeverEvicted**

```go
// dirty なページは、キャッシュ上限を超えていても絶対に追い出されない
// ことを白箱で確認する(すべて dirty ならソフトな上限として何もしない)。
func TestDirtyPageNeverEvicted(t *testing.T) {
	path := filepath.Join(t.TempDir(), "test.db")
	p, err := Open(path)
	if err != nil {
		t.Fatal(err)
	}
	defer p.Close()

	p.SetCacheLimit(2)

	const n = 3
	ids := make([]PageID, n)
	for i := 0; i < n; i++ {
		page, err := p.Allocate()
		if err != nil {
			t.Fatal(err)
		}
		copy(page.Data[:], fmt.Sprintf("dirty-%d", i))
		p.MarkDirty(page.ID)
		ids[i] = page.ID
	}

	// 追い出しを誘発するため Get を繰り返す。すべて dirty のままなので、
	// 追い出せるページが 1 枚もなく何も起こらないはず。
	for round := 0; round < 5; round++ {
		for i := 0; i < n; i++ {
			if _, err := p.Get(ids[i]); err != nil {
				t.Fatal(err)
			}
		}
	}

	// 白箱検査: Flush 前でも、dirty な 3 ページはすべてキャッシュに残っている。
	for i := 0; i < n; i++ {
		page, ok := p.cache[ids[i]]
		if !ok {
			t.Fatalf("dirty なページ %d がキャッシュから消えています", ids[i])
		}
		if !page.dirty {
			t.Fatalf("ページ %d が dirty ではありません", ids[i])
		}
		want := fmt.Sprintf("dirty-%d", i)
		if !bytes.HasPrefix(page.Data[:], []byte(want)) {
			t.Fatalf("ページ %d の内容 = %q, want prefix %q", ids[i], page.Data[:len(want)], want)
		}
	}
}
```

上限を 2 に設定した状態で 3 ページを確保し、**どれも `Flush` せずに**(すべて dirty のまま)何度も `Get` して追い出しを誘発します。規則 1 のとおり、dirty なページは追い出し対象から除外されるので、上限を超えていても 3 ページ全部がキャッシュに残り続けます。「すべて追い出せないなら何もしない」という `evictIfNeeded` の最後の一文 — ソフトな上限という性質そのものを検証しているテストです。

そして削除を試すための新しいツール、`deletedemo` です。

**cmd/deletedemo/main.go(全文)**

```go
// cmd/deletedemo/main.go
// btree を使って mini.db からキーを削除する動作確認デモ。
// コマンドライン引数で削除件数 N を指定する(必須)。
// キー 1..N を Delete するので、cmd/btreedemo で挿入したデータを
// 削除しながら木が縮んでいく様子を cmd/treedump で観察できる。
package main

import (
	"fmt"
	"os"
	"strconv"

	"minidb/btree"
	"minidb/pager"
)

func main() {
	if len(os.Args) != 2 {
		fmt.Fprintln(os.Stderr, "使い方: deletedemo <削除件数 N>")
		os.Exit(1)
	}
	n, err := strconv.Atoi(os.Args[1])
	if err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}

	pg, err := pager.Open("mini.db")
	if err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}

	tree, err := btree.Open(pg)
	if err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}

	for k := 1; k <= n; k++ {
		if err := tree.Delete(uint64(k)); err != nil {
			fmt.Fprintln(os.Stderr, err)
			os.Exit(1)
		}
	}

	if err := pg.Close(); err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}
	fmt.Printf("mini.db からキー 1〜%d を削除しました\n", n)
}
```

`btreedemo`(第 7 章)と対になる作りです。既存の `mini.db` を開き、キー 1 から N まで `Delete` を呼ぶだけの単純なツールです。これで「挿入して育てる」→「削除して縮める」→「再挿入する」という一連の流れを、`treedump` で観察しながら追えます。

**第 1 段階: 1000 件挿入する**

```console
$ rm -f mini.db && go run ./cmd/btreedemo 1000 && go run ./cmd/treedump | tail -4

総ページ数: 11
フリーリスト: 先頭=0 ページ数=0
```

第 7 章 7.9 節で見たのと同じ木ができます。高さ 2、総ページ数 11、フリーリストはまだ空です。

**第 2 段階: 全件削除する**

```console
$ go run ./cmd/deletedemo 1000 && go run ./cmd/treedump
mini.db からキー 1〜1000 を削除しました
ページ 10: リーフ セル数=0

木の高さ: 1 (ルート = ページ 10)
総ページ数: 11
フリーリスト: 先頭=3 ページ数=9
```

キー 1〜1000 を削除すると、木は**セル数 0 のリーフ 1 枚(ページ 10)だけ**に畳まれます。高さは 2 から 1 へ収縮 — 8.4 節で見た「ルートの内部ノードが縮んだ、その一瞬」が実際に起きた証拠です。総ページ数は 11 のまま変わりませんが、フリーリストには**先頭=3、ページ数=9** — もともと木を構成していた 11 ページのうち、9 ページ(旧ルートの内部ノードと、空になった 8 枚のリーフ)がフリーリストへ回収され、生き残っているのは新しいルートになった空リーフ(ページ 10)だけです。

**第 3 段階: 再び 1000 件挿入する**

```console
$ go run ./cmd/btreedemo 1000 && go run ./cmd/treedump | tail -4
mini.db に 1000 件を挿入しました

木の高さ: 2 (ルート = ページ 9)
総ページ数: 11
フリーリスト: 先頭=0 ページ数=0
```

読み解くべき点は 3 つです。

1. **全削除で 11 ページ中 9 ページがフリーリストへ返却され、木は空リーフ 1 枚だけになりました。** 高さは 2 から 1 へ収縮しています。
2. **再挿入しても総ページ数は 11 のまま**です。フリーリストにあった 9 ページが `allocateFromFreelist` によってすべて再利用され、ファイルは 1 バイトも伸びていません。`TestReuseAfterDeleteAll` で確認したのと同じ現象が、実ファイル上でも起きています。
3. **ルートがページ 3 からページ 9 に変わりました。** これはページ番号が「確保された順」を律儀に記録している(第 7 章 7.9 節)ことの帰結です。フリーリストからの再利用はスタック(LIFO)なので、最後に解放されたページから先に取り出され、木は以前とは違うページ番号の組み合わせで組み直されます。木の**形**(高さ 2、リーフ 9 枚)は前回とまったく同じですが、それを構成する物理的なページ番号は再利用によって入れ替わっている — フリーリストが「同じ形の木を、違う場所に作り直す」働きをしていることが、この数字の変化から読み取れます。

## 8.8　まとめ

- 削除は再配分・マージという教科書の複雑さを持たず、空になったページをフリーリストへ返却するだけの単純な実装である。木の高さが縮むのは、ルートの内部ノードがセル 0・右端の子 1 枚だけに縮んだ、その一瞬だけ
- フリーリストは、解放されたページ自身の先頭 4 バイトを「次の空きページ番号」として使う連結リストである。削除と再挿入を繰り返しても、ファイルは際限なく伸び続けない
- LRU キャッシュは「dirty なページ」と「たった今使おうとしているページ」を追い出さない、2 つの例外を持つソフトな上限である。その上に「書き換えの途中で Get / Allocate を呼ぶなら先に MarkDirty」という上位層の規約が成り立つ
- `MarkDirty` は第 4 章の「書き換えたら呼ぶ」記録係から、本章で「書き換える前に呼ぶ」ピン留めの代用へ育った。第 13 章のジャーナルで、この規約はさらに本質的な役目を得る
- これで B-Tree は増える・育つ・縮むのすべてを覚えました。第 3 部ではこの木に **SQL という言葉**を教えます。今の Alice のレコードは `[]byte("Alice,30")` という手作りのバイト列にすぎませんが、そこにテーブルとカラムという意味を与えていきます。
