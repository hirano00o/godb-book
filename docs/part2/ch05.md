# 第 5 章　B-Tree の理論 — B-Tree と B+Tree、テーブル用とインデックス用

## 5.1　検索の問題をディスクの言葉で言い直す

第 1 章の壁 1(検索が遅い)を思い出してください。id でソートされた配列なら二分探索で O(log n) ですが、配列への挿入は O(n) です。配列は静的なデータにしか向かず、動的に増減するデータを高速に検索するには木構造が要ります。

メモリの上だけで考えるなら、答えはすでに知られています。平衡化した二分探索木(赤黒木など)です。ノードは「キー・値・左右の子へのポインタ」だけを持つ数十バイトの構造体で、ポインタを使って自由自在につなげます。挿入も検索も O(log n)、メモリ上ならこれで十分です。

しかしデータベースが相手にするのはメモリではなくディスクです。第 2 章で学んだとおり、ディスクは 4096 バイトの**ページ**単位でしか読み書きできません。二分探索木のノード 1 個はたかだか数十バイトですが、それを 1 個読むためだけに 4096 バイトのページを丸ごと 1 枚読み込むことになります。100 万行のテーブルに対する二分探索木の高さは log₂(10⁶) ≈ 20 — 1 件のレコードを探すのに、根から葉まで**20 回のページ読み込み**が発生する計算です。1 回のページ読み込みにマイクロ秒〜ミリ秒のオーダーがかかることを思えば(第 4 章)、この 20 回は決して無視できるコストではありません。

ここで発想を転換します。_「1 ページ読み込んだからには、そのページで最大限まで絞り込む」_。ノードをページそのものにし、1 個のノードに数十個ではなく**数百個のキーと分岐**を詰め込んでしまえばよいのです。1 ページ読むごとに候補が数百分の一に絞られるなら、100 万行でも 3〜4 回の読み込みで目的の行にたどり着けます。この「ノード = ページ、1 ノードに大量のキーを詰める多分岐の木」が **B-Tree** です。

木の「枝分かれの多さ」を**ファンアウト**(1 ノードが持つ子の数)と呼びます。ファンアウトが大きいほど木は横に太く縦に低くなり、根から葉までのページ読み込み回数(=木の高さ)が減ります。B-Tree の設計とは、突き詰めれば*ページというディスクの最小単位に、ファンアウトを最大限詰め込む工夫*なのです。

## 5.2　B-Tree の構造と不変条件

B-Tree は多分岐の平衡探索木です。各ノードはソート済みのキー列を持ち、隣り合う 2 つのキーに挟まれた子ノードは、その範囲に収まるキーだけを保持します。二分探索木の「左は小さい、右は大きい」を、そのまま N 分岐に拡張したものだと考えれば自然です。

B-Tree が検索性能を保証できるのは、次の不変条件を常に維持しているからです。

- **すべてのリーフが同じ深さにある**(完全に平衡している) — どのキーを探しても、根からリーフまでの読み込み回数は必ず一定
- **各ノードは一定以上埋まっている**(目安として半分以上) — スカスカのノードが増えて木が不必要に高くなるのを防ぐ
- **挿入・削除のあともこの 2 条件を保つ** — 木は操作のたびに自己修復する

平衡の保ち方の直観だけ、ここで先出ししておきます。B-Tree は赤黒木のように「回転」で調整するのではなく、ノードが埋まりきったら**分割**して上に伸びます。リーフが分割されればその親が子を 1 つ増やし、親も埋まっていれば親自身が分割され……という連鎖が根まで達すると、最後に**根が割れて木全体の高さが 1 増えます**。木は下に伸びるのではなく上に伸びる — この一言を覚えておいてください。分割の具体的な手順は第 7 章で自分の手で実装します。

## 5.3　B-Tree と B+Tree — 値をどこに置くか

ここまで「B-Tree」と一括りに呼んできましたが、実は値(レコード本体)をどこに置くかで 2 つの流派があります。

元祖の B-Tree(狭義)は、内部ノードにもキーと一緒にレコードを格納します。探索がキーに一致した時点で、内部ノードであってもそこで打ち切って値を返せるのが利点です。

これに対して **B+Tree** は、値をリーフにしか置きません。内部ノードはキーと子ポインタだけを持つ、純粋な道標に徹します。一見遠回りに思えますが、これには明確な利点があります。

- **内部ノードが痩せる** — レコード本体を持たない分、1 ページに詰め込めるキー数(=ファンアウト)が増える。ファンアウトが増えれば木はさらに低くなる
- **範囲走査が単純になる** — `WHERE age BETWEEN 20 AND 30` のような範囲検索は、最初の 1 件をリーフで見つけたあと、リーフを順に読み進めるだけで完結する

多くの教科書の B+Tree は、この範囲走査をさらに速くするため、リーフ同士を兄弟リンク(次のリーフへのポインタ)でつなぎます。しかし**SQLite はこのリンクを持ちません**。隣のリーフへ移動したいときは、親ノードまで戻ってから隣の子をたどります。遠回りに見えますが、リンクを持たなければ、リーフを 1 枚分割しても隣のリーフのリンクを書き換えずに済み、更新するページが増えません。第 4 部で学ぶジャーナリングでは「書き換えるページの枚数」がそのまま退避コストになるため、この身軽さが効いてきます。

<div class="sqlite-note">

<span class="note-title">SQLite ではこうなっている: 「B-Tree」の呼び方</span> SQLite のテーブル用 B-Tree は、分類上は B+Tree 型です(レコードはリーフのみに置かれ、内部ノードは rowid の道標に徹します)。ただし SQLite の公式ドキュメントもソースコードも、B-Tree と B+Tree を区別せずどちらも単に「B-Tree」と呼びます。本書もこの慣習にならい、以後 minidb の木を一貫して「B-Tree」と呼びますが、その型としては B+Tree 型であることをここで整理しておきます。

</div>

## 5.4　テーブル用とインデックス用 — 2 種類の木

第 3 章の inspect は、ページ種別として `0x02` / `0x05` / `0x0a` / `0x0d` の 4 種類を表示していました。実は SQLite は B-Tree を 2 つの異なる目的で使い分けており、この 4 種類はその組み合わせ(テーブル用 or インデックス用 × 内部 or リーフ)にほかなりません。

**テーブル用 B-Tree** — キーは **rowid**(整数)、値はレコード本体そのもの。ページ種別は `0x05`(内部)/ `0x0d`(リーフ)です。第 3 章で inspect が表示していた、あの値です。「rowid k の行をください」に答えるための木で、第 1 章の図 1-2 で VDBE と B-Tree の間を流れていた言葉がまさにこれでした。

**インデックス用 B-Tree** — キーは**列の値**(+ 同値のレコードを区別するための rowid)で、値そのものは持ちません。ページ種別は `0x02`(内部)/ `0x0a`(リーフ)です。テーブル用が「rowid → 行」の木であるのに対し、インデックス用は「**列の値 → rowid** の変換表」として働きます。

`WHERE name = 'Bob'` のような検索は、この 2 つの木のリレーで実行されます。

1. `name` 列に張られたインデックス用 B-Tree を検索し、`'Bob'` に対応する rowid を得る
2. その rowid を使ってテーブル用 B-Tree を検索し、実際の行データを取り出す

インデックスがなければ手順 1 は全行スキャンになってしまいますが、インデックス用 B-Tree があれば手順 1 自体も O(log n) で終わります。この実装は第 12 章で行います。

これで第 3 章の inspect が表示していたページ種別 4 種の意味が、すべて出揃いました。`0x05` / `0x0d` はテーブル用、`0x02` / `0x0a` はインデックス用 — 同じ B-Tree という道具が、キーの選び方と値の持ち方を変えるだけで 2 つの役割を演じ分けているのです。

## 5.5　動かして確かめる — 本物の木の高さを測る

理論はここまでにして、本物のファイルで木の高さとファンアウトを実測しましょう。使うのは第 3 章で作った `inspect` です(コードは `code/ch04` の状態のままで、この章では新しいコードは書きません)。

まず 1000 件のレコードを入れてみます。

```console
$ rm -f big.db
$ sqlite3 big.db "PRAGMA page_size = 4096; CREATE TABLE users (id INTEGER PRIMARY KEY, name TEXT, age INTEGER); WITH RECURSIVE c(x) AS (SELECT 1 UNION ALL SELECT x+1 FROM c WHERE x < 1000) INSERT INTO users(name, age) SELECT 'user' || x, x % 100 FROM c;"
$ go run ./cmd/inspect big.db
=== ファイルヘッダ ===
マジック文字列   : "SQLite format 3"
ページサイズ     : 4096 バイト
総ページ数       : 7
ジャーナル方式   : write=1 read=1 (1=rollback journal, 2=WAL)
フリーリスト     : 先頭ページ=0, ページ数=0
スキーマクッキー : 1
テキスト符号化   : 1 (1=UTF-8)

=== 各ページの B-Tree ヘッダ ===
ページ 1: 種別=table leaf(テーブルリーフ) セル数=1 セル本体開始=4004
ページ 2: 種別=table interior(テーブル内部ノード) セル数=4 セル本体開始=4072
ページ 3: 種別=table leaf(テーブルリーフ) セル数=254 セル本体開始=526
ページ 4: 種別=table leaf(テーブルリーフ) セル数=240 セル本体開始=500
ページ 5: 種別=table leaf(テーブルリーフ) セル数=240 セル本体開始=502
ページ 6: 種別=table leaf(テーブルリーフ) セル数=240 セル本体開始=500
ページ 7: 種別=table leaf(テーブルリーフ) セル数=26 セル本体開始=3706
```

ページ 1 は `sqlite_schema`(第 3 章で出てきた「メタデータもテーブル」の実体)、ページ 2〜7 が users テーブルの木です。ページ 2 の種別 `table interior` — 第 3 章の演習で「これが現れたら B-Tree の階層化の瞬間」と予告した `0x05` の正体が、ついに姿を現しました。セル数 4 の内部ノードは、右端の子を合わせて**子 5 枚**を持ちます。実際、リーフはページ 3〜7 の 5 枚。セル数を足すと 254 + 240 + 240 + 240 + 26 = **ちょうど 1000** — users テーブルの全行が、この 5 枚のリーフに過不足なく収まっています。根(ページ 2)からリーフまでで木の**高さは 2**です。

ここで電卓を叩いてみましょう。リーフ 1 枚に約 240 セル入っているということは、1 セルはおよそ 4096 ÷ 240 ≈ 17 バイト、ページヘッダとセルポインタ配列の分を差し引けばおよそ 16 バイト前後と見積もれます。`id INTEGER, name TEXT, age INTEGER` という小さなレコードなら、この見積もりは無理のない数字です。

次に、桁を 3 つ増やして 100 万件で試します。

```console
$ rm -f big.db
$ sqlite3 big.db "PRAGMA page_size = 4096; CREATE TABLE users (id INTEGER PRIMARY KEY, name TEXT, age INTEGER); WITH RECURSIVE c(x) AS (SELECT 1 UNION ALL SELECT x+1 FROM c WHERE x < 1000000) INSERT INTO users(name, age) SELECT 'user' || x, x % 100 FROM c;"
$ wc -c < big.db
21045248
$ go run ./cmd/inspect big.db | grep -c "table leaf"
5124
$ go run ./cmd/inspect big.db | grep -c "table interior"
14
$ sqlite3 big.db "SELECT rootpage FROM sqlite_schema WHERE name = 'users';"
2
```

総ページ数は 21045248 ÷ 4096 = **5138**。内訳は sqlite_schema のリーフ 1 + 内部 14 + users のリーフ 5123 です(grep の table leaf 5124 件のうち 1 件が sqlite_schema、残り 5123 件が users)。内部 14 枚は、ルート 1 枚(rootpage = 2)+ 第 2 層 13 枚という構成で、リーフ 5123 枚 ÷ 13 ≈ 1 枚あたり子 394 — つまり内部ノード 1 枚が平均 394 のファンアウトを持っています。木の構造は「ルート → 内部(13 枚) → リーフ(5123 枚)」の**高さ 3**です。

100 万行から 1 行を探すのに読むページは、ルート・内部・リーフの**わずか 3 枚**。5.1 節で見積もった二分木の約 20 回と比べると、読み込み回数は 1 桁以上少なくなっています。これがファンアウトを稼ぐことの威力です。

**表 5-1　高さとファンアウトから到達できる行数の目安**

| 高さ | 到達行数の目安 | 計算式(ファンアウト 200・リーフ 200 セルと仮定) |
| ---- | -------------- | ----------------------------------------------- |
| 2    | 約 4 万行      | 200¹ × 200 = 40,000                             |
| 3    | 約 800 万行    | 200² × 200 = 8,000,000                          |
| 4    | 約 16 億行     | 200³ × 200 = 1,600,000,000                      |

ルートから 1 段下がるごとにファンアウト倍、最後にリーフ 1 枚あたりのセル数を掛けるので、到達行数 ≈ ファンアウト^(高さ-1) × リーフ 1 枚あたりのセル数、という式で見積もれます。実測ではリーフ約 240 セル・内部ノードの分岐約 400 だったので、この表の「ファンアウト 200」はやや控えめな仮定です。それでも高さわずか 4 で 16 億行に届きます。

## 5.6　minidb の B-Tree を設計する

実測で理論を裏付けたところで、minidb 自身の B-Tree を設計します。方針はシンプルです。

- **テーブル用 B-Tree のみを実装する**(インデックス用は第 12 章で必要になった時点で追加する)
- **キーは `uint64`**、**値は可変長のバイト列**とする(値の中身、すなわちレコード形式の定義は第 3 部で行う)
- **ページ種別バイトは SQLite と同じ値を使う** — リーフ `0x0d`、内部 `0x05`。inspect で本物のファイルを読んだ知識が、そのまま自分の DB にも通用するようにするためです

リーフページのレイアウトは次のとおりです。

| ページ内オフセット | サイズ   | 内容                                               |
| ------------------ | -------- | -------------------------------------------------- |
| 0                  | 1        | ページ種別 `0x0d`                                  |
| 1〜2               | 2        | セル数(ビッグエンディアン `uint16`)                |
| 3〜4               | 2        | セル本体領域の開始オフセット                       |
| 5〜7               | 3        | 予約(ゼロ)                                         |
| 8〜                | 2×セル数 | セルポインタ配列(キー昇順、各 `uint16`)            |
| 末尾側             | 可変     | セル本体: キー(`uint64`) + 値の長さ(`uint16`) + 値 |

内部ページのレイアウトは次のとおりです。

| ページ内オフセット | サイズ   | 内容                                              |
| ------------------ | -------- | ------------------------------------------------- |
| 0                  | 1        | ページ種別 `0x05`                                 |
| 1〜2               | 2        | セル数                                            |
| 3〜4               | 2        | セル本体領域の開始オフセット                      |
| 5〜8               | 4        | 右端の子ページ番号(`uint32`)                      |
| 9〜11              | 3        | 予約(ゼロ)                                        |
| 12〜               | 2×セル数 | セルポインタ配列                                  |
| 末尾側             | 可変     | セル本体: キー(`uint64`) + 子ページ番号(`uint32`) |

内部ノードのセルが持つキーは、「この子の部分木に含まれるキーはすべてこのキー以下である」という意味を持ちます(つまりキー = 左部分木の最大キー)。図 5-2 で見た「≤ 17 はこちら」の道標が、そのままこのキーの役割です。

ルートページ番号は、第 2 章で設計したヘッダページ(ページ 0)のオフセット 16〜19 に記録します(値 0 は「木がまだ作られていない」を表します)。第 2 章で「予約(ゼロ)」としていた領域の、最初の住人です。これは SQLite が `sqlite_schema` の `rootpage` 列でやっていることの最小版で、第 3 部でカタログ機構へと発展させます。

<div class="warn">

<span class="note-title">minidb の割り切り(第 2 部の実装範囲)</span>

- **varint を使わず、固定 8 バイトのキーにする** — 本物の SQLite は可変長エンコーディングでキーを切り詰めて格納する
- **オーバーフローページを持たず、値は 1 ページに収まる上限を課す** — 本物は収まりきらない大きな値を専用のオーバーフローページの連鎖に逃がす

- **削除時のマージ・リバランスは実装せず、理論の説明にとどめる** — 本物は削除のたびにノードの結合や再配分を行い、半分埋まりの不変条件を保つ(第 8 章)

</div>

実装は 3 段階に分けて進めます。第 6 章でリーフ単体の挿入・検索を実装し、第 7 章でページが埋まったときの分割と内部ノードを実装し、第 8 章で削除・フリーリスト・LRU キャッシュを実装します。この章で描いた設計図が、そのまま次章からの実装の土台になります。

## 5.7　まとめ

- ディスクは 4096 バイトのページ単位でしか読めないため、数十バイトのノードを持つ二分木はページ読み込み回数(=木の高さ)が大きくなりすぎる。1 ノードに数百のキーを詰める多分岐の B-Tree が、ディスクに適した探索構造である
- B-Tree は「すべてのリーフが同じ深さ」「各ノードは一定以上埋まっている」という不変条件を、分割によって上に伸びることで保つ
- 値をリーフだけに置く B+Tree は内部ノードを痩せさせてファンアウトを稼ぐ。SQLite のテーブル用 B-Tree も型としては B+Tree であり、テーブル用(rowid → 行)とインデックス用(列の値 → rowid)の 2 種類の木が `WHERE` 句の高速化を支えている
- 実測でも、100 万行のテーブルはわずか高さ 3 の木に収まっており、理論と実測は一致した

次章では、いよいよ手を動かします。4096 バイトのページ 1 枚をリーフノードにし、Alice, Bob, Carol がバイト列になってページに並び、キーで検索できるようになる — minidb の B-Tree の最初の一歩です。
