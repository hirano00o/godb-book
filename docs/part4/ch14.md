## 14.1　正しさの代金を取り返す

第 13 章の最後で、こう締めくくりました。

> `exec` パッケージのテストスイート全体の実行時間を測ると、第 12 章時点の **0.687 秒**から、本章では **19.352 秒**(約 28 倍)に伸びました。

原因はコミットプロトコルそのものにありました。ロールバックジャーナル方式のコミット 1 回は、①ジャーナルへエントリ列を書く、②ジャーナルを fsync、③ジャーナルヘッダを書く、④ジャーナルを fsync、⑤DB 本体へ Flush して fsync、⑥ジャーナルを削除、という 6 手順を踏みます。このうち `fsync` は②④⑤の **3 回**——ジャーナル用に 2 回、DB 本体用に 1 回です。第 13 章の autocommit は、`BEGIN` を書かないすべての SQL 文にこの 6 手順・3 回の fsync をまるごと支払わせるので、`INSERT` を 1 つ打つたびにミリ秒単位のコストが積み上がります。壊れなくなった代わりに、遅くなった——これが第 13 章の正直な帳尻でした。

この帳尻を、問いの立て方を変えることで取り返します。ロールバックジャーナル方式が遅いのは、**「変更前」を退避してから「本体」を書く**からです。退避と本体書き込みという 2 度の仕事(＋それぞれの fsync)が、遅さの正体そのものでした。ならば、こう問いを転換したらどうでしょうか。**「変更後」の内容をログに追記するだけでコミットを終え、本体を書くのは後回しにしたら?**

「後回しにする」という言い方には、少し語弊があります。本体をまったく書かないわけではありません。ただ、**コミットのたびに**書く必要がなくなるだけです。ログに追記された変更後の内容は、それ自体が「最新の正しいデータ」として振る舞えます。DB 本体への反映は、コミットより低い頻度で、まとめて後から行えばよいのです。

この 2 つの方式には、教科書的な整理があります。

- **undo ログ**(ロールバックジャーナル)——「これから上書きする、変更前の内容」を先に退避しておく。**失敗したら、退避しておいたものに戻す(undo)**。本体は先に(コミットの一部として)書き換えてしまってよい——その代わり、途中でクラッシュしたときに戻せるよう保険をかけておく、という考え方です
- **redo ログ**(WAL、Write-Ahead Logging)——「これから確定させる、変更後の内容」を先にログへ書いておく。本体はまだ書き換えない。**成功した分は、後で本体へ書き戻せば済む(redo)**。クラッシュしても、ログに残っている「成功したはずの変更」を後から反映し直せばよい、という考え方です

本物の SQLite がこの WAL 方式を `journal_mode=WAL` として実装したのは 2010 年、バージョン 3.7.0 のことです。この章では、その最小版を自分の手で作ります。

第 3 章 3.5 節の演習にはこうありました。

> (3) `PRAGMA journal_mode=WAL` を実行すると、ヘッダのジャーナル方式が 2 に変わることを確認してください。

このとき対象にしていたのは、`sqlite3` コマンドラインシェルが作った本物の `sample.db` でした。自分の `inspect` はまだ読むだけで、`PRAGMA` を実行する術を持っていなかったからです。この章では、この演習をようやく**自分のフォーマットに対して**回収します——`mini.db` 自身に `PRAGMA journal_mode=WAL` を打ち、そのヘッダが書き換わる様子を、今度は自分の実装で確かめます。

## 14.2　設計 — 追記だけでコミットする

### WAL ファイルのフォーマット

WAL ファイルは `<DB ファイル名>-wal` という名前で、DB ファイルと同じディレクトリに置きます。ロールバックジャーナル(`journal.go`)がヘッダ+固定長エントリの単純な列だったのと同様、WAL ファイルも次の 2 部構成です。

- **ヘッダ(16 バイト)** — マジック文字列 `"minidbwl"`(8 バイト)+ 予約領域(8 バイト)
- **フレームの並び** — 1 フレームは「ページ番号(`uint32` ビッグエンディアン、4 バイト)+ コミット印(`uint32` ビッグエンディアン、4 バイト)+ ページ内容そのもの(4096 バイト)」

ジャーナルの「エントリ」に対応する単位を、WAL では**フレーム**と呼びます。中身の構造(ページ番号 + ページ内容)はほとんど同じですが、決定的な違いが 1 つあります。ジャーナルのエントリが持つのは「変更**前**の内容」でしたが、WAL のフレームが持つのは「変更**後**の内容」です。

### コミット = 追記 + 末尾コミット印、fsync は 1 回

WAL 方式のコミットはこうなります。**dirty ページをそれぞれ 1 フレームとして WAL ファイルの末尾へ追記し、最後の 1 フレームだけにコミット印(`commit=1`)を立てて、fsync を 1 回呼ぶ。** DB 本体には一切触れません。

fsync が 1 回で済む理由は単純です。ロールバックジャーナル方式が「ジャーナルへの確定」と「本体への確定」という 2 つの異なる場所への書き込みをそれぞれ fsync していたのに対し、WAL 方式は**書き込み先が WAL ファイル 1 つだけ**だからです。追記が全部終わってから 1 回 fsync すれば、そのフレーム列全体がディスクに到達したことを保証できます。

「最後のフレームだけにコミット印を立てる」という部分にも意味があります。1 つのトランザクションが複数ページを変更していれば、WAL には複数のフレームが連続して追記されますが、それらが本当に「1 つのトランザクションとして丸ごと成功したか」を判定する印は、**列の最後尾にしか要りません**。先頭や途中のフレームにコミット印は不要です——後述するリカバリが、この末尾の 1 個を目印にして「ここまでは有効」と判定するからです。

### 読み取りの 2 層構造 — WAL は本体を上書きするレイヤ

WAL にコミット済みの新しい内容が追記されても、DB 本体は無傷のままです。では、`Get(pageID)` はどちらを読めばよいのでしょうか。

答えは、**メモリ上に持つ `walIndex`(ページ番号 → WAL 内の最新コミット済みフレームのオフセットの対応表)を先に見る**ことです。`walIndex` にそのページがあれば WAL から読み、なければ DB 本体から読みます。WAL は DB 本体を置き換えるものではなく、**「DB 本体の内容を、最新のコミット結果で上書きするレイヤ」**として働きます。

### リカバリ — 「最後のコミット印より後ろを無視する」だけ

ロールバックジャーナル方式のリカバリは「有効なジャーナルがあれば、その内容を本体へ書き戻す」という**復元書き戻し**が必要でした。WAL 方式のリカバリは、これよりずっと単純です。**WAL ファイルを先頭から走査し、最後のコミット印より後ろにあるフレームを無視するだけ**です。

これは undo ログと redo ログの非対称そのものです。ロールバックジャーナルは「本体が既に書き換わってしまっているかもしれない」ことを前提に、それを**元に戻す**作業が要ります。WAL は本体を一切書き換えていないので、戻すものが最初からありません。クラッシュで中途半端に追記されたフレーム(コミット印まで到達しなかった、いわゆる「尻切れ」)があっても、それは単に「無視すればよい、まだ存在しないのと同じもの」です——復元も書き戻しも要らず、**「どこまでが有効な末尾か」を判定するだけ**でリカバリが完結します。

### チェックポイント — WAL を本体へ書き戻して空にする

コミットのたびに WAL へ追記するだけでは、WAL ファイルはいつまでも太り続け、読み取りのたびに `walIndex` を経由する間接参照も減りません。そこで**チェックポイント**という操作を用意します。WAL 上のコミット済みフレームをすべて DB 本体へ書き戻し、WAL ファイルをヘッダだけに切り詰めて空にする処理です。同じフレームを何度書き戻しても DB 本体の内容は変わらない(フレームは差分ではなく常にページの完全な内容だから)ので、この操作は**冪等**です。途中でクラッシュしても、最初からやり直せば必ず同じ結果に行き着きます。

チェックポイントの実行タイミングは 3 つあります。**(1) `Close` 時**——次に `Open` するたびに WAL 全体を読み直す手間を省く、いわば「きれいな終了」。**(2) 閾値超過時**——コミット済みフレーム数が一定を超えたら `Commit` の中で自動的に実行し、WAL が際限なく太るのを防ぐ。**(3) `PRAGMA wal_checkpoint` による明示要求**——利用者が任意のタイミングで反映したいとき。

ここで、会計の話をしておく必要があります。**コミットの fsync は 3 回から 1 回に減りましたが、それは消えたわけではなく、チェックポイントに「まとめて後払い」されているだけです。** チェックポイントは `writeBackWALPages`(本体への書き込み + fsync 1 回)と、WAL の `Truncate` + fsync という、それ自体コストのかかる処理です。ただし、チェックポイントの頻度はコミットよりずっと低く抑えられます——1000 回のコミットにつき 1 回のチェックポイントで済ませれば、fsync の総回数は「コミットごとに 1 回 + 1000 回に 1 回の重いチェックポイント」に圧縮されます。**払う場所と頻度を変えることこそが、WAL 方式の核心**です。

<div class="sqlite-note">

<span class="note-title">SQLite ではこうなっている: チェックサム・salt・wal-index 共有メモリ</span> 本物の WAL は、minidb のような単純なコミット印(1 ビット)だけでフレームの有効性を判定しません。各フレームにチェックサムを持たせ、WAL ファイル全体にはランダムな **salt** 値を振ります。クラッシュ後の再オープン時には、salt が一致し、かつチェックサムが連鎖的に正しく計算できるフレームだけを有効と見なします——ディスクの物理セクタが部分的にしか書き込まれない(torn write)ケースを、コミット印 1 個より遥かに厳密に検出するためです。さらに本物の WAL は、`walIndex` に相当する対応表を **wal-index** と呼び、これを `-shm` という別ファイル(共有メモリ)に置きます。複数プロセスがこの共有メモリを見れば、それぞれが WAL ファイルを毎回スキャンし直さずに済みます。そして各リーダーは「今この瞬間、WAL のどこまでを自分のスナップショットと見なすか」を接続時に固定するため、書き込み中の WAL があってもリーダーはブロックされません——**readers-don't-block-writers** という SQLite WAL モードの謳い文句の正体です。minidb は単一プロセス・単一接続を前提にしているのでこの共有機構は要りませんが、この「複数の読者が同時に安全に WAL を覗く」という主題は、第 15 章で正面から扱います。

</div>

## 14.3　実装 — wal.go

`journal.go` と対をなす `wal.go` を、`pager` パッケージに新しく追加します。全文を 3 分割して掲載します。

**pager/wal.go(1) — パッケージコメント・定数・walPath・ensureWALFile**

```go
// wal.go は Write-Ahead Logging(WAL)方式によるトランザクションの
// 耐久性・原子性を担う、WAL ファイルの読み書きを扱う。
//
// ロールバックジャーナル方式(journal.go)は「変更前の内容」をジャーナルへ
// 退避してから DB 本体を書き換える。WAL 方式はその逆で、「変更後の内容」を
// WAL ファイルへ追記するだけでコミットを終える。DB 本体は一切書き換えない。
// 読み取りは「WAL にあれば WAL、なければ DB 本体」という 2 層構造になり、
// WAL は「DB 本体の内容を最新のコミット結果で上書きするレイヤ」として働く
// (pager.go の readPage 参照)。
//
// この方式の核心は、コミットのたびに必要な fsync が 1 回で済むこと。
// ロールバックジャーナル方式は
//  1. ジャーナルへ退避 + fsync
//  2. DB 本体へ書き戻し + fsync(Flush)
//  3. ジャーナル削除 + fsync
//
// と 3 回の fsync を要するが、WAL 方式は「WAL への追記 + fsync」の 1 回
// だけで耐久性を確保できる(DB 本体への反映はチェックポイントまで遅延され、
// チェックポイントの頻度はコミットより低く保てる)。
package pager

import (
	"encoding/binary"
	"errors"
	"fmt"
	"os"
)

const (
	// walMagic は WAL ファイルの先頭 8 バイト。
	walMagic = "minidbwl"

	// walHeaderSize は WAL のヘッダサイズ。マジック(8B)+ 予約(8B)。
	walHeaderSize = 16

	// walFrameHeaderSize は 1 フレームのヘッダサイズ。
	// ページ番号(uint32 BE、4B)+ コミット印(uint32 BE、4B)。
	walFrameHeaderSize = 8

	// walFrameSize は 1 フレームの総サイズ(ヘッダ + ページ本体)。
	walFrameSize = walFrameHeaderSize + PageSize
)

// walCheckpointThreshold はコミット済みフレーム数がこれを超えたら
// Commit のたびに自動でチェックポイントする閾値。テストから小さい値に
// 差し替えられるよう var にしている(package pager の白箱テストが直接
// 書き換える)。
var walCheckpointThreshold = 1000

// walPath はこの DB の WAL ファイルのパスを返す。
func (p *Pager) walPath() string {
	return p.path + "-wal"
}

// closeWALFile は Open の失敗経路で WAL ファイルを閉じ忘れないための
// 後始末用ヘルパー。walFile が nil でも安全に呼べる。
func (p *Pager) closeWALFile() {
	if p.walFile != nil {
		p.walFile.Close()
		p.walFile = nil
	}
}

// ensureWALFile は WAL ファイルが開かれていなければ開く(存在しなければ
// ヘッダだけの新規ファイルを作る)。通常は SetJournalMode(WAL) の時点で
// 既に開かれているはずだが、「ヘッダを WAL 用に書き換えた直後、WAL
// ファイルを作る前」にクラッシュした場合への保険として、walCommit からも
// 呼べるようにしてある。
func (p *Pager) ensureWALFile() error {
	if p.walFile != nil {
		return nil
	}
	f, err := os.OpenFile(p.walPath(), os.O_RDWR|os.O_CREATE, 0o644)
	if err != nil {
		return err
	}
	info, err := f.Stat()
	if err != nil {
		f.Close()
		return err
	}
	if info.Size() == 0 {
		header := make([]byte, walHeaderSize)
		copy(header[0:8], walMagic)
		if _, err := f.WriteAt(header, 0); err != nil {
			f.Close()
			return err
		}
		if err := f.Sync(); err != nil {
			f.Close()
			return err
		}
	}
	p.walFile = f
	if p.walIndex == nil {
		p.walIndex = make(map[PageID]int64)
	}
	p.walEnd = walHeaderSize
	return nil
}
```

`ensureWALFile` の末尾で `p.walEnd = walHeaderSize` を無条件に設定している点に、先取りで注目してください。これは「WAL ファイルを新規に用意した直後は、有効なフレーム列がまだ 0 個」という状態を表しています。この `walEnd` こそが、この節の後半で最も重要な役回りを演じます。

**pager/wal.go(2) — openWALIfPresent・scanWALFrames**

```go
// openWALIfPresent は Open の際に呼ばれる。WAL ファイルが残っていれば
// 先頭から走査し、コミット印までのフレームだけを walIndex に反映する。
//
// 最後のコミット印より後ろのフレーム(コミットの途中でクラッシュした
// 尻切れ)は index に入れず、ファイル自体をそこまで切り詰める。これにより
// 次の walCommit の追記が尻切れ部分を上書きする形になり、「尻切れの無視」
// がそのままクラッシュリカバリとして働く。
func (p *Pager) openWALIfPresent() error {
	f, err := os.OpenFile(p.walPath(), os.O_RDWR, 0o644)
	if errors.Is(err, os.ErrNotExist) {
		return nil
	}
	if err != nil {
		return err
	}

	info, err := f.Stat()
	if err != nil {
		f.Close()
		return err
	}
	if info.Size() < walHeaderSize {
		// ヘッダすら書き切れていない壊れた WAL。無視して素の状態から始める。
		f.Close()
		return nil
	}
	header := make([]byte, walHeaderSize)
	if _, err := f.ReadAt(header, 0); err != nil {
		f.Close()
		return err
	}
	if string(header[0:8]) != walMagic {
		f.Close()
		return fmt.Errorf("WAL ファイルではありません: %s", p.walPath())
	}

	index, totalFrames, lastCommitEnd, err := scanWALFrames(f, info.Size())
	if err != nil {
		f.Close()
		return err
	}
	if err := f.Truncate(lastCommitEnd); err != nil {
		f.Close()
		return err
	}

	p.walFile = f
	p.walIndex = index
	p.walFrames = totalFrames
	p.walEnd = lastCommitEnd
	return nil
}

// scanWALFrames は WAL ファイル f をヘッダの直後からフレーム単位で走査し、
// コミット済みのページ → オフセット対応(index)、コミット済みフレームの
// 総数(totalFrames)、最後のコミット印の直後のオフセット(lastCommitEnd、
// 尻切れフレームを切り詰める境界)を返す。
//
// pending は「まだこのトランザクションのコミット印(commit=1)に
// 到達していないフレーム」を溜めておくバッファ。コミット印に到達したら
// まとめて index へ反映する。コミット印に到達しないまま走査が終われば
// (= クラッシュで途中まで書かれた尻切れ)、pending の中身は棄てられる。
func scanWALFrames(f *os.File, size int64) (index map[PageID]int64, totalFrames int, lastCommitEnd int64, err error) {
	index = make(map[PageID]int64)
	pending := make(map[PageID]int64)
	pendingCount := 0

	head := make([]byte, walFrameHeaderSize)
	offset := int64(walHeaderSize)
	lastCommitEnd = offset
	for offset+walFrameSize <= size {
		if _, err := f.ReadAt(head, offset); err != nil {
			return nil, 0, 0, fmt.Errorf("WAL フレームの読み取りに失敗: %w", err)
		}
		id := PageID(binary.BigEndian.Uint32(head[0:4]))
		commit := binary.BigEndian.Uint32(head[4:8])

		pending[id] = offset
		pendingCount++
		offset += walFrameSize

		if commit == 1 {
			for pid, poff := range pending {
				index[pid] = poff
			}
			totalFrames += pendingCount
			pending = make(map[PageID]int64)
			pendingCount = 0
			lastCommitEnd = offset
		}
	}
	return index, totalFrames, lastCommitEnd, nil
}
```

**危険その 1: pending バッファが棄てる「尻切れ」。** `scanWALFrames` はフレームを読むたびに、それをいったん `pending` へ溜めます。`index`(有効な読み取り対象)へ反映するのは、コミット印(`commit == 1`)を持つフレームに出会った、その瞬間だけです。もし WAL の末尾が「コミット印に達しないまま」終わっていたら——つまりコミットの途中でクラッシュしていたら——最後の `pending` は一度も `index` へ反映されないまま、関数を抜けて静かに消えます。**尻切れフレームを「読まない」のではなく、そもそも `pending` から `index` へ昇格させない**という書き方が、14.2 節で述べた「最後のコミット印より後ろを無視する」というリカバリの規則を、そのままコードにしています。`openWALIfPresent` はこれに加えて `f.Truncate(lastCommitEnd)` で尻切れ部分を物理的に切り落とすので、次の `walCommit` はこの尻切れの**跡地**から書き始めることになります——この「跡地から書く」という設計判断が、次の危険につながります。

**pager/wal.go(3) — walCommit・writeBackWALPages・checkpoint・Checkpoint・モード切替**

```go
// walCommit は WAL モードでのコミット処理。dirty ページをすべて WAL
// ファイル末尾へフレームとして追記し、最後の 1 フレームだけコミット印
// (commit=1)を立てる。fsync は末尾への追記が終わった後の 1 回だけ行い、
// それが成功して初めて walIndex を更新する。DB 本体には一切書き込まない。
//
// 書き始めの位置はファイルサイズではなく walEnd(有効なフレーム列の末尾)。
// 以前のコミットが書き込みエラーで失敗していた場合、コミット印のない
// 孤児フレームがファイル末尾に残っていることがある。ファイルサイズから
// 書き始めると、孤児フレームの直後に次のコミットが続き、後の再オープン時に
// スキャナが孤児フレームを次のコミットの一部として拾ってしまう
// (ロールバック済みの変更が蘇生する)。walEnd から書けば孤児は上書きされる。
func (p *Pager) walCommit(dirty []*Page) error {
	if err := p.ensureWALFile(); err != nil {
		return err
	}

	startOffset := p.walEnd

	offset := startOffset
	frame := make([]byte, walFrameSize)
	for i, page := range dirty {
		binary.BigEndian.PutUint32(frame[0:4], uint32(page.ID))
		commit := uint32(0)
		if i == len(dirty)-1 {
			commit = 1
		}
		binary.BigEndian.PutUint32(frame[4:8], commit)
		copy(frame[8:], page.Data[:])
		if _, err := p.walFile.WriteAt(frame, offset); err != nil {
			return fmt.Errorf("WAL への書き込みに失敗: %w", err)
		}
		offset += walFrameSize
	}

	// fsync は 1 回だけ。ロールバックジャーナル方式が 3 回必要とするのに
	// 対し、この 1 回にコミットの fsync 回数を削減できることが WAL 方式の
	// 核心の利点(package コメント参照)。
	if err := p.walFile.Sync(); err != nil {
		return err
	}

	offset = startOffset
	for _, page := range dirty {
		p.walIndex[page.ID] = offset
		page.dirty = false
		offset += walFrameSize
	}
	p.walFrames += len(dirty)
	p.walEnd = offset
	return nil
}

// writeBackWALPages は walIndex が指す全ページを WAL から読み出して DB
// 本体へ書き戻し、fsync する。WAL のフレームは常にページの完全な内容
// (差分ではない)なので、同じフレームを重ねて書き戻しても結果は変わらない
// (冪等)。チェックポイントの途中でクラッシュしても、最初からやり直せば
// 必ず同じ DB 本体に行き着く。
func (p *Pager) writeBackWALPages() error {
	if len(p.walIndex) == 0 {
		return nil
	}
	buf := make([]byte, PageSize)
	for id, offset := range p.walIndex {
		if _, err := p.walFile.ReadAt(buf, offset+walFrameHeaderSize); err != nil {
			return fmt.Errorf("チェックポイント: ページ %d の読み取りに失敗: %w", id, err)
		}
		if _, err := p.file.WriteAt(buf, int64(id)*PageSize); err != nil {
			return fmt.Errorf("チェックポイント: ページ %d の書き戻しに失敗: %w", id, err)
		}
	}
	return p.file.Sync()
}

// checkpoint はチェックポイント本体。WAL 上のコミット済みページをすべて
// DB 本体へ反映し(writeBackWALPages)、WAL ファイルをヘッダだけに
// truncate して fsync し、walIndex をクリアする。
//
// 実行タイミングは 3 つ: (1) Close 時(Tx 自動 Rollback の後)、
// (2) Commit 直後にコミット済みフレーム数が walCheckpointThreshold を
// 超えたとき自動、(3) PRAGMA wal_checkpoint による明示要求。
func (p *Pager) checkpoint() error {
	if p.walFile == nil {
		return nil
	}
	if err := p.writeBackWALPages(); err != nil {
		return err
	}
	if err := p.walFile.Truncate(walHeaderSize); err != nil {
		return err
	}
	if err := p.walFile.Sync(); err != nil {
		return err
	}
	p.walIndex = make(map[PageID]int64)
	p.walFrames = 0
	p.walEnd = walHeaderSize
	return nil
}

// Checkpoint は WAL 上のコミット済みページを DB 本体へ反映し、WAL を
// 空にする(PRAGMA wal_checkpoint から呼ばれる)。ロールバックジャーナル
// モードやトランザクション中は呼び出せない。
func (p *Pager) Checkpoint() error {
	if p.journalMode != JournalModeWAL {
		return errors.New("チェックポイントは WAL モードでのみ実行できます")
	}
	if p.inTx {
		return errors.New("トランザクション中はチェックポイントを実行できません")
	}
	return p.checkpoint()
}

// switchToWAL はロールバックジャーナル方式から WAL 方式へ切り替える。
// ヘッダページの journalMode を書き換えて Flush で確定させてから、
// WAL ファイルを新規に作る。
func (p *Pager) switchToWAL() error {
	header, err := p.Get(headerPageID)
	if err != nil {
		return err
	}
	binary.BigEndian.PutUint32(header.Data[journalModeOffset:journalModeOffset+4], uint32(JournalModeWAL))
	header.dirty = true
	p.journalMode = JournalModeWAL
	if err := p.Flush(); err != nil {
		return err
	}
	return p.ensureWALFile()
}

// switchToRollback は WAL 方式からロールバックジャーナル方式へ切り替える。
// まずチェックポイントで WAL の内容を DB 本体へ反映してから WAL
// ファイルを削除し、最後にヘッダページの journalMode を書き換えて
// Flush で確定させる。
func (p *Pager) switchToRollback() error {
	if err := p.checkpoint(); err != nil {
		return err
	}
	walPath := p.walPath()
	p.closeWALFile()
	if err := os.Remove(walPath); err != nil && !errors.Is(err, os.ErrNotExist) {
		return err
	}

	header, err := p.Get(headerPageID)
	if err != nil {
		return err
	}
	binary.BigEndian.PutUint32(header.Data[journalModeOffset:journalModeOffset+4], uint32(JournalModeRollback))
	header.dirty = true
	p.journalMode = JournalModeRollback
	return p.Flush()
}

// SetWALCheckpointThreshold はテストから自動チェックポイントの閾値を
// 差し替えるためのヘルパー(SetCacheLimit と同じ立て付け)。
func SetWALCheckpointThreshold(n int) { walCheckpointThreshold = n }
```

<div class="warn">

<span class="note-title">レビューで見つかったバグ: walEnd という設計</span> `walCommit` が書き始め位置を決めるのに使っている `p.walEnd`——「有効な(コミット済みの)フレーム列の末尾」——は、この章の初版には存在しませんでした。初版は単純に `f.Stat()` で得た**ファイルサイズ**を書き始め位置にしていました。レビューでこの実装の危険性が指摘され、`walEnd` という専用フィールドに置き換わりました。

危険はこうです。`walCommit` の途中で書き込みエラーが起きた(ディスクフル、I/O エラーなど)としましょう。フレームの一部はすでに WAL ファイルへ `WriteAt` 済みかもしれませんが、`fsync` にはまだ到達していません。このとき、末尾に残っているのは**コミット印を持たない、中途半端なフレーム**です——本来ならロールバックされたのと同じ扱いを受けるべき、無効な書きかけの内容です。

ここでファイルサイズを次のコミットの書き始め位置に使ってしまうと、何が起きるでしょうか。次の(正常な)コミットは、この孤児フレームの**直後**から新しいフレームを書き始めます。そして、その正常なコミットの最後のフレームにコミット印が立ちます。すると再オープン時、`scanWALFrames` は先頭から順にフレームを読み進め、孤児フレームも「まだコミット印に到達していない `pending`」としていったん取り込みます——そのすぐ後ろに続く、正常なコミットの一部として。コミット印に到達した瞬間、`pending` は丸ごと `index` へ反映されます。**その中には、本来失敗して消えるはずだった孤児フレームのページも含まれています。** 失敗した(ロールバックされたのと同じであるべき)変更が、後続の無関係なコミットに紛れ込む形で蘇生してしまうのです。

`walEnd` から書けば、この危険は起きません。孤児フレームは「有効なフレーム列の末尾」の**外側**にあるので、次の `walCommit` は孤児フレームがあった位置を**上書き**します——孤児は物理的に消え、蘇生のしようがありません。同じ理由で、`checkpoint` が WAL を `Truncate(walHeaderSize)` した後は `p.walEnd = walHeaderSize` にリセットしています。もしこのリセットを忘れて `walEnd` が切り詰め前の大きな値のままだったら、次の `walCommit` はファイルの**存在しない**(truncate 済みの)領域から書き始めることになり、その間に穴(ゼロ埋めされた未初期化領域)が空いてしまいます。「切り詰めた先には、必ずヘッダ直後から書き直す」という規律を、`walEnd` のリセットが保証しています。

**追記型ログの正しさは、突き詰めれば「どこが有効な末尾か」の管理に尽きます。** ファイルサイズという物理的な事実と、「意味的に有効な末尾」という論理的な事実は、書き込みが失敗しうる世界では**別物**です。この 2 つを取り違えないことが、WAL 方式全体の正しさの土台でした。14.4 節の `TestWALOrphanFramesNotResurrected` が、この危険を実際に手で再現して検証します。

</div>

### チェックポイントの順序 — 本体が先、WAL の切り詰めが後

`checkpoint` の 3 手順、`writeBackWALPages`(本体への書き戻し + fsync)→ `walFile.Truncate` → `walFile.Sync()` には、順序上の意図があります。**本体への fsync が終わって初めて、WAL を切り詰めます。** もし逆に WAL を先に切り詰めてしまうと、本体への書き戻しがまだ途中(あるいは未着手)の状態で、WAL 側の「最新のコミット結果」という記録だけが消えてしまいます——ログを消すのは、そのログが指し示すデータが安全な場所(DB 本体)へ届いてから、という原則です。`writeBackWALPages` 自体は前述のとおり冪等なので、この手順の途中でクラッシュしても、次に `checkpoint` が(あるいは次回 `Open` 時のリカバリを経て通常の読み取りが)同じ結果に収束します。

### モード切替 — journalMode はヘッダの一部として永続化される

`switchToWAL`/`switchToRollback` はどちらも、切替の確定を**ヘッダページの書き換え + その場での `Flush`**によって行います。ロールバックジャーナルから WAL への切替(`switchToWAL`)はヘッダを書き換えてから WAL ファイルを作り、WAL からロールバックジャーナルへの切替(`switchToRollback`)はチェックポイントで WAL の内容を本体へ反映してから WAL ファイルを削除し、最後にヘッダを書き換えます。どちらの向きでも、モードを表すフィールド(ヘッダのオフセット 28-31、`pager.go` 側で定義)は WAL を経由せず、Flush によって直接確定します——モードそのものを記録するフィールドが WAL 越しにしか読めないようでは、「今このファイルは WAL モードかどうか」を判定するために WAL の存在有無に頼る、循環した設計になってしまうからです。この 28-31 バイト目のフィールドと `readPage` の WAL 優先ロジックは、次節で `pager.go` 側の変更として詳しく見ます。

`wal.go` の道具を使う側、`pager.go` の変更・追加部分を、実際のファイル内の並び順で示します。無変更部分(`Get`/`Allocate`/`MarkDirty`/`touch`/`evictIfNeeded`/`journal.go` まわり など)は第 13 章のままです。完成形は `code/ch14/pager/pager.go` を参照してください。

**pager/pager.go(1) — フィールド追加と JournalMode 型・アクセサ**

```go

	journalMode JournalMode // ロールバックジャーナル方式か WAL 方式か

	// WAL モードでのみ使うフィールド(詳細は wal.go)。
	walFile   *os.File         // WAL ファイル(WAL モードでのみ開く)

// JournalMode はトランザクションの耐久性・原子性をどの方式で確保するかを表す。
type JournalMode int

const (
	// JournalModeRollback はコミット時ジャーナリング(第 13 章)。既定値。
	JournalModeRollback JournalMode = iota
	// JournalModeWAL は Write-Ahead Logging(本章)。
	JournalModeWAL
)

// String はジャーナルモードを表示用の名前で返す。
func (m JournalMode) String() string {
	switch m {
	case JournalModeRollback:
		return "rollback"
	case JournalModeWAL:
		return "wal"
	default:
		return fmt.Sprintf("JournalMode(%d)", int(m))
	}
}

// JournalMode は現在のジャーナルモードを返す。
func (p *Pager) JournalMode() JournalMode { return p.journalMode }

// SetJournalMode はジャーナルモードを切り替える。トランザクション中は
// 呼び出せない(切替の途中でコミット処理の方式が変わってしまわないよう、
// トランザクションの外側でだけ許す)。既に指定のモードであれば何もしない。
//
// どちらの向きの切替も、確定はヘッダページの書き換え + その場での
// Flush によって行う(WAL を経由させない)。これにより、モードを表す
// フラグ自体は常に「今すぐ読み直しても正しい」状態を保つ。
func (p *Pager) SetJournalMode(m JournalMode) error {
	if p.inTx {
		return errors.New("トランザクション中はジャーナルモードを変更できません")
	}
	if m == p.journalMode {
		return nil
	}
	switch m {
	case JournalModeWAL:
		return p.switchToWAL()
	case JournalModeRollback:
		return p.switchToRollback()
	default:
		return fmt.Errorf("不明なジャーナルモードです: %d", int(m))
	}
}
```

**pager/pager.go(2) — Open の openWALIfPresent 呼び出し**

```go

	// 側にあることがあるため(WAL モードでの変更は DB 本体を経由しない)、
```

`openWALIfPresent` の呼び出しが `loadHeader` より**前**にある理由は、第 13 章で `recoverFromJournal` を `loadHeader` より前に置いた理由と同じ形をしています。WAL モードでの変更はヘッダページも例外なく WAL 経由で反映されるので(`switchToWAL`/`switchToRollback` を除けば、ヘッダページも他の dirty ページとまったく同じ扱いで WAL に書かれます)、`loadHeader` が読むべき「本当に最新のヘッダ」は WAL の中にあるかもしれません。WAL を先に読み込んで `walIndex` を整えておかなければ、`loadHeader`(内部で `readPage` を呼ぶ)は DB 本体の**古い**ヘッダを読んでしまいます。

**pager/pager.go(3) — initHeader・loadHeader — ヘッダレイアウト 28-31**

```go
// initHeader はヘッダページを初期化してディスクに書き込む。
// レイアウト:
//
//	オフセット 0-7  : マジック文字列 "minidb01"
//	オフセット 8-11 : ページサイズ(ビッグエンディアン uint32)
//	オフセット 12-15: 総ページ数(ビッグエンディアン uint32)
//	オフセット 16-19: ルートページ番号(ビッグエンディアン uint32)
//	オフセット 20-23: フリーリスト先頭ページ番号(ビッグエンディアン uint32、0=空)
//	オフセット 24-27: フリーリストのページ数(ビッグエンディアン uint32)
//	オフセット 28-31: ジャーナルモード(ビッグエンディアン uint32、0=ロールバックジャーナル、1=WAL)
func (p *Pager) initHeader() error {
	page := &Page{ID: headerPageID}
	copy(page.Data[0:8], Magic)
	binary.BigEndian.PutUint32(page.Data[8:12], PageSize)

	p.numPages = 1 // ヘッダページ自身
	binary.BigEndian.PutUint32(page.Data[12:16], p.numPages)
	// journalMode は既定でロールバックジャーナル(0)。ゼロ値のまま
	// なので書き込みは不要だが、レイアウト上の意味を明示するために残す。
	binary.BigEndian.PutUint32(page.Data[journalModeOffset:journalModeOffset+4], uint32(JournalModeRollback))
	p.journalMode = JournalModeRollback

	p.cache[headerPageID] = page
	p.touch(headerPageID)
	page.dirty = true
	return p.Flush()
}

// loadHeader は既存ファイルのヘッダページを読み込んで検証する。
func (p *Pager) loadHeader() error {
	page, err := p.readPage(headerPageID)
	if err != nil {
		return err
	}
	if string(page.Data[0:8]) != Magic {
		return errors.New("minidb ファイルではありません")
	}
	if got := binary.BigEndian.Uint32(page.Data[8:12]); got != PageSize {
		return fmt.Errorf("ページサイズが不一致: file=%d, build=%d", got, PageSize)
	}
	p.numPages = binary.BigEndian.Uint32(page.Data[12:16])
	p.journalMode = JournalMode(binary.BigEndian.Uint32(page.Data[journalModeOffset : journalModeOffset+4]))
	p.cache[headerPageID] = page
	p.touch(headerPageID)
	return nil
}
```

第 3 章で本物の SQLite ファイルヘッダのオフセット 18-19(書き込み/読み取りバージョン)に見た `1=rollback journal, 2=WAL` という値が、ここで**自分のフォーマット**として蘇ります。ただし数値の割り当てはあえて揃えていません——minidb はオフセット 28-31 という別の位置に、`0=ロールバックジャーナル、1=WAL` という自分自身の番号を持ちます。SQLite のバイト位置や数値を輸入するのではなく、「モードという意味をヘッダの固定オフセットに刻む」という**設計そのもの**を再現するのが、この章の演習回収の趣旨です。14.5 節で、この `1` を自分の `xxd` で確かめます。

**pager/pager.go(4) — Close のチェックポイント**

```go
// Close は Flush してからファイルを閉じる。トランザクション中であれば、
// コミットされていない変更を確定させてしまわないよう、まず自動的に
// Rollback してから閉じる。WAL モードのときは、WAL に溜まった変更を
// DB 本体へ反映してから閉じる(次回 Open のたびに WAL 全体を読み直す
// 手間を省くための、いわば「きれいな終了」)。
func (p *Pager) Close() error {
	if p.inTx {
		if err := p.Rollback(); err != nil {
			p.file.Close()
			return err
		}
	}
	if p.walFile != nil {
		if err := p.checkpoint(); err != nil {
			p.file.Close()
			p.walFile.Close()
			return err
		}
		if err := p.walFile.Close(); err != nil {
			p.file.Close()
			return err
		}
		p.walFile = nil
	}
	if err := p.Flush(); err != nil {
		p.file.Close()
		return err
	}
	return p.file.Close()
}
```

`p.walFile != nil` という条件は「WAL モードで、かつ WAL ファイルが実際に開かれている」ことを意味します(ロールバックジャーナルモードのままなら `walFile` は常に `nil` です)。ここで `checkpoint()` を呼ぶことで、`Close` を挟んだ後の DB ファイルは常に「WAL を読み直さなくても、それだけで正しい」状態になります——14.5 節で `ls` によってこの結果を確かめます。

**pager/pager.go(5) — Commit の WAL 分岐と自動チェックポイント**

```go
// Commit はトランザクションを確定する。モードによって手順が異なる:
//
//   - ロールバックジャーナル: 変更前ページをジャーナルへ退避してから
//     dirty ページをディスクへ書き戻し、最後にジャーナルを削除する。
//   - WAL: dirty ページを WAL に追記するだけで、DB 本体には触れない
//     (詳細は walCommit)。
//
// dirty ページが 1 枚もなければ(変更のないトランザクション)、
// どちらの方式でも何も書かずにそのままトランザクションを終える。
func (p *Pager) Commit() error {
	if !p.inTx {
		return errors.New("トランザクションが開始されていません")
	}

	dirty := p.dirtyPages()
	if len(dirty) == 0 {
		p.inTx = false
		return nil
	}

	if p.journalMode == JournalModeWAL {
		if err := p.walCommit(dirty); err != nil {
			return err
		}
		p.inTx = false
		// フレームが溜まりすぎる前に自動でチェックポイントする。コミット
		// そのものは既に WAL への fsync で耐久性を得ているので、ここでの
		// チェックポイント失敗はデータ消失にはつながらないが、呼び出し側に
		// 状況を伝えるためエラーはそのまま返す。
		if p.walFrames > walCheckpointThreshold {
			return p.checkpoint()
		}
		return nil
	}

	if err := p.writeJournal(dirty); err != nil {
		return err
	}
	if err := p.flush(); err != nil {
		return err
	}
	// ジャーナルの削除こそが「コミットの瞬間」。ここまでの手順(ジャーナル
	// 書き込み → fsync → ヘッダ書き込み → fsync → DB 本体へ Flush)が
	// すべて終わって初めて安全に消せる。
	if err := os.Remove(p.journalPath()); err != nil {
		return err
	}

	p.inTx = false
	return nil
}
```

`Commit` の骨格(`dirtyPages` の取得、0 枚ならジャーナルすら作らない早期リターン)は第 13 章のままです。増えたのは `p.journalMode == JournalModeWAL` の分岐 1 つだけで、この分岐に入れば `walCommit` を呼んで即座に `p.inTx = false` へ戻ります——ロールバックジャーナル側の 6 手順(`writeJournal`→`flush`→`os.Remove`)に比べて、WAL 側は `walCommit` の 1 呼び出しで完結する分、コードの見た目でも軽いことが分かります。自動チェックポイントのコメントにあるとおり、`p.walFrames > walCheckpointThreshold` を超えた場合の `checkpoint()` 呼び出しが失敗しても、直前の `walCommit` はすでに fsync 済みで耐久性を得ているため、コミット自体の成否には影響しません。それでも呼び出し側にエラーを伝えるのは、チェックポイント失敗(たとえばディスクフル)を利用者に隠さないためです。

**pager/pager.go(6) — readPage の WAL 優先**

```go
// readPage はページを 1 枚読み込む(キャッシュを介さない)。WAL に
// このページのコミット済みフレームがあればそちらを優先する。WAL は
// 「DB 本体の内容を最新のコミット結果で上書きするレイヤ」として働く。
func (p *Pager) readPage(id PageID) (*Page, error) {
	page := &Page{ID: id}
	if offset, ok := p.walIndex[id]; ok {
		if _, err := p.walFile.ReadAt(page.Data[:], offset+walFrameHeaderSize); err != nil {
			return nil, fmt.Errorf("WAL からのページ %d の読み取りに失敗: %w", id, err)
		}
		return page, nil
	}
	_, err := p.file.ReadAt(page.Data[:], int64(id)*PageSize)
	if err != nil {
		return nil, fmt.Errorf("ページ %d の読み取りに失敗: %w", id, err)
	}
	return page, nil
}
```

図 14-1 で描いた 2 層構造が、実装ではこの**たった数行**に収まっています。`p.walIndex[id]` に見つかれば、そのオフセットへ `walFrameHeaderSize`(8 バイト、フレームヘッダぶん)を足した位置から `PageSize` バイトを WAL ファイルから読み、見つからなければ従来どおり DB 本体を読みます。追加された分岐は if 文 1 つだけで、既存の DB 本体読み取り経路には一切手を入れていません。**設計が「WAL を本体の上に重ねるレイヤ」として素直だったからこそ、実装もこれだけ小さく済んだ**——ロールバックジャーナル方式が `Commit`/`Rollback` という書き込み側のプロトコルにコードの複雑さを集中させていたのに対し、WAL 方式は書き込み側(`walCommit`)と読み取り側(この数行)の両方に少しずつ複雑さを配っている、と見ることもできます。

```go
// parsePragma は "PRAGMA name;" または "PRAGMA name = value;" を解析する。
func (p *parser) parsePragma() (Statement, error) {
	if _, err := p.expectKeyword("PRAGMA"); err != nil {
		return nil, err
	}
	nameTok, err := p.expectIdentLike()
	if err != nil {
		return nil, err
	}

	stmt := &PragmaStmt{Name: nameTok.Text}
	if tok := p.peek(); tok.Kind == TokenSymbol && tok.Text == "=" {
		p.next()
		valueTok, err := p.expectIdentLike()
		if err != nil {
			return nil, err
		}
		stmt.Value = valueTok.Text
	}
	return stmt, nil
}

// expectIdentLike は識別子、またはキーワードとして予約されている語を
// 1 つ読み取る。PRAGMA の名前・値には journal_mode のような通常の識別子と
// WAL / DELETE のようなキーワード相当の語の両方が現れうる(DELETE は
// DELETE 文と衝突するキーワードだが、PRAGMA の値としては単なる語として
// 扱いたい)ため、expectIdent より緩い規則で受け取る。
func (p *parser) expectIdentLike() (Token, error) {
	tok := p.peek()
	if tok.Kind == TokenIdent || tok.Kind == TokenKeyword {
		return p.next(), nil
	}
	return Token{}, fmt.Errorf("位置 %d: 識別子が必要ですが %q があります", tok.Pos, tok.Text)
}
```

`expectIdentLike` が `expectIdent` より緩い理由には、この章ならではの事情があります。`PRAGMA journal_mode = DELETE` の `DELETE` は、`DELETE FROM ...` 文の先頭キーワードとして予約されている語です。ふつうの識別子検査(`TokenIdent` のみ許可)では弾かれてしまいますが、PRAGMA の値としては「DELETE という名前の語」を受け取りたいだけです。`TokenIdent` と `TokenKeyword` の両方を受け付けることで、この衝突を字句解析側の特別扱いなしに吸収しています。

**exec/engine.go(2) — executePragma・pragmaJournalMode・pragmaModeName**

```go
// executePragma は PRAGMA 文を実行する。対応するのは journal_mode
// (閲覧・rollback/wal 切替)と wal_checkpoint(明示チェックポイント)のみ。
func (e *Engine) executePragma(stmt *sql.PragmaStmt) (*Result, error) {
	switch strings.ToLower(stmt.Name) {
	case "journal_mode":
		return e.pragmaJournalMode(stmt.Value)
	case "wal_checkpoint":
		if stmt.Value != "" {
			return nil, fmt.Errorf("PRAGMA wal_checkpoint は値を取りません")
		}
		if err := e.pg.Checkpoint(); err != nil {
			return nil, err
		}
		return &Result{Message: "チェックポイントを実行しました"}, nil
	default:
		return nil, fmt.Errorf("未対応の PRAGMA です: %s", stmt.Name)
	}
}

// pragmaJournalMode は PRAGMA journal_mode を処理する。値が指定されて
// いなければ現在のモードを返し、指定されていればモードを切り替える。
// 表示名は WAL/DELETE という SQLite の PRAGMA 語彙に合わせる
// (pager.JournalMode.String() が返す rollback/wal という Go 内部向けの
// 名前とは、あえて分けている)。
func (e *Engine) pragmaJournalMode(value string) (*Result, error) {
	if value == "" {
		return &Result{Message: fmt.Sprintf("journal_mode = %s", pragmaModeName(e.pg.JournalMode()))}, nil
	}
	switch strings.ToUpper(value) {
	case "WAL":
		if err := e.pg.SetJournalMode(pager.JournalModeWAL); err != nil {
			return nil, err
		}
		return &Result{Message: "journal_mode を wal に変更しました"}, nil
	case "DELETE":
		if err := e.pg.SetJournalMode(pager.JournalModeRollback); err != nil {
			return nil, err
		}
		return &Result{Message: "journal_mode を delete に変更しました"}, nil
	default:
		return nil, fmt.Errorf("未対応の journal_mode です: %s", value)
	}
}

// pragmaModeName は JournalMode を PRAGMA journal_mode の表示名(SQLite に
// 合わせて WAL は "wal"、ロールバックジャーナルは "delete")に変換する。
func pragmaModeName(m pager.JournalMode) string {
	if m == pager.JournalModeWAL {
		return "wal"
	}
	return "delete"
}
```

`journal_mode` の応答語彙が `wal`/`delete` という、`pager.JournalMode.String()` の `wal`/`rollback` とは**あえて異なる**名前になっている点に注目してください。`pragmaModeName` という専用の変換関数を挟んでいるのは、Go の内部表現(`String()`)と SQL 利用者向けの語彙(SQLite 互換の `wal`/`delete`)を分けるためです。本物の SQLite の `PRAGMA journal_mode` は、ロールバックジャーナル方式を歴史的経緯から `delete`(コミット後にジャーナルファイルを削除する、という挙動に由来する名前)と呼びます。minidb のロールバックジャーナルも、コミットの最後にジャーナルファイルを `os.Remove` していました(第 13 章の `Commit`)——**振る舞いの名前**として `delete` は理にかなっており、`rollback` という Go 内部の型名よりも SQLite ユーザーにとって自然です。

**PRAGMA が autocommit の対象外である理由。** `Execute` の `switch` で `PragmaStmt` は `BeginStmt`/`CommitStmt`/`RollbackStmt` と並び、`e.explicitTx`/`autocommit` の分岐に一切触れずに直接処理されます。これは、`SetJournalMode` と `Checkpoint` がどちらも**それ自体で完結した操作**だからです。`SetJournalMode` はヘッダの書き換え + その場での `Flush`(または `checkpoint`)で確定し、`Checkpoint` も呼び出しの中で完結します。これらを `pg.Begin()`/`pg.Commit()` で包んでしまうと、たとえば「WAL モード中に `Begin` で Tx を開始し、その中で `SetJournalMode` を呼ぶ」という、`SetJournalMode` 自身が明示的に拒んでいる状況(`p.inTx` のガード)を自ら作り出すことになり、無意味などころか矛盾します。**PRAGMA はトランザクションの中身ではなく、トランザクションの外側にある設定変更**なので、Tx を張らずに直接実行するのが正しい設計です。

```go
func readDBBody(t *testing.T, path string, id PageID) []byte {
	t.Helper()
	f, err := os.Open(path)
	if err != nil {
		t.Fatal(err)
	}

	buf := make([]byte, PageSize)
	if _, err := f.ReadAt(buf, int64(id)*PageSize); err != nil {
		t.Fatal(err)
	}

}

// 一方、DB 本体ファイルは旧値のままで、WAL ファイルが作られていることを
// 確認する(コミット時追記が「DB 本体には一切書かない」ことの直接的な証拠)。
func TestWALCommitAndRead(t *testing.T) {
	path := filepath.Join(t.TempDir(), "test.db")
	p, err := Open(path)
	if err != nil {
		t.Fatal(err)
	}
	defer p.Close()

	// ロールバックジャーナルモードのまま、コミット済みの初期値を作る。
	if err := p.Begin(); err != nil {
		t.Fatal(err)
	}
	page, err := p.Allocate()
	if err != nil {
		t.Fatal(err)
	}
	copy(page.Data[:], "old value")
	p.MarkDirty(page.ID)
	if err := p.Commit(); err != nil {
		t.Fatal(err)
	}

	if err := p.SetJournalMode(JournalModeWAL); err != nil {
		t.Fatal(err)
	}

	if err := p.Begin(); err != nil {
		t.Fatal(err)
	}
	got, err := p.Get(page.ID)
	if err != nil {
		t.Fatal(err)
	}
	p.MarkDirty(got.ID)
	copy(got.Data[:], "new value via wal")
	if err := p.Commit(); err != nil {
		t.Fatal(err)
	}

	if p.walFrames != 1 {
		t.Fatalf("walFrames = %d, want 1", p.walFrames)
	}

	// キャッシュ経由(まだ載っている)でも新値が読める。
	reread, err := p.Get(page.ID)
	if err != nil {
		t.Fatal(err)
	}
	if !bytes.HasPrefix(reread.Data[:], []byte("new value via wal")) {
		t.Fatalf("Get() の内容 = %q, want prefix %q", reread.Data[:20], "new value via wal")
	}

	// キャッシュから追い出し、readPage の WAL 経由読み取りも確認する。
	delete(p.cache, page.ID)
	if elem, ok := p.lruIndex[page.ID]; ok {
		p.lru.Remove(elem)
		delete(p.lruIndex, page.ID)
	}
	rereadFromWAL, err := p.Get(page.ID)
	if err != nil {
		t.Fatal(err)
	}
	if !bytes.HasPrefix(rereadFromWAL.Data[:], []byte("new value via wal")) {
		t.Fatalf("WAL 経由の Get() の内容 = %q, want prefix %q", rereadFromWAL.Data[:20], "new value via wal")
	}

	// DB 本体ファイルは旧値のまま(WAL コミットは DB 本体に一切書かない)。
	body := readDBBody(t, path, page.ID)
	if !bytes.HasPrefix(body, []byte("old value")) {
		t.Fatalf("DB 本体の内容 = %q, want prefix %q(WAL コミットで DB 本体が書き換わってしまっている)", body[:20], "old value")
	}

	if _, err := os.Stat(path + "-wal"); err != nil {
		t.Fatalf("WAL ファイルが存在しません: %v", err)
	}
```

`TestWALCommitAndRead` は、この章の核心命題——**「コミットは WAL への追記だけで完結し、DB 本体には一切書かない」**——を最も直接的に確かめるテストです。同じページを 3 通りの経路(キャッシュ経由の `Get`、キャッシュから追い出した後の `readPage` 経由、そして `readDBBody` による DB 本体の直接読み取り)で読み比べ、前者 2 つは新値、最後の 1 つだけが旧値のままであることを確認しています。

**pager/wal_test.go(2) — TestWALPersistence**

```go
// Commit → Close(チェックポイント)→ 再 Open で、新しい値が DB 本体に
```

**pager/wal_test.go(3) — TestWALTornTailRecovery**

```go

	p.MarkDirty(page2.ID)

		t.Fatal(err)
```

### A/B 計測(10,000 件 INSERT、seeddemo)

`cmd/seeddemo` で `users` テーブルへ 10,000 件を `INSERT` し、rollback モードと WAL モードで所要時間を比べます。あらかじめ `a.db`(rollback のまま)と `b.db`(`CREATE TABLE` の後に `PRAGMA journal_mode = WAL` を実行済み)を REPL で用意してあります。

```console
$ time go run ./cmd/seeddemo a.db 10000   # rollback モード
go run ./cmd/seeddemo a.db 10000  1.02s user 11.85s system 12% cpu 1:39.55 total

$ time go run ./cmd/seeddemo b.db 10000   # WAL モード(PRAGMA 切替済み)
go run ./cmd/seeddemo b.db 10000  0.42s user 2.60s system 10% cpu 29.310 total
```

**99.55 秒 → 29.31 秒。約 3.4 倍です。** 内訳を見ると、理論値とよく符合します。第 13 章のコミットプロトコルは 1 コミットあたり 3 回の fsync(ジャーナル用 2 回 + 本体用 1 回)を要し、WAL は 1 回だけです。単純な fsync 回数の比なら 3 倍のはずですが、実測は 3.4 倍——超過分は、`walCheckpointThreshold`(1000 フレーム)ごとに走る自動チェックポイントの後払いコストです。14.2 節で述べたとおり、「コミットの fsync は消えたのではなく、チェックポイントへまとめて後払いされる」という会計そのものが、この実測値の中に織り込まれています。それでも、後払いされたコストを含めてなお 3.4 倍速いという事実が、WAL 方式の実利を示しています。

`user`/`system` の内訳も雄弁です。**rollback モードの 11.85 秒の system 時間が、WAL モードでは 2.60 秒まで落ちています。** `user` 時間(CPU がアプリケーションのコードを実行していた時間)はどちらも 1 秒前後とほとんど変わらないのに対し、`system` 時間(カーネルに処理を委ねていた時間、その大半が `fsync` の完了待ち)だけが大きく縮んでいます。**待っていたのはカーネルの `fsync` だった**——第 4 章 4.3 節で述べた「`fsync` はミリ秒単位のコストがかかる高価な操作」という理屈が、`user`/`system` という OS レベルの計測値の対比として、ここにはっきり現れています。

第 12 章 12.5 節で見た `.timer` による **240 倍**(`WHERE id = 77777` と `WHERE name = 'user77777'` の実行時間差)と、この章の **3.4 倍**は、同じ「速さ」という言葉でも指している最適化の層がまったく違います。**読みの最適化はプラン(どの経路でデータへたどり着くか)、書きの最適化はログ形式(どうディスクへ確定させるか)。** 第 12 章はクエリオプティマイザ、この章はストレージエンジンのコミットプロトコル——両方合わさって、初めて「実用に足りるデータベース」の速さに近づきます。

### WAL ファイルの観察

## 14.6　まとめ

- **undo ログ(ロールバックジャーナル)と redo ログ(WAL)** の違いを整理した。前者は「変更前を退避してから本体を書く」ので本体を書く分だけ遅く、失敗したら退避した内容へ戻す。後者は「変更後をログに追記するだけ」でコミットを終え、本体への反映は後回しにできる——コミットの fsync が 3 回から 1 回に減る核心の理由
- WAL のフォーマット(ヘッダ 16B + フレーム = ページ番号 4B + コミット印 4B + 内容 4096B)と、読み取りの 2 層構造(`walIndex` にあれば WAL、なければ DB 本体)を設計した。リカバリは「最後のコミット印より後ろを無視する」だけで済み、ロールバックジャーナルのような復元書き戻しが要らない——これが undo と redo の非対称の核心である
- `wal.go` を実装した。`scanWALFrames` の `pending` バッファが尻切れフレームを棄てること、`walCommit` が書き始め位置をファイルサイズではなく `walEnd` から取ることで書き込み失敗時の孤児フレームの蘇生を防ぐこと(レビューで見つかった危険の教材化)、チェックポイントが本体への fsync を先に・WAL の truncate を後に行う冪等な処理であることを確かめた。**追記型ログの正しさは「どこが有効な末尾か」の管理に尽きる**
- `pager.go` に `JournalMode` 型とヘッダオフセット 28-31 を追加し、`readPage` の WAL 優先分岐(たった数行)、`Open` の `openWALIfPresent`、`Commit` の WAL 分岐と自動チェックポイント、`Close` のチェックポイントを実装した。SQL に `PRAGMA journal_mode`/`PRAGMA wal_checkpoint` を追加し(語彙は SQLite 互換の `wal`/`delete`)、PRAGMA が autocommit の対象外(Tx を張らない、それ自体で完結した設定変更)であることを確認した
- 動作確認で、`exec` のテスト実行時間を押し上げていた fsync のコストを、`seeddemo` による 10,000 件 INSERT の A/B 計測で **99.55 秒 → 29.31 秒(約 3.4 倍)**という実測値として取り戻した。`user`/`system` の内訳(11.85 秒 → 2.60 秒の system 時間削減)は「待っていたのはカーネルの fsync だった」ことを裏付け、第 3 章の演習(ヘッダのジャーナル方式フィールド)を自分のフォーマット(`0000 0001` = WAL)で回収した

壊れなくなり、そして再び速くなりました。**速くて壊れない**——第 13 章と第 14 章の 2 章で、ついにこの両立を実現しました。しかし、まだ大きな前提が残っています。ここまでの `minidb` は、常に「同時に 1 人」だけがファイルを開いている状況しか想定していません。もし 2 つ目の REPL が同じ `mini.db` を同時に開いたら、何が起きるでしょうか。第 1 章 1.1 節で立てた 4 つの壁のうち、最後の壁——壁 4(同時アクセスで壊れる)——へ、第 15 章で挑みます。
