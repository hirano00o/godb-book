## 15.1　最後の壁 — 第 1 章の壁 4

第 1 章 1.1 節は、4 つの壁を並べてこの本の地図を描きました。そのうち最後の 1 つには、こう書かれていました。

> 2 つのプロセスが同時に読み書きしたら、更新は簡単に失われます(いわゆるロストアップデート)。_複数の読み書きが混在しても、それぞれが一貫した世界を見られる仕組み_ — ロックと同時実行制御が必要で、これも第 4 部で扱います。

そして 1.4 節では、この壁を正面から扱わないための割り切りも、同時に宣言していました。

> minidb の設計上の割り切りも明示しておきます。**データベースは単一ファイル、ページサイズは 4096 バイト固定、文字コードは UTF-8 のみ、当面は単一プロセスからの利用を前提**とします。

第 13 章はさらに、ACID の 4 性質のうち何がすでに片付いていて、何が残っているかを先んじて整理していました。

> **I(分離性、Isolation)** — 複数のトランザクションが同時に走っても、互いの結果が混線しない。第 15 章で扱う

**A**(原子性)と **D**(耐久性)は第 13・14 章のジャーナリングと WAL で、**C**(一貫性)は第 6 章の `BTree.Insert` がすでに担っています。残る **I**(分離性)を、この章でついに実装します。その一方で、`pager.Open` は誰の許可も得ずにファイルを開き、`Commit` は他の接続の存在を一切気にせず dirty ページを書き戻す——第 2 章からずっと生き延びていた「単一プロセス前提」を、この章で卒業します。

### 思考実験 — 2 つの REPL が同じ DB を開いたら

具体的に何が壊れるかを、今の(ロックを持たない)minidb で辿ってみます。ターミナルを 2 つ開き、両方で `go run ./cmd/minidb mini.db` を実行したとします。

1. 接続 A が `SELECT age FROM users WHERE id = 1` を実行し、`age = 30` を B-Tree のページごとキャッシュへ読み込む
2. 接続 B が `UPDATE users SET age = 31 WHERE id = 1` を実行してコミットする — ディスク上の age は 31 になる
3. 接続 A が(B の変更をまったく知らないまま)`UPDATE users SET age = 32 WHERE id = 1` を実行する。A のキャッシュは B のコミットより前のまま古く固まっている。A の書き込みは「古い状態からの更新」であり、B がつけた 31 という値は、A が上書きした瞬間に跡形もなく消える

3 の結果を指して**ロストアップデート**と呼びます。誰もエラーを出さず、誰も気づかないまま、B の更新はなかったことになりました。第 13・14 章で積み上げてきた ACID の A(原子性)と D(耐久性)は、1 つの接続の中では完璧に守られています——しかし 2 つの接続をまたいだ瞬間、その保証はあっさり意味を失います。

### 対策は 2 つセットで

このロストアップデートを塞ぐには、2 つの独立した仕組みが要ります。

- **書く権利の調停(ロック)** — 「今この瞬間、誰が書き込んでよいか」を決める。複数の接続が同時に書き込もうとしたとき、一方だけが勝ち、他方は待つか諦めるかを選ぶ
- **読んだものの鮮度確認(変更カウンタ)** — ロックが取れたとしても、手元のキャッシュそのものが古いままでは意味がない。「自分が最後に読んでから、他の誰かがコミットしていないか」を確認し、していれば読み直す

上の思考実験のステップ 3 は、実はロックだけでは防げません。A が `UPDATE` を発行する時点でロックを取得できたとしても(B はすでにコミットを終えてロックを解放している)、A のキャッシュにある `age = 30` という値そのものが古いままです。ロックが答えるのは「今書いてよいか」、変更カウンタが答えるのは「今読んでいるものは最新か」——この章では、この 2 つをセットで実装します。

## 15.2　設計 — flock と変更カウンタ

### OS のアドバイザリロック — flock(2)

複数プロセスが 1 つのファイルへの読み書きを調停する仕組みは、OS が用意しています。Unix 系 OS の `flock(2)` システムコールです。POSIX の `fcntl` ロックと違い、`flock` はファイル全体に対して単純な種類のロックしか持ちません。

- **共有ロック(`LOCK_SH`)** — 複数のプロセスが同時に取得できる。読み取り同士は競合しない、という前提に立つ
- **排他ロック(`LOCK_EX`)** — 同時に 1 つのプロセスしか取得できない。他のプロセスが共有・排他いずれかのロックを持っている間は取得できない
- **ノンブロッキング(`LOCK_NB`)** — 通常 `flock` は取得できるまでブロックして待つが、`LOCK_NB` を重ねると、取得できなければ即座にエラーを返す

`flock` が**アドバイザリロック**(勧告的ロック)であることには注意が要ります。カーネルがファイルへの実際の読み書きを強制的に禁止するわけではありません——ロックを一切気にせず `read`/`write` を呼べば、それはそのまま通ります。プロセス同士が「ロックを確認してから読み書きする」という規約を守って初めて、ロックは意味を持ちます。minidb のすべての読み書きは `Pager` を経由するので、この規約は `Pager` の内部に閉じ込められ、利用者が意識する必要はありません。

もう 1 つ、`flock` には決定的な利点があります。**ロックを保持しているプロセスが(正常終了であれクラッシュであれ)終了すれば、カーネルが自動的にそのロックを解放します。** 明示的な `unlock` を呼び忘れても、あるいはそもそも呼べないほど手荒く(`kill -9` で)プロセスが死んでも、ロックは道連れにならず消えます。もしロックが「ファイルに書かれたフラグ」のような自前の仕組みだったら、クラッシュしたプロセスの死骸が残したロックを誰も片付けられず、DB は永遠に「誰かが使用中」のまま固まってしまいます——次章で行うクラッシュ実験でも、この「カーネルが自動的に片付けてくれる」という性質がそのまま効いてきます。

### minidb のロック規則

ロールバックジャーナルモードと WAL モードでは、ロックを保持する「単位」が異なります。

**表 15-1　ロックの保持単位と規則**

| モード                 | 保持単位             | 取得タイミング       | 解放タイミング             | 備考                                                                                       |
| ---------------------- | -------------------- | -------------------- | -------------------------- | ------------------------------------------------------------------------------------------ |
| ロールバックジャーナル | トランザクション単位 | `Begin` で共有ロック | `Commit`/`Rollback` で解放 | 読み取りのみの Tx は排他ロックへ昇格しない。書き込みコミットの直前だけ排他ロックへ昇格する |
| WAL                    | 接続単位             | `Open` で排他ロック  | `Close` で解放             | 単一接続専用。Open〜Close の間ずっと保持し続ける                                           |

ロールバックジャーナルモードの規則は単純です。`Begin` は必ず共有ロックを取ります——読み取りだけの `SELECT` であっても、他の接続がその瞬間に書き込み中でないことを確認する必要があるからです。共有ロック同士は競合しないので、複数の接続が同時に読み取りトランザクションを開けます。書き込みを伴うコミット(dirty ページが 1 枚以上ある `Commit`)だけが、共有ロックを排他ロックへ昇格させます。読み取りだけのトランザクションは、この昇格を一度も経験せずに `Commit`/`Rollback` で共有ロックを手放して終わります。

WAL モードはまったく違う設計です。**接続そのものが、`Open` した瞬間から `Close` するまでずっと排他ロックを持ち続けます。** これは第 14 章で確認した事情の直接の帰結です。minidb の `walIndex`(ページ番号 → WAL 内オフセットの対応表)はプロセス内のメモリにしか存在せず、複数の接続で共有する仕組み——本物の SQLite が `-shm` という共有メモリファイルで実現している `wal-index`(第 14 章 sqlite-note)——を minidb は持っていません。2 つ目の接続が同じ WAL ファイルを覗いても、1 つ目の接続がメモリ上に持つ `walIndex` を見ることはできず、整合性を保てません。だから WAL モードは、単一接続だけを許すことで問題そのものを回避します——接続単位の排他ロックは、この「単一接続専用」という制約を強制する道具です。

### 失敗の意味論 — 待たずに ErrBusy

ロックが取得できなかったとき、minidb は**待ちません**。`LOCK_NB` により即座にエラーを返し、それを `ErrBusy`(SQLite の `SQLITE_BUSY` に相当)として呼び出し元へ伝えます。ブロックして待つ選択肢もありえますが、それは「いつまで待つか」「デッドロックにならないか」という新しい問題を持ち込みます——本書はこれを避け、SQLite の既定の挙動と同じ「即座に失敗を返し、リトライは呼び出し側の責任」という単純な意味論を選びます。

明示トランザクション(`BEGIN`...`COMMIT`)の途中で `ErrBusy` を受け取っても、トランザクションは生きたままです。利用者は改めて `COMMIT` を打って再試行するか、`ROLLBACK` で諦めるかを選べます。15.3 節で見るとおり、この「トランザクションを生かしたまま返す」という性質を壊さないことが、この章の実装でもっとも注意を要した点でした。

### 変更カウンタ — 鮮度確認の道具

ロックが解決するのは「今書いてよいか」だけです。15.1 節の思考実験で見たとおり、ロックを取れても手元のキャッシュが古いままなら、ロストアップデートは防げません。そこでヘッダページに**変更カウンタ**を 1 つ追加します。オフセット 32-35、コミットのたびに 1 ずつ増える `uint32` です。

第 3 章で、本物の SQLite のヘッダのオフセット 24-27 に **file change counter** というフィールドがあることを確認しました。変更カウンタは、その minidb 版です。使い方は単純です。`Begin` が共有ロックを取得した直後、ディスク上の変更カウンタの値を読み、メモリ上に持っている値と比較します。違っていれば——つまり、自分が最後にこの DB を見てから、他の接続が少なくとも 1 回コミットしていれば——キャッシュを丸ごと破棄して読み直します。

この設計には、第 12 章で見た**スキーマクッキー**(プリペアドステートメントを再コンパイルすべきかの判定に SQLite が使う整数)と同じ形の発想があります。**「何が変わったか」を細かく追跡する代わりに、「何かが変わったか」を 1 個の整数比較だけで済ませる。** 差分を検出する複雑な仕組みを持たない代わりに、変わったとわかった瞬間はキャッシュを全部捨てるという、粗いが確実な安全策を取ります。15.3 節で見るとおり、この「丸ごと捨てる」という荒っぽさが許されるのには理由があります。

### ロックと変更カウンタの分業

この 2 つの道具は、片方だけでは役目を果たせません。**ロックだけ**を実装し変更カウンタを省いたら、15.1 節の思考実験の 3 番目のステップ(A が B のコミットを知らないまま古いキャッシュへ上書きする)は防げないままです——A は自分の番が来たときに正しくロックを取得できてしまい、ロック自体は何のエラーも出しません。壊れているのはロックの取得ではなく、A が読んでいる**中身**だからです。逆に**変更カウンタだけ**を実装しロックを省いたら、A と B が寸分違わぬタイミングでコミットを試みたとき、2 つの `Commit` が同時にジャーナルへ書き込みに行き、ファイルの同じ範囲を取り合って壊れます——カウンタは「読んだものが古いかどうか」しか答えず、「今この瞬間、書いてよいのは誰か」には答えられません。ロックは書き込みの**同時実行**を防ぎ、変更カウンタは読み取りの**陳腐化**を防ぐ——守備範囲が異なる 2 つの道具だからこそ、両方が要ります。

## 15.3　実装 — lock.go と pager のフック

まず `pager` パッケージに、この章で新しく追加する `lock.go` の全文を掲載します。

**pager/lock.go(全文)**

```go
// lock.go は flock(2) による、複数プロセス(または同一プロセス内の複数
// Pager インスタンス)間の同時アクセス制御を担う。
//
// Unix 専用(syscall.Flock を直接使う)。Windows では動作しない。
package pager

import (
	"container/list"
	"errors"
	"syscall"
)

// ErrBusy は他の接続がデータベースを使用中で、ロックを取得できなかった
// ことを表す(SQLite の SQLITE_BUSY に相当)。
var ErrBusy = errors.New("データベースがロックされています(他の接続が使用中です)")

// flockNB は DB ファイルの fd に対して flock(2) をノンブロッキングモード
// (LOCK_NB)付きで呼び出す薄いラッパー。取得できなければ ErrBusy を返す。
//
// flock はプロセス単位ではなくオープンファイル記述(fd)単位のロックなので、
// 同一プロセス内であっても別々の fd(= 別々の Pager インスタンス)同士は
// きちんと競合する。これを利用して、テストは 2 プロセスを起動せずとも
// 1 プロセス内で 2 つの Pager を開くだけで競合を再現できる。
func (p *Pager) flockNB(how int) error {
	if err := syscall.Flock(int(p.file.Fd()), how|syscall.LOCK_NB); err != nil {
		if errors.Is(err, syscall.EWOULDBLOCK) {
			return ErrBusy
		}
		return err
	}
	return nil
}

// lockShared は共有ロック(LOCK_SH)を取得する。共有ロックは複数の接続が
// 同時に保持できる(読み取り同士は競合しない)。
func (p *Pager) lockShared() error {
	return p.flockNB(syscall.LOCK_SH)
}

// lockExclusive は排他ロック(LOCK_EX)を取得する。
//
// 既に共有ロックを保持している状態からこれを呼ぶ(SH → EX への昇格)場合、
// flock(2) には「共有ロックを保持したまま排他ロックへ昇格する」操作が
// ない。そのためカーネル内部では、いったん共有ロックを手放してから
// 改めて排他ロックを取り直す形になり、その一瞬の隙間に別の接続が
// 割り込んでロックを奪う可能性が理論上ある。SQLite が
// SHARED → RESERVED → EXCLUSIVE という 3 段階のロックを用意し、
// 書き込みを始める前にまず RESERVED を取って「これから書き込むつもりだ」
// という意図を早期に宣言しているのは、まさにこの隙間を塞ぐためである。
// minidb は SHARED/EXCLUSIVE の 2 段階しか持たず、この素朴さ
// (昇格の瞬間に理論上の競合窓が空くこと)を受け入れる。
func (p *Pager) lockExclusive() error {
	return p.flockNB(syscall.LOCK_EX)
}

// unlock は保持しているロック(共有・排他いずれも)を解放する。
func (p *Pager) unlock() error {
	return syscall.Flock(int(p.file.Fd()), syscall.LOCK_UN)
}

// invalidateCacheIfStale はディスク上の変更カウンタとメモリ上の値を比較し、
// 異なっていれば(= 他の接続がこの Begin より前にコミットしていた)
// キャッシュ全体を無効化する。
//
// 呼び出しは Begin が共有ロックを取得した直後に限られ、その時点では
// トランザクションはまだ始まっていない(dirty ページは 1 枚も存在しない)。
// そのためキャッシュを丸ごと空にしてヘッダページだけ読み直せば十分で、
// 部分的な差分マージのような複雑な処理は要らない。
func (p *Pager) invalidateCacheIfStale() error {
	onDisk, err := p.changeCounterOnDisk()
	if err != nil {
		return err
	}
	if onDisk == p.changeCounter {
		return nil
	}
	p.cache = make(map[PageID]*Page)
	p.lru = list.New()
	p.lruIndex = make(map[PageID]*list.Element)
	return p.loadHeader()
}
```

**`flock` は fd 単位のロックです。** これが `flockNB` のコメントに書かれている、最初に押さえるべき性質です。プロセス単位ではなく、`Fd()` が返すオープンファイル記述の単位でロックが競合します。同一プロセス内で 2 つの `Pager` インスタンスが同じパスを別々に `Open` すれば、それぞれが別々の fd を持つので、きちんと競合します。これは実装上の副産物ではなく、この章のテストの設計を直接支えています——後述の `lock_test.go` の 5 本のテストはすべて、1 つの `go test` プロセスの中で 2 つの `Pager` を開くだけで、2 プロセスを起動せずに競合を再現しています。

**昇格の隙間 — SH から EX へ、瞬間だけ丸裸になる。** `lockExclusive` のコメントが説明しているとおり、`flock(2)` には「共有ロックを保持したまま排他ロックへ昇格する」という原子的な操作がありません。カーネルの実装は、内部的にいったん共有ロックを手放してから改めて排他ロックを取り直す形になります。この「手放してから取り直す」の間、理論上はごくわずかな隙間が空きます——別の接続がその隙間に割り込んでロックを先に奪う可能性が(確率は低くとも)ゼロではありません。

本物の SQLite がこの隙間を塞ぐために持っているのが、`SHARED` → `RESERVED` → `EXCLUSIVE` という 3 段階のロックです。書き込みを始めるとき、SQLite はいきなり `EXCLUSIVE` を取りにいくのではなく、まず `RESERVED`(「これから書き込むつもりだ」という意図の宣言。他の `SHARED` を持つ読者とは共存できるが、他の `RESERVED` とは共存できない)を取ります。これにより「自分が書き込むつもりであること」を早期に他の接続へ知らせ、それから安全なタイミングで `EXCLUSIVE` へ進みます。minidb は `SHARED`/`EXCLUSIVE` の 2 段階しか持たないので、この早期宣言というクッションがなく、昇格の瞬間に理論上の競合窓を抱えたままです——素朴さを受け入れた設計判断であり、隠された欠陥ではありません(この節の後半の warn で、この隙間が実際に噛んだ別の穴を扱います)。

**`invalidateCacheIfStale` が「丸ごと捨てて読み直す」だけで済む理由。** この関数が呼ばれるのは、`Begin` が共有ロックを取得した直後、ただ 1 か所だけです。その時点でトランザクションはまだ始まっておらず、dirty なページは 1 枚も存在しません——直前の `Commit`/`Rollback` がすべての dirty ページを解消してからでなければ、次の `Begin` は呼べないからです。つまり「キャッシュに載っているすべてのページは、ディスク上の内容とまだ矛盾していない、ただ古いだけ」という保証がすでにあります。差分だけを部分的にマージするような複雑な処理は要らず、キャッシュを空にしてヘッダページだけ読み直せば、それだけで「最新の状態から始まる、まっさらなトランザクション」が用意できます。15.2 節で触れた「粗いが確実」という設計判断の裏付けが、まさにこの「呼び出しどきが 1 か所に限定されている」という性質です。

### pager.go のフック

`lock.go` の道具を使う側、`pager.go` の変更・追加部分を、実際のファイル内の並び順で示します。無変更部分(`Get`/`Allocate`/`MarkDirty`/`touch`/`evictIfNeeded`/`journal.go`・`wal.go` まわり など)は第 14 章のままです。完成形は `code/ch15/pager/pager.go` を参照してください。

**pager/pager.go(1) — フィールド追加(`changeCounter`・`walLocked`)**

```go
	inTx bool // トランザクション中かどうか(Begin〜Commit/Rollback)

	journalMode JournalMode // ロールバックジャーナル方式か WAL 方式か

	changeCounter uint32 // 変更カウンタのメモリ上の現在値(詳細は changeCounterOffset)

	// walLocked は WAL モード中、Open〜Close の間ずっと保持している
	// 排他ロックを掴んでいるかどうか(詳細は lock.go)。
	walLocked bool

	// WAL モードでのみ使うフィールド(詳細は wal.go)。
	walFile   *os.File         // WAL ファイル(WAL モードでのみ開く)
	walIndex  map[PageID]int64 // ページ → WAL 内の最新コミット済みフレームのオフセット
	walFrames int              // WAL に書かれているコミット済みフレームの総数
	walEnd    int64            // 有効な(コミット済みの)フレーム列の末尾オフセット。
	// 次の walCommit はここから書き始める。ファイルサイズではなくこの値を
	// 使うことで、書き込みエラーで失敗したコミットの孤児フレームが末尾に
	// 残っていても、次のコミットがそれを上書きできる(蘇生を防ぐ)。
}
```

`changeCounter` は 15.2 節の変更カウンタのメモリ上の現在値、`walLocked` は WAL モードの接続単位ロックを今掴んでいるかどうかのフラグです。第 14 章までの `Pager` に、この 2 つが増えました。

**pager/pager.go(2) — Open で WAL モードの接続単位ロックを取得**

```go
	// 既存ファイル: ヘッダページを検証して総ページ数を読み取る
	if err := p.loadHeader(); err != nil {
		file.Close()
		p.closeWALFile()
		return nil, err
	}

	// WAL モードの DB は接続単位で排他ロックを取り、Close まで保持する
	// (詳細は switchToWAL のコメント)。既に WAL モードで永続化された
	// ファイルを開く場合はここで取得する。
	if p.journalMode == JournalModeWAL {
		if err := p.lockExclusive(); err != nil {
			file.Close()
			p.closeWALFile()
			return nil, err
		}
		p.walLocked = true
	}
	return p, nil
}
```

`loadHeader` が読み込んだ `journalMode` が `JournalModeWAL` であれば、`Open` の最後で排他ロックを取得します。**この分岐が要るのは、「WAL モードとして永続化済みの DB を、2 回目以降に開く」ケースのためです。** 新規に `PRAGMA journal_mode = WAL` でモードを切り替える場合のロック取得は、後述の `switchToWAL`(`wal.go`)側の責務です——`Open` はあくまで「すでに WAL モードだったファイルを開き直す」場合を担当します。

**pager/pager.go(3) — ヘッダレイアウトへの追記と changeCounter の初期化・読み込み**

```go
// initHeader はヘッダページを初期化してディスクに書き込む。
// レイアウト:
//
//	オフセット 0-7  : マジック文字列 "minidb01"
//	オフセット 8-11 : ページサイズ(ビッグエンディアン uint32)
//	オフセット 12-15: 総ページ数(ビッグエンディアン uint32)
//	オフセット 16-19: ルートページ番号(ビッグエンディアン uint32)
//	オフセット 20-23: フリーリスト先頭ページ番号(ビッグエンディアン uint32、0=空)
//	オフセット 24-27: フリーリストのページ数(ビッグエンディアン uint32)
//	オフセット 28-31: ジャーナルモード(ビッグエンディアン uint32、0=ロールバックジャーナル、1=WAL)
//	オフセット 32-35: 変更カウンタ(ビッグエンディアン uint32。本物の SQLite の
//	                  ヘッダにある file change counter、オフセット 24-27 の
//	                  minidb 版。コミットのたびに 1 増える。他の接続が
//	                  Begin 時にこの値の変化を見てキャッシュの陳腐化を検知する
//	                  ために使う。詳細は lock.go)
func (p *Pager) initHeader() error {
	page := &Page{ID: headerPageID}
	copy(page.Data[0:8], Magic)
	binary.BigEndian.PutUint32(page.Data[8:12], PageSize)

	p.numPages = 1 // ヘッダページ自身
	binary.BigEndian.PutUint32(page.Data[12:16], p.numPages)
	// journalMode は既定でロールバックジャーナル(0)。ゼロ値のまま
	// なので書き込みは不要だが、レイアウト上の意味を明示するために残す。
	binary.BigEndian.PutUint32(page.Data[journalModeOffset:journalModeOffset+4], uint32(JournalModeRollback))
	p.journalMode = JournalModeRollback
	// changeCounter も既定で 0(ゼロ値のまま書き込みは不要だが明示のため残す)。
	binary.BigEndian.PutUint32(page.Data[changeCounterOffset:changeCounterOffset+4], 0)
	p.changeCounter = 0

	p.cache[headerPageID] = page
	p.touch(headerPageID)
	page.dirty = true
	return p.Flush()
}

// loadHeader は既存ファイルのヘッダページを読み込んで検証する。
func (p *Pager) loadHeader() error {
	page, err := p.readPage(headerPageID)
	if err != nil {
		return err
	}
	if string(page.Data[0:8]) != Magic {
		return errors.New("minidb ファイルではありません")
	}
	if got := binary.BigEndian.Uint32(page.Data[8:12]); got != PageSize {
		return fmt.Errorf("ページサイズが不一致: file=%d, build=%d", got, PageSize)
	}
	p.numPages = binary.BigEndian.Uint32(page.Data[12:16])
	p.journalMode = JournalMode(binary.BigEndian.Uint32(page.Data[journalModeOffset : journalModeOffset+4]))
	p.changeCounter = binary.BigEndian.Uint32(page.Data[changeCounterOffset : changeCounterOffset+4])
	p.cache[headerPageID] = page
	p.touch(headerPageID)
	return nil
}
```

ヘッダのレイアウト表に、第 14 章のジャーナルモード(28-31)の隣、オフセット 32-35 として変更カウンタが加わりました。`initHeader`(新規ファイル)は 0 で明示的に初期化し、`loadHeader`(既存ファイル)はディスクから読んだ値をそのまま `p.changeCounter` へ格納します——他のフィールドとまったく同じ、素直な追加です。

**pager/pager.go(4) — Close で接続単位ロックを解放**

```go
// Close は Flush してからファイルを閉じる。トランザクション中であれば、
// コミットされていない変更を確定させてしまわないよう、まず自動的に
// Rollback してから閉じる。WAL モードのときは、WAL に溜まった変更を
// DB 本体へ反映してから閉じる(次回 Open のたびに WAL 全体を読み直す
// 手間を省くための、いわば「きれいな終了」)。WAL モードの接続単位の
// 排他ロック(Open 参照)もここで解放する。
func (p *Pager) Close() error {
	if p.inTx {
		if err := p.Rollback(); err != nil {
			p.file.Close()
			return err
		}
	}
	if p.walFile != nil {
		if err := p.checkpoint(); err != nil {
			p.file.Close()
			p.walFile.Close()
			return err
		}
		if err := p.walFile.Close(); err != nil {
			p.file.Close()
			return err
		}
		p.walFile = nil
	}
	if p.walLocked {
		// ロック解放の失敗はファイルを閉じる邪魔をしない。fd を閉じれば
		// いずれにせよカーネルが flock を自動的に解放するため、ここでの
		// エラーは記録だけして処理を続ける実害はないが、呼び出し側に
		// 状況を伝えるためエラーはそのまま返す。
		if err := p.unlock(); err != nil {
			p.file.Close()
			return err
		}
		p.walLocked = false
	}
	if err := p.Flush(); err != nil {
		p.file.Close()
		return err
	}
	return p.file.Close()
}
```

`p.walLocked` が立っている(WAL モードで、かつ接続単位ロックを実際に保持している)ときだけ `unlock` を呼びます。コメントにあるとおり、この解放が失敗してもファイルを閉じる処理自体は続行します——fd を閉じればいずれにせよカーネルが flock を自動的に解放するので実害はありませんが、呼び出し側に状況を隠さないためにエラーはそのまま返します。

**pager/pager.go(5) — Begin のロック取得とキャッシュ無効化**

```go
// Begin はトランザクションを開始する。以後、Commit か Rollback まで
// ディスクへの書き戻し(Flush)は行われない。二重 Begin はエラー。
//
// ロールバックジャーナルモードでは、まず DB ファイルに共有ロックを取る
// (他の接続が読み取り中でも Begin できるが、書き込み中なら ErrBusy)。
// 取得できたら、ディスク上の変更カウンタとメモリ上の値を比較し、他の
// 接続がその間にコミットしていればキャッシュを無効化する
// (invalidateCacheIfStale、詳細は lock.go)。
//
// WAL モードでは、接続そのものが Open〜Close の間ずっと排他ロックを
// 保持しているため(詳細は Open・switchToWAL)、Begin では何もしない。
func (p *Pager) Begin() error {
	if p.inTx {
		return errors.New("トランザクションは既に開始しています")
	}
	if p.journalMode == JournalModeRollback {
		if err := p.lockShared(); err != nil {
			return err
		}
		if err := p.invalidateCacheIfStale(); err != nil {
			_ = p.unlock()
			return err
		}
	}
	p.inTx = true
	return nil
}
```

`Begin` の骨格(二重 `Begin` を拒む早期リターン、`p.inTx = true`)は第 13 章のままです。増えたのは `p.journalMode == JournalModeRollback` の分岐 1 つだけ——共有ロックを取り(`lockShared`)、成功したら `invalidateCacheIfStale` で鮮度を確認します。`invalidateCacheIfStale` 自体が失敗した場合、`_ = p.unlock()` でせっかく取った共有ロックを律儀に手放してから返しています。ロックを取ったのに `inTx` を立てないまま関数を抜けると、そのロックはどこからも解放されない孤児になってしまうためです。

WAL モードがここで何もしない理由は明快です。接続単位のロックは `Open` の時点ですでに取得済みで、`Close` まで保持し続けます。`Begin` のたびに何かを取り直す必要が、そもそもありません。

**pager/pager.go(6) — Commit のロック昇格と変更カウンタの先行インクリメント**

```go
// Commit はトランザクションを確定する。モードによって手順が異なる:
//
//   - ロールバックジャーナル: 変更前ページをジャーナルへ退避してから
//     dirty ページをディスクへ書き戻し、最後にジャーナルを削除する。
//   - WAL: dirty ページを WAL に追記するだけで、DB 本体には触れない
//     (詳細は walCommit)。
//
// dirty ページが 1 枚もなければ(変更のないトランザクション)、
// どちらの方式でも何も書かずにそのままトランザクションを終える。
//
// dirty ページが 1 枚以上あれば、実際のコミット処理より前に変更カウンタを
// インクリメントしてヘッダページを dirty にする(bumpChangeCounter)。
// これによりカウンタの更新自体もジャーナル/WAL の保護下に入り、
// クラッシュしてもカウンタと実際の変更内容が食い違わない。
//
// ロールバックジャーナルモードで dirty ページがあるときは、書き込みに
// 入る前に共有ロックを排他ロックへ昇格させる(lockExclusive)。取得
// できなければ ErrBusy を返す — この時点ではまだ何もディスクに書いて
// いないので、トランザクションは生きたまま残り、呼び出し側は再試行するか
// Rollback を選べる。コミットが完了したらロックを解放する。
func (p *Pager) Commit() error {
	if !p.inTx {
		return errors.New("トランザクションが開始されていません")
	}

	dirty := p.dirtyPages()
	if len(dirty) == 0 {
		p.inTx = false
		if p.journalMode == JournalModeRollback {
			return p.unlock()
		}
		return nil
	}

	if p.journalMode == JournalModeRollback {
		if err := p.lockExclusive(); err != nil {
			// flock の昇格(SH→EX)は「解放してから取り直す」ため、失敗した
			// 時点で元の共有ロックは失われている(BSD 由来の仕様)。ここで
			// 共有ロックを取り直しておかないと、ErrBusy 後も生きている
			// このトランザクションが以後ロックなしで読み続けてしまう。
			_ = p.lockShared()
			return err
		}
	}

	if err := p.bumpChangeCounter(); err != nil {
		return err
	}
	dirty = p.dirtyPages() // ヘッダが新たに dirty になった分を含め直す

	if p.journalMode == JournalModeWAL {
		if err := p.walCommit(dirty); err != nil {
			return err
		}
		p.inTx = false
		// フレームが溜まりすぎる前に自動でチェックポイントする。コミット
		// そのものは既に WAL への fsync で耐久性を得ているので、ここでの
		// チェックポイント失敗はデータ消失にはつながらないが、呼び出し側に
		// 状況を伝えるためエラーはそのまま返す。
		if p.walFrames > walCheckpointThreshold {
			return p.checkpoint()
		}
		return nil
	}

	if err := p.writeJournal(dirty); err != nil {
		return err
	}
	if err := p.flush(); err != nil {
		return err
	}
	// ジャーナルの削除こそが「コミットの瞬間」。ここまでの手順(ジャーナル
	// 書き込み → fsync → ヘッダ書き込み → fsync → DB 本体へ Flush)が
	// すべて終わって初めて安全に消せる。
	if err := os.Remove(p.journalPath()); err != nil {
		return err
	}

	p.inTx = false
	return p.unlock()
}
```

`Commit` は `bumpChangeCounter`(次項)を呼んでから `dirty = p.dirtyPages()` を**やり直しています**。これは見落としやすい 1 行ですが省けません。`bumpChangeCounter` はヘッダページを新たに dirty にするので、その前に取っていた `dirty` のスライスにはヘッダページの変更が含まれていません。もしこの再取得を忘れると、変更カウンタのインクリメントがジャーナル(または WAL)へ書き込まれないまま `flush` されてしまい、クラッシュ後の整合性(カウンタと実際の変更内容が食い違わない)が壊れます。

<div class="warn">

<span class="note-title">レビューで見つけた穴: EX 昇格が失敗すると SH まで失われている</span> `Commit` の `lockExclusive` 呼び出しが失敗したときの処理は、この章の初版ではこうなっていました——`return err` の 1 行だけで、`_ = p.lockShared()` は存在しませんでした。一見自然です。`Begin` が取った共有ロックはまだ手元にあるはずで、`ErrBusy` を返してもトランザクションは「共有ロックを保持したまま」生き続ける、と考えたからです。

しかし `man flock` の記述に立ち返ると、これは誤りでした。この節の冒頭で触れたとおり、`flock(2)` に SH → EX の原子的な昇格はありません。カーネルは内部で「いったん今のロックを手放してから、要求されたロックを取り直す」という手順を踏みます。ここで**取り直しに失敗した**場合——つまり `lockExclusive` が `ErrBusy` を返す場合——手放した共有ロックは戻ってきません。呼び出し元から見れば「`lockExclusive` を呼んだのに何も変わらなかった」ように見えますが、実際には「共有ロックを失った」という副作用だけが確定してしまっています。

この状態のまま `return err` すると、`p.inTx` は `true` のままなのに、実体としてはロックを一切持たない、丸裸のトランザクションが残ります。呼び出し元(`exec.Engine`)はこの後、`ErrBusy` を受け取ってもトランザクションを生かしたまま `SELECT` を続けられる——`ErrBusy` 後もロックなしで読み続ける穴です。他の接続がその隙にコミットしても、このトランザクションは何の妨げも受けずに古い(あるいは書き換わりつつある)ページを読み進めてしまいます。

修正は 1 行、`_ = p.lockShared()` を失敗時の分岐に加えるだけでした。取り直しは最善努力で構いません(これも失敗すれば `p.inTx` は `true` のままロックなしになりますが、それは「他の接続が今まさに書き込み中」という、極めて短い競合窓でしか起きません)。**ロックの API が失敗を返したとき、手元に何が残っているかは、直感ではなく仕様書まで戻って確かめる必要がある。** `flock` の「SH→EX 昇格は解放してから取り直す」という一文は man ページの奥にひっそり書かれているだけで、関数のシグネチャからは読み取れません。この教訓は、この節の冒頭で見た「昇格の隙間」とまったく同じ根から生えています。

</div>

**pager/pager.go(7) — bumpChangeCounter**

```go
// bumpChangeCounter は変更カウンタをインクリメントし、ヘッダページを
// dirty にする。Commit が dirty ページの存在を確認した直後、既存の
// コミット処理(ジャーナル書き込み / WAL 追記)より前に呼ぶことで、
// カウンタの更新自体もジャーナル/WAL の保護下に入る。
func (p *Pager) bumpChangeCounter() error {
	header, err := p.Get(headerPageID)
	if err != nil {
		return err
	}
	p.changeCounter++
	binary.BigEndian.PutUint32(header.Data[changeCounterOffset:changeCounterOffset+4], p.changeCounter)
	header.dirty = true
	return nil
}
```

`bumpChangeCounter` は `Commit` が dirty ページの存在を確認した直後、ジャーナル書き込み(またはWAL 追記)より**前**に呼ばれます。こうすることで、カウンタの更新自体もジャーナル/WAL の保護下に入ります——クラッシュしてカウンタの更新だけが失われる、というような食い違いは起きません。

**pager/pager.go(8) — Rollback のロック解放とカウンタの巻き戻し**

```go
// Rollback は変更をすべて捨てる。dirty ページをキャッシュ(と LRU)から
// 取り除き、ディスク上のコミット済みヘッダページを読み直して numPages を
// 復元する。トランザクション中はディスクへ一切書いていないので、
// 消すべきジャーナルもない。
//
// ロールバックジャーナルモードでは、最後に保持しているロック(共有、
// または Commit が ErrBusy で失敗して生き残ったトランザクションなら
// 排他のこともある)を解放する。
func (p *Pager) Rollback() error {
	if !p.inTx {
		return errors.New("トランザクションが開始されていません")
	}

	for id, page := range p.cache {
		if !page.dirty {
			continue
		}
		delete(p.cache, id)
		if elem, ok := p.lruIndex[id]; ok {
			p.lru.Remove(elem)
			delete(p.lruIndex, id)
		}
	}

	// ヘッダページ自身が dirty だった場合は上のループで既にキャッシュから
	// 落ちている。ディスク上の(トランザクション開始前のままの)内容を
	// 直接読み直し、numPages と変更カウンタを復元する。これにより
	// Allocate によるメモリ上の割り当てや bumpChangeCounter による
	// カウンタの先行インクリメントも巻き戻る。
	header, err := p.readPage(headerPageID)
	if err != nil {
		return err
	}
	p.numPages = binary.BigEndian.Uint32(header.Data[12:16])
	p.changeCounter = binary.BigEndian.Uint32(header.Data[changeCounterOffset : changeCounterOffset+4])

	p.inTx = false
	if p.journalMode == JournalModeRollback {
		return p.unlock()
	}
	return nil
}
```

`Rollback` に増えた行は 2 つだけです。`p.changeCounter` をディスクの値へ読み直す 1 行(`bumpChangeCounter` によるメモリ上の先行インクリメントを巻き戻す)と、末尾でロールバックジャーナルモードならロックを解放する分岐です。`Rollback` が保持しているロックは、通常なら `Begin` が取った共有ロックですが、`Commit` が `ErrBusy` で失敗した直後に呼ばれた `Rollback` であれば、直前の warn で見た「取り直しに成功していれば共有」「取り直しにも失敗していれば無」のどちらかになりえます——`unlock`(`syscall.Flock(..., LOCK_UN)`)はロックを保持していない状態で呼んでもエラーにならないので、どちらのケースでも安全に呼べます。

**pager/pager.go(9) — changeCounterOffset 定数と changeCounterOnDisk**

```go
// journalMode はヘッダページのオフセット 28-31 に記録する(pager.go 冒頭の
// JournalMode 型を参照)。
const journalModeOffset = 28

// changeCounter はヘッダページのオフセット 32-35 に記録する
// (Pager 構造体のコメントおよび initHeader のレイアウト表を参照)。
const changeCounterOffset = 32

// changeCounterOnDisk はディスク上のヘッダページを直接読み込み(キャッシュを
// 経由しない)、変更カウンタの値を返す。他の接続がコミットしていれば、
// メモリ上の p.changeCounter とは異なる値が返る。Begin がこれを使って
// キャッシュの陳腐化を検知する(詳細は lock.go)。
func (p *Pager) changeCounterOnDisk() (uint32, error) {
	var buf [4]byte
	if _, err := p.file.ReadAt(buf[:], int64(headerPageID)*PageSize+changeCounterOffset); err != nil {
		return 0, fmt.Errorf("変更カウンタの読み取りに失敗: %w", err)
	}
	return binary.BigEndian.Uint32(buf[:]), nil
}
```

`changeCounterOnDisk` が `p.file.ReadAt` を直接呼び、`p.Get`(キャッシュ経由)を使わない点が肝心です。もし `Get` を使ってしまうと、キャッシュに載っている(まだ古いかもしれない)ヘッダページをそのまま返してしまい、「他の接続がコミットしたかどうか」を判定する意味がなくなります。**鮮度を確認するための読み取りは、鮮度を確認する対象であるキャッシュを迂回しなければなりません。**

### wal.go の変更部分 — switchToWAL/switchToRollback とロックの受け渡し

`switchToWAL`/`switchToRollback`(第 14 章)にも、接続単位ロックの取得・解放が組み込まれます。

**pager/wal.go(差分) — switchToWAL・switchToRollback**

```go
// switchToWAL はロールバックジャーナル方式から WAL 方式へ切り替える。
// ヘッダページの journalMode を書き換えて Flush で確定させてから、
// WAL ファイルを新規に作る。
//
// WAL モードは接続単位の排他ロックを Close まで保持する方式なので
// (pager.go の Open、lock.go 参照)、切り替えの最初に排他ロックを取る。
// minidb の walIndex はプロセス内メモリにしか存在せず、複数接続で
// 共有する仕組み(SQLite の -shm のような共有メモリ)を持たないため、
// WAL モードは単一接続専用にせざるを得ない(第 14 章の sqlite-note 参照)。
// ロックが取れなければモードもヘッダも一切書き換えずに ErrBusy を返す。
func (p *Pager) switchToWAL() error {
	if err := p.lockExclusive(); err != nil {
		return err
	}

	header, err := p.Get(headerPageID)
	if err != nil {
		_ = p.unlock()
		return err
	}
	binary.BigEndian.PutUint32(header.Data[journalModeOffset:journalModeOffset+4], uint32(JournalModeWAL))
	header.dirty = true
	p.journalMode = JournalModeWAL
	if err := p.Flush(); err != nil {
		_ = p.unlock()
		return err
	}
	if err := p.ensureWALFile(); err != nil {
		_ = p.unlock()
		return err
	}
	p.walLocked = true
	return nil
}

// switchToRollback は WAL 方式からロールバックジャーナル方式へ切り替える。
// まずチェックポイントで WAL の内容を DB 本体へ反映してから WAL
// ファイルを削除し、ヘッダページの journalMode を書き換えて Flush で
// 確定させ、最後に接続単位の排他ロックを解放する(以後はロールバック
// ジャーナルモードのトランザクション単位ロックに委ねる)。
func (p *Pager) switchToRollback() error {
	if err := p.checkpoint(); err != nil {
		return err
	}
	walPath := p.walPath()
	p.closeWALFile()
	if err := os.Remove(walPath); err != nil && !errors.Is(err, os.ErrNotExist) {
		return err
	}

	header, err := p.Get(headerPageID)
	if err != nil {
		return err
	}
	binary.BigEndian.PutUint32(header.Data[journalModeOffset:journalModeOffset+4], uint32(JournalModeRollback))
	header.dirty = true
	p.journalMode = JournalModeRollback
	if err := p.Flush(); err != nil {
		return err
	}
	if p.walLocked {
		if err := p.unlock(); err != nil {
			return err
		}
		p.walLocked = false
	}
	return nil
}
```

`switchToWAL` は関数の**先頭**でロックを取ります——ヘッダを書き換えるより前です。ロックが取れなければ、モードもヘッダも一切書き換えずに `ErrBusy` を返します。これは 15.2 節の「WAL モードは単一接続専用」という制約を、モード切替の入り口で強制する形になっています。それ以降の各失敗経路(`p.Get` の失敗、`Flush` の失敗、`ensureWALFile` の失敗)がすべて `_ = p.unlock()` を挟んでから返している点にも注目してください。**一度取ったロックを、失敗経路のどこであっても律儀に手放す**——`Commit` の warn で見た「取ったロックが孤児にならないように」という配慮が、ここでも一貫しています。

`switchToRollback` は逆順です。チェックポイントと WAL ファイルの削除、ヘッダの書き換えと `Flush` をすべて終えた**最後**に、`p.walLocked` を確認してロックを解放します。以後はロールバックジャーナルモードのトランザクション単位ロックに制御を委ねる、という切り替えの区切りです。

### engine.go — autocommit が Rollback しないと詰む

`exec/engine.go` の `autocommit` にも、この章で実装中に判明した 1 行の修正が入ります。

**exec/engine.go(差分) — autocommit の Commit 失敗時に Rollback**

```go
// autocommit は stmt を「この 1 文だけのトランザクション」として実行する。
// 実行または Commit が失敗したときは Rollback するが、呼び出し元にとって
// 重要なのは「なぜ失敗したか」なので、Rollback 自体のエラーより元のエラーを
// 優先して返す。
//
// Commit の失敗(例えば ErrBusy)でも Rollback するのは、明示トランザクション
// (BEGIN...COMMIT)とは事情が異なるため。明示トランザクションなら
// pg.InTx() が真のまま残り、利用者は改めて COMMIT を打って再試行するか
// ROLLBACK を選べる。しかし autocommit の場合、利用者に見えている操作は
// 「元の SQL 文を再実行する」ことだけであり、そこには Begin が含まれる。
// ここで Rollback せずにトランザクションを生かしたままにすると、次の
// autocommit の Begin が「トランザクションは既に開始しています」に
// 阻まれ、REPL がそれ以降ずっと行き詰まってしまう。
func (e *Engine) autocommit(stmt sql.Statement, input string) (*Result, error) {
	if err := e.pg.Begin(); err != nil {
		return nil, err
	}
	res, err := e.execStmt(stmt, input)
	if err != nil {
		_ = e.pg.Rollback()
		return nil, err
	}
	if err := e.pg.Commit(); err != nil {
		_ = e.pg.Rollback()
		return nil, err
	}
	return res, nil
}
```

これは、この章の実装中に実際に踏んだ詰みでした。ロールバックジャーナルモードで `Commit` が `ErrBusy` を返しても、`Pager.Begin`/`Commit` の設計(前節)は「トランザクションを生かしたまま返す」ことを選んでいます——明示トランザクションにとっては、これは正しい振る舞いです。`COMMIT` をもう一度打つか `ROLLBACK` するかを、利用者が選べます。

しかし `autocommit` には、その語彙がありません。`Engine.Execute` が `autocommit` を呼ぶのは、利用者が `BEGIN` を打たずに 1 文だけを発行したときです。利用者からは「1 つの SQL 文を実行した」としか見えず、その裏で `Begin` が呼ばれていることは意識されません。もしここで `Commit` が失敗したときに `Rollback` を呼ばずに `nil, err` を返してしまうと、`e.pg` の `inTx` は `true` のまま宙ぶらりんになります。利用者が(エラーメッセージを見て)同じ `INSERT` をもう一度打つと、`autocommit` は再び `e.pg.Begin()` から始めようとしますが、これは「トランザクションは既に開始しています」という、第 13 章由来のエラーで即座に拒まれます——REPL は二度と動かなくなります。

修正は `Commit` の失敗時にも `_ = e.pg.Rollback()` を呼ぶ、この 1 行だけです。**明示トランザクションは再試行の語彙(COMMIT をもう一度、または ROLLBACK)を持つが、autocommit は持たない——だから autocommit は自動で Rollback する。** これは SQLite の意味論とも一致します。SQLite の autocommit モードでの `SQLITE_BUSY` は、その文全体が失敗として扱われ、次の文からやり直せる状態に戻ります。

```go
// 2 つの Engine(別々の Pager)で同じ DB ファイルを開き、A が明示

// 競合を再現できる(詳細は pager/lock_test.go)。
func TestEngineConcurrentWriteBlockedByReaderLock(t *testing.T) {
	path := filepath.Join(t.TempDir(), "test.db")

	pgA, err := pager.Open(path)
	if err != nil {
		t.Fatal(err)
	}
	t.Cleanup(func() { pgA.Close() })
	a, err := NewEngine(pgA)
	if err != nil {
		t.Fatal(err)
	}
	mustExec(t, a, "CREATE TABLE users (id INTEGER PRIMARY KEY, name TEXT, age INTEGER)")

	pgB, err := pager.Open(path)
	if err != nil {
		t.Fatal(err)
	}
	t.Cleanup(func() { pgB.Close() })
	b, err := NewEngine(pgB)
	if err != nil {
		t.Fatal(err)
	}

	// A: 明示トランザクションで共有ロックを保持したままにする。
	mustExec(t, a, "BEGIN")
	mustExec(t, a, "SELECT * FROM users")

	// B: autocommit の INSERT。SH 同士は共存できるので Begin 自体は
	// 通るが、Commit で SH → EX への昇格に失敗して ErrBusy になる。
	insertSQL := "INSERT INTO users VALUES (1, 'Alice', 30)"
	if _, err := b.Execute(insertSQL); err == nil {
		t.Fatal("B の INSERT が成功してしまいました(A が共有ロックを保持中のはず)")
	} else if !strings.Contains(err.Error(), "ロックされています") {
		t.Fatalf("B の INSERT のエラー = %v, want 「ロックされています」を含む", err)
	}

	// A: COMMIT してロックを手放す(このトランザクションは読み取りのみ
	// なので dirty ページは無く、実体は SH の解放だけになる)。
	mustExec(t, a, "COMMIT")

	// B: 同じ文を再実行すれば、今度は成功する。
	res, err := b.Execute(insertSQL)
	if err != nil {
		t.Fatalf("A の COMMIT 後の B の INSERT 再試行が失敗しました: %v", err)
	}
	if res.Message != "1 行を挿入しました" {
		t.Fatalf("Message = %q", res.Message)
	}

	got := mustExec(t, a, "SELECT * FROM users")
	if len(got.Rows) != 1 || got.Rows[0][1].Text != "Alice" {
		t.Fatalf("A から見た SELECT 結果 = %v, want Alice の 1 行", got.Rows)
	}
}
```

`lock_test.go` の `TestCommitBusyWhileReaderActive` と同じ現象を、`Engine`(SQL の実行主体)越しに確認しています。A の明示トランザクション(`BEGIN`)が共有ロックを保持している間、B の `autocommit` な `INSERT` はどこで失敗するでしょうか。B の `Begin` 自体は共有ロック同士なので通ります——問題は B の `Commit` です。dirty ページ(挿入した行)を書き戻そうとして共有 → 排他への昇格を試み、A がまだ共有ロックを握っているために失敗します。**A は読み取り専用のトランザクションでしかないのに、B の書き込みを退けています。** この非対称こそが、15.4 節の実機実験で確かめる現象です。

`wal_test.go` にも 2 か所の修正が入ります。1 つは既存テストの期待値の更新、もう 1 つはクラッシュ模擬の手段の変更です。

**pager/wal_test.go(差分 1) — bumpChangeCounter によるフレーム数の変化**

```go
	if err := p.Commit(); err != nil {
		t.Fatal(err)
	}

	// 変更カウンタのインクリメント(bumpChangeCounter)によりヘッダページも
	// dirty になるため、対象ページ本体と合わせて 2 フレームになる。
	if p.walFrames != 2 {
		t.Fatalf("walFrames = %d, want 2", p.walFrames)
	}
```

第 14 章時点のこのテストは、1 ページだけを変更するコミットが 1 フレームになることを期待していました。この章で `bumpChangeCounter` がヘッダページを新たに dirty にするようになったため(前述の pager.go(7))、同じコミットが実際に書き込むフレームは 2 枚——変更対象のページ本体と、カウンタを書き加えたヘッダページ——に増えます。これはバグではなく、変更カウンタの実装が WAL の中身に正しく反映されていることの証拠です。

**pager/wal_test.go(差分 2) — 単一接続化に伴うクラッシュ模擬の変更**

```go
	// p はまだ WAL モードの接続単位ロック(排他)を保持したままなので、
	// このまま Open(path) すると ErrBusy になってしまう。実際のクラッシュ
	// では OS がプロセスの終了時に flock を自動的に解放するので、それを
	// 模して p.unlock() だけを呼ぶ(p.Close() はチェックポイントで WAL を
	// 切り詰めてしまい、上で作った尻切れを消してしまうため使えない)。
	if err := p.unlock(); err != nil {
		t.Fatal(err)
	}
```

第 14 章のこのテストは、WAL に尻切れフレームを作った後、`p` をそのままにして 2 つ目の `Pager` で同じパスを再オープンし、リカバリの挙動を確認していました。この章で WAL モードが接続単位の排他ロックを `Close` まで保持するようになったため(15.2 節の表 15-1)、`p` を閉じずに 2 つ目を開こうとすると、そのまま `ErrBusy` になってしまいます。かといって `p.Close()` を呼べば、`Close` 自身がチェックポイントを実行して WAL を切り詰めてしまい、テストがせっかく作った「尻切れ」の検証対象が消えてしまいます。そこで `p.unlock()` だけを呼び、ロックの解放だけを行います——これは 15.2 節で述べた「プロセスが死ねばカーネルが自動的に flock を解放する」という性質を、テストの中で手作業により模したものです。実際のクラッシュでは `p.Close()` のような後始末は一切走らず、ロックだけがカーネルの手で消えます。このテストの `p.unlock()` は、その「後始末なしでロックだけが消える」状況を意図的に再現しています。

## 15.4　動かして確かめる — 2 つの REPL

準備として、`users` テーブルを作り 1 行だけ入れた `mini.db` を用意します。

```console
$ rm -f mini.db
$ printf "CREATE TABLE users (id INTEGER PRIMARY KEY, name TEXT, age INTEGER);\nINSERT INTO users VALUES (1, 'Alice', 30);\n.exit\n" | go run ./cmd/minidb mini.db
```

別々のターミナルを 2 つ開き、両方とも `go run ./cmd/minidb mini.db` を実行します。

### 端末 A — BEGIN で共有ロックを 6 秒保持する

端末 A で、明示トランザクションを開始したまま `COMMIT` を打たずにしばらく待ちます。

```console
minidb> BEGIN;
トランザクションを開始しました
minidb> SELECT * FROM users;
id | name | age
---------------
1 | Alice | 30
minidb> COMMIT;
コミットしました
minidb> .exit
```

### 端末 B — A の保持中に割り込む

A が `BEGIN` の後、`SELECT` を打って `COMMIT` を打たずに待っている間に、端末 B で `INSERT` を試みます。

```console
minidb> INSERT INTO users VALUES (2, 'Bob', 25);
エラー: データベースがロックされています(他の接続が使用中です)
minidb> .exit
```

### 端末 B — A の解放後に再試行する

A が `COMMIT` を打ってロックを手放した後、端末 B で同じ `INSERT` をもう一度打ちます。

```console
minidb> INSERT INTO users VALUES (2, 'Bob', 25);
1 行を挿入しました
minidb> SELECT * FROM users;
id | name | age
---------------
1 | Alice | 30
2 | Bob | 25
minidb> .exit
```

### 読み解き

B の 1 回目の `INSERT` が失敗した理由は、15.3 節で辿ったコードそのものです。B の `INSERT` は `autocommit` として実行され、`e.pg.Begin()` は共有ロック同士なので問題なく通ります。しかし `e.pg.Commit()` は、挿入した行を含む dirty ページを書き戻すために共有ロックを排他ロックへ昇格させようとします——その瞬間、A がまだ `BEGIN` で共有ロックを握ったままです。**A はただの読み取りトランザクションなのに、B の書き込みを退けています。** これがロールバックジャーナル方式(SQLite の rollback モード)の性質そのものです。「読者が書き手をブロックする」という制約は、第 14 章の sqlite-note で触れた WAL モードの `readers-don't-block-writers`(読者は書き手をブロックしない)という謳い文句と、正確に対をなします。この章で実装したのはロールバックジャーナルモードのロック規則だけですが、`PRAGMA journal_mode = WAL` で切り替えれば、この「A が B をブロックする」場面そのものが起きなくなります——読み取りと書き込みが、それぞれ別の場所(DB 本体と WAL)を見るようになるからです。

B の再試行が成功し、Bob がようやく `users` テーブルへ入りました。15.1 節の思考実験で描いたロストアップデート——B の変更が A の後発コミットに黙って踏み潰される事故——は、もう起こりません。ロックが「A が握っている間、B の書き込みを待たせる」ことで衝突そのものを未然に防ぎ、変更カウンタが「A・B どちらの接続も、コミット直後の相手の変更を次の `Begin` で必ず読み直す」ことを保証しています。

<div class="column-note">

<span class="note-title">本物の SQLite でも同じ実験ができる</span> 手元に `sqlite3` コマンドラインシェルがあれば、同じ実験を本物の SQLite に対しても試せます。1 つ目の `sqlite3 test.db` で `BEGIN; SELECT * FROM users;` を打って止めたまま、2 つ目の `sqlite3 test.db` から `INSERT` を試みると、`database is locked` というエラーが返ります——minidb の `ErrBusy` に相当する SQLite 自身のメッセージです。既定のジャーナルモードでは、SQLite も minidb と同じ「読者が書き手をブロックする」規則で動いていることを、自分の手で確かめてみてください。

</div>

## 15.5　まとめ

- flock(2) による共有/排他ロックを実装した。ロールバックジャーナルモードはトランザクション単位(`Begin` で共有、書き込みコミットで排他へ昇格)、WAL モードは接続単位(`Open` で排他、`Close` まで保持)という、モードごとに異なるロックの規則を設計した
- 変更カウンタ(ヘッダオフセット 32-35)を実装した。`Begin` 直後にディスク上の値と比較し、他の接続がコミットしていればキャッシュを丸ごと破棄して読み直す——「1 個の整数比較で無効化を済ませる」という、第 12 章のスキーマクッキーと同型の設計
- SH → EX への昇格には flock 由来の隙間があり、SQLite の SHARED/RESERVED/EXCLUSIVE という多段ロックがこの隙間を「書き込み意図の早期宣言」で塞いでいることを、自作の 2 段ロックとの対比で確認した。レビューで見つかった「EX 昇格失敗時に SH まで失われる」穴と、その 1 行修正を通じて、ロック API の仕様を man ページまで戻って確かめることの大切さを学んだ
- `autocommit` が `Commit` の失敗時にも `Rollback` しないと `inTx` が残って以後の全文が詰むこと、明示トランザクションと autocommit で「再試行の語彙」の有無が違うことを確認した
- 2 つの REPL を実際に動かし、読み取り専用のトランザクションが書き込みをブロックする(ロールバックジャーナル方式の性質)ことと、それでもロストアップデートが起きなくなったことを実機で確かめた

第 1 章 1.1 節で立てた 4 つの壁——検索、部分更新、クラッシュ、同時アクセス——が、これですべて崩れました。壁 1 は第 2 部の B-Tree で、壁 2 は第 1 部のページとページャで、壁 3 は第 13・14 章のジャーナリングと WAL で、そして壁 4 はこの章のロックと変更カウンタで。しかし、まだ検証していないことが 1 つ残っています。第 13 章以来「クラッシュしても壊れない」と何度も書いてきましたが、その主張は一度も**本物のクラッシュ**では試されていません——テストが手で作る「尻切れジャーナル」や「孤児フレーム」は、あくまでクラッシュが残すはずの状態を人間が推測して再現したものです。次章では、`kill -9` で実際にプロセスを殺し、この本がこれまで積み重ねてきた主張を、本物の電源断にもっとも近い形で検証します。そしてそれが、この本の実装編の締めくくりになります。
