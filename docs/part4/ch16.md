## 16.1　本書の主張を、殺して試す

第 15 章の最後は、こう締めくくられていました。

> 第 13 章以来「クラッシュしても壊れない」と何度も書いてきましたが、その主張は一度も**本物のクラッシュ**では試されていません——テストが手で作る「尻切れジャーナル」や「孤児フレーム」は、あくまでクラッシュが残すはずの状態を人間が推測して再現したものです。次章では、`kill -9` で実際にプロセスを殺し、この本がこれまで積み重ねてきた主張を、本物の電源断にもっとも近い形で検証します。そしてそれが、この本の実装編の締めくくりになります。

その予告を、この最終章で果たします。第 13〜15 章は「こう書けば壊れないはずだ」という設計を積み上げてきました——コミットプロトコルの表(第 13 章 表 13-1)、undo ログと redo ログの非対称(第 14 章)、ロックと変更カウンタの分業(第 15 章)。しかしどの章も、検証の手段は「クラッシュが残すはずの状態を、テストコードの中で手で作る」ことに留まっていました。`journal_test.go` の `TestCrashBeforeJournalHeader` はヘッダを全ゼロのまま放置したファイルを `os.WriteFile` で直接作りましたし、`wal_test.go` はコミット印のないフレームを手で追記しました。これらはどれも「クラッシュが起きたら、ディスク上はこうなっているはずだ」という**推測**を人間が組み立てたものであり、実際にプロセスを殺して確かめたことは一度もありません。

この章はその最後の一歩を埋めます。**実際にコミットの途中でプロセスを即死させ、次に開いたときに何が起きるかを、自分の目で見る。** これが本書の実装編の最後の主張であり、最後の検証です。

### 障害注入(fault injection)という技法

意図的に壊れた状況を作り出してソフトウェアの振る舞いを確かめる技法を、**障害注入(fault injection)**と呼びます。ディスク I/O をわざと失敗させる、メモリ確保をわざと失敗させる、あるいはこの章で行うように、処理の途中でプロセスをわざと殺す——正常系のテストでは決して踏まない経路を、意図的に踏みにいく手法です。

第 1 章 1.3 節の sqlite-note で、SQLite のテストコードは本体コードの数百倍あると述べました。その分量の中核を占めているのが、まさにこの障害注入です。あらゆる書き込みのタイミングでディスク I/O エラーを発生させる、あらゆるメモリ確保のタイミングで失敗させる、そしてコミットの過程を人為的に中断させて電源断相当の状況を作る——正常に動くことを確かめるテストよりも、**異常な状況でも壊れないことを確かめるテスト**の方が、実装そのものよりずっと多くのコードを要求します。この章で作る `pager/crash.go` と `cmd/crashdemo` は、その巨大な体系のうち「コミットの途中でプロセスを止める」という、最も基本的な 1 種類だけを切り出した、ごく小さな縮図です。

第 14 章 14.2 節で、「コミットの `fsync` は 3 回から 1 回に減ったが、それは消えたのではなくチェックポイントへまとめて後払いされているだけだ」という会計の話をしました。障害注入は、この会計に似た性質を持っています。**「壊れない」という主張のコストは、実装の時点では払い切れません。** どれほど注意深く表 13-1(第 13 章)のようなコミットプロトコルの時系列を設計しても、それが本当に安全かどうかは、実際にその時系列のどこかでプロセスを止めてみるまで確定しません。この章はその未払いの検証コストを、最後にまとめて払いに行く章です。

### os.Exit と kill -9 と電源断 — 3 つを混同しない

障害注入の実装に入る前に、この章の技術的な柱となる区別を先に立てておきます。**「プロセスを殺す」と一口に言っても、殺し方によってディスク上に残るものが違う**、という区別です。

- **`os.Exit`** — Go の標準ライブラリが提供する、プロセスの即時終了です。呼んだ瞬間にプロセスが終わり、**`defer` はひとつも実行されません**。`Pager.Close` が呼ばれないのはもちろん、`Close` の中にある自動 `Rollback`(第 13 章)や WAL のチェックポイント(第 14 章)、ロックの解放(第 15 章、もっとも `flock` はプロセスの終了そのものでカーネルが解放するので実害はありません)も、一切実行されません
- **`kill -9`(`SIGKILL`)** — OS がプロセスへ送る、捕捉不可能な強制終了シグナルです。`SIGTERM` と違い、プロセス側には一切の後片付けの機会が与えられません
- **電源断** — マシンそのものの電源が落ちる、最も過酷な障害です

`os.Exit` と `kill -9` は、**ディスク上に残る結果という点では区別がつきません**。どちらもプロセスに後片付けをさせないまま即座に消し去るという意味で同じです。`pager/crash.go` のコメントにこう書いた理由がこれです。

> os.Exit による即死は defer も Close も走らせない — kill -9 で殺されたプロセスとディスク上の状態は区別がつかない。

だから、この章の実験で `os.Exit` を使えば、`kill -9` で本当にプロセスを殺した場合と同じ結果が得られます——わざわざ 2 プロセス構成にして `kill -9` を外部から撃ち込む必要はありません。

しかし `os.Exit`/`kill -9` は、**電源断とは違います**。ここが見落とされがちな一線です。第 4 章 4.3 節で確認したとおり、`write()` システムコールが成功を返しても、そのデータはまだ OS の**ページキャッシュ**にあるだけで、物理ディスクへの到達を意味しません。`fsync` を挟んで初めて到達が保証されます。プロセスが `os.Exit` や `kill -9` で死んでも、**OS 自体は生き続けています**——ページキャッシュに残ったデータは消えません。同じマシンで直後にファイルを開き直せば、`fsync` していないデータでもそのまま読めてしまいます。これに対して電源断は OS ごと、そしてページキャッシュを保持している RAM ごと消し去ります。`fsync` していないデータは、本当に失われます。

**プロセスクラッシュまでは自作の実験で完全に再現できます。しかし電源断そのものの検証には、本物の電源を抜くか、OS レイヤに踏み込んだより深い障害注入(仮想マシンの強制停止や、専用の VFS でページキャッシュへの反映自体をシミュレートする、といった手法)が要ります。** この章はそこまでは踏み込みません——できることとできないことを、正直に線引きしておきます。

**表 16-0　3 つの「殺し方」の違い**

| 殺し方               | `defer`/後始末   | OS 自体    | ページキャッシュ                  | この章で再現できるか             |
| -------------------- | ---------------- | ---------- | --------------------------------- | -------------------------------- |
| `os.Exit`            | 一切実行されない | 生き続ける | 残る(未 `fsync` でも直後に読める) | できる(この章で使用)             |
| `kill -9`(`SIGKILL`) | 一切実行されない | 生き続ける | 残る(未 `fsync` でも直後に読める) | `os.Exit` と結果が同じなので不要 |
| 電源断               | 一切実行されない | 停止する   | 消える(未 `fsync` は失われる)     | できない(本物の電源が要る)       |

表の左 2 列(`defer`/後始末が一切実行されない)は `os.Exit` と `kill -9` で共通しており、この 2 つが「ディスク上に残る結果という点では区別がつかない」ことの根拠です。右 2 列(ページキャッシュが残るか消えるか)は電源断だけが異なり、これが「電源断とは違う」の根拠です。この表 1 枚が、16.1 節の技術的な柱をそのまま可視化しています。

この区別は、単なる注意書きでは終わりません。**この章の 2 つの注入点のうち、WAL 側の注入点がどこに置かれているかを直接左右します。**

### pager/crash.go — 障害注入のフック

この区別を踏まえて、障害注入の仕組みそのものを実装します。`pager` パッケージに新しく追加する `crash.go` の全文です。

**pager/crash.go(全文)**

```go
// crash.go は障害注入(fault injection)のためのフックを提供する。
// クラッシュ実験(cmd/crashdemo)やテスト(crash_test.go)が、コミット
// プロトコルの特定の瞬間にプロセスを止め、クラッシュを決定的に
// 再現するために使う。通常運転では debugCrashHook は nil のままで、
// crashPoint の呼び出しは何もしない。
package pager

// debugCrashHook は障害注入フック。テストやデモが特定の瞬間にプロセスを
// 即死させ、クラッシュを決定的に再現するために使う。通常運転では nil の
// まま何もしない。
//
// os.Exit による即死は defer も Close も走らせない — kill -9 で殺された
// プロセスとディスク上の状態は区別がつかない。
var debugCrashHook func(point string)

// crashPoint は名前付きの注入点。debugCrashHook が設定されていれば呼ぶ。
func crashPoint(point string) {
	if debugCrashHook != nil {
		debugCrashHook(point)
	}
}

// SetDebugCrashHook は障害注入フックを設定する(デモ・テスト用)。
func SetDebugCrashHook(fn func(point string)) { debugCrashHook = fn }
```

やっていることは単純です。パッケージレベルの変数 `debugCrashHook` に関数を 1 つセットしておけば、`crashPoint` がその名前で呼ばれるたびにフックが発火します。通常運転(`debugCrashHook == nil`)では `crashPoint` は完全に無害な no-op です——本番のコミット処理に、障害注入のための分岐や判定コストを一切持ち込みません。`SetDebugCrashHook` は非公開の `debugCrashHook` を外(この章の `cmd/crashdemo` や `crash_test.go`)から差し替えるための、唯一の公開口です。

この仕組みの本体はコードではなく、**コミットプロトコルのどの瞬間に `crashPoint` を置くか**という設計判断にあります。第 13 章と第 14 章で確立した 2 つのコミットプロトコル——ロールバックジャーナルと WAL——それぞれに、1 か所ずつ注入点を仕込みます。

### 注入点 1 — ロールバックジャーナル: after-journal

**pager/pager.go(差分) — Commit 内の after-journal 注入点**

```go
	if err := p.writeJournal(dirty); err != nil {
		return err
	}
	// この時点でジャーナルは有効(fsync 済み)だが DB 本体はまだ無傷。
	// ここでクラッシュすれば、次回 Open の recoverFromJournal が
	// このジャーナルを使って未完のトランザクションを巻き戻す。
	crashPoint("after-journal")
	if err := p.flush(); err != nil {
		return err
	}
```

これは `Commit`(第 13 章)の一部です。`writeJournal` が返ってきた直後——つまりジャーナルへのエントリ列の書き込みと、マジック+エントリ数を持つヘッダの書き込みが**両方とも `fsync` を終えて確定した**直後——に `crashPoint("after-journal")` を置きます。表 13-1(第 13 章)の言葉で言えば、行④(ジャーナル有効・DB 本体無傷)の状態でプロセスを止めるということです。ここでクラッシュすれば、DB 本体は 1 バイトも書き換わっていないのに、ジャーナルはすでに有効——次に `Open` したときの `recoverFromJournal` が、まさにこの状況を正すために書かれた関数です。

### 注入点 2 — WAL: mid-wal-commit(電源断との区別が形になった場所)

**pager/wal.go(差分) — walCommit 内の mid-wal-commit 注入点**

```go
func (p *Pager) walCommit(dirty []*Page) error {
	if err := p.ensureWALFile(); err != nil {
		return err
	}

	startOffset := p.walEnd

	offset := startOffset
	frame := make([]byte, walFrameSize)
	for i, page := range dirty {
		binary.BigEndian.PutUint32(frame[0:4], uint32(page.ID))
		commit := uint32(0)
		if i == len(dirty)-1 {
			commit = 1
			// コミット印を持つ最後のフレームを書く直前。ここまでの
			// フレーム(あれば)は既にディスクへ書かれているが、
			// コミット印はまだファイル上のどこにも存在しない。ここで
			// クラッシュすれば、次回 Open の openWALIfPresent が
			// コミット印を見つけられずこの尻切れフレーム列を切り詰める。
			//
			// 書き込みループを完全に終えた後(この最後の WriteAt も
			// 完了した後)にクラッシュ点を置かないのは、書き込み済みの
			// バイト列は fsync していなくても OS のページキャッシュに
			// 残り続け、プロセスを os.Exit で終了させただけでは
			// (実機の電源断とは違い)再オープン時にそのまま読めて
			// しまうため。コミット印そのものを書く前に止めることで、
			// fsync の有無に関わらず確実に「尻切れ」を再現する。
			crashPoint("mid-wal-commit")
		}
		binary.BigEndian.PutUint32(frame[4:8], commit)
		copy(frame[8:], page.Data[:])
		if _, err := p.walFile.WriteAt(frame, offset); err != nil {
			return fmt.Errorf("WAL への書き込みに失敗: %w", err)
		}
		offset += walFrameSize
	}
```

WAL 側の注入点には、16.1 節の冒頭で立てた区別がそのままコードのコメントとして刻まれています。もう一度読んでください。

> 書き込みループを完全に終えた後(この最後の WriteAt も完了した後)にクラッシュ点を置かないのは、書き込み済みのバイト列は fsync していなくても OS のページキャッシュに残り続け、プロセスを os.Exit で終了させただけでは(実機の電源断とは違い)再オープン時にそのまま読めてしまうため。コミット印そのものを書く前に止めることで、fsync の有無に関わらず確実に「尻切れ」を再現する。

もし `crashPoint` をループの**後**(最後の `WriteAt` が完了した後、`walFile.Sync()` の前)に置いていたらどうなっていたでしょうか。コミット印を持つ最後のフレームまで含め、すべてのバイト列はすでに `WriteAt` を終えています。`fsync` していないので物理ディスクへの到達は保証されていませんが、**同じ OS の上で直後に読み直せば**、それは(ページキャッシュに残っているので)そのまま読めてしまいます。`os.Exit` で終わらせた実験は同じマシン・同じ OS の上で完結するため、この「読めてしまう」が実際に起きます。結果、尻切れフレームを再現したかったはずが、実際には**綺麗にコミットが完了したのと見分けがつかない**状態になってしまいます。

だから注入点は、コミット印を書く**前**、つまりループが最後のフレームの処理に入った、その入り口に置かれています。この位置でクラッシュすれば、それ以前のフレーム(もしあれば)は完了して `WriteAt` 済みですが、コミット印を持つはずだった最後のフレームは**1 バイトも書かれていません**。`fsync` を実際に呼んだかどうかに関係なく、確実に「尻切れ」を作り出せます。**電源断とプロセスクラッシュの違いを踏まえて初めて選べる、注入点の位置**——これが 16.1 節冒頭の区別が実装に落ちた場所です。

`pager.go`・`wal.go` の他の部分(`Get`/`Allocate`/`MarkDirty`/`bumpChangeCounter`/`checkpoint`/`scanWALFrames` など)は第 15 章のままです。完成形は `code/ch16/pager/pager.go`・`code/ch16/pager/wal.go` を参照してください。

## 16.2　実験 — 3 つのクラッシュ

道具が揃いました。これを使い、実際にプロセスを殺すデモツール `cmd/crashdemo` を実装します。

**cmd/crashdemo/main.go(全文)**

```go
// cmd/crashdemo/main.go
// クラッシュ実験用のデモツール。コミットプロトコルの特定の瞬間に
// os.Exit でプロセスを即死させ、次に minidb で開き直したときの復旧の
// 様子を観察するために使う。
//
// 使い方:
//
//	go run ./cmd/crashdemo <db ファイル> <シナリオ>
//
// シナリオ:
//
//	uncommitted  — BEGIN して 1 行 INSERT した状態で即死(コミットしない)
//	journal      — コミット中、ジャーナル書き込み完了・本体反映前に即死
//	wal          — (WAL モードの DB で)コミット中、WAL フレーム書き込み後・fsync 前に即死
package main

import (
	"fmt"
	"os"

	"minidb/exec"
	"minidb/pager"
)

func main() {
	if len(os.Args) != 3 {
		fmt.Fprintln(os.Stderr, "使い方: crashdemo <db ファイル> <シナリオ>")
		os.Exit(1)
	}
	path, scenario := os.Args[1], os.Args[2]

	pg, err := pager.Open(path)
	if err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}
	defer pg.Close()

	engine, err := exec.NewEngine(pg)
	if err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}

	// テーブル作成と既存行の確認だけの整備コミットは、以降のシナリオの
	// 準備を単純にするため、シナリオに関係なく普通に成功させる。
	if err := ensureUsersTable(engine); err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}

	switch scenario {
	case "uncommitted":
		runUncommitted(engine)
	case "journal":
		runJournal(engine)
	case "wal":
		runWAL(engine)
	default:
		fmt.Fprintf(os.Stderr, "不明なシナリオです: %s(uncommitted / journal / wal のいずれかを指定してください)\n", scenario)
		os.Exit(1)
	}
}

// ensureUsersTable は users テーブルが無ければ作成する。
func ensureUsersTable(engine *exec.Engine) error {
	tables, err := engine.Tables()
	if err != nil {
		return err
	}
	for _, t := range tables {
		if t == "users" {
			return nil
		}
	}
	_, err = engine.Execute("CREATE TABLE users (id INTEGER PRIMARY KEY, name TEXT, age INTEGER)")
	return err
}

// runUncommitted は BEGIN して 1 行 INSERT した状態で、COMMIT せずに
// 即死する。トランザクション中はディスクへ一切書かないため、次回 Open
// すればこの行は影も形もない。
func runUncommitted(engine *exec.Engine) {
	if _, err := engine.Execute("BEGIN"); err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}
	if _, err := engine.Execute("INSERT INTO users VALUES (900, 'Doomed', 0)"); err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}
	fmt.Println("コミットせずに即死します")
	os.Exit(1)
}

// runJournal は autocommit の INSERT が、ジャーナル書き込み完了・本体
// 反映前(pager.Commit の "after-journal" 注入点)に即死するよう仕込む。
func runJournal(engine *exec.Engine) {
	pager.SetDebugCrashHook(func(point string) {
		if point != "after-journal" {
			return
		}
		fmt.Println("ジャーナル書き込み直後・本体反映前に即死します")
		os.Exit(1)
	})
	if _, err := engine.Execute("INSERT INTO users VALUES (901, 'Phantom', 0)"); err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}
	// フックが発火して途中で死ぬはずなので、ここには到達しない。
	fmt.Fprintln(os.Stderr, "想定外: クラッシュフックが発火せず、コミットが正常終了しました")
	os.Exit(1)
}

// runWAL は autocommit の INSERT が、WAL フレーム書き込み後・fsync 前
// (pager.walCommit の "mid-wal-commit" 注入点)に即死するよう仕込む。
// 呼び出し側が事前に PRAGMA journal_mode = WAL で WAL モードに切り替えて
// おく必要がある。
func runWAL(engine *exec.Engine) {
	pager.SetDebugCrashHook(func(point string) {
		if point != "mid-wal-commit" {
			return
		}
		fmt.Println("WAL フレーム書き込み後・fsync 前に即死します")
		os.Exit(1)
	})
	if _, err := engine.Execute("INSERT INTO users VALUES (902, 'Torn', 0)"); err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}
	fmt.Fprintln(os.Stderr, "想定外: クラッシュフックが発火せず、コミットが正常終了しました(journal_mode は WAL になっていますか?)")
	os.Exit(1)
}
```

3 つのシナリオが並んでいます。

- **`uncommitted`** — `BEGIN` して 1 行 `INSERT` した状態で、`COMMIT` を打たずに `os.Exit` します。障害注入のフックすら使いません——トランザクション中は(第 13 章 13.2 節の前提どおり)ディスクへ一切書かれないため、何も特別な仕掛けをしなくても、この行は最初から存在しないのと同じです
- **`journal`** — `pager.SetDebugCrashHook` で `"after-journal"` にフックを仕込んでから `autocommit` の `INSERT` を実行します。フックが発火した瞬間に `os.Exit(1)` するので、`INSERT` 文自体は最後まで実行を終えません
- **`wal`** — 同様に `"mid-wal-commit"` にフックを仕込みます。こちらは呼び出し側があらかじめ `PRAGMA journal_mode = WAL` で WAL モードへ切り替えておく必要があります

3 つのシナリオはすべて `ensureUsersTable` で `users` テーブルの用意を済ませてから始まります——この整備コミットはシナリオに関係なく普通に成功させ、以降の実験の前提を単純にしています。`runJournal`・`runWAL` の末尾にある「想定外」の `fmt.Fprintln` は、フックが発火せずに `INSERT` が正常終了してしまった場合の保険です。もしそうなったら、それは `crashPoint` の呼び出し位置が実際には通っていないという実装のバグを意味します。

`main` の import に `minidb/pager` だけでなく `minidb/exec` も並んでいる点に注目してください。`crashdemo` は `pager.Pager` を直接操作するのではなく、`exec.NewEngine` で `Engine` を作り、`engine.Execute("INSERT INTO users VALUES ...")` という**本物の SQL 文字列**を実行しています。第 13〜15 章のテストコード(`journal_test.go`・`wal_test.go`・`lock_test.go`)はどれも `pager` パッケージの内部 API(`Begin`/`Allocate`/`MarkDirty`/`Commit`)を直接叩く**単体テスト**でした。`crashdemo` はそれとは一段違う立ち位置にあります——SQL の字句解析(第 9 章)・構文解析(第 9 章)・バイトコードへのコンパイル(第 10 章)・VM の実行(第 10〜12 章)を経て、最後に `pager` へたどり着く、**利用者が実際に打つのと同じ経路**でクラッシュを起こします。これは 16.2 節の実験が「`pager` パッケージの内部ロジックが正しい」ことだけでなく、「minidb というアプリケーション全体が、実際の利用シーンで壊れない」ことまで検証していることを意味します。

### 実験 1 — 未コミットは消える

`BEGIN` して 1 行 `INSERT` し、`COMMIT` を打たずに即死します。

```console
$ go run ./cmd/crashdemo mini.db uncommitted
コミットせずに即死します
exit status 1
$ ls
mini.db
$ printf "SELECT * FROM users;\n.exit\n" | go run ./cmd/minidb mini.db
minidb> SELECT * FROM users;
id | name | age
---------------
1 | Alice | 30
minidb> .exit
```

`ls` の出力に `mini.db-journal` も `mini.db-wal` も現れません。トランザクション中は `Flush` が(第 13 章のガードにより)呼べないため、`Doomed`(id=900)という行は 1 バイトもディスクへ届いていません。`os.Exit` は `defer` を一切実行しないので `Pager.Close` の自動 `Rollback`(第 13 章)すら走りませんが、走る必要もありません——最初から書いていないものを消す処理は不要だからです。再オープン後の `SELECT` に `Doomed` は影も形もなく、Alice だけがそのまま残っています。

### 実験 2 — コミット中のクラッシュ、ジャーナルが現場に残る

`"after-journal"` にフックを仕込んで `INSERT INTO users VALUES (901, 'Phantom', 0)` を実行し、ジャーナル書き込み完了・本体反映前に即死します。

```console
$ go run ./cmd/crashdemo mini.db journal
ジャーナル書き込み直後・本体反映前に即死します
exit status 1
$ ls -la mini.db mini.db-journal
12288 mini.db
8216 mini.db-journal
$ printf "SELECT * FROM users;\n.exit\n" | go run ./cmd/minidb mini.db
minidb> SELECT * FROM users;
id | name | age
---------------
1 | Alice | 30
minidb> .exit
$ ls mini.db-journal
(mini.db-journal は存在しない)
```

**この 8216 バイトは、分解すると読み解けます。** 第 13 章のジャーナルフォーマットはヘッダ 16 バイト(マジック 8B + エントリ数 4B + 予約 4B)+ エントリの並び(1 エントリ = ページ番号 4B + ページ内容 4096B = 4100B)でした。8216 を当てはめると、`16 + 2 × 4100 = 8216`——**エントリはちょうど 2 枚**です。

`Phantom` の `INSERT` はテーブル本体のページ 1 枚を書き換えただけのはずなのに、なぜ 2 枚なのでしょうか。答えは第 15 章の `bumpChangeCounter` です。`Commit` は dirty ページが 1 枚以上あるとき、実際のコミット処理(この場合は `writeJournal`)より前に変更カウンタをインクリメントし、**ヘッダページも dirty にします**。だから `writeJournal` が退避したのは、変更カウンタを書き換えたヘッダページと、`Phantom` の行を書き込んだデータページの、合わせて 2 枚——バイト数を数えるだけで、「この 1 回のコミットが何枚のページに触れたか」を逆算できてしまいます。

再オープン後の `SELECT` に `Phantom` は現れず、`mini.db-journal` も跡形もなく消えています。`Open` が呼ぶ `recoverFromJournal`(第 13 章)が、有効なジャーナル(マジックもエントリ数も揃っている)を見つけ、退避されていた 2 枚のページの「変更前の内容」を DB 本体へ無条件に書き戻し、それからジャーナル自身を削除しました。表 13-1 の行④——ジャーナルは有効、DB 本体はまだ無傷——から復旧が始まり、コミット前の状態へ正しく巻き戻っています。

### 実験 3 — WAL の尻切れ

WAL モードへ切り替えてから、`"mid-wal-commit"` にフックを仕込んで `INSERT INTO users VALUES (902, 'Torn', 0)` を実行します。

```console
$ printf "PRAGMA journal_mode = WAL;\n.exit\n" | go run ./cmd/minidb mini.db
minidb> PRAGMA journal_mode = WAL;
journal_mode を wal に変更しました
minidb> .exit
$ go run ./cmd/crashdemo mini.db wal
WAL フレーム書き込み後・fsync 前に即死します
exit status 1
$ ls -la mini.db mini.db-wal
12288 mini.db
4120 mini.db-wal
$ printf "SELECT * FROM users;\n.exit\n" | go run ./cmd/minidb mini.db
minidb> SELECT * FROM users;
id | name | age
---------------
1 | Alice | 30
minidb> .exit
$ ls -la mini.db-wal
16 mini.db-wal
```

**この 4120 バイトも、実験 2 と同じ流儀で分解できます。** 第 14 章の WAL フォーマットはヘッダ 16 バイト+フレーム(1 フレーム = ページ番号 4B + コミット印 4B + ページ内容 4096B = 4104B)でした。`16 + 1 × 4104 = 4120`——**書き込みを完了できたフレームは、たった 1 枚**です。

ここでも `bumpChangeCounter` の効果でヘッダページとデータページの 2 枚が dirty になっていたはずです。`walCommit` は `dirtyPages()`(PageID 昇順、第 13 章)の順に 1 枚ずつフレームを書きます。ヘッダページ(`headerPageID = 0`)は必ず最小の PageID なので、必ず先頭で処理されます——つまり `i == len(dirty)-1` の条件に当たらず、`crashPoint` を経ずにそのまま書き終わっている枚数です。次に処理されるのが、**最後**の 1 枚である `Torn` の行を持つデータページ。ここで `i == len(dirty)-1` が成立し、`crashPoint("mid-wal-commit")` が発火してプロセスが即死します——このフレームの `WriteAt` はまだ 1 バイトも呼ばれていません。

つまりディスクに残った唯一のフレーム(4104 バイト)は、`Torn` の内容ではなく、**コミット印を持たないヘッダページのフレーム**です。`Torn` という行データ自体は、ディスク上のどこにも存在しません。バイト数の逆算だけで、「どちらのページが生き残り、どちらが本当に消えたか」まで言い当てられます。

再オープン後、`mini.db-wal` は 16 バイト——WAL ヘッダだけです。`openWALIfPresent`(第 14 章)の `scanWALFrames` はこの唯一のフレームを `pending` に溜めますが、コミット印(`commit=1`)を持つフレームには一度も出会わないまま走査を終えます。`pending` は `index` へ一度も昇格せず、静かに捨てられ、`f.Truncate(lastCommitEnd)` がこの尻切れフレームを物理的に切り落とします。第 14 章で「尻切れフレームは復元も書き戻しも要らず、無視すればよい、まだ存在しないのと同じもの」と書いた、その言葉どおりの結果がここに実機の数字として現れています。

### 3 つの実験が語ること

3 つの実験を並べて見て、気づくことが 3 つあります。

**1. どの実験でも、Alice は無傷、幽霊(`Doomed`/`Phantom`/`Torn`)は不在です。** クラッシュのたびにコミット前のデータが正しく守られ、コミットされなかった変更は跡形もなく消えました。これは第 13〜15 章の主張——「壊れない」——が、推測ではなく実際にプロセスを殺した上での結果です。

**2. ユーザーは何も操作していません。** `crashdemo` の直後に打った `SELECT` の前に、`.repair` のような特別なコマンドは一切実行していません。ただ `go run ./cmd/minidb mini.db` で普通に**開いただけ**です。`Open` の内部で `recoverFromJournal` や `openWALIfPresent` が黙って走り、静かに、正しく直っています。これは偶然ではなく設計です——第 13 章の sqlite-note で触れた、本物の SQLite が hot journal(クラッシュの痕跡が残ったジャーナル)を利用者に気付かせず処理する、あの挙動そのものを、minidb も体現しています。

**3. どの実験でも、次の `mini.db` を開く操作は一度も `ErrBusy` に阻まれていません。** `crashdemo` はロックを明示的に解放せずに `os.Exit` で死んでいますが(`defer pg.Close()` すら走りません)、それでも直後の `minidb` はロックの競合なく開けています。これは第 15 章で実装した `flock` の性質——**ロックを保持しているプロセスが終了すれば、カーネルが自動的にそのロックを解放する**——がそのまま効いているからです。もし minidb 自前のロック(ファイルに書き込むフラグのような仕組み)を使っていたら、`crashdemo` の死骸が残したロックを誰も片付けられず、次の `minidb` はいつまでも `ErrBusy` を返し続けたはずです。第 15 章で「クラッシュ実験でも、この性質がそのまま効いてくる」と予告していた伏線が、ここで回収されました。

<div class="column-note">

<span class="note-title">自分の手で kill -9 を試す</span> `crashdemo` は `os.Exit` でプロセスを止めますが、16.1 節で確認したとおり、これは `kill -9` と結果が区別できません。それでも「本物の `kill -9` で確かめたい」なら、2 つの端末で試せます。1 つ目の端末で `go run ./cmd/minidb mini.db` を起動して `BEGIN;` だけ打ったまま待たせ、2 つ目の端末で `ps` からそのプロセス ID を見つけて `kill -9 <PID>` を撃ち込んでください。1 つ目の端末は何の断りもなく即座に消え、`mini.db` はコミット前の状態のまま残ります——実験 1 と、寸分違わぬ結果が得られるはずです。

### pager/crash_test.go — go test の中でクラッシュを再現する

`cmd/crashdemo` は人間が手で動かす実験用ツールですが、この章にはもう 1 つ、`go test` の中だけで完結する自動テストがあります。ここで問題になるのが、**`os.Exit` はテストプロセスそのものを道連れにしてしまう**ということです。`crashdemo` のように独立したプロセスとして実行するなら構いませんが、`go test` の 1 テストケースの中で `os.Exit` を呼べば、その瞬間に `go test` プロセス全体が終了し、以降のテストは 1 つも走らずに終わってしまいます。

そこで `crash_test.go` は、`os.Exit` の代わりに **panic + recover** を使います。全文を掲載します。

**pager/crash_test.go(全文)**

```go
package pager

import (
	"bytes"
	"os"
	"path/filepath"
	"testing"
)

// crashSentinel は障害注入テスト専用の panic 値。os.Exit と違って
// テストプロセス自体を道連れにしないよう、注入点に到達したら
// crashPoint の呼び出し元(pager 内部)から一気に巻き戻り、テストが
// recover して「クラッシュが起きた」ことを検知する。
type crashSentinel struct{ point string }

// simulateCrashAt は debugCrashHook を point 到達時に crashSentinel を
// panic するよう設定する。以後のコミット処理は途中で巻き戻り、Flush や
// Commit の後始末(ジャーナル削除・fsync 等)は一切実行されない。
func simulateCrashAt(point string) {
	SetDebugCrashHook(func(p string) {
		if p == point {
			panic(crashSentinel{point: p})
		}
	})
}

// crashClose はクラッシュ相当の後始末を行うテスト用ヘルパー。Flush /
// Commit / チェックポイントを一切通さず、DB ファイルの fd だけを生で
// close する。flock は fd に紐付くので、これだけで解放される
// (カーネルがクラッシュしたプロセスの fd を後始末するのと同じ)。
// 放置した Pager をそのまま残すと、同一プロセス内では fd が生きたままの
// flock が新しい Open を ErrBusy にしてしまうため、この後始末が必要になる。
func crashClose(t *testing.T, p *Pager) {
	t.Helper()
	if err := p.file.Close(); err != nil {
		t.Fatal(err)
	}
}

// runUntilCrash は fn(通常はトランザクション 1 つ分の Begin→変更→Commit)
// を実行し、simulateCrashAt で仕込んだ注入点に到達して panic することを
// 期待する。到達しなかった(= 正常終了してしまった)場合はテストを失敗させる。
func runUntilCrash(t *testing.T, fn func()) {
	t.Helper()
	defer func() {
		r := recover()
		if r == nil {
			t.Fatal("クラッシュフックが発火せず、正常終了してしまいました")
		}
		if _, ok := r.(crashSentinel); !ok {
			panic(r) // 想定外の panic はそのまま伝播させる
		}
	}()
	fn()
}

// TestCrashAfterJournalRecovers は、ロールバックジャーナルモードの
// コミットが "after-journal"(ジャーナル書き込み完了・本体反映前)で
// クラッシュした場合、次回 Open の recoverFromJournal が未完の
// トランザクションを正しく巻き戻すことを確認する。
func TestCrashAfterJournalRecovers(t *testing.T) {
	t.Cleanup(func() { SetDebugCrashHook(nil) })

	path := filepath.Join(t.TempDir(), "test.db")
	p, err := Open(path)
	if err != nil {
		t.Fatal(err)
	}

	// 整備コミット: 1 行目相当の変更を普通にコミットする。
	if err := p.Begin(); err != nil {
		t.Fatal(err)
	}
	row1, err := p.Allocate()
	if err != nil {
		t.Fatal(err)
	}
	copy(row1.Data[:], "row1")
	p.MarkDirty(row1.ID)
	if err := p.Commit(); err != nil {
		t.Fatal(err)
	}
	numPagesAfterRow1 := p.NumPages()

	simulateCrashAt("after-journal")

	runUntilCrash(t, func() {
		if err := p.Begin(); err != nil {
			t.Fatal(err)
		}
		row2, err := p.Allocate()
		if err != nil {
			t.Fatal(err)
		}
		copy(row2.Data[:], "row2")
		p.MarkDirty(row2.ID)
		_ = p.Commit() // ここで crashSentinel が panic するはず
	})

	crashClose(t, p)

	if _, err := os.Stat(path + "-journal"); err != nil {
		t.Fatalf("クラッシュ直後はジャーナルが残っているはず: err=%v", err)
	}

	p2, err := Open(path)
	if err != nil {
		t.Fatalf("クラッシュ後の再オープンが失敗しました: %v", err)
	}
	defer p2.Close()

	if p2.NumPages() != numPagesAfterRow1 {
		t.Fatalf("再オープン後の NumPages = %d, want %d(2 行目の Allocate が巻き戻っていない)", p2.NumPages(), numPagesAfterRow1)
	}

	got1, err := p2.Get(row1.ID)
	if err != nil {
		t.Fatal(err)
	}
	if !bytes.HasPrefix(got1.Data[:], []byte("row1")) {
		t.Fatalf("1 行目の内容 = %q, want prefix %q", got1.Data[:4], "row1")
	}

	if _, err := os.Stat(path + "-journal"); !os.IsNotExist(err) {
		t.Fatalf("再オープン後もジャーナルファイルが残っています: err=%v", err)
	}
}

// TestCrashMidWALRecovers は、WAL モードのコミットが "mid-wal-commit"
// (フレーム書き込み完了・fsync 前)でクラッシュした場合、次回 Open の
// openWALIfPresent が尻切れフレームを切り詰め、コミット済みの内容だけが
// 見えることを確認する。
func TestCrashMidWALRecovers(t *testing.T) {
	t.Cleanup(func() { SetDebugCrashHook(nil) })

	path := filepath.Join(t.TempDir(), "test.db")
	p, err := Open(path)
	if err != nil {
		t.Fatal(err)
	}
	if err := p.SetJournalMode(JournalModeWAL); err != nil {
		t.Fatal(err)
	}

	// 整備コミット: 1 行目相当の変更を普通にコミットする。
	if err := p.Begin(); err != nil {
		t.Fatal(err)
	}
	row1, err := p.Allocate()
	if err != nil {
		t.Fatal(err)
	}
	copy(row1.Data[:], "row1")
	p.MarkDirty(row1.ID)
	if err := p.Commit(); err != nil {
		t.Fatal(err)
	}

	walPath := path + "-wal"
	committedInfo, err := os.Stat(walPath)
	if err != nil {
		t.Fatal(err)
	}
	committedSize := committedInfo.Size()

	simulateCrashAt("mid-wal-commit")

	runUntilCrash(t, func() {
		if err := p.Begin(); err != nil {
			t.Fatal(err)
		}
		row2, err := p.Allocate()
		if err != nil {
			t.Fatal(err)
		}
		copy(row2.Data[:], "row2")
		p.MarkDirty(row2.ID)
		_ = p.Commit() // ここで crashSentinel が panic するはず
	})

	tornInfo, err := os.Stat(walPath)
	if err != nil {
		t.Fatal(err)
	}
	if tornInfo.Size() <= committedSize {
		t.Fatalf("クラッシュ直後の WAL サイズ = %d, want > %d(尻切れフレームが書かれているはず)", tornInfo.Size(), committedSize)
	}

	crashClose(t, p)

	p2, err := Open(path)
	if err != nil {
		t.Fatalf("クラッシュ後の再オープンが失敗しました: %v", err)
	}
	defer p2.Close()

	got1, err := p2.Get(row1.ID)
	if err != nil {
		t.Fatal(err)
	}
	if !bytes.HasPrefix(got1.Data[:], []byte("row1")) {
		t.Fatalf("1 行目の内容 = %q, want prefix %q", got1.Data[:4], "row1")
	}

	walAfter, err := os.Stat(walPath)
	if err != nil {
		t.Fatal(err)
	}
	if walAfter.Size() != committedSize {
		t.Fatalf("再オープン後の WAL サイズ = %d, want %d(尻切れが切り詰められていない)", walAfter.Size(), committedSize)
	}
}
```

`simulateCrashAt` が仕込むのは `os.Exit` ではなく、`crashSentinel` という専用の型を値に持つ `panic` です。`runUntilCrash` はこの `panic` を `defer`/`recover` で捕まえ、`crashSentinel` 型であることを確認してからテストを継続します——もし別の型の `panic`(想定外のバグ)であれば、`panic(r)` でそのまま再送出し、握りつぶしません。この技法により、**1 つの `go test` プロセスの中で、コミット処理が「途中で強制的に巻き戻る」状況を安全に再現できます**。`panic` は関数呼び出しのスタックを巻き戻しながら伝播するので、`crashPoint` を呼んだその場から `Commit`/`walCommit` の後始末(ジャーナル削除・`fsync` など)を一切実行せずに抜け出す——`os.Exit` が `defer` を一切走らせないのと、結果として同じ効果が得られます。

`crashClose` にも注目してください。**`Flush`/`Commit`/チェックポイントを一切通さず、DB ファイルの `fd` だけを生で `close` します。** これは 16.2 節の「3 つの実験が語ること」で見た、`flock` が `fd` に紐付くという性質(第 15 章)をテストの中でも利用したものです。`fd` を閉じればそれだけでロックが解放されるので、クラッシュを模した `Pager` を放置したまま次の `Open` を呼んでも `ErrBusy` になりません——`crashdemo` を `os.Exit` させたときにカーネルが自動的に行っていることを、テストの中では明示的な 1 行で模しています。

**`TestCrashAfterJournalRecovers`** と **`TestCrashMidWALRecovers`** は、16.2 節で見た実験 2・実験 3 を、それぞれ `go test` の中で自動化したものです。どちらも同じ骨格を踏みます。まず「1 行目」を普通に `Begin`→`Allocate`→`Commit` してコミット済みの土台を作り(**整備コミット**、`crashdemo` の `ensureUsersTable` と同じ役回りです)、それから `simulateCrashAt` で注入点を仕込み、「2 行目」相当の `Begin`→`Allocate`→`Commit` を `runUntilCrash` の中で実行して、狙った注入点で確実に `panic` することを確かめます。

2 本のテストで、クラッシュ後に確認する対象が違うことにも意味があります。`TestCrashAfterJournalRecovers` は再オープン後の `NumPages()` が「1 行目コミット後」の値まで巻き戻っていることを確認します——ロールバックジャーナルは**ページ単位**の変更前イメージを退避する仕組み(第 13 章)なので、「何ページ分の変更が巻き戻ったか」という粒度で検証するのが自然です。一方 `TestCrashMidWALRecovers` はページ数ではなく、**WAL ファイルのバイトサイズ**そのものを比較します——WAL は追記型のログであり(第 14 章)、リカバリは「有効なフレーム列の末尾がどこか」という**バイト単位**の切り詰めで完結するので、検証もその粒度に合わせるのが自然です。同じ「クラッシュしても壊れない」という主張でも、その主張を裏付ける最も直接的な観測量は、コミットプロトコルの設計そのものによって変わります。

もう 1 点、`TestCrashAfterJournalRecovers` はクラッシュ**直後**(まだ再オープンしていない時点)で `mini.db-journal` に相当するファイルが存在することも確認しています。これは「クラッシュが本当に途中で起きた」ことの直接証拠です——もし `crashPoint` が実は発火せず、`Commit` が最後まで完走してしまっていたら、この時点でジャーナルはすでに削除されているはずだからです。テストが最終結果(内容が正しいこと)だけでなく、**過程(本当にクラッシュが起きたこと)**まで確かめている点は、16.2 節の `crashdemo` が末尾に「想定外」の分岐を用意しているのと同じ用心深さです。

この 2 本のテストと `crashdemo` の関係は、CI とデモの役割分担そのものです。どちらも、16.2 節で人間の目で確かめた現象を検証していますが、`crashdemo` は人間が実際に `ls` や `SELECT` を打って目で確かめるための道具であり、`crash_test.go` はそれと同じ現象を `go test ./...` のたびに機械的に再検証するための道具です。

第 15 章の `flock` と変更カウンタがこれに答えました。ロックが「今この瞬間、誰が書き込んでよいか」を調停し、変更カウンタが「自分が読んでいるものは最新か」を保証する——2 つの道具が分業することで、ロストアップデートは起きなくなりました。そして本章では、そのロックが**クラッシュにも強い**ことを確かめました。`flock` は保持しているプロセスの死とともにカーネルが自動的に解放するので、クラッシュした接続がロックを抱えたまま居座ることはありません。

## 16.4　この先の学習へ

本書は、完全な RDBMS を作ることを目指してはいません。まえがきで宣言したとおり、minidb は SQLite の設計思想を踏襲しつつ、独自の簡易フォーマットに**割り切って**実装してきました。その割り切りの 1 つ 1 つが、実は次に学ぶべきことの入り口です。この最後の節では、本書が意図的に手を付けなかった発展課題を、それぞれ「どの章の何を拡張するか」を添えて挙げます。

### 二次インデックス — 第 12 章の宿題

第 12 章 12.2 節は、二次インデックスを実装しない理由をこう説明していました。

> `btree.BTree` のキーは第 2 章以来一貫して `uint64` 固定です(第 6 章でセルのキーをそう定義しました)。`name`(TEXT)をキーにするインデックスを作るには、キーの比較を「数値の大小」から「バイト列の辞書順比較」へ拡張する必要があります——`interior.findChild` や `leaf.findSlot` の二分探索(第 6・7 章)が使っている `<` 比較を、`bytes.Compare` のようなバイト列比較に差し替える改修です。

この拡張ができれば、`CREATE INDEX` 文を実装し、`WHERE name = 'x'` を全件スキャンなしで解決できるようになります。あわせて、第 12 章が指摘したもう 1 つの難所——`UPDATE`/`DELETE` の 2 相方式が、テーブル本体だけでなくすべてのインデックス用 B-Tree も同期して書き換えなければならない問題——にも向き合うことになります。

着手するなら、まず `btree` パッケージのキー比較を `uint64` の `<` から `bytes.Compare` へ一般化するところから始めるのが素直です。テーブル用 B-Tree(キー = rowid)と二次インデックス用 B-Tree(キー = インデックス対象列の値 + rowid)を同じ型で表現できるようにしてから、`exec` パッケージ側で `CREATE INDEX` のコンパイルと、`isPKEquality`(第 12 章)の隣に「使えるインデックスが他にもあるか」を判定するロジックを追加する、という 2 段階の作業になります。

もう 1 つ、見落としやすい波及先があります。テーブル本体と各インデックス用 B-Tree はそれぞれ独立したページの集まりですが、1 回の `INSERT`/`UPDATE`/`DELETE` はそのすべてを**同じトランザクションの中で**一貫して書き換える必要があります。ここで効いてくるのが第 13 章のコミット時ジャーナリングと第 14 章の WAL です。どちらも「dirty になったページを丸ごと退避・追記する」という設計なので(第 13 章の `dirtyPages`、第 14 章の `walCommit`)、テーブル本体と複数のインデックスにまたがる dirty ページが増えても、コミットプロトコルそのものを変える必要はありません——**ジャーナル・WAL の設計は、変更が及ぶページの枚数に依存しない**という性質が、この章まで積み上げてきた設計の思わぬ配当として効いてきます。

### varint とオーバーフローページ — まえがきの割り切り

まえがき(この本の歩き方)はこう宣言していました。

> 完全互換を目指すと、varint エンコーディングやオーバーフローページといった仕様の再現作業に労力の大半を奪われ、「概念を理解する」という本来の目的から外れてしまうからです。

本物の SQLite は整数を可変長の **varint** で符号化してレコードを圧縮し、1 ページに収まらない巨大な値を**オーバーフローページ**の連鎖へ逃がします。minidb のレコード形式(第 9 章)は固定長の型タグと値をそのまま並べる素直な形で、値のサイズにもページ 1 枚に収まる範囲という制約があります。varint の実装は「可変長の整数をどうエンコード・デコードするか」という符号化の練習として、オーバーフローページは「1 つの論理データを複数の物理ページにまたがらせる」という、第 5〜8 章の B-Tree とはまた違う設計判断を要求します。

まえがきはこの割り切りを「読むのは本物、書くのは簡易版」という言葉で正当化していました。varint とオーバーフローページに挑むということは、その簡易版を本物のフォーマットへ一歩近づける作業そのものです。取り組む際は、第 3 章の `inspect` で本物の SQLite ファイルを覗いたときの手順——バイナリを 1 バイトずつ読み、仕様書と突き合わせながら意味を確定させていく手順——がそのまま再利用できます。

### 削除時のマージ・リバランス — 第 8 章の理論

第 8 章 8.1 節は、第 5 章 5.6 節の割り切りをこう振り返っていました。

> 削除時のマージ・リバランスは実装せず、理論の説明にとどめる — 本物は削除のたびにノードの結合や再配分を行い、半分埋まりの不変条件を保つ(第 8 章)

minidb の削除は「完全に空になったページだけをフリーリストへ回収する」という最も単純な形に留まっています。教科書どおりの実装には、隣接ノードから何セルか分けてもらう**再配分(redistribution)**と、隣接ノードと合体する**マージ(merge)**、そしてマージが親のセル数を下限割れさせたときにさらに 1 段上へ連鎖していく処理が要ります。第 7 章で見た分割の「電話連鎖」の、削除版の実装です。

実装の難所は、分割よりも場合分けが多いことそのものです。左の兄弟と組むか右の兄弟と組むか、その兄弟に再配分できるだけの余裕があるかないか、マージした結果が親のセル数をさらに下限割れさせるかどうか——これらの分岐を 1 つずつ実装し、そのすべての組み合わせをテストで踏むことになります。この章まで積み上げてきたコミット時ジャーナリング(第 13 章)は、こうした複数ページにまたがる複雑な書き換えでこそ真価を発揮します。**再配分やマージがどれほど込み入っても、`Commit` の前に dirty になったページをまとめて退避するという仕組み自体は変わらない**——複雑な B-Tree の操作と、単純なコミットプロトコルとを分離しておいたことの恩恵を、ここでも受け取れます。

### MVCC — 第 14〜15 章の先

第 14 章の sqlite-note は、本物の WAL が実現する **readers-don't-block-writers**(読者は書き手をブロックしない)という性質に触れていました。minidb は単一プロセス・単一接続を前提にしているため、複数の読者が同時に安全に WAL を覗く仕組み(`wal-index` を共有メモリファイル `-shm` に置く、各リーダーが接続時点のスナップショットを固定する)は実装していません。これを実装すれば、第 15 章で確認した「読み取り専用のトランザクションが書き込みをブロックする」という制約そのものを解消できます——MVCC(Multi-Version Concurrency Control、多版型同時実行制御)と呼ばれる領域の入り口です。

第 15 章 15.4 節の実機実験を思い出してください。端末 A が `BEGIN; SELECT * FROM users;` のまま止まっていると、端末 B の `INSERT` は `ErrBusy` で弾かれました。MVCC の考え方に立てば、この場面は本来ブロックする理由がありません——A は「今この瞬間の WAL の状態」を見ているだけで、B が新しいフレームを追記しても、A のスナップショットには影響しないはずだからです。minidb がこの場面をブロックしてしまうのは、`walIndex` がプロセス内メモリの `map[PageID]int64`(第 14 章)にすぎず、複数の接続で共有する手段を持たないという、まさにこの割り切りのためです。MVCC の実装は、この `walIndex` を接続をまたいで共有し、かつ各接続が「自分が `Begin` した時点のスナップショット」を固定して読み続けられるようにする、という 2 つの仕事に分解できます。

### クエリプランナの本格化 — 第 12 章の isPKEquality の先

第 12 章の sqlite-note はこう書いていました。

> minidb の `isPKEquality` は、その巨大な領域が担う仕事のうち「使えるインデックス(この場合は主キー)が WHERE の形とぴったり一致するときだけ使う」という、最も単純な 1 パターンの種にすぎません。

本物のクエリオプティマイザは、テーブルの行数やヒストグラムといった統計情報、複数の利用可能なインデックスからの選択、`JOIN` の結合順序の決定まで担います。二次インデックスが実装できれば、「複数のインデックス候補からどれを使うべきか」を決めるコスト見積もりの入り口に立てます。

`isPKEquality` は `WHERE` の**構文の形**だけを見て判定する、極めて静的な仕組みでした(第 12 章)。本格的なオプティマイザに近づく第一歩は、この判定に「行数」という動的な情報を足すことです。テーブルの行数が分かれば、「全件スキャンで何行読むことになるか」を見積もれるようになり、複数のインデックス候補があるときに「どちらが安いか」を初めて比較できます。第 12 章で `.timer` を使って測った 0.103ms と 24.601ms という実測値は、この見積もりが正しければ再現できるはずの数字でもあります——**測って確かめられる形で最適化を語れる**という、この本が一貫して大事にしてきた態度が、ここでも指針になります。

### ネットワーク層・サーバ化

第 1 章 1.2 節の図 1-1 は、RDBMS の最上部を「インターフェース層 — SQL 文字列を受け取る(ネットワーク経由 / ライブラリ呼び出し)」と描いていました。minidb はこれまで一貫して `cmd/minidb` という単一プロセスの REPL、あるいはライブラリとしての直接呼び出しに留まってきました。TCP でリッスンしてクライアントからの SQL をネットワーク越しに受け取るサーバへ育てれば、この図のいちばん上の層に初めて実体が入ります。同時に、単一プロセス前提を外れた瞬間に第 15 章のロック設計(`flock`)がそのまま通用するのか、複数クライアントを 1 つの `Pager` でどう捌くのかといった、新しい設計判断が要求されます。

興味深いのは、第 15 章の `flock` によるロックは、実は「単一プロセス」という前提を最初から必要としていないことです。`flock` はもともと**複数プロセス**の競合を調停するための OS の仕組み(15.2 節)であり、`lock_test.go` の 5 本のテストがそれを 1 プロセス内の複数 `Pager` インスタンスで再現できていたのも、`flock` が fd 単位のロックだからでした。ネットワークサーバ化そのものよりも、**サーバ内部で複数クライアントの接続をどう `Pager` にマッピングするか**(クライアントごとに別々の `Pager` を持つのか、1 つの `Pager` を共有しクライアント側はコマンドを送るだけにするのか)という設計判断の方が、実は本質的な難所です。

### SQLite ソースの歩き方

ここまでの発展課題は、どれも本物の SQLite がすでに答えを持っています。第 1 章と第 12 章の sqlite-note で実測した行数を、最後にもう一度並べておきます(いずれも SQLite 3.53.3 の `src/` を実測、行数はコメントを含む)。

| ファイル                  | 行数        | 対応する本書の章                                         |
| ------------------------- | ----------- | -------------------------------------------------------- |
| `tokenize.c`              | 約 900 行   | 第 9 章(字句解析)                                        |
| `parse.y`(Lemon 文法定義) | 約 2,200 行 | 第 9 章(構文解析)                                        |

`vdbe.c` はバイトコードを命令ごとに実行する仮想マシン本体(第 10 章で作った `exec.VM` の本家)にあたるファイルです。約 9,400 行のうち大半は巨大な switch 文で、`EXPLAIN` で覗いたあのオペコード(第 1 章 1.3 節)の 1 つ 1 つがどう解釈されるかが 1 命令 = 1 ケースで並んでいます。minidb の `Run` メソッド(第 10 章)の switch と同じ構造なので、読み方はもう知っているはずです。

読む順番に迷ったら、本書と同じ順序をおすすめします。**まず `pager.c` でページ入出力とキャッシュの土台を掴み、次に `btree.c` でその上に載る索引構造を追い、`vdbe.c` でバイトコードの実行を見て、`where.c` でその上のクエリプランニングを見る。** そして `wal.c` は `pager.c` の中でも特にコミットプロトコルに関わる部分として、独立して読む価値があります。本書の各章は、これらのファイルが実際に何を解決しようとしているかの「地図」です——地図を持って本物のコードに踏み込めば、1 つ 1 つの関数が何のためにあるのか、驚くほど見晴らしよく読めるはずです。
