## 1.1　データベースは何を解決しているのか

データベースの内部を学ぶ最良の出発点は、「もしデータベースがなかったら」を考えることです。ユーザー情報を保存するアプリケーションを、データベースなしで作るとしましょう。素朴に思いつくのは、1 行 1 レコードのテキストファイル(CSV や JSON Lines)への追記です。

```console
users.csv
1,Alice,30
2,Bob,25
3,Carol,41
```

数百件ならこれで十分動きます。しかしデータが増え、利用者が増えると、次々に壁にぶつかります。

### 壁 1: 検索が遅い

「id が 500000 のユーザー」を探すには、ファイルを先頭から 1 行ずつ読むしかありません。計算量は O(n)。100 万行あれば平均 50 万行を読むことになります。行の長さが可変なので「500000 行目に飛ぶ」こともできません。*目的のデータに、データ量に関わらずほぼ一定の手数でたどり着く仕組み*が必要です。これに答えるのが第 2 部で作る **B-Tree** です。

### 壁 2: 部分更新ができない

Bob の年齢を 25 から 26 に変えたいだけでも、話は単純ではありません。テキストファイルの途中のバイト列を「伸縮」させることはできないため、実務的には全体を読み込み、書き換え、丸ごと書き戻すことになります。1 レコードの更新コストがファイルサイズに比例するのは受け入れがたい性質です。*ファイルの一部だけを安全に書き換えられる単位*が必要です。これに答えるのが第 2 章から登場する**ページ**という考え方です。

### 壁 3: クラッシュでデータが壊れる

ファイルを書き戻している最中に、プロセスが落ちたら? OS ごと電源断になったら? 書き込みが中途半端に終わり、ファイルは半分だけ新しい壊れた状態になります。もっと厄介なことに、`write()` システムコールが成功を返しても、データはまだ OS のバッファにあるだけで、ディスクに届いていないかもしれません。*「操作は完全に行われたか、まったく行われなかったか、どちらかである」ことを保証する仕組み*が必要です。これがトランザクションの原子性(Atomicity)であり、第 4 部のジャーナリングと WAL で実装します。

### 壁 4: 同時アクセスで壊れる

2 つのプロセスが同時に読み書きしたら、更新は簡単に失われます(いわゆるロストアップデート)。_複数の読み書きが混在しても、それぞれが一貫した世界を見られる仕組み_ — ロックと同時実行制御が必要で、これも第 4 部で扱います。

<div class="column-note">

<span class="note-title">4 つの壁 = 本書の地図</span> この 4 つの壁は、そのまま本書の構成に対応しています。壁 2(部分更新)を第 1 部のページとページャで、壁 1(検索)を第 2 部の B-Tree で、SQL という操作言語を第 3 部で、壁 3・4(耐障害性と同時実行)を第 4 部で乗り越えます。データベースとは、この 4 つの壁を一つずつ塗り固めた、ファイル入出力の上の「工学の積層」なのです。

</div>

各層のポイントを一つずつ押さえます。

**SQL コンパイラ** — SQL は「何が欲しいか」だけを述べる宣言型言語で、「どう取ってくるか」は書きません。そのため RDBMS は SQL 文字列を字句解析(トークナイザ)・構文解析(パーサ)して構文木を作り、さらに実行手順(実行計画)へ変換します。「コンパイラ」という名前のとおり、プログラミング言語処理系とまったく同じ技術が使われています。

**実行エンジン** — 実行計画を実際に実行する部分です。実装方式には、構文木を再帰的にたどる tree-walking 方式と、いったんバイトコードに落として仮想マシンで実行する VM 方式があります。SQLite は後者で、この選択は第 3 部で minidb の設計を決めるときに改めて検討します。

**アクセスメソッド** — 「id = 42 の行をください」に対し、全行を読まずに答えるためのデータ構造です。ディスク上のデータ構造としてはほぼすべての RDBMS が B-Tree(またはその変種 B+Tree)を採用しています。メモリ上の探索木(二分探索木や赤黒木)ではなくなぜ B-Tree なのか — それはディスクの物理特性と深く関係しており、第 2 章と第 5 章で解き明かします。

**バッファ・トランザクション管理** — ディスクはメモリより桁違いに遅いため、読んだページはメモリにキャッシュします。また書き込みの原子性を保証するため、変更をいきなり本体ファイルに書かず、ジャーナルや WAL を経由させます。

**ストレージ層** — 最終的にはすべて OS への `read` / `write` / `fsync` に行き着きます。データベースが信頼できるのは、この最下層で「何をどの順で書き、いつ fsync するか」を極めて注意深く制御しているからです。

この図で特に注目してほしいのは、層と層の間を流れる「言葉」が下に行くほど単純になっていくことです。最上部では `SELECT name FROM users WHERE id = 2` という複雑な文字列だったものが、VDBE と B-Tree の間では「rowid 2 の行をください」になり、B-Tree と Pager の間では「**ページ 3 をください**」というたった一言になります。複雑さを一段ずつ剥がしていくこの構造のおかげで、私たちは**いちばん下の単純な層から順に、動くものを積み上げていく**ことができます。

### 動かして確かめる: バイトコードを覗いてみる

この層構造は、実は今すぐ手元で確かめられます。SQLite の CLI には、SQL がどんなバイトコードにコンパイルされたかを表示する `EXPLAIN` コマンドがあるからです。

```console
$ sqlite3 sample.db
sqlite> CREATE TABLE users(id INTEGER PRIMARY KEY, name TEXT, age INTEGER);
sqlite> INSERT INTO users VALUES (1,'Alice',30),(2,'Bob',25),(3,'Carol',41);
sqlite> EXPLAIN SELECT name FROM users WHERE id = 2;
addr  opcode         p1    p2    p3    p4             p5  comment
----  -------------  ----  ----  ----  -------------  --  -------------
0     Init           0     7     0                    0   Start at 7
1     OpenRead       0     2     0     2              0   root=2 iDb=0; users
2     Integer        2     1     0                    0   r[1]=2
3     SeekRowid      0     6     1                    0   intkey=r[1]
4     Column         0     1     2                    0   r[2]= cursor 0 column 1
5     ResultRow      2     1     0                    0   output=r[2]
6     Halt           0     0     0                    0
7     Transaction    0     0     1     0              1   usesStmtJournal=0
8     Goto           0     1     0                    0
```

たった 1 行の SELECT 文が、9 個の命令に翻訳されました(出力は SQLite 3.53.3 のもの。バージョンにより命令列は多少異なります)。いくつか拾って読むと、前掲の図がそのまま動いているのが分かります。

- `OpenRead`(addr 1)— users テーブルの B-Tree を読み取り用に開きます。comment 列の `root=2` は「この B-Tree のルートは**ページ 2**にある」という意味で、早くも「ページ」が顔を出しています(第 3 章で、このページそのものをバイナリ解析します)
- `SeekRowid`(addr 3)— B-Tree に対する「rowid 2 の行を探せ」。本文で述べた、VDBE と B-Tree の間を流れる言葉そのものです
- `Column`・`ResultRow`(addr 4〜5)— 見つかった行から name 列を取り出し、結果として返します
- `Transaction`(addr 7)— 実行は読み取りトランザクションの開始から始まります(`Init` が addr 7 へ飛び、`Goto` で addr 1 に戻る流れです)。たった 1 行の SELECT でもトランザクションの中で動く — この意味は第 4 部で明らかになります

いま個々の命令を覚える必要はまったくありません。「SQL は本当にバイトコードにコンパイルされ、B-Tree とページに対する単純な操作の列になる」— この実感だけ持って先へ進んでください。第 10 章で、この仕組みを自分の手で作ります。

<div class="sqlite-note">

<span class="note-title">SQLite ではこうなっている: コード規模の感覚</span> SQLite の中核はおよそ 15 万行の C コードで書かれています(テストコードはその数百倍あることで有名です)。中でも最大の単一ファイルが B-Tree を実装する btree.c(約 1.2 万行)で、ページャ(pager.c、約 8 千行)と WAL(wal.c、約 5 千行)を合わせると、ストレージ層だけで約 2.4 万行に達します(SQLite 3.53.3 の src/ を実測。行数はコメントを含む)。1 つの木構造とファイル入出力の実装にこれだけの行数が費やされている — ストレージを正しく速く扱うことがいかに難しいかを、この数字は物語っています。本書が第 1 部・第 2 部をまるごとストレージ層に割くのも同じ理由です。

</div>

## 1.4　これから作る minidb の全体像

本書で作る minidb は、SQLite の構成をそのまま縮小した Go プログラムです。最終的なパッケージ構成を先に示します(第 1 部で作るのは太字の部分です)。

| パッケージ        | 責務                                               | 対応章       |
| ----------------- | -------------------------------------------------- | ------------ |
| **`pager`**       | **ページ単位のファイル入出力とキャッシュ**         | **第 4 章**  |
| **`cmd/inspect`** | **本物の SQLite ファイルを解析するツール(学習用)** | **第 3 章**  |
| `btree`           | ページ上に構築するテーブル用 B-Tree                | 第 5〜8 章   |
| `sql`             | トークナイザとパーサ                               | 第 9 章      |
| `exec`            | 実行エンジン                                       | 第 10〜12 章 |
| `txn`             | ジャーナル・WAL・ロック                            | 第 13〜15 章 |
| `cmd/minidb`      | 対話シェル(REPL)                                   | 第 11 章〜   |

minidb の設計上の割り切りも明示しておきます。**データベースは単一ファイル、ページサイズは 4096 バイト固定、文字コードは UTF-8 のみ、当面は単一プロセスからの利用を前提**とします。SQLite が持つ可変ページサイズや多様なジャーナルモードは、概念の理解に必要になった時点で言及し、実装は最も本質的な形に絞ります。

## 1.5　まとめ

- データベースは「検索効率・部分更新・耐障害性・同時実行」という 4 つの壁を乗り越えるための、ファイル I/O の上の工学の積層である
- RDBMS は SQL コンパイラ / 実行エンジン / B-Tree / ページャ / ストレージという層構造を持ち、下の層ほど扱う言葉が単純になる
- SQLite はこの構成を最小限の部品で体現しており、minidb は同じ構成を Go で下から積み上げていく

次章では、いよいよ最下層の主役「ページ」を理解します。なぜデータベースはファイルを 4096 バイト刻みで扱うのか — その理由はハードウェアの物理にまで根を下ろしています。
