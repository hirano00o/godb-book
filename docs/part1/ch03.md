# 第 3 章　本物の SQLite ファイルを読む — ヘッダとページをバイナリ解析

<div class="chap-goal">

<span class="note-title">この章のゴール</span>

- SQLite ファイルの先頭 100 バイト(ファイルヘッダ)の主要フィールドを 16 進ダンプから読み取れる
- B-Tree ページヘッダの構造を理解し、ページの種別とセル数を特定できる
- SQLite ファイルを解析する Go プログラム `inspect` を実装し、実ファイルに対して動かせる

</div>

## 3.1　解剖する検体を用意する

まず `sqlite3` コマンドで、小さなデータベースファイルを作ります。テーブル 1 つ、レコード 3 件だけの最小構成です。

(第 1 章の `EXPLAIN` 実験で作った sample.db が残っているとテーブル作成に失敗するため、いったん削除してから進めます。)

```console
$ rm -f sample.db
$ sqlite3 sample.db
sqlite> PRAGMA page_size = 4096;
sqlite> CREATE TABLE users (id INTEGER PRIMARY KEY, name TEXT, age INTEGER);
sqlite> INSERT INTO users (name, age) VALUES ('Alice', 30), ('Bob', 25), ('Carol', 41);
sqlite> .quit
$ ls -l sample.db
-rw-r--r-- 1 user user 8192  sample.db
```

ファイルサイズに注目してください。**8192 バイト = 4096 × 2**。テーブル 1 つとレコード 3 件を入れただけで、ファイルはきっちり 2 ページ分になっています。前章で学んだ「ファイルはページの並びである」が、いきなり目に見える形で現れました。ではこの 2 ページには何が入っているのか — バイナリを直接覗いて確かめます。

## 3.2　先頭 100 バイト: ファイルヘッダを読む

`xxd` コマンドで先頭部分をダンプします(`xxd` は Linux にも macOS にも入っており、どちらでも同じ出力になります)。

```console
$ xxd sample.db | head -8
00000000: 5351 4c69 7465 2066 6f72 6d61 7420 3300  SQLite format 3.
00000010: 1000 0101 0040 2020 0000 0002 0000 0002  .....@  ........
00000020: 0000 0000 0000 0000 0000 0001 0000 0004  ................
00000030: 0000 0000 0000 0000 0000 0001 0000 0000  ................
00000040: 0000 0000 0000 0000 0000 0000 0000 0000  ................
00000050: 0000 0000 0000 0000 0000 0000 0000 0002  ................
00000060: 002e 95cb 0d00 0000 010f a400 0fa4 0000  ................
00000070: 0000 0000 0000 0000 0000 0000 0000 0000  ................
```

SQLite ファイルの先頭 100 バイトは**ファイルヘッダ**で、レイアウトは公式仕様(_Database File Format_)で 1 バイト単位まで定義されています。ダンプと突き合わせながら、主要フィールドを読み解きましょう。**すべての多バイト整数はビッグエンディアン**です。

| オフセット | サイズ | フィールド               | 今回の値(ダンプから)                                |
| ---------- | ------ | ------------------------ | --------------------------------------------------- |
| 0          | 16     | マジック文字列           | `53 51 4c 69 ...` = `"SQLite format 3\0"`           |
| 16         | 2      | ページサイズ             | `10 00` = 0x1000 = **4096**                         |
| 18         | 1      | 書き込みバージョン       | `01` = ロールバックジャーナル方式(2 なら WAL)       |
| 19         | 1      | 読み取りバージョン       | `01` = 同上                                         |
| 28         | 4      | 総ページ数               | `00 00 00 02` = **2 ページ**(ファイルサイズと一致!) |
| 32         | 4      | フリーリスト先頭ページ   | `00 00 00 00` = 空きページなし                      |
| 36         | 4      | フリーリストのページ数   | `00 00 00 00`                                       |
| 40         | 4      | スキーマクッキー         | `00 00 00 01` = スキーマ変更 1 回(CREATE TABLE)     |
| 56         | 4      | テキストエンコーディング | `00 00 00 01` = UTF-8                               |

前章で設計した minidb のヘッダページ(マジック・ページサイズ・総ページ数)が、本物の SQLite にもそっくり同じ発想で存在していることが確認できます。いくつか補足します。

- **スキーマクッキー**は `CREATE TABLE` などスキーマが変わるたびに増えるカウンタです。SQLite はコンパイル済みの SQL(プリペアドステートメント)を使い回しますが、その間にスキーマが変わっていたら再コンパイルが必要です。その検出をこの 1 個の整数比較で済ませています。
- **フリーリスト**は、レコード削除などで不要になったページを捨てずに「空きページの連結リスト」として取っておく仕組みです。ファイルは一度伸びたら基本的に縮まず、空きは再利用される — この設計は第 8 章(削除)で minidb にも導入します。
- **ジャーナル方式**のフィールドが「ファイルヘッダに」あることは示唆的です。ロールバックジャーナルと WAL の違いはファイルの読み方そのものに影響するため、ここで宣言されるのです(第 4 部で詳述)。
- ダンプの 0x60 行の先頭 4 バイト `00 2e 95 cb` は、このファイルを最後に書いた SQLite の**バージョン番号**です(0x002e95cb = 3053003 = バージョン 3.53.3)。手元のダンプでここだけ値が違っていても、使っている SQLite のバージョンの違いなので心配いりません。

<div class="sqlite-note">

<span class="note-title">SQLite ではこうなっている: ページ番号は 1 始まり</span> minidb はページ番号を 0 始まりにしましたが、SQLite のページ番号は **1 始まり**で、ページ 1 の先頭 100 バイトにファイルヘッダが同居します(ページ 0 は存在せず、番号 0 は「該当ページなし」を表す番兵として使われます — 上のフリーリスト先頭 = 0 がまさにそれです)。ページ 1 は「先頭 100 バイトだけ特別なデータページ」という、やや変則的な構造になっています。

</div>

## 3.3　ページの中身: B-Tree ページヘッダ

ファイルヘッダの直後(オフセット 100)からは、もうページの中身の世界です。SQLite のほぼすべてのページは B-Tree のノードであり、各ページの先頭には **B-Tree ページヘッダ**(リーフで 8 バイト、内部ノードで 12 バイト)が置かれます。本章では先頭 7 バイトを読みます。

| ページ内オフセット | サイズ | フィールド                                                                                                         |
| ------------------ | ------ | ------------------------------------------------------------------------------------------------------------------ |
| 0                  | 1      | ページ種別 — `0x02`: インデックス内部 / `0x05`: テーブル内部 / `0x0a`: インデックスリーフ / `0x0d`: テーブルリーフ |
| 1                  | 2      | ページ内フリーブロックの先頭オフセット(0 なら断片なし)                                                             |
| 3                  | 2      | **セル数** — このページに入っているレコード(セル)の個数                                                            |
| 5                  | 2      | **セル本体領域の開始オフセット** — レコード本体はページ末尾から詰められる                                          |

先ほどのダンプのオフセット 100(16 進で 0x64)を見ると、`0d 00 00 00 01 0f a4` とあります。種別 `0x0d` = テーブルリーフ、セル数 1、セル本体は 0x0fa4 = 4004 バイト目から。つまり**ページ 1 にはレコードが 1 件だけ入っている**ことになります。users テーブルには 3 件入れたのに、です。この謎はツールを完成させてから回収しましょう。

「セル本体はページ末尾から詰める」という点も B-Tree 理解の伏線です。ページ内は、先頭からヘッダとセルへのポインタ配列が伸び、末尾からセル本体が伸びる**両端成長**のレイアウトになっています。中央の空きが尽きたときが「ページ分割」のときです(第 7 章)。

## 3.4　解析ツール `inspect` を実装する

ここまでの知識を Go プログラムに落とします。仕様は「SQLite ファイルを受け取り、(1) ファイルヘッダの主要フィールド、(2) 全ページの B-Tree ページヘッダを表示する」。パーサの構造は素直で、前章の `encoding/binary` がそのまま活躍します。

**cmd/inspect/main.go — SQLite ファイル解析ツール(完全版)**

```go
// cmd/inspect/main.go
// SQLite データベースファイルの先頭 100 バイト(ファイルヘッダ)と
// 各ページの B-Tree ページヘッダを解析して表示するツール。
package main

import (
	"encoding/binary"
	"fmt"
	"io"
	"os"
)

// SQLite ファイルヘッダ(先頭 100 バイト)のうち、本章で扱うフィールド。
// すべてビッグエンディアンで格納されている。
type FileHeader struct {
	Magic         [16]byte // "SQLite format 3\x00"
	PageSize      uint16   // オフセット 16: ページサイズ
	WriteVersion  uint8    // オフセット 18: 1=journal, 2=WAL
	ReadVersion   uint8    // オフセット 19: 1=journal, 2=WAL
	PageCount     uint32   // オフセット 28: ファイル内の総ページ数
	FreelistHead  uint32   // オフセット 32: フリーリスト先頭ページ番号
	FreelistCount uint32   // オフセット 36: フリーリストのページ数
	SchemaCookie  uint32   // オフセット 40: スキーマ変更のたびに増える
	TextEncoding  uint32   // オフセット 56: 1=UTF-8, 2=UTF-16le, 3=UTF-16be
}

// ReadFileHeader は r から 100 バイト読み取り、ヘッダとして解析する。
func ReadFileHeader(r io.Reader) (*FileHeader, error) {
	buf := make([]byte, 100)
	if _, err := io.ReadFull(r, buf); err != nil {
		return nil, fmt.Errorf("ヘッダの読み取りに失敗: %w", err)
	}

	h := &FileHeader{}
	copy(h.Magic[:], buf[0:16])
	if string(h.Magic[:]) != "SQLite format 3\x00" {
		return nil, fmt.Errorf("SQLite ファイルではありません")
	}

	h.PageSize = binary.BigEndian.Uint16(buf[16:18])
	h.WriteVersion = buf[18]
	h.ReadVersion = buf[19]
	h.PageCount = binary.BigEndian.Uint32(buf[28:32])
	h.FreelistHead = binary.BigEndian.Uint32(buf[32:36])
	h.FreelistCount = binary.BigEndian.Uint32(buf[36:40])
	h.SchemaCookie = binary.BigEndian.Uint32(buf[40:44])
	h.TextEncoding = binary.BigEndian.Uint32(buf[56:60])
	return h, nil
}

// B-Tree ページヘッダ。ページ先頭(ページ 1 だけはオフセット 100)に置かれる。
type BTreePageHeader struct {
	PageType    uint8  // 0x02/0x05=内部, 0x0a/0x0d=リーフ
	FreeBlock   uint16 // ページ内フリーブロックの先頭
	CellCount   uint16 // このページに入っているセル(レコード)の数
	CellContent uint16 // セル本体領域の開始オフセット
}

func pageTypeName(t uint8) string {
	switch t {
	case 0x02:
		return "index interior(インデックス内部ノード)"
	case 0x05:
		return "table interior(テーブル内部ノード)"
	case 0x0a:
		return "index leaf(インデックスリーフ)"
	case 0x0d:
		return "table leaf(テーブルリーフ)"
	default:
		return fmt.Sprintf("不明 (0x%02x)", t)
	}
}

// ReadBTreePageHeader は page(1 ページ分のバイト列)から
// B-Tree ページヘッダを解析する。pageNo が 1 のときだけ
// ファイルヘッダ 100 バイトの直後から始まる点に注意。
func ReadBTreePageHeader(page []byte, pageNo uint32) BTreePageHeader {
	offset := 0
	if pageNo == 1 {
		offset = 100
	}
	return BTreePageHeader{
		PageType:    page[offset],
		FreeBlock:   binary.BigEndian.Uint16(page[offset+1 : offset+3]),
		CellCount:   binary.BigEndian.Uint16(page[offset+3 : offset+5]),
		CellContent: binary.BigEndian.Uint16(page[offset+5 : offset+7]),
	}
}

func main() {
	if len(os.Args) != 2 {
		fmt.Fprintln(os.Stderr, "使い方: inspect <sqlite ファイル>")
		os.Exit(1)
	}

	f, err := os.Open(os.Args[1])
	if err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}
	defer f.Close()

	h, err := ReadFileHeader(f)
	if err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}

	fmt.Println("=== ファイルヘッダ ===")
	fmt.Printf("マジック文字列   : %q\n", string(h.Magic[:15]))
	fmt.Printf("ページサイズ     : %d バイト\n", h.PageSize)
	fmt.Printf("総ページ数       : %d\n", h.PageCount)
	fmt.Printf("ジャーナル方式   : write=%d read=%d (1=rollback journal, 2=WAL)\n",
		h.WriteVersion, h.ReadVersion)
	fmt.Printf("フリーリスト     : 先頭ページ=%d, ページ数=%d\n",
		h.FreelistHead, h.FreelistCount)
	fmt.Printf("スキーマクッキー : %d\n", h.SchemaCookie)
	fmt.Printf("テキスト符号化   : %d (1=UTF-8)\n", h.TextEncoding)

	// 各ページの B-Tree ページヘッダを表示する
	fmt.Println("\n=== 各ページの B-Tree ヘッダ ===")
	page := make([]byte, h.PageSize)
	for no := uint32(1); no <= h.PageCount; no++ {
		// ページ番号 no は、ファイル先頭から (no-1)*PageSize バイト目
		if _, err := f.ReadAt(page, int64(no-1)*int64(h.PageSize)); err != nil {
			fmt.Fprintln(os.Stderr, err)
			os.Exit(1)
		}
		bh := ReadBTreePageHeader(page, no)
		fmt.Printf("ページ %d: 種別=%s セル数=%d セル本体開始=%d\n",
			no, pageTypeName(bh.PageType), bh.CellCount, bh.CellContent)
	}
}
```

実装のポイントを 3 つ挙げます。

- **マジック文字列の検証を最初に行う** — フォーマットの前提が崩れたバイト列を読み進めても無意味な数値が出てくるだけです。「これは本当に自分の知っているフォーマットか」を入り口で確かめるのは、バイナリを扱うプログラムの鉄則です。
- **`io.ReadFull` を使う** — `Read` は要求より少ないバイト数で返ることが仕様上あり得ます。「きっかり 100 バイト読めなければエラー」という意図には `io.ReadFull` が正確です。
- **`ReadAt` でページに飛ぶ** — `ページ番号 n のオフセット = (n-1) × ページサイズ`(SQLite は 1 始まりなので -1)という前章の住所計算が、そのままコードになっています。`ReadAt` はシーク位置という状態を持たないため、こうしたランダムアクセスに向いています。

## 3.5　動かす — そして謎を回収する

```console
$ go build -o inspect ./cmd/inspect && ./inspect sample.db
=== ファイルヘッダ ===
マジック文字列   : "SQLite format 3"
ページサイズ     : 4096 バイト
総ページ数       : 2
ジャーナル方式   : write=1 read=1 (1=rollback journal, 2=WAL)
フリーリスト     : 先頭ページ=0, ページ数=0
スキーマクッキー : 1
テキスト符号化   : 1 (1=UTF-8)

=== 各ページの B-Tree ヘッダ ===
ページ 1: 種別=table leaf(テーブルリーフ) セル数=1 セル本体開始=4004
ページ 2: 種別=table leaf(テーブルリーフ) セル数=3 セル本体開始=4062
```

手書きで読んだ値と完全に一致し、さらにページ 2 の姿も見えました。**ページ 2 のセル数は 3** — users テーブルの 3 レコードはこちらに入っていたのです。ではセル数 1 のページ 1 は何か。

答えは `sqlite_schema`(旧称 `sqlite_master`)です。SQLite は「どんなテーブルがあり、その実体がどのページから始まるか」というカタログ情報自体を、1 つのテーブルとしてページ 1 に格納します。今回の 1 セルの中身は、私たちが実行した `CREATE TABLE users ...` の定義そのもの(と、users の実体がページ 2 にあるという情報)です。`SELECT * FROM users` が実行されるとき、SQLite はまずページ 1 のカタログを引いて users の在り処(ページ 2)を知り、それからページ 2 を読む — _メタデータもまたテーブルであり、テーブルはページに載る_。この再帰的な美しさは、minidb でも第 3 部でカタログを作るときに拝借します。

<div class="column-note">

<span class="note-title">やってみよう(演習)</span> (1) レコードを 1000 件 INSERT してから `inspect` を実行し、総ページ数とページ種別がどう変わるか観察してください。`0x05`(テーブル内部ノード)が現れたら、それが第 2 部で作る B-Tree の階層化の瞬間です。(2) `DROP TABLE users` するとフリーリストのカウントがどう変わるかも見てみましょう。(3) `PRAGMA journal_mode=WAL` を実行すると、ヘッダのジャーナル方式が 2 に変わることを確認してください。

</div>

## 3.6　まとめ

- SQLite ファイルは先頭 100 バイトのファイルヘッダに、マジック・ページサイズ・総ページ数・ジャーナル方式などの自己記述情報を持つ
- 各ページは B-Tree ノードで、先頭のページヘッダに種別・セル数・セル本体開始位置が記録され、ページ内は両端成長でレイアウトされる
- スキーマ情報(カタログ)自体もテーブルとしてページ 1 に格納されており、「すべてはページの上のテーブルである」という一貫した構造を持つ
- 100 行あまりの Go プログラムで、世界で最も使われているデータベースのファイルが読めた

他人のフォーマットが読めたなら、自分のフォーマットを書く準備は整いました。次章では minidb の心臓部の最初の部品 — ページャを実装します。
