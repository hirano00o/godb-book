# 第 2 章　ファイルとページ — なぜページ単位で管理するのか

<div class="chap-goal">

<span class="note-title">この章のゴール</span>

- データベースがファイルを固定長の「ページ」で扱う理由を、ハードウェアの特性から説明できる
- ページ番号とファイルオフセットの関係を計算できる
- minidb のファイルフォーマット(ヘッダページ+データページ)を設計し、Go でバイナリを読み書きする道具(`encoding/binary`)を使える

</div>

## 2.1　ディスクは「ブロックの海」である

第 1 章の壁 2(部分更新ができない)を思い出してください。あの問題の根本は、ファイルを「連続した可変長テキスト」として扱っていたことにあります。データベースは発想を逆転させます。**ファイルを最初から固定長の区画に切り、区画単位でしか読み書きしない**。この区画が**ページ**です。

なぜこれが正解なのか。理由はソフトウェアの都合ではなく、その下にある物理装置の性質にあります。

### ストレージはそもそもブロック単位でしか読み書きできない

HDD も SSD も、1 バイトだけを読み書きすることはできません。HDD は 512 バイト〜4KB のセクタ、SSD は 4KB 以上のページ(NAND ページ)という単位でしか動作しない**ブロックデバイス**です。アプリケーションが「1 バイトだけ書いて」と頼んでも、装置内部では 4KB を読み、1 バイト書き換え、4KB を書き戻しています。つまり *4KB 未満の細かい I/O は物理的に存在せず、細かく頼むだけ損*なのです。

### OS もページ単位で世界を見ている

OS の仮想メモリ管理もファイルキャッシュ(ページキャッシュ)も、伝統的に 4KB のページを単位としています。データベースのページサイズをこれに揃えると、DB の 1 ページ = OS の 1 ページ = ディスクの 1 ブロックがきれいに対応し、無駄な分割や結合が発生しません。SQLite のデフォルトページサイズが 4096 バイトなのは、まさにこの整合性のためです。

### 固定長は「住所計算」を可能にする

そして最大の利点がこれです。全ページが同じ大きさなら、**ページ番号だけからファイル内の位置(オフセット)が即座に計算できます**。

この単純な掛け算が、データベース全体を支える土台です。上位層(B-Tree)は「ページ 3 が欲しい」と番号で頼むだけでよく、シーク位置の計算、読み込み、キャッシュはすべて下位層に任せられます。可変長レコードの世界では不可能だった O(1) のランダムアクセスが、固定長ページの世界では自明に手に入るのです。

さらに、ページは**書き込みの単位**としても機能します。レコードを 1 件更新したいときは、そのレコードが載っているページだけを読み、メモリ上で書き換え、そのページだけを書き戻す。ファイル全体の書き直しは不要になり、壁 2 は崩れました。第 4 部で学ぶジャーナリングも「変更前のページを退避しておく」という形でページを単位に動作します。ページとは、I/O の単位・キャッシュの単位・復旧の単位を兼ねる、データベースの「原子」なのです。

<div class="sqlite-note">

<span class="note-title">SQLite ではこうなっている: ページサイズ</span> SQLite のページサイズは 512〜65536 バイトの 2 のべき乗から選べ、現在のデフォルトは 4096 です(`PRAGMA page_size` で確認・変更できます)。歴史的には 1024 がデフォルトでしたが、ストレージと OS の標準が 4KB に収斂したことを受けて 2016 年に 4096 へ変更されました。ページサイズはファイル作成時に決まり、ヘッダに記録されます — つまり「ファイル自身が自分の読み方を知っている」わけです。第 1 章で作った sample.db があれば、`sqlite3 sample.db "PRAGMA page_size;"` と打つと `4096` が返ってきます。次章で実際にこの値をバイナリから読み出します。

</div>

## 2.2　minidb のファイルフォーマットを設計する

理屈が固まったところで、minidb のファイルフォーマット第 1 版を設計します。方針は「SQLite の考え方を、最小の形で」です。

- データベース全体は**単一ファイル**
- ファイルは **4096 バイト固定のページの並び**。ページ番号は 0 始まり
- **ページ 0 はヘッダページ**とし、ファイル全体のメタ情報を置く
- ページ 1 以降はデータページ。中身の構造(B-Tree ノード)は第 2 部で定義する

<span class="note-title">設計の観点: なぜメタ情報をファイル内に持つのか</span> ページサイズや総ページ数は「プログラム側の定数でいいのでは?」と思うかもしれません。しかしデータベースファイルはプログラムより長生きします。5 年後の minidb がページサイズを変えても、5 年前に作られたファイルは 4096 のままです。*ファイルフォーマットとは未来の自分との契約書*であり、読み方を決めるパラメータはファイル自身に刻んでおく — これは SQLite が 20 年以上の後方互換を守り続けている流儀そのものです。

## 2.3　Go でバイナリを読み書きする — `encoding/binary`

ヘッダページの「ページサイズ 4096 を 4 バイトで記録する」を実装するには、多バイト整数をバイト列に変換する規則、すなわち**エンディアン(バイトオーダー)**を決めなければなりません。4096 は 16 進数で `0x00001000` ですが、これを 4 バイトに並べる順序には 2 通りあります。

- **ビッグエンディアン** — 上位バイトから順に `00 00 10 00`。人間が 16 進数を書く順と同じ
- **リトルエンディアン** — 下位バイトから順に `00 10 00 00`。x86 や ARM の CPU がメモリ上で使う順

Go の標準ライブラリ `encoding/binary` で両方を試してみましょう。

**cmd/endian/main.go — エンディアンの実験**

```go
// cmd/endian/main.go
// 数値がバイト列としてどう格納されるかを確かめる実験。
package main

import (
	"encoding/binary"
	"fmt"
)

func main() {
	buf := make([]byte, 4)
	var n uint32 = 4096 // 16 進数では 0x00001000

	binary.BigEndian.PutUint32(buf, n)
	fmt.Printf("ビッグエンディアン   : % x\n", buf)

	binary.LittleEndian.PutUint32(buf, n)
	fmt.Printf("リトルエンディアン   : % x\n", buf)

	// 読み戻しも対にして行う
	binary.BigEndian.PutUint32(buf, n)
	fmt.Printf("読み戻し             : %d\n", binary.BigEndian.Uint32(buf))
}
```

```console
$ go run ./cmd/endian
ビッグエンディアン   : 00 00 10 00
リトルエンディアン   : 00 10 00 00
読み戻し             : 4096
```

minidb では**ビッグエンディアンを採用**します。SQLite のファイルフォーマットがすべてビッグエンディアンで定義されているのに合わせるためで、次章で本物のファイルを読むときにも同じコードパターンがそのまま使えます。ネットワークプロトコルの標準(ネットワークバイトオーダー)もビッグエンディアンであり、「ファイルや通信路など*外の世界*に出すバイト列はビッグエンディアン」は広く見られる慣習です。

<div class="warn">

<span class="note-title">注意: エンディアンは「決めて、書き残す」ことがすべて</span> どちらのエンディアンが優れているかという議論に実益はほとんどありません。重要なのは、フォーマット仕様として一方に決め、読み書きの両側で必ず同じ規則を使うことです。`binary.BigEndian.PutUint32` で書いたものは `binary.BigEndian.Uint32` で読む — この対称性が崩れた瞬間、データは静かに壊れます。

</div>

## 2.5　まとめ

- ストレージも OS も 4KB 前後のブロック単位で動いており、データベースがページ単位で I/O するのはハードウェアの物理に沿った選択である
- 固定長ページは `オフセット = ページ番号 × ページサイズ` という住所計算を可能にし、I/O・キャッシュ・復旧すべての単位になる
- minidb はページ 0 をヘッダページとし、マジック文字列・ページサイズ・総ページ数をビッグエンディアンで記録する

設計図は描けました。しかし自分のフォーマットを実装する前に、先人の設計図を読んでみましょう。次章では本物の SQLite ファイルをバイナリレベルで解剖します。この章で学んだページとエンディアンの知識が、そのまま解読の道具になります。
