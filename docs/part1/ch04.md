# 第 4 章　ページャの実装 — ページの読み書きとキャッシュ

<div class="chap-goal">

<span class="note-title">この章のゴール</span>

- ページャの 4 つの責務(読み書き・キャッシュ・ダーティ管理・永続化保証)を説明できる
- minidb の `pager` パッケージを実装し、テストで動作を検証できる
- `fsync` がなぜ必要か、ページャの API 設計が上位層に何を約束しているかを説明できる

</div>

## 4.1　ページャの責務を定義する

ページャは、SQLite のアーキテクチャ図(図 1-2)で B-Tree のすぐ下に位置していた層です。上位層に対する約束はただ一つ、**「ページ番号を言えば、そのページのメモリ上のコピーを渡す。書き換えたと言われたものは、いつか確実にディスクへ戻す」**。この一文を分解すると 4 つの責務になります。

| 責務                     | 内容                                                                         | 対応する API                              |
| ------------------------ | ---------------------------------------------------------------------------- | ----------------------------------------- |
| 読み書き                 | ページ番号 ⇔ ファイルオフセットの変換と実際の I/O                            | `Get` / (内部の `readPage` / `writePage`) |
| ページの確保             | ファイル末尾に新しいページを増やし、総ページ数を管理                         | `Allocate`                                |
| キャッシュとダーティ管理 | 読んだページをメモリに保持し、書き換えられたページ(ダーティページ)を記憶する | キャッシュは `Get` に内蔵 / `MarkDirty`   |
| 永続化の保証             | ダーティページをまとめて書き戻し、`fsync` でディスク到達を保証               | `Flush` / `Close`                         |

逆に、ページャが**知らないこと**も明確にしておきます。ページの中に何が入っているか(B-Tree ノードなのか何なのか)をページャは一切関知しません。ページャにとってページは 4096 バイトのただのバイト列です。この無知こそが層の分離であり、上位層を自由に作り替えられる余地を生みます。

## 4.2　キャッシュはなぜ必須なのか

ページキャッシュは「あると速い」程度の最適化ではなく、データベースでは実質的に必須の部品です。理由は 2 つあります。

第一に**速度差**です。メモリアクセスが数十ナノ秒に対し、NVMe SSD の読み込みは数十マイクロ秒、HDD なら数ミリ秒 — 千倍から十万倍の開きがあります。第 2 部で作る B-Tree は、1 回の検索で根から葉まで数ページをたどりますが、根に近いページはあらゆる検索で毎回通ります。ここがキャッシュに乗っているかどうかで、性能は文字どおり桁が変わります。

第二に**同一性**です。同じページを 2 回読むたびに新しいコピーを作ると、片方への書き込みがもう片方に見えず、静かにデータが壊れます。「1 つのページ番号にはメモリ上のコピーが高々 1 つ」という不変条件を守る場所として、キャッシュ(`map[PageID]*Page`)が必要なのです。`Get` が同じポインタを返し続けることには、性能以上の意味があります。

第 1 版のキャッシュは「読んだものは全部保持」という最も単純な戦略を採ります。メモリ上限を設けた追い出し(LRU)は、B-Tree が動き出してアクセスパターンが生まれてから導入するほうが、効果を測りながら設計できます(第 2 部末で扱います)。

<div class="sqlite-note">

<span class="note-title">SQLite ではこうなっている: キャッシュサイズ</span> SQLite のページキャッシュはデフォルトで約 2MB(`PRAGMA cache_size` で変更可能)に制限され、あふれた場合はダーティでないページから追い出されます。また SQLite のページャはキャッシュだけでなく、ジャーナル管理・ロック・WAL の読み書きまで担う巨大な部品で、pager.c 単体で 7000 行を超えます。本章の minidb 版はその「キャッシュと I/O」の芯だけを抜き出したものです。第 4 部で、この同じ Pager にジャーナルを教え込んでいきます。

</div>

## 4.3　`pager` パッケージの実装

では実装です。前章までに決めたフォーマット(ヘッダページ = ページ 0、マジック `"minidb01"`、ビッグエンディアン)をコードに落とします。まずは全体を掲載します。少し長いですが、一つひとつの部品はここまでの積み重ねそのものです。

**pager/pager.go — ページャ本体(完全版)**

```go
// Package pager は minidb のストレージ層の最下層、
// 「ページ単位のファイル入出力とキャッシュ」を担当する。
package pager

import (
	"encoding/binary"
	"errors"
	"fmt"
	"os"
)

const (
	// PageSize は 1 ページのバイト数。SQLite のデフォルトに合わせる。
	PageSize = 4096

	// Magic は minidb ファイルの先頭 8 バイト。
	Magic = "minidb01"

	// headerPageID はメタ情報を置くページ。常にファイルの先頭。
	headerPageID PageID = 0
)

// PageID はページ番号。ページ n はファイルの n*PageSize バイト目から始まる。
type PageID uint32

// Page はメモリ上に読み込まれた 1 ページ。
type Page struct {
	ID    PageID
	Data  [PageSize]byte
	dirty bool // ディスクに書き戻す必要があるか
}

// Pager はページの読み書きとキャッシュを担当する。
// 上位層(B-Tree)はファイルオフセットを一切意識せず、
// PageID だけでページを取得・更新する。
type Pager struct {
	file     *os.File
	numPages uint32           // ヘッダページ含む総ページ数
	cache    map[PageID]*Page // 読み込み済みページのキャッシュ
}

// Open は minidb ファイルを開く。存在しなければ新規作成し、
// ヘッダページ(ページ 0)を初期化する。
func Open(path string) (*Pager, error) {
	file, err := os.OpenFile(path, os.O_RDWR|os.O_CREATE, 0o644)
	if err != nil {
		return nil, err
	}

	p := &Pager{
		file:  file,
		cache: make(map[PageID]*Page),
	}

	info, err := file.Stat()
	if err != nil {
		file.Close()
		return nil, err
	}

	if info.Size() == 0 {
		// 新規ファイル: ヘッダページを作って書き込む
		if err := p.initHeader(); err != nil {
			file.Close()
			return nil, err
		}
		return p, nil
	}

	// 既存ファイル: ヘッダページを検証して総ページ数を読み取る
	if err := p.loadHeader(); err != nil {
		file.Close()
		return nil, err
	}
	return p, nil
}

// initHeader はヘッダページを初期化してディスクに書き込む。
// レイアウト:
//
//	オフセット 0-7 : マジック文字列 "minidb01"
//	オフセット 8-11: ページサイズ(ビッグエンディアン uint32)
//	オフセット 12-15: 総ページ数(ビッグエンディアン uint32)
func (p *Pager) initHeader() error {
	page := &Page{ID: headerPageID}
	copy(page.Data[0:8], Magic)
	binary.BigEndian.PutUint32(page.Data[8:12], PageSize)

	p.numPages = 1 // ヘッダページ自身
	binary.BigEndian.PutUint32(page.Data[12:16], p.numPages)

	p.cache[headerPageID] = page
	page.dirty = true
	return p.Flush()
}

// loadHeader は既存ファイルのヘッダページを読み込んで検証する。
func (p *Pager) loadHeader() error {
	page, err := p.readPage(headerPageID)
	if err != nil {
		return err
	}
	if string(page.Data[0:8]) != Magic {
		return errors.New("minidb ファイルではありません")
	}
	if got := binary.BigEndian.Uint32(page.Data[8:12]); got != PageSize {
		return fmt.Errorf("ページサイズが不一致: file=%d, build=%d", got, PageSize)
	}
	p.numPages = binary.BigEndian.Uint32(page.Data[12:16])
	p.cache[headerPageID] = page
	return nil
}

// NumPages はヘッダページを含む総ページ数を返す。
func (p *Pager) NumPages() uint32 { return p.numPages }

// Get はページを取得する。キャッシュにあればそれを、
// なければディスクから読み込んで返す。
func (p *Pager) Get(id PageID) (*Page, error) {
	if uint32(id) >= p.numPages {
		return nil, fmt.Errorf("ページ %d は存在しません(総ページ数 %d)", id, p.numPages)
	}
	if page, ok := p.cache[id]; ok {
		return page, nil
	}
	page, err := p.readPage(id)
	if err != nil {
		return nil, err
	}
	p.cache[id] = page
	return page, nil
}

// Allocate はファイル末尾に新しいページを確保して返す。
// ディスクへの書き込みは Flush まで遅延される。
func (p *Pager) Allocate() (*Page, error) {
	page := &Page{ID: PageID(p.numPages), dirty: true}
	p.numPages++
	p.cache[page.ID] = page

	// ヘッダページの総ページ数も更新する
	header, err := p.Get(headerPageID)
	if err != nil {
		return nil, err
	}
	binary.BigEndian.PutUint32(header.Data[12:16], p.numPages)
	header.dirty = true
	return page, nil
}

// MarkDirty はページの内容を書き換えたことをページャに伝える。
// 上位層は Data を書き換えたら必ずこれを呼ぶ。
func (p *Pager) MarkDirty(id PageID) {
	if page, ok := p.cache[id]; ok {
		page.dirty = true
	}
}

// Flush はダーティなページをすべてディスクに書き戻し、
// fsync でストレージへの到達を保証する。
func (p *Pager) Flush() error {
	for _, page := range p.cache {
		if !page.dirty {
			continue
		}
		if err := p.writePage(page); err != nil {
			return err
		}
		page.dirty = false
	}
	// OS のバッファに残っているデータを物理ディスクまで書かせる。
	// これを省くと、電源断でファイルが壊れる可能性がある。
	return p.file.Sync()
}

// Close は Flush してからファイルを閉じる。
func (p *Pager) Close() error {
	if err := p.Flush(); err != nil {
		p.file.Close()
		return err
	}
	return p.file.Close()
}

// readPage はディスクからページを 1 枚読み込む(キャッシュを介さない)。
func (p *Pager) readPage(id PageID) (*Page, error) {
	page := &Page{ID: id}
	_, err := p.file.ReadAt(page.Data[:], int64(id)*PageSize)
	if err != nil {
		return nil, fmt.Errorf("ページ %d の読み取りに失敗: %w", id, err)
	}
	return page, nil
}

// writePage はページをディスク上の正しい位置に書き込む。
func (p *Pager) writePage(page *Page) error {
	_, err := p.file.WriteAt(page.Data[:], int64(page.ID)*PageSize)
	if err != nil {
		return fmt.Errorf("ページ %d の書き込みに失敗: %w", page.ID, err)
	}
	return nil
}
```

設計判断をいくつか拾って解説します。

### `Open` の二枝: 新規作成と検証

`Open` はファイルサイズ 0 なら新規作成(`initHeader`)、既存ならヘッダ検証(`loadHeader`)に分岐します。`loadHeader` はマジック文字列とページサイズを検証し、合わなければ即座にエラーを返します。第 3 章で書いた inspect と同じ「入り口で前提を確かめる」流儀です。特にページサイズの検証は将来の自分を守ります。ビルドによって `PageSize` 定数を変えた minidb が古いファイルを開いたとき、黙って壊すのではなくエラーで止まれます。

### `Allocate` はヘッダも更新する

新ページの確保は「総ページ数を 1 増やす」というヘッダページの更新を必ず伴います。`Allocate` の中でヘッダページを取得してページ数フィールドを書き換え、ダーティにしています。*メタデータと実データの整合性を保つのは、両方を知っている層の仕事*です。なお新ページはこの時点ではメモリ上にしか存在せず、ディスクへの反映は `Flush` まで遅延されます。

### `MarkDirty` という契約

ページャはページの `Data` を上位層に直接触らせる設計にしました(コピーを渡さない)。その代わり、**書き換えたら `MarkDirty` を呼ぶ**という契約を課しています。呼び忘れると変更は Flush されず消えます — これは危うさでもあり、SQLite も同様に「書く前に宣言する」API(後述のジャーナルでは書き換え*前*の宣言が本質的に重要になります)を採っています。第 13 章でジャーナルを導入すると、この `MarkDirty` が「変更前のページ内容を退避するフック」へと成長します。伏線として覚えておいてください。

### `Flush` と `fsync` — 「書けた」の本当の意味

`Flush` はダーティページを `WriteAt` で書き戻したあと、必ず `file.Sync()`(システムコールの `fsync`)を呼びます。ここは本章で最も重要な行です。`write` が成功しても、データは OS のページキャッシュに乗っただけで、ディスクにはまだ届いていないかもしれません。その状態で電源が落ちれば、書いたはずのデータは消えます。`fsync` は「この内容を物理媒体まで届けよ」と OS に命じ、完了まで待つ唯一の手段です。データベースの耐久性(ACID の D)は、突き詰めれば「正しい場所で fsync を呼んでいるか」に懸かっています。

<div class="warn">

<span class="note-title">fsync は高くつく — だからこそ設計が要る</span> `fsync` はミリ秒単位のコストがかかる高価な操作です。1 ページ書くたびに呼んでいては性能が壊滅するため、minidb では「ダーティをまとめて書いて最後に 1 回」という形にしています。実は WAL(第 14 章)の存在意義の半分は「fsync の回数と場所を最適化すること」にあります。速さと壊れなさはトレードオフではなく、設計で両立させるもの — それを体感するのが第 4 部です。

</div>

## 4.4　テストで検証する

ページャの正しさは「書いて、閉じて、開き直して、読める」に尽きます。プロセスをまたいだ永続性をテストで再現するため、`Close` して別インスタンスで `Open` し直す構成にします。

**pager/pager_test.go — ラウンドトリップテスト**

```go
package pager

import (
	"bytes"
	"path/filepath"
	"testing"
)

// 新規作成 → ページ確保 → 書き込み → 閉じる → 開き直して読める、
// という一連の流れを検証する。
func TestPagerRoundTrip(t *testing.T) {
	path := filepath.Join(t.TempDir(), "test.db")

	// --- 書き込み側 ---
	p, err := Open(path)
	if err != nil {
		t.Fatal(err)
	}
	if got := p.NumPages(); got != 1 {
		t.Fatalf("新規ファイルの総ページ数 = %d, want 1", got)
	}

	page, err := p.Allocate()
	if err != nil {
		t.Fatal(err)
	}
	copy(page.Data[:], "hello, minidb")
	p.MarkDirty(page.ID)

	if err := p.Close(); err != nil {
		t.Fatal(err)
	}

	// --- 読み込み側 ---
	p2, err := Open(path)
	if err != nil {
		t.Fatal(err)
	}
	defer p2.Close()

	if got := p2.NumPages(); got != 2 {
		t.Fatalf("再オープン後の総ページ数 = %d, want 2", got)
	}

	loaded, err := p2.Get(page.ID)
	if err != nil {
		t.Fatal(err)
	}
	if !bytes.HasPrefix(loaded.Data[:], []byte("hello, minidb")) {
		t.Fatalf("ページ内容が一致しません: %q", loaded.Data[:16])
	}
}

// 存在しないページの取得はエラーになる。
func TestGetOutOfRange(t *testing.T) {
	path := filepath.Join(t.TempDir(), "test.db")
	p, err := Open(path)
	if err != nil {
		t.Fatal(err)
	}
	defer p.Close()

	if _, err := p.Get(99); err == nil {
		t.Fatal("存在しないページの取得がエラーになりませんでした")
	}
}

// minidb ファイルでないものを開くとエラーになる。
func TestOpenInvalidFile(t *testing.T) {
	path := filepath.Join(t.TempDir(), "not-a-db")
	if err := writeJunk(path); err != nil {
		t.Fatal(err)
	}
	if _, err := Open(path); err == nil {
		t.Fatal("不正なファイルのオープンがエラーになりませんでした")
	}
}
```

**cmd/pagerdemo/main.go — 動作確認用ミニデモ**

```go
// cmd/pagerdemo/main.go
// pager を使って mini.db を作り、1 ページ書き込む動作確認デモ。
package main

import (
	"fmt"
	"os"

	"minidb/pager"
)

func main() {
	p, err := pager.Open("mini.db")
	if err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}
	page, err := p.Allocate()
	if err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}
	copy(page.Data[:], "hello, minidb")
	p.MarkDirty(page.ID)
	if err := p.Close(); err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}
	fmt.Println("mini.db を作成しました(2 ページ)")
}
```

## 4.5　まとめ

- ページャの約束は「番号を言えばページを渡し、ダーティと言われたものは確実にディスクへ戻す」— ページの中身には関知しない
- キャッシュは速度のためだけでなく、「1 ページにつきメモリ上のコピーは 1 つ」という同一性の保証装置でもある
- `write` の成功はディスク到達を意味しない。耐久性は `fsync` を正しい場所で呼ぶことで初めて成立する
- `MarkDirty` は将来ジャーナルへ成長する伏線である
